## 0. Regra de leitura

Este documento define o **target canônico** para identidade e atletas. Ele distingue explicitamente conceitos que no código atual ainda aparecem misturados dentro de `Player` ou de fluxos local-first.

A separação fundamental é:

```text
USER
= identidade autenticada

PLAYER
= identidade esportiva persistente/global

PARTICIPANT
= participação contextual/histórica
```

Portanto:

```text
USER ≠ PLAYER ≠ PARTICIPANT
```

Essa distinção é estrutural e não apenas terminológica. Ela afeta banco, privacidade, deleção, Guest, Session, Match, Competition, Stats, Ratings e Account Linking.

# 1. Current State — evidência do repositório

## 1.1 `Player` atual concentra responsabilidades demais

O type atual de `Player` contém simultaneamente:

- identidade esportiva (`id`, `username`, nome/apelido);
- aparência (`avatarUrl`);
- características físicas e esportivas;
- vetor completo de atributos;
- perfil derivado;
- forma atual;
- status físico/lesão;
- `communityIds`;
- `isGuest`;
- `cloudId` / `cloudOwnerId`;
- avaliações/agregados;
- `syncStatus` / `lastSyncedAt` / `deletedAt`;
- `userId`;
- estado transitório de unlink.

Isso mistura identidade, relação com Community, avaliação, sync, Guest e vínculo de conta em um único aggregate client-side.

## 1.2 Player global já existe como direção correta

A migration de identidade global declara explicitamente `players.id` como identidade global canônica e adiciona `username` único case-insensitive. Também cria lookup controlado por username que retorna apenas `id`, `username` e `name`.

Essa direção é preservada no target:

```text
Player.id
= global sports identity
```

O que muda é a remoção de outras responsabilidades indevidas dessa entidade.

## 1.3 Community relation atual ainda carrega governance-like role

`community_players` atualmente possui `status`, `role`, `sync_version` e `deleted_at`; `role` aceita `owner | admin | player | guest`, e policies permitem operações com base em roles de Community incluindo `organizer`.

No target:

```text
CommunityPlayer
= sports relation only

CommunityMembership
= access/governance relation
```

Logo `CommunityPlayer.role` administrativo é legado.

## 1.4 User↔Player link atual já possui workflow de aprovação

Hoje existe:

```text
players.user_id
player_link_proposals
propose_player_link()
approve_player_link()
reject_player_link()
cancel_my_link_proposal()
```

O FK `players.user_id` usa `ON DELETE SET NULL`, o que já é melhor que apagar Player junto com account.

O target preserva a ideia de link controlado e proposal/claim, mas move o vínculo para uma entidade própria `PlayerAccountLink`, em vez de manter `user_id` como propriedade direta da identidade esportiva.

## 1.5 Fluxos locais ainda criam identidade persistente cedo demais

O fluxo atual de criação local:

- cria `Player` para Community diretamente;
- preenche atributos iniciais com `5`;
- coloca `communityIds` no Player;
- `applyGuestPlayerUpsert()` pode adicionar Guest ao array persistente de Players.

No target isso é separado:

```text
Guest participation
DOES NOT imply
persistent Player creation
```

## 1.6 Conta atual pressupõe Player cedo demais

O `AccountSnapshot` atual contém obrigatoriamente `playerId`, de modo que preparar a conta também prepara/associa identidade esportiva.

No target:

```text
User account
MAY exist without Player
```

A criação/vinculação do Player ocorre somente quando a experiência realmente exige identidade esportiva persistente.

# 2. N3.02.01 — User Identity

## N4.02.01.01 — Definição

`User` representa o principal autenticado reconhecido pelo sistema de Auth.

Responsabilidades:

```text
Authentication
Account security
Platform preferences
CommunityMembership
Consent/privacy requests
PlayerAccountLink when applicable
```

Não é responsável por:

```text
sports attributes
historical Match identity
Community sports roster
Player evaluations
```

## N5.02.01 — Invariantes

- User pode existir sem Player.
- User pode pertencer a Community sem necessariamente jogar.
- User não carrega governance global de Communities no Player.
- Auth identity não é autorização suficiente para recurso contextual.
- Deletar User não apaga automaticamente Player nem fatos esportivos históricos.

## N6.02.01 — Commands/Queries conceituais

```text
CreateAccount / SignUp
Authenticate
UpdateAccountProfile
RequestAccountDeletion
RequestPrivacyExport
GetMyAccount
GetMyPlayerLink
```

Auth implementation pertence à plataforma; a semântica de conta permanece separada da identidade esportiva.

## N7.02.01 — Data

Conceitualmente:

```text
auth.users
user_profiles
```

`user_profiles` não deve duplicar atributos esportivos do Player.

## N8.02.01 — Segurança

- actor deriva de `auth.uid()` server-side;
- email não deve ser usado como FK de domínio;
- troca de email não altera Player identity;
- Account takeover não deve permitir reatribuir Player arbitrariamente;
- operações de link/merge/deletion podem exigir MFA/step-up conforme risco.

## N10.02.01

- User cria conta e nunca cria Player: conta permanece válida.
- User administrador de Community, mas não atleta: nenhuma identidade esportiva falsa é criada.
- Email muda: historical participations e Player IDs permanecem intactos.

# 3. N3.02.02 — Player Identity

## N4.02.02.01 — Definição

`Player` é a identidade esportiva persistente/global de uma pessoa no universo do Volley.

```text
Player
├── id
├── public/display identity fields
├── objective sports traits where appropriate
├── status/lifecycle of the identity
└── references to MediaAsset as applicable
```

Ele **não** deve carregar diretamente:

```text
Community membership/governance
Session participation
Match participation
raw evaluation aggregates
sync metadata
cloud/local identity remapping
User ownership
```

## N5.02.02 — Identificador

```text
Player.id = UUID final/global
```

O mesmo Player pode:

```text
Community A
Community B
Community C
```

sem ser duplicado por Community.

## N5.02.02.02 — Username

Username pode servir como handle de descoberta controlada.

Requisitos:

- uniqueness global se mantida como feature;
- case-insensitive;
- não é chave primária;
- pode mudar sob política futura sem quebrar referências;
- lookup público/autenticado retorna somente DTO mínimo permitido.

## N5.02.02.03 — Lifecycle

Candidato conceitual:

```text
ACTIVE
MERGED
RESTRICTED/ARCHIVED if future requirement
```

Não usar hard-delete de Player referenciado historicamente como rotina.

## N8.02.02 — Duplicate identity

Detectar possível duplicidade é diferente de automaticamente mesclar.

Nome/apelido/altura/posição não são prova suficiente de que duas rows representam a mesma pessoa.

## N10.02.02

- Dois Players com mesmo nome podem coexistir.
- Username único não impede pessoas homônimas.
- Alterar nome/avatar/posição atual não modifica MatchRoster histórico.

# 4. N3.02.03 — Participant Identity

## N4.02.03.01 — Definição

`Participant` representa uma pessoa **dentro de uma participação operacional/histórica**.

Dependendo do contexto materializado, o nome físico pode ser:

```text
SessionParticipant
MatchParticipation
MatchRosterEntry
CompetitionRosterEntry
```

A ideia comum é:

> preservar quem participou naquele contexto, mesmo se Player mudar depois.

## N5.02.03 — Relação com Player

Participant pode ser:

```text
linked_player_id = Player.id
```

ou:

```text
linked_player_id = null
source = GUEST
```

Participação não exige Player persistente.

## N5.02.03.02 — Snapshot

Participant histórico deve capturar somente o que precisa ser historicamente estável, por exemplo:

```text
display_name_at_time
player_id? / guest marker
team/roster assignment
relevant rule/position snapshot when justified
```

Não copiar o Player inteiro indiscriminadamente.

## N8.02.03 — Imutabilidade histórica

Mudanças futuras em Player:

```text
name
avatar
height
position
Community relation
account link
```

não reescrevem facts históricos.

## N10.02.03

- Player renomeado após Match: histórico preserva representação definida para aquele momento.
- Player mesclado: referências históricas são redirecionadas/interpretadas sem apagar provenance.
- Guest permanece válido mesmo sem nunca ser promovido a Player.

# 5. N3.02.04 — Guest Participant

## N4.02.04.01 — Definição

Guest é uma pessoa que participa sem exigir:

```text
User
Player
CommunityMembership
```

conforme contexto permitido.

Quick Session é o principal caso.

## N5.02.04 — Regra central

```text
GUEST PARTICIPATION
≠
CREATE PLAYER
```

O target rejeita o comportamento conceitual em que `applyGuestPlayerUpsert()` transforma automaticamente uma participação Guest em Player persistente.

## N5.02.04.02 — Promoção explícita

Se depois for desejável transformar Guest em Player:

```text
PromoteGuestToPlayer
```

é uma operação explícita.

Ela deve:

- criar ou localizar Player apropriado;
- permitir review de duplicidade;
- vincular futuras participações conforme policy;
- não reescrever necessariamente todo histórico passado sem audit/provenance.

## N5.02.04.03 — Accountless participants

Guest sem User não pode:

- votar digitalmente em fluxo que exige identidade autenticada;
- exercer capability de Organizer;
- receber ownership/governance;
- assumir account claim automaticamente.

## N10.02.04

- Quick Session com 12 nomes Guest não cria 12 Players globais.
- Mesmo nome Guest em duas Quick Sessions não é automaticamente deduplicado globalmente.
- Organizer decide promover um Guest: workflow explícito, sem guess silencioso.

# 6. N3.02.05 — Player Account Link

## N4.02.05.01 — Objetivo

`PlayerAccountLink` representa associação controlada entre User e Player.

Target conceitual:

```text
PlayerAccountLink
├── id
├── player_id
├── user_id
├── status
├── linked_at
├── linked_by / approved_by as applicable
├── unlinked_at
└── provenance
```

## N5.02.05 — Cardinalidade inicial

Hipótese forte para V1:

```text
one ACTIVE User ↔ one ACTIVE Player
```

Ou seja:

- um User não controla vários Players simultaneamente;
- um Player não possui dois Users ativos simultaneamente.

Essa cardinalidade deve ser reavaliada somente com caso de produto concreto.

## N5.02.05.02 — Por que entidade própria

Comparado com `players.user_id`, uma relação própria permite:

- histórico de link/unlink;
- proposal/claim state;
- audit;
- conflict resolution;
- futuras mudanças de cardinalidade sem alterar Player;
- deleção de User sem mutar a identidade esportiva além do vínculo.

## N6.02.05 — Commands

```text
ProposePlayerAccountLink
ApprovePlayerAccountLink
RejectPlayerAccountLink
CancelPlayerAccountLinkProposal
UnlinkPlayerAccount
```

Possíveis operações privilegiadas futuras:

```text
ForceResolvePlayerAccountLink
```

somente com capability de plataforma, justificativa e audit forte.

## N7.02.05 — Data constraints

Exemplo conceitual:

```text
unique ACTIVE link per player
unique ACTIVE link per user
```

Proposals pendentes também precisam de dedupe apropriado.

## N8.02.05 — Security

- payload não fornece `actor_user_id` autoritativo;
- proposal de User A não pode ser aprovada por qualquer User B;
- `PlayerAccountLink` é operação sensível a account takeover;
- aprovação pode exigir vínculo contextual/ownership/capability claramente definido;
- MFA/step-up é candidato para casos de risco elevado.

## N10.02.05

- Dois approvals concorrentes para Users diferentes: apenas um active link final.
- User já ligado a Player A tenta reivindicar B: conflict explícito.
- Player já ligado a outro User não é reassociado por simples username lookup.

# 7. N3.02.06 — Player Claim / Conflict Resolution

## N4.02.06.01 — Claim

Claim é o processo pelo qual um User afirma ser a pessoa representada por Player existente.

Não deve ser tratado como simples `UPDATE players SET user_id = auth.uid()`.

## N5.02.06 — Evidências e autoridade

O target não fixa ainda uma única política universal de aprovação, porque os casos podem variar:

```text
Player criado pelo próprio User
Player criado por Organizer
Player importado de legado
Player já associado a Community
Player com account link existente
```

Mas qualquer policy precisa prevenir account hijacking.

## N5.02.06.02 — Estados candidatos

```text
PENDING
APPROVED
REJECTED
CANCELLED
SUPERSEDED
```

## N5.02.06.03 — Conflict classes

```text
USER_ALREADY_LINKED
PLAYER_ALREADY_LINKED
MULTIPLE_PLAUSIBLE_PLAYERS
LEGACY_IDENTITY_AMBIGUOUS
SECURITY_REVIEW_REQUIRED
```

## N6.02.06 — Resolution

Conflito não deve ser resolvido por:

```text
latest request wins
first admin click wins
same display name
same email guessed from text
```

## N8.02.06 — Anti-hijack

Operações de claim devem registrar:

- actor;
- target Player;
- result;
- approval path;
- correlation/command ID;
- audit quando aplicável.

Não registrar secrets/documentos desnecessários em telemetry.

## N10.02.06

- Attacker conhece Player UUID/username: isso não basta para claim.
- Duas proposals concorrentes: conflito determinístico e auditável.
- Legacy Player sem owner claro: não escolher aprovador arbitrário.

# 8. N3.02.07 — Global Player

## N4.02.07.01 — Modelo

Player é global para evitar duplicar a mesma identidade esportiva em cada Community.

```text
Player P
├── CommunityPlayer A
├── CommunityPlayer B
└── CommunityPlayer C
```

## N5.02.07 — O que global NÃO significa

Global não implica:

```text
public searchable directory of everyone
public ratings
public Community membership list
public history
public evaluations
```

Escopo de descoberta e visibilidade é policy separada.

## N5.02.07.02 — Discovery

O lookup atual por username mínimo é uma direção reaproveitável, mas deve respeitar privacy policy definida em N2.16.

Candidatos:

```text
exact username lookup
controlled discovery
no arbitrary enumeration
rate limiting
```

## N8.02.07 — Enumeration abuse

Se `@username` global existir:

- evitar endpoints que listem todos os Players;
- rate limit discovery;
- não retornar Community list, evaluations ou private data no lookup mínimo.

## N10.02.07

- User autenticado procura username exato: recebe DTO mínimo.
- Tentativa de enumerar players por prefixo não recebe directory irrestrito por padrão.
- Player global em Community A não concede acesso aos dados privados dele em B.

# 9. N3.02.08 — Community Player

## N4.02.08.01 — Definição

`CommunityPlayer` representa que um Player faz parte do universo esportivo de uma Community.

Target:

```text
CommunityPlayer
├── community_id
├── player_id
├── sports status/context fields
├── joined/added timestamps if needed
└── contextual sports metadata only
```

## N5.02.08 — Não é Membership

```text
CommunityMembership
= User access/governance

CommunityPlayer
= Player sports relation
```

Podem existir independentemente.

### Exemplos válidos

```text
A)
User is Admin
but not Player

B)
Player belongs to Community
but has no User account

C)
User + Player linked
and both Membership + CommunityPlayer exist
```

## N5.02.08.02 — Remover governance do modelo esportivo

O atual `community_players.role = owner/admin/player/guest` não permanece como target.

Owner/Admin/Member pertencem a `CommunityMembership`.

Organizer é operational responsibility do Membership/assignment.

## N5.02.08.03 — Contextual sports state

Possíveis informações contextuais, somente quando houver requisito real:

```text
active/inactive in sports roster
jersey number in that Community
preferred local position override?
contextual notes with privacy rules
```

Mas atributos de avaliação não devem ser simplesmente gravados como mutable fields no CommunityPlayer; Ratings possui source facts/projections próprios.

## N6.02.08 — Commands

```text
AddPlayerToCommunity
RemovePlayerFromCommunitySportsRoster
ReactivateCommunityPlayer
```

Esses commands não criam Membership automaticamente.

## N10.02.08

- Organizer adiciona Player sem account à Community: `CommunityPlayer` criado, Membership não.
- Admin entra na Community sem jogar: Membership criado, CommunityPlayer não.
- Remover Membership de User não apaga automaticamente CommunityPlayer nem história esportiva.

# 10. N3.02.09 — Objective Player Traits

## N4.02.09.01 — Separação entre trait e evaluation

O Player atual contém atributos, altura, mão dominante, posição, status físico e avaliação dentro do mesmo shape. No target classificaremos cada dado pelo significado.

### Candidatos a traits relativamente objetivos

```text
height
handedness
preferred/main positions
secondary positions
```

Mesmo esses podem mudar com o tempo e precisam de edição autorizada.

### Não são traits objetivos

```text
attack score
serve score
reception score
vision score
consistency
emotional control
```

Esses pertencem ao modelo de Evaluation / Skill Profile.

## N5.02.09 — Health/injury caution

`lesionado` e `limitacaoFisica` atuais podem constituir dados de saúde/contexto sensível em determinados usos.

No target:

- não serão mantidos como simples campo aberto global sem privacy review;
- qualquer modelagem futura precisa definir finalidade, visibilidade, retenção e necessidade;
- não devem ser reutilizados automaticamente pelo balancer sem decisão explícita.

## N5.02.09.02 — Position

Posição esportiva pode possuir:

```text
Player preference/general identity
```

e snapshots/contextual constraints em Team Formation.

A posição usada em um sorteio histórico precisa ser snapshotada junto ao BalanceInput quando relevante; mudar Player depois não reescreve sorteio passado.

## N10.02.09

- Alterar altura atual não muda BalanceSnapshot histórico.
- “Lesionado=false” não é default usado para inferir ausência de informação médica.
- Missing trait não vira zero numérico.

# 11. N3.02.10 — Player Privacy

## N4.02.10.01 — Princípio

Player ser global não o torna público.

Dados devem ter classificação e visibility policy própria.

Candidatos de visibilidade:

```text
PRIVATE
COMMUNITY_CONTEXT
PUBLIC
```

Não necessariamente como uma única enum genérica em todo campo; a política concreta pertence aos read models.

## N5.02.10 — Data classes

### Identity/display

```text
name
nickname
username
avatar
```

Mesmo esses não são automaticamente públicos globalmente.

### Sports traits

```text
position
height
handedness
```

visibility conforme finalidade.

### Evaluations

Muito mais restritas.

Individual evaluator scores/notes não devem ser expostos a membros comuns por padrão.

### Statistics/history

Continuam dados pessoais e precisam de scope apropriado.

## N5.02.10.02 — Minimal discovery DTO

Lookup por username deve retornar apenas o mínimo necessário para identificar candidato correto.

Não incluir automaticamente:

- email;
- Memberships;
- private stats;
- raw evaluations;
- account link security data.

## N5.02.10.03 — Avatar

Player deve referenciar `MediaAsset`, não URL externa arbitrária como autoridade final. Media pipeline e visibility ficam em N2.11.

## N8.02.10 — Logs

Telemetry não deve duplicar:

```text
raw evaluation vector
notes
email
health notes
```

quando IDs e metadados bastam.

## N10.02.10

- Conhecer Player UUID não revela raw evaluation.
- Search por username retorna DTO mínimo.
- Player profile público futuro não herda automaticamente todos os dados internos.

# 12. N3.02.11 — Player Merge

## N4.02.11.01 — Problema

Duplicidades de Player são inevitáveis em algum grau:

- criação local/legacy;
- nomes iguais;
- importações;
- Guest promovido duas vezes;
- criação em Communities diferentes antes de descoberta do Player global.

Precisamos de operação explícita de merge.

## N5.02.11 — Merge não é delete + update cego

`MergePlayers(source, target)` deve preservar:

- historical participation references;
- evaluations/provenance;
- CommunityPlayer relations;
- stats contribution identity;
- media/links conforme policy;
- audit do merge.

## N5.02.11.02 — Canonical target

Um Player torna-se canonical target; outro fica `MERGED`/alias/tombstone suficiente para impedir ressurgimento da duplicidade.

Não reutilizar o source UUID para nova pessoa.

## N5.02.11.03 — Conflitos

Antes do merge verificar:

```text
both linked to different Users?
conflicting identity evidence?
duplicate Community relations?
active competitions/matches?
raw evaluation semantics?
```

Alguns conflitos exigem revisão manual.

## N6.02.11 — Commands/Queries

```text
PreviewPlayerMerge
MergePlayers
GetPlayerMergeHistory
```

`Preview` é importante para mostrar impacto antes da operação irreversível/semi-irreversível.

## N7.02.11 — Transactionality

Merge deve ser tratado como command server-side privilegiado, com transaction e locks apropriados.

Para grande volume histórico, pode usar redirects/alias em vez de atualizar bilhões de rows imediatamente; isso fica aberto para escala futura.

## N8.02.11 — Security

- não disponível a qualquer Organizer por padrão;
- exige capability forte de plataforma/contexto;
- candidato a MFA/step-up;
- audit obrigatório;
- command idempotent.

## N10.02.11

- Source e target ligados a Users diferentes: merge bloqueado para revisão.
- Retry do mesmo command não duplica migrations/relinks.
- Histórico anterior ao merge continua consultável e não perde provenance.

# 13. N3.02.12 — Account Deletion vs Sports History

## N4.02.12.01 — Regra central

```text
DELETE ACCOUNT
≠
DELETE SPORTS HISTORY
```

Porém isso também não significa “guardar tudo para sempre”. O tratamento final depende de finalidade, base legal, retenção e direitos LGPD definidos em N2.16.

## N5.02.12 — Separar operações

### Account deletion

Pode implicar:

```text
disable/remove auth identity
remove account profile data according to policy
remove/revoke PlayerAccountLink
remove Membership access
revoke device/session credentials
clear private client caches
```

### Player identity/history

Pode exigir:

```text
retain justified historical facts
anonymize/pseudonymize selected display data
preserve Match/Competition integrity
preserve snapshots necessary for other participants' history
```

## N5.02.12.02 — No destructive auth cascade

Dados esportivos compartilhados/históricos não podem depender de FK `auth.users ON DELETE CASCADE` como lifecycle principal.

O schema legado ainda possui tabelas operacionais com `owner_id ... ON DELETE CASCADE`; esse padrão deve ser removido durante migração para facts/história compartilhados.

## N5.02.12.03 — Actor references

Quando um registro precisa saber quem executou uma ação, referência histórica pode usar:

```text
actor_user_id nullable / SET NULL
+ audit snapshot/minimal identifier where justified
```

em vez de cascade destrutivo.

## N5.02.12.04 — Backups

Deletion workflow precisa considerar restauração de backup. Um restore não pode ressuscitar indefinidamente dados já eliminados quando a política exige reaplicar deleções/anonymization.

## N6.02.12 — Command conceitual

```text
RequestAccountDeletion
↓
Verify identity / step-up
↓
Create Privacy/Deletion workflow
↓
Unlink account
↓
Apply per-data-class retention/deletion/anonymization
↓
Delete/disable Auth account at safe stage
↓
Record deletion ledger/tombstone as necessary
```

## N8.02.12 — Concurrent operations

Account deletion concorrendo com:

```text
Player link proposal
Community membership change
Match/Session activity
notification jobs
media processing
```

precisa de revalidation e deterministic outcome.

## N10.02.12

- User deleta conta após jogar 100 Matches: os demais participantes não perdem placares/história.
- PlayerAccountLink deixa de conceder controle após account deletion.
- Restore de backup anterior à deletion reaplica deletion ledger/policy antes de reabrir tráfego.

# 14. N3.02.13 — Historical Participant Snapshots

## N4.02.13.01 — Objetivo

História esportiva precisa ser independente do estado mutable atual.

Snapshot é usado quando a pergunta histórica é:

> quem/como estava representado naquele evento?

Não:

> qual é o Player agora?

## N5.02.13 — Snapshot minimalism

Snapshot deve armazenar o mínimo necessário para interpretação histórica.

Exemplos possíveis:

```text
participant_id
player_id nullable
display_name_at_time
team assignment
position/role at time when relevant
source/provenance
```

Não copiar:

```text
full Player JSON
```

# 20. Realtime Policy

Identity changes são baixa frequência.

Realtime pode servir para:

- invalidar Player profile cache;
- refletir account link status;
- atualizar Community roster quando Player adicionado/removido;

mas não é necessário transmitir toda mudança de Player como event stream público.

Nunca transmitir:

- raw evaluations;
- security details de link proposals;
- private identity fields;

em channels genéricos.

# 24. N10 — Adversarial / Acceptance Matrix

## ID-N10-001 — Same name

Given two distinct people named “João Silva”, system permits two distinct Player IDs. Name dedupe alone cannot merge them.

## ID-N10-002 — Guest pollution

100 Quick Sessions with Guest names do not create 100 global Players unless explicit promotion occurs.

## ID-N10-003 — Cross-community identity

Same Player can belong to Communities A/B while Membership/access remain independently authorized.

## ID-N10-004 — Admin non-player

Community Admin can operate governance without Player identity being created automatically.

## ID-N10-005 — Player no account

Organizer can add athlete to Community roster while no User exists.

## ID-N10-006 — Claim by UUID

Attacker with target Player UUID cannot link account without authorized claim flow.

## ID-N10-007 — Concurrent claim

Two Users attempt approval concurrently for same Player; DB ends with at most one ACTIVE link.

## ID-N10-008 — User already linked

User linked to Player A cannot become simultaneously ACTIVE on Player B without explicit conflict resolution/unlink policy.

## ID-N10-009 — Account deletion

Deleting account removes access/link but does not erase other participants’ Match history.

## ID-N10-010 — Player edit

Changing Player name/avatar/position does not alter immutable MatchRoster/Participant snapshot semantics.

## ID-N10-011 — Merge conflict

Players linked to two different active Users cannot be merged silently.

## ID-N10-012 — Merge retry

Same MergePlayers command retried 100 times yields one logical merge.

## ID-N10-013 — Legacy guest

Legacy `Player.isGuest=true` with historical references is not simply deleted during migration; importer preserves history and records provenance/classification.

## ID-N10-014 — Community removal

Removing a User Membership does not delete Player or CommunityPlayer automatically unless a separate sports-roster command is executed.

## ID-N10-015 — Raw evaluation privacy

Member with Player UUID cannot query another Organizer’s raw evaluation simply through ID enumeration.

## ID-N10-016 — Username enumeration

Discovery endpoint does not expose an unbounded directory or additional private relations.

## ID-N10-017 — Unknown data

Missing height/evaluation/trait does not become numerical zero during import or read model projection.

## ID-N10-018 — Backup restore

Account deleted after backup remains unlinked/deleted according to deletion ledger after restore procedure.

## ID-N10-019 — Identity projection failure

SkillProfile projection can be rebuilt without modifying Player identity.

## ID-N10-020 — Current system regression

New canonical Player type must not reintroduce `communityIds`, `syncStatus`, `cloudId`, `evaluationAggregate` or `isGuest` as core identity fields without explicit ADR.

# 25. Decisions / Hypotheses / Open Questions

## DECIDED

- `User ≠ Player ≠ Participant`.
- Player é identidade esportiva global.
- User pode existir sem Player.
- Player pode existir sem User.
- Guest não cria Player automaticamente.
- CommunityMembership e CommunityPlayer são independentes.
- Historical participation usa snapshots/provenance.
- Account deletion não deve apagar automaticamente sports history.
- Vínculo User↔Player será entidade/relação própria no target.
- Merge deve ser explícito, auditável e preservar referências.

- V1 terá no máximo um ACTIVE PlayerAccountLink por User e por Player.
- Username continuará globalmente único e será discovery handle principal, sujeito a privacy review.
- Player Merge será operação de alta segurança com MFA/step-up para staff/privileged actors.

- Exata política de quem pode aprovar claim quando Player foi criado por terceiros/legado.

- Requisitos futuros para múltiplos perfis esportivos por uma mesma conta, caso surjam.
- Política detalhada para dados físicos/saúde e menores de idade.

# 27. Definition of Identity Compliance

Uma implementação está alinhada a N2.02 quando:

1. conta autenticada e identidade esportiva podem existir separadamente;
2. Guests participam sem pollution do catálogo global;
3. Player possui UUID global final;
4. Communities relacionam Players por `CommunityPlayer`, não arrays no Player;
5. governance vive em Membership, não CommunityPlayer;
6. Player Account Link possui workflow controlado e constraints anti-hijack;
7. current traits/profile não reescrevem história;
8. evaluations/skill projections não pertencem à identidade-base;
9. merge é explícito e preserva provenance;
10. account deletion preserva apenas facts legitimamente necessários e não usa destructive cascade como shortcut;
11. privacy de Player global é definida por read models/policies, não por existência da row;
12. legacy `cloudId/localId/syncStatus/communityIds/isGuest` não contaminam o target canonical model.
