## 0. Regra de leitura

Este documento define o **target canônico** para Communities.

A separação central é:

```text
Community
├── people with access/governance → CommunityMembership
├── athletes                    → CommunityPlayer
├── entry requests              → CommunityJoinRequest
├── operational responsibility  → Membership responsibility / assignment
├── sessions                    → Session
├── evaluations                 → PlayerEvaluation
└── competitions                → Competition
```

Portanto:

```text
CommunityMembership ≠ CommunityPlayer
Governance Role ≠ Operational Responsibility
Organizer ≠ Admin
JoinRequest ≠ Membership
```

Community funciona como um **contexto organizacional persistente**, próximo de um tenant para autorização e dados compartilhados, mas **não é um tenant absoluto** porque `Player` é global e pode aparecer em várias Communities.

# 1. Current State — evidência do repositório

## 1.1 Community client-side ainda carrega infraestrutura de sync

O type atual de `Community` contém, além de dados de produto:

```text
cloudOwnerId
cloudId
syncStatus
lastSyncedAt
deletedAt
```

Também carrega diretamente defaults operacionais, `visibility` e `joinCode`.

No target, `cloud/local/sync` não pertence ao aggregate canônico; defaults mais ricos terão estrutura própria e serão snapshotados na Session.

## 1.2 Membership atual mistura filiação e pedido de entrada

O type atual `CommunityMember` usa:

```text
role:
owner | admin | moderator | organizador | member

status:
active | pending | invited | rejected
```

Isso faz uma mesma row representar simultaneamente:

- filiação efetiva;
- pedido ainda não aprovado;
- convite;
- rejeição histórica.

O target separa essas responsabilidades.

## 1.3 O banco já evoluiu de `organizer` para modelos diferentes — e depois reintroduziu `organizador`

A migration `community_model_v2` inicialmente migrou `organizer → moderator` e estabeleceu roles `owner/admin/moderator/member`, com Membership status para entrada/aprovação.

Uma migration posterior criou novamente `organizador` como role e adicionou `community_role_capabilities` e `community_role_capability_overrides`.

Isso mostra que a semântica de Organizer permaneceu ambígua no legado.

O target resolve a ambiguidade estruturalmente:

```text
CommunityMembership
├── governance_role: OWNER | ADMIN | MEMBER
└── operational_responsibilities: set<Responsibility>
    └── ORGANIZER
```

## 1.4 Capability layer atual é uma boa direção, mas o override configurável não é target V1

O backend já possui uma função `community_has_capability()` e usa capabilities como:

```text
edit_community_info
manage_members
approve_members
remove_members
manage_sessions
manage_evaluations
```

Essa ideia — **autorizar por capability contextual em vez de confiar no frontend** — é preservada.

Porém o target V1 não terá um “permission builder” arbitrário nem overrides de role configuráveis por Community.

Capabilities serão derivadas de:

```text
active Membership
+ governance role
+ operational responsibilities
+ resource-specific assignments
+ platform override only where explicitly defined
```

## 1.5 Join flow atual ainda grava `pending` em `community_members`

O backend atual `request_to_join_community()` faz upsert em `community_members` com `role='member'` e `status='pending'`; approve muda status para `active`, reject para `rejected`.

No target:

```text
CommunityJoinRequest
PENDING → APPROVED / REJECTED / WITHDRAWN

APPROVED
→ creates/activates CommunityMembership
```

## 1.6 Leave atual deleta Membership row

O RPC legado `leave_community()` executa `DELETE FROM community_members` para não-owner.

No target, Membership possui lifecycle histórico e sair significa:

```text
status = LEFT
```

não apagar a relação como se ela nunca tivesse existido.

## 1.7 Ownership transfer atual é platform-master-only

A capability layer atual implementa `transfer_community_ownership()` como operação permitida apenas a capability global `manage_community_ownership`, promovendo o novo owner e rebaixando o anterior.

O target muda a semântica normal de produto:

- o Owner atual poderá transferir ownership de sua Community por command específico;
- operação é transacional e de alta segurança;
- Platform Staff mantém somente caminho de recuperação/break-glass explicitamente auditado;
- Admin comum não transfere ownership por ser Admin.

## 1.8 `community_players.role` já está deprecated

O próprio banco registra que `community_players.role` foi superseded pela tabela real de RBAC e não deve receber novas features.

Isso é compatível com o target, que remove governance de `CommunityPlayer` completamente.

## 1.9 Community local-first ainda existe no código

O fluxo atual permite:

```text
createLocalCommunity()
syncStatus = local
local deletion → pending sync
duplicateLocalCommunity()
Player.communityIds[] adjustments
```

No target, uma Community compartilhada é **online-authoritative**.

Um formulário/draft pode existir localmente, mas não existe “Community efetiva criada offline e sincronizada depois” como authority concorrente.

# 2. N3.03.01 — Community Aggregate

## N4.03.01.01 — Definição

Community é o contexto persistente em que um grupo organiza acesso, atletas, Sessions, avaliações, configurações e Competitions.

Target conceitual:

```text
Community
├── id: UUID
├── name
├── slug? / handle?               [optional / mutable]
├── description?
├── media_asset_id?               [optional]
├── lifecycle_status
├── visibility policy
├── discoverability policy
├── join policy
├── created_at
├── updated_at
└── domain revision where needed
```

Não deve conter diretamente:

```text
member IDs[]
player IDs[]
session IDs[]
role ACL JSON
cloud/local sync IDs
mutable session state
all defaults in one unbounded JSON settings blob
```

## N5.03.01 — Aggregate boundary

Community é owner de:

- sua identidade organizacional;
- lifecycle;
- policies de descoberta/entrada;
- Membership governance;
- ownership invariant;
- defaults de Community.

Não é owner interno de:

- Player global;
- Session internals;
- Match internals;
- Competition internals;
- Evaluation internals.

Esses contexts referenciam `community_id`, mas preservam ownership próprio.

## N5.03.01.02 — Creation transaction

`CreateCommunity` deve ser atômico:

```text
BEGIN
  create Community
  create creator Membership as ACTIVE OWNER
  create/default CommunityDefaults if needed
  record audit/domain event/outbox as applicable
COMMIT
```

Nunca deve existir um estado observável em que Community foi criada sem Owner.

## N6.03.01 — Commands / Queries

```text
CreateCommunity
UpdateCommunityProfile
GetCommunity
GetCommunityDashboard
```

CRUD genérico de row não é o contrato de aplicação para comportamentos ricos.

## N8.03.01 — Failure semantics

Se Membership OWNER falhar na criação:

```text
Community creation fails as a whole.
```

Não criar Community órfã para “corrigir depois”.

## N10.03.01

- Crash entre INSERT Community e Owner Membership não deixa Community sem owner.
- Retry do mesmo `CreateCommunity` command ID não cria duas Communities.
- Payload não consegue escolher outro `creator_user_id`; actor deriva de Auth.

# 3. N3.03.02 — Community Lifecycle

## N4.03.02.01 — Lifecycle alvo

V1:

```text
ACTIVE
ARCHIVED
```

Possível estado separado futuro:

```text
SUSPENDED_BY_PLATFORM
```

somente se houver necessidade real de moderação/plataforma.

Não misturar suspensão de um **Member** com suspensão da **Community**.

## N5.03.02 — ACTIVE

Community ativa permite operações conforme capabilities e policies.

## N5.03.02.02 — ARCHIVED

Archive significa:

- histórico preservado;
- Community deixa de operar normalmente;
- novas Sessions/JoinRequests e mutations ordinárias são bloqueadas conforme policy;
- leitura histórica continua disponível a quem tiver direito;
- não é hard-delete.

## N5.03.02.03 — Restore

Restaurar uma Community arquivada pode existir como command controlado.

Se implementado:

```text
RestoreCommunity
```

revalida ownership, policies e dependências atuais.

## N8.03.02 — Delete

Hard-delete não é lifecycle normal de Community com história compartilhada.

LGPD/account deletion não deve ser confundida com “apagar a Community inteira” quando há múltiplos titulares e fatos compartilhados.

## N10.03.02

- Archive não apaga Sessions/Matches/Competitions passadas.
- Archived Community não aceita nova JoinRequest silenciosamente.
- Community archive não remove Player global.

# 4. N3.03.03 — Visibility / Discoverability

## N4.03.03.01 — Três perguntas distintas

Precisamos separar:

```text
VISIBILITY
Quem pode ver conteúdo da Community?

DISCOVERABILITY
Quem consegue descobrir que a Community existe?

JOIN POLICY
Como alguém consegue entrar?
```

O legado trata principalmente `visibility = private/public`, mas isso é insuficiente para todas as combinações futuras.

## N5.03.03 — Exemplos de combinações válidas

```text
Discoverable + private content + approval required

Hidden + invite/code only

Public profile + restricted member content
```

## N5.03.03.02 — V1 pragmático

Não precisamos inventar dezenas de enums no primeiro schema.

Podemos iniciar com uma pequena policy explícita, mas o modelo e os commands não devem assumir que `public = open join`.

## N6.03.03 — Queries

```text
SearchDiscoverableCommunities
GetPublicCommunityPreview
GetCommunityForMember
```

DTO público deve ser diferente do DTO interno de Member/Admin quando necessário.

## N8.03.03 — Privacy

Descobrir Community não concede automaticamente acesso a:

- Membership list completa;
- emails;
- avaliações;
- private Sessions;
- Player details fora do scope permitido.

## N10.03.03

- Community discoverable aparece em busca, mas conteúdo privado continua protegido.
- Conhecer Community UUID não ignora visibility/access policy.
- Search result não vaza emails ou lista completa de Members.

# 5. N3.03.04 — Join Policy

## N4.03.04.01 — Definição

Join Policy decide como User pode iniciar entrada na Community.

Possíveis modos conceituais:

```text
APPROVAL_REQUIRED
INVITE_ONLY
OPEN_JOIN                    [future/optional]
```

Exact enum permanece sujeito à decisão de produto, mas deve ser independente de visibility.

## N5.03.04 — Join code

`join_code` é uma **credencial para iniciar um fluxo**, não autorização permanente.

Portanto:

```text
KNOW JOIN CODE
≠
IS MEMBER
```

Requisitos:

- suficiente entropia;
- revogável/rotacionável;
- rate-limited;
- não aparece em logs/analytics desnecessários;
- não é usado como read authorization depois da entrada.

## N5.03.04.02 — Public discovery

Uma Community discoverable/public pode continuar exigindo approval.

Não derivar Join Policy apenas da visibilidade.

## N6.03.04 — Commands

```text
ChangeCommunityJoinPolicy
GenerateJoinCode
RotateJoinCode
DisableJoinCode
```

## N10.03.04

- Código vazado pode ser desativado sem remover Members existentes.
- User com código não consegue consultar dados internos antes de aprovação.
- Brute force de códigos recebe rate limiting.

# 6. N3.03.05 — Join Request

## N4.03.05.01 — Entidade separada

Target:

```text
CommunityJoinRequest
├── id
├── community_id
├── user_id
├── source              // code, discovery, invite-flow if applicable
├── status
├── created_at
├── decided_at?
├── decided_by?
└── decision metadata minimal/auditable
```

Lifecycle:

```text
PENDING
  ├──→ APPROVED
  ├──→ REJECTED
  └──→ WITHDRAWN
```

## N5.03.05 — Unique active request

No máximo uma request `PENDING` por `(community_id, user_id)`.

Repetir o mesmo pedido não cria filas infinitas de rows ativas.

## N5.03.05.02 — Approval semantics

`ApproveCommunityJoinRequest` deve ser transacional:

```text
lock/revalidate request
verify approver capability in request.community_id
verify request still PENDING
create/reactivate CommunityMembership as ACTIVE MEMBER
mark request APPROVED
record actor/time/audit
commit
```

## N5.03.05.03 — Rejection

Rejection preserva request histórica; não transforma Membership em `rejected`.

## N5.03.05.04 — Withdrawal

O próprio solicitante pode retirar request pendente conforme policy.

## N6.03.05 — Commands

```text
RequestCommunityJoin
WithdrawCommunityJoinRequest
ApproveCommunityJoinRequest
RejectCommunityJoinRequest
```

## N7.03.05 — Offline

Todos são:

```text
ONLINE_ONLY
```

Não existe aprovação offline enfileirada.

## N8.03.05 — Authorization by resource context

O servidor recebe `join_request_id`, resolve:

```text
request
→ request.community_id
→ actor Membership in THAT Community
→ capability
```

Não confia em `community_id` separado fornecido pelo browser para autorizar.

## N10.03.05

- Admin de Community A tenta aprovar request de B por UUID: denied.
- Duas aprovações concorrentes: uma transição lógica; Membership não duplica.
- User já ACTIVE solicita novamente: resposta idempotente/domain-specific, sem request paralela absurda.
- Rejected request permanece auditável sem criar Membership rejeitada.

# 7. N3.03.06 — Membership

## N4.03.06.01 — Definição

`CommunityMembership` representa relação efetiva entre **User** e Community.

Target:

```text
CommunityMembership
├── id
├── community_id
├── user_id
├── governance_role
├── status
├── joined_at
├── status_changed_at
├── created_by? / source?
└── revision/audit metadata where appropriate
```

## N5.03.06 — Lifecycle

```text
ACTIVE
SUSPENDED
LEFT
REMOVED
```

Possível `INVITED` não deve ser colocado aqui apenas por conveniência; se invitations forem necessárias, modelá-las explicitamente ou definir contrato separado no momento da feature.

## N5.03.06.02 — Historical preservation

`LEFT` e `REMOVED` preservam a relação histórica.

Não usar DELETE físico como fluxo normal para:

```text
LeaveCommunity
RemoveCommunityMember
```

## N5.03.06.03 — Rejoin

User que já possui Membership histórica e é aprovado novamente pode:

- reativar a row existente, ou
- criar Membership revision/history separada.

A escolha física final deve preservar auditabilidade; o contrato lógico é uma nova entrada efetiva, não apagar o passado.

## N5.03.06.04 — Membership ≠ CommunityPlayer

Membership não cria Player/CommunityPlayer automaticamente.

User pode ser:

```text
Admin sem jogar
Member sem Player link
Member ligado a Player que ainda não foi adicionado ao sports roster
```

## N10.03.06

- User sai: Membership passa a LEFT; Player/CommunityPlayer/history permanecem conforme próprios contexts.
- User removido: não perde account global nem Player global.
- Suspended Membership não recebe capabilities mesmo com role ADMIN gravada.

# 8. N3.03.07 — Governance Roles

## N4.03.07.01 — Roles V1

```text
OWNER
ADMIN
MEMBER
```

Somente isso para governance V1.

## N5.03.07 — OWNER

Owner possui responsabilidade final de governança da Community:

- profile/settings governáveis;
- Membership administration;
- ownership transfer;
- archive/restore conforme policy;
- atribuição de responsabilidades operacionais conforme capability.

Owner não recebe automaticamente controle de Match apenas por ser Owner.

## N5.03.07.02 — ADMIN

Admin auxilia governança:

- pode gerenciar Members conforme capability definida;
- pode aprovar/rejeitar JoinRequests se policy permitir;
- pode editar Community conforme capability;
- não transfere ownership apenas por ser Admin;
- não é Organizer automaticamente.

## N5.03.07.03 — MEMBER

Member é acesso ordinário.

Pode possuir responsabilidades operacionais adicionais, como `ORGANIZER`, sem virar Admin.

## N5.03.07.04 — Por que não MODERATOR no target inicial

O legado possui `moderator`, especialmente para aprovação de pedidos.

Não carregaremos o role apenas por compatibilidade. Se surgir requisito comprovado de uma função de moderação distinta de Admin, introduzimos um governance role explícito por ADR/requisito — não um role genérico para preencher lacunas.

## N5.03.07.05 — No role hierarchy as authorization shortcut

Evitar lógica:

```text
OWNER > ADMIN > MEMBER
therefore owner/admin can do everything below
```

Capabilities são definidas por operação/contexto.

Isso é especialmente necessário porque capabilities operacionais não seguem a mesma hierarquia.

## N10.03.07

- Admin não consegue executar Organizer-only command sem responsabilidade/assignment.
- Member com ORGANIZER consegue operar Session sem receber `manage_members`.
- Novo governance role não é adicionado apenas para resolver uma tela.

# 9. N3.03.08 — Operational Responsibilities

## N4.03.08.01 — Modelo

Uma Membership ativa pode possuir responsabilidades operacionais independentes do governance role.

Conceitualmente:

```text
CommunityMembership
├── governance_role: OWNER | ADMIN | MEMBER
└── operational_responsibilities
    ├── ORGANIZER
    └── future: REFEREE / STATISTICIAN / COACH ...
```

## N5.03.08 — Persistência

Evitar uma coluna enum singular como:

```text
membership.role = ORGANIZER
```

Possíveis implementações:

```text
community_membership_responsibilities
(membership_id, responsibility)
```

ou estrutura equivalente relacional.

## N5.03.08.02 — Capability derivation

```text
Membership ACTIVE
+ governance_role
+ responsibilities
+ resource assignment
→ Capability
```

Não confiar em badge/UI.

## N5.03.08.03 — Future-proofing

Quando surgir `REFEREE`, perguntar:

```text
É governance?
É responsabilidade operacional?
É assignment de Match/Competition?
```

antes de alterar role enum.

## N10.03.08

- MEMBER + ORGANIZER é estado válido.
- ADMIN sem ORGANIZER é estado válido.
- OWNER sem ORGANIZER é estado válido.
- remover ORGANIZER não remove Membership.

# 10. N3.03.09 — Organizer Responsibility

## N4.03.09.01 — Semântica canônica

Organizer é a pessoa que pode organizar a operação esportiva de Sessions/Matches.

Inclui, conforme capability/assignment:

```text
create/configure/publish Session
open/close registration
manage effective roster within allowed rules
generate/edit/confirm teams
start Session
prepare/start/control/pause/finish Match
register/correct sporting events
evaluate Players where evaluation policy grants it
```

## N5.03.09 — Não inclui governance automaticamente

Organizer **não** recebe por implicação:

```text
edit Community profile
approve/remove Members
change governance roles
transfer ownership
archive Community
manage Competition administration
```

## N5.03.09.02 — Community eligibility vs Session assignment

Community responsibility `ORGANIZER` significa:

```text
eligible to organize
```

Não necessariamente:

```text
can mutate every Session created by every other Organizer
```

O contexto Session usa `SessionOrganizerAssignment` para determinar responsibility específica.

Owner/Admin podem ter **administrative override controlado** onde explicitamente definido, mas isso não converte seu governance role em Organizer permanente.

## N5.03.09.03 — Organizer and evaluation

Se a Community policy permite avaliação esportiva por Organizers, a capability deriva da responsabilidade esportiva.

Admin não ganha avaliação apenas por ser Admin.

## N5.03.09.04 — Organizer ≠ MatchController

Organizer é elegibilidade/responsabilidade.

`MatchController` é a autoridade técnica corrente de uma Match, definida no contexto Match.

## N10.03.09

- Organizer consegue criar Session mas não remover Admin.
- Admin consegue aprovar Membership mas não AwardPoint se não possuir Match control.
- Dois Organizers existem; um não altera automaticamente a Session do outro sem assignment/override.

# 11. N3.03.10 — Ownership

## N4.03.10.01 — Invariante

Toda Community ACTIVE deve possuir:

```text
EXACTLY ONE ACTIVE OWNER
```

## N5.03.10 — Enforcement em duas camadas

### Database

Garantir **at most one** owner ativo, por exemplo por unique partial index/constraint equivalente.

### Semantic transaction

Garantir **at least one** owner ao criar, transferir, suspender/remover/leave/archive conforme regras.

Um CHECK simples por row não consegue garantir sozinho “pelo menos um owner na tabela inteira”.

## N5.03.10.02 — Owner restrictions

Owner não pode:

- Leave diretamente;
- ser Removed diretamente;
- ser Suspended enquanto único Owner;
- ter role rebaixada por command genérico.

Esses casos exigem `TransferCommunityOwnership` ou recovery privilegiado.

## N5.03.10.03 — Creator ≠ eternal owner column

Após creation, ownership é representado pela Membership OWNER, não por `communities.owner_id` como authority paralela.

Campos `created_by` podem existir para provenance, mas não autorizam gestão para sempre.

## N10.03.10

- Community nunca termina commit com zero owner.
- `created_by` antigo não mantém poderes depois de ownership transfer.
- duas requisições concorrentes de transfer não produzem dois owners ativos.

# 12. N3.03.11 — Ownership Transfer

## N4.03.11.01 — Command dedicado

```text
TransferCommunityOwnership
```

Não é `ChangeMemberRole(role=OWNER)`.

## N5.03.11 — Preconditions

- actor autenticado;
- actor é Owner ativo ou recovery platform capability explicitamente autorizada;
- target é Membership ACTIVE da mesma Community;
- target não é current owner;
- MFA/step-up conforme Security policy;
- expected revision/concurrency protection onde necessário.

## N5.03.11.02 — Transaction

Sem estado observável inválido:

```text
BEGIN
  lock Community / relevant Memberships
  revalidate actor + target
  atomically switch ownership
  old owner → ADMIN by default policy
  audit ownership transfer
  increment revision/event
COMMIT
```

A implementação física deve respeitar a constraint de unicidade; não depender de um momento intermediário com dois owners se a constraint final for exatamente um.

## N5.03.11.03 — Old owner role

Default inicial:

```text
OLD OWNER → ADMIN
```

Se produto desejar `MEMBER`, isso deve ser opção explícita/policy, nunca efeito colateral invisível.

## N5.03.11.04 — Platform recovery

Platform Staff pode precisar recuperar Community sem Owner por corrupção/incident.

Esse caminho:

- não é fluxo de produto normal;
- exige MFA forte;
- audit + reason;
- break-glass/runbook.

## N10.03.11

- Owner tenta transferir para User de outra Community: denied.
- Target Membership suspensa: denied.
- Response se perde após commit: retry mesmo command retorna ownership já transferida, sem flip-flop.
- Dois transfers concorrentes serializam/rejeitam stale state.

# 13. N3.03.12 — Member Suspension / Removal / Leave

## N4.03.12.01 — Estados diferentes têm semânticas diferentes

```text
SUSPENDED
acesso temporariamente bloqueado

LEFT
próprio User encerrou filiação

REMOVED
Community governance encerrou filiação
```

Não usar um único boolean `active` para esconder a causa.

## N5.03.12 — Suspend

`SuspendCommunityMember`:

- preserva role/responsibilities para possível restore;
- remove capabilities enquanto suspenso;
- não apaga CommunityPlayer automaticamente;
- pode impedir Registration/Session actions futuras.

## N5.03.12.02 — Restore

`RestoreCommunityMember` retorna Membership a ACTIVE conforme preconditions.

## N5.03.12.03 — Remove

`RemoveCommunityMember`:

- status → REMOVED;
- actor capability verificada;
- Owner protegido;
- não apaga histórico esportivo;
- não remove Player global;
- pode disparar revogação de active operational assignments conforme contexts proprietários.

## N5.03.12.04 — Leave

`LeaveCommunity`:

- somente o próprio active Member;
- Owner não pode sair antes de transfer;
- status → LEFT;
- não é DELETE físico.

## N8.03.12 — Realtime/revocation edge

Membership revoke deve ser efetivo para **commands imediatamente** após commit, mesmo que uma Realtime subscription antiga demore a ser desconectada.

Command authorization sempre revalida Membership/capability server-side.

## N10.03.12

- Suspended Admin com channel Realtime ainda aberto não consegue executar command.
- Removed Organizer não consegue continuar criando novas Sessions.
- Leave não remove historical Match participation.

# 14. N3.03.13 — Community Defaults

## N4.03.13.01 — Definição

Community pode guardar defaults que aceleram criação de Sessions:

```text
default location
schedule preferences
Session rule defaults
Team Formation defaults
court/rotation preferences
team selection policy default
```

## N5.03.13 — Default ≠ live dependency

Ao criar/configurar Session:

```text
CommunityDefault
↓ COPY
Session Snapshot / Config
```

Depois:

```text
changing Community default
DOES NOT rewrite existing Session
```

## N5.03.13.02 — Versioning

Quando semântica de default/rules importar historicamente, snapshot registra versão/policy correspondente.

## N5.03.13.03 — Avoid giant settings blob

Não criar um `community.settings jsonb` ilimitado para qualquer feature.

# 15. N3.03.14 — Community Archive

## N4.03.14.01 — Archive é operação semântica

```text
ArchiveCommunity
```

não `softDeleteCommunity()` genérico.

## N5.03.14 — Preconditions candidatas

Antes de archive, verificar ao menos:

- actor capability;
- active critical operations (Session LIVE, Competition active etc.) conforme policy;
- ownership consistente;
- efeitos sobre JoinRequests abertas.

## N5.03.14.02 — Consequências

- impedir novas Sessions;
- manter Memberships e roles para histórico/restore;

## N5.03.14.03 — Public discovery

## N10.03.14

- Archive com Match LIVE é bloqueado ou exige fluxo explícito, nunca orphan state.
- Search pública não apresenta archived Community como disponível para entrada.
- Restore não recria Members perdidos porque archive não os deletou.

# 16. N3.03.15 — Community Authorization Boundary

## N4.03.15.01 — Regra central

Toda autorização contextual segue:

```text
JWT / auth.uid()
↓
resolve target resource
↓
resolve REAL community_id from resource
↓
active CommunityMembership
↓
governance role / operational responsibility
↓
resource-specific assignment
↓
Capability
↓
command allowed/denied
```

## N5.03.15 — Anti-BOLA / IDOR

Nunca confiar em:

```text
payload.community_id
payload.role
payload.isAdmin
client capability list
route param alone
```

como prova de autorização.

Exemplo:

```text
ApproveJoinRequest(request_id)
```

servidor busca request e usa `request.community_id`.

Não:

```text
ApproveJoinRequest(request_id, community_id_from_browser)
```

seguido de auth apenas sobre o segundo campo.

## N5.03.15.02 — Capability model target

Capabilities continuam sendo o contrato de autorização, mas V1 evita uma ACL configurável genérica.

Exemplo conceitual:

### Governance

```text
COMMUNITY_EDIT_PROFILE
COMMUNITY_MANAGE_MEMBERS
COMMUNITY_APPROVE_JOIN_REQUEST
COMMUNITY_REMOVE_MEMBER
COMMUNITY_TRANSFER_OWNERSHIP
COMMUNITY_ARCHIVE
```

### Operational eligibility

```text
SESSION_CREATE
SESSION_ORGANIZE
PLAYER_EVALUATE
```

Essas últimas dependem de responsibility/assignment, não simplesmente ADMIN.

## N5.03.15.03 — Platform roles

Platform Admin/Staff é boundary separada da Community.

Não usar:

```text
master = implicit owner of every Community
```

como lógica normal de domínio.

Break-glass existe somente para suporte/incident com capability, MFA e audit específicos.

## N5.03.15.04 — RLS

RLS funciona como defense-in-depth.

Critical shared mutations devem preferir semantic commands/RPCs em vez de permitir INSERT/UPDATE/DELETE arbitrário de Membership/JoinRequest pelo browser.

## N5.03.15.05 — Offline

Community governance é:

```text
ONLINE_AUTHORITATIVE
```

Não enfileirar:

```text
ApproveJoinRequest
ChangeGovernanceRole
TransferOwnership
RemoveMember
```

para “sincronizar depois”.

## N10.03.15

- Admin A muda UUID da request no DevTools para request B: servidor autoriza pelo contexto real e nega.
- Organizer não consegue UPDATE Community profile por tabela direta.
- Client altera local role para OWNER: servidor ignora.
- Membership é suspensa depois de JWT emitido: command posterior consulta estado canônico e falha.

# 31. N10 — Adversarial / Acceptance Matrix

## COM-N10-001 — Community without owner

Simulate failure during creation. No committed Community may exist without exactly one active Owner.

## COM-N10-002 — Two owners race

Two concurrent ownership transfers cannot end with two active owners or zero owners.

## COM-N10-003 — Owner leaves

`LeaveCommunity` by current Owner is rejected until ownership is transferred.

## COM-N10-004 — Creator after transfer

Original creator loses Owner-specific capabilities after transfer even if `created_by` remains in history.

## COM-N10-005 — Organizer governance escalation

MEMBER+ORGANIZER attempts `RemoveCommunityMember`: denied.

## COM-N10-006 — Admin operational escalation

ADMIN without ORGANIZER/assignment attempts Organizer-only Session command: denied unless explicit administrative override exists for that command.

## COM-N10-007 — Cross-community JoinRequest BOLA

Admin of A sends `ApproveCommunityJoinRequest(request_id_of_B)`: denied after server resolves B from request.

## COM-N10-008 — Client role tamper

User changes local state to `OWNER`; server capabilities remain unchanged.

## COM-N10-009 — Stale JWT

Membership becomes SUSPENDED while token remains valid; next Community command is denied by canonical membership check.

## COM-N10-010 — Join code leak

Leaked code permits only allowed request/preview flow; no member-only reads.

## COM-N10-011 — Duplicate Join request

Double-click/retry creates at most one effective PENDING request.

## COM-N10-012 — Concurrent approval

Two admins approve same request; one logical transition and one effective Membership.

## COM-N10-013 — Reject vs approve race

Approve and Reject race serializes; request has one terminal state and no inconsistent Membership.

## COM-N10-014 — Membership history

Leave/Remove does not delete row/history or historical audit facts.

## COM-N10-015 — CommunityPlayer independence

Removing Membership does not delete CommunityPlayer automatically.

## COM-N10-016 — Player independence

Archiving Community does not delete global Players.

## COM-N10-017 — Defaults snapshot

Change Community balancing default after Session roster/draw; historical/session config remains unchanged.

## COM-N10-018 — Archive while live

Archive command detects active critical workflow and blocks or uses explicit policy; no orphan live Match.

## COM-N10-019 — Realtime revoke lag

Removed Member retains socket for several seconds but every subsequent command is still denied.

## COM-N10-020 — Legacy organizer migration

Legacy `organizador` becomes MEMBER + ORGANIZER, not ADMIN.

## COM-N10-021 — Legacy moderator ambiguity

Migration does not silently promote every moderator to ADMIN without evidence/policy.

## COM-N10-022 — Permission override resurrection

New feature cannot depend on legacy `community_role_capability_overrides` after target cutover without explicit ADR.

## COM-N10-023 — Public discovery privacy

Searchable Community result leaks no emails, raw evaluations or private Member details.

## COM-N10-024 — Archive restore

Archive then restore preserves ownership/Membership history and does not recreate deleted facts from client cache.

## COM-N10-025 — Offline governance

Device offline cannot “approve locally” a JoinRequest and show success as confirmed.

# 32. Decisions / Hypotheses / Open Questions

## DECIDED

- Community is persistent organizational context, not global Player tenant.
- CommunityMembership and CommunityPlayer are independent.
- CommunityJoinRequest is separate from Membership.
- Governance roles V1 are `OWNER | ADMIN | MEMBER`.
- `ORGANIZER` is operational responsibility, not governance role.
- Organizer does not imply Community governance.
- Community Organizer eligibility does not imply control over every Session; Session assignment refines authority.
- Every active Community has exactly one active Owner.
- CreateCommunity creates Community + Owner atomically.
- Owner cannot leave before ownership transfer.
- Ownership transfer is a dedicated transaction.
- Membership lifecycle preserves Left/Removed/Suspended history.
- Community shared mutations are online-authoritative.
- Defaults are copied to Session snapshots, not live references.
- Archive preserves history.
- Critical authorization is capability/resource-context based.
- V1 does not expose arbitrary ACL/permission builder.

## STRONG HYPOTHESIS

- Old Owner becomes ADMIN after ownership transfer by default.
- Owner and Admin can approve JoinRequests; no Moderator role is needed initially.
- A small static capability map is preferable to persisted role-capability overrides in V1.
- Archived Community can be restored unless future compliance/product requirements say otherwise.

## OPEN

- Exact enum for visibility/discoverability/join policy combinations.
- Whether V1 should support `OPEN_JOIN` or only approval/invite flows.
- Exact treatment/migration of existing `moderator` Memberships.
- Whether Admin may Archive Community or only Owner.
- Exact administrative override policy for Owner/Admin over Sessions owned by Organizer.
- Whether invitations deserve a first-class `CommunityInvitation` entity in V1 or later.
- Retention period/details for rejected/withdrawn JoinRequests.

# 34. Definition of Community Compliance

An implementation is aligned with N2.03 when:

1. Community creation is server-authoritative and atomically creates one Owner;

11. Community defaults are snapshot into Sessions where needed;
12. Archive preserves history instead of deleting shared facts;
13. critical governance mutations are online-only;
14. capability checks are server-side and RLS-backed;
