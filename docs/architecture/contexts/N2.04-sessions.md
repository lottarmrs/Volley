## 0. Regra de leitura

Este documento define o **target canônico** de Session.

As separações fundamentais são:

```text
Session ≠ Match
Session ≠ Competition
Session ≠ Fixture
Session ≠ RegistrationWindow
Session ≠ TeamDraw
Session ≠ MatchControlLease
```

Uma Session representa o **evento operacional que reúne pessoas, configuração, quadras e execução esportiva em um intervalo/contexto**.

Ela pode hospedar:

```text
0..N Matches
1..N Courts
0..N Fixtures associados
```

A Session organiza a atividade; Match executa um confronto; Competition estrutura a disputa; Registration captura intenção de entrada; TeamDraw materializa a formação de times.

# 1. Current State — evidência do repositório

## 1.1 `Session` atual mistura várias fases do fluxo

O type atual possui:

```text
status:
  draft
  players_selected
  configured
  teams_generated
  active
  paused
  finished
  cancelled
```

Isso mistura:

- lifecycle da Session;
- seleção de participantes;
- configuração;
- formação de times;
- estado live.

No target, essas dimensões serão separadas em aggregates/estados próprios.

## 1.2 `SessionType = tournament | free_play` mistura conceitos

Hoje:

```text
SessionType = tournament | free_play
SessionConfig = TournamentConfig | FreePlayConfig
```

`TournamentConfig` inclui estrutura de competição como:

- round robin / knockout / groups;
- classification points;
- standings rules;
- final / third-place;
- playoff targets.

Isso transforma Session em Competition engine.

No target:

```text
SessionContext:
QUICK | COMMUNITY

PlayMode:
FREE_PLAY | STRUCTURED_MATCHES

Competition:
separate bounded context
```

Nomes finais de enums podem mudar, mas a separação semântica não.

## 1.3 Participantes e Teams atuais são arrays dentro da Session

O type e o banco usam:

```text
selectedPlayerIds[]
teamIds[]
```

O banco também grava:

```text
selected_player_ids text[]
team_ids text[]
config jsonb
```

Isso dificulta:

- snapshots históricos;
- revisions;
- FKs reais;
- provenance;
- staleness do TeamDraw;
- Guest participants;
- Registration materialization.

No target, relações são normalizadas.

## 1.4 Infraestrutura local/cloud está embutida

`Session` atual contém:

```text
cloudId
syncStatus
lastSyncedAt
deletedAt
```

Banco possui:

```text
local_id
sync_version
deleted_at
```

Esses campos são legado da arquitetura local-first/global-sync e não pertencem ao modelo canônico de Session.

## 1.5 `owner_id` atual é creator/ownership técnico com cascade perigoso

`public.sessions.owner_id` referencia `auth.users(id) ON DELETE CASCADE`.

Isso é inadequado para história compartilhada: deletar conta não pode apagar Sessions/Matches históricas.

No target, creator/actor references usam semântica apropriada e delete behavior não destrutivo.

## 1.6 Controle live atual vive na Session

Hoje Session possui:

```text
controlled_by_user_id
control_claimed_at
control_device_id
```

E RPCs:

```text
claim_session_ownership
transfer_session_ownership
```

A intenção correta é impedir duas pessoas produzindo placares concorrentes. Porém o target separa:

```text
SessionOrganizerAssignment
= responsibility for Session

MatchControlLease
= current technical controller of one Match
```

Uma Session com múltiplas courts pode ter Matches simultâneas; portanto controle live global por Session se torna restritivo.

## 1.7 Heartbeat atual evidencia a tensão local/cloud

A migration atual reduziu expiração e passou a depender de heartbeat porque `point_events` da nuvem não acompanhavam os pontos registrados localmente durante Session.

No target, o protocolo offline/live será explícito no Match Engine em vez de inferir atividade de Session a partir de sync eventual.

# 2. N3.04.01 — Session Aggregate

## N4.04.01.01 — Definição

Session é a raiz operacional de um encontro esportivo.

Target conceitual:

```text
Session
├── id
├── context: QUICK | COMMUNITY
├── community_id?          // obrigatório em COMMUNITY
├── name/title
├── scheduled_start?
├── scheduled_end?
├── location?
├── lifecycle_status
├── publication state/reference
├── active rules snapshot
├── formation configuration
├── court rotation configuration
├── organizer assignments
├── courts
├── roster revisions
└── timestamps / revision
```

Outras entidades referenciam Session, mas não ficam serializadas dentro dela.

## N5.04.01 — Não conter como arrays autoritativos

Não usar no aggregate target:

```text
selectedPlayerIds[]
teamIds[]
pointIds[]
matchIds[] as relational authority
```

As relações vivem em tabelas/aggregates próprios.

## N5.04.01.02 — Root revision

Session pode possuir `revision` para optimistic concurrency de mudanças da própria Session.

Não reutilizar `updated_at` como concurrency token.

## N6.04.01 — Commands principais

```text
CreateSession
UpdateSessionSchedule
UpdateSessionConfiguration
PublishSession
AssignSessionOrganizer
AddSessionCourt
FinalizeSessionRoster
StartSession
FinishSession
CancelSession
```

Commands de Registration/TeamDraw/Match pertencem aos respectivos contexts.

## N8.04.01 — Authority

```text
QUICK before publish:
local/device authority

COMMUNITY:
server authority
```

## N10.04.01

- Session não precisa ter Match para existir em DRAFT.
- Session pode ter três Matches simultâneas em courts distintas sem três Sessions artificiais.
- TeamDraw removido/revisado não exige mutar `teamIds[]` dentro de Session.

# 3. N3.04.02 — Session Context: QUICK / COMMUNITY

## N4.04.02.01 — QUICK

Quick Session é criada sem Community obrigatória.

Características:

```text
community_id = null
local authority before publish
offline-capable
guests allowed
registration not required
```

## N4.04.02.02 — COMMUNITY

Community Session pertence a uma Community.

Características:

```text
community_id required
server-authoritative
organizer eligibility from Community context
may use Registration
may use Voting
shared realtime/read models
```

## N5.04.02 — Um engine, duas autoridades

Quick e Community reutilizam:

- Session rules;
- participants;
- Team Formation;
- Match preparation/execution;
- statistics concepts.

Mas não devem ser forçadas à mesma política de autoridade.

## N5.04.02.02 — Publish Quick

`PublishQuickSession` é handoff explícito:

```text
LOCAL AUTHORITY
↓ successful publish
SERVER AUTHORITY
```

Não existe merge bidirecional contínuo depois disso.

## N10.04.02

- Quick offline funciona sem Community.
- Community Session offline pode ter draft local, mas não “nascer compartilhada” sem commit.
- Publicação falha: Quick local permanece íntegra.

# 4. N3.04.03 — Session Lifecycle

## N4.04.03.01 — Lifecycle pequeno

Target inicial:

```text
DRAFT
  ↓
SCHEDULED
  ↓
IN_PROGRESS
  ↓
COMPLETED

CANCELLED
```

Quick pode seguir caminho reduzido:

```text
DRAFT → IN_PROGRESS → COMPLETED
```

## N5.04.03 — O que NÃO pertence ao lifecycle

Não usar `Session.status` para representar:

```text
players selected
registration open
voting open
teams generated
publication state
Match paused
```

Esses estados pertencem a outros contexts/state machines.

## N5.04.03.02 — PAUSED

Pausa de uma Match não precisa pausar a Session inteira.

Se no futuro existir suspensão operacional de Session inteira, deve ter semântica própria e não ser reutilização automática de Match.PAUSED.

## N6.04.03 — Transition guards

Exemplos:

```text
DRAFT → SCHEDULED
requires valid shared schedule when applicable

SCHEDULED → IN_PROGRESS
via StartSession readiness checks

IN_PROGRESS → COMPLETED
via FinishSession blockers
```

## N10.04.03

- TeamDraw gerado enquanto Session DRAFT não muda lifecycle para `teams_generated`.
- Registration aberta não muda Session para status próprio.
- Uma Match pausada não torna Session inteira PAUSED automaticamente.

# 5. N3.04.04 — Session Scheduling

## N4.04.04.01 — Scheduling data

Candidatos:

```text
scheduled_start_at
scheduled_end_at?
timezone / canonical instant strategy
location
```

Datas/horários compartilhados devem ser representados de maneira inequívoca conforme Data Architecture.

## N5.04.04 — Schedule ≠ occurrence truth

Schedule informa intenção.

Fatos reais ficam separados:

```text
started_at
completed_at
```

Não sobrescrever horário planejado com horário real.

## N5.04.04.02 — Reschedule

Reschedule de Session compartilhada:

- é command server-side;
- incrementa revision;
- pode invalidar reminders pendentes;
- não altera automaticamente Fixtures sem policy de Competition.

## N6.04.04 — Commands

```text
ScheduleSession
RescheduleSession
ChangeSessionLocation
```

podem ser unificados conforme API final, desde que sejam semanticamente claros.

## N10.04.04

- Session atrasou 30 minutos: planned e actual continuam distinguíveis.
- Reminder antigo é suprimido/recalculado após reschedule.
- Fixture ligada à Session não é silenciosamente remarcada se Competition exigir aprovação própria.

# 6. N3.04.05 — Session Publication

## N4.04.05.01 — Publication é dimensão separada

Session existir não significa estar publicada para membros.

Possível state:

```text
UNPUBLISHED
PUBLISHED
```

ou timestamps equivalentes com regras claras.

## N5.04.05 — Efeitos de publish

Publish pode:

- tornar Session visível a público elegível;
- habilitar Registration conforme configuração;
- criar notification intents;
- expor schedule em agenda.

Mas esses side effects acontecem **depois do commit** e não definem sucesso do domínio.

## N5.04.05.02 — Unpublish

Política precisa considerar se Registration já possui entries.

V1 provável:

- antes de Registration/participação relevante: permitido;
- depois: operação restrita/cancelamento explícito, não simples toggle invisível.

Detalhe final fica OPEN até fluxo de produto consolidado.

## N10.04.05

- Push falha após Publish: Session continua publicada.
- Client perde response: retry com mesmo command ID recupera publicação, não duplica notificações.

# 7. N3.04.06 — Session Organizer Assignment

## N4.04.06.01 — Conceito

Community `ORGANIZER` concede **elegibilidade operacional**.

Session pode registrar quem está efetivamente responsável:

```text
SessionOrganizerAssignment
├── session_id
├── membership_id / user_id
├── assigned_at
├── assigned_by
├── status
└── optional responsibility subtype future
```

## N5.04.06 — Por que assignment

Sem assignment, todos os Organizers da Community poderiam potencialmente editar todas as Sessions uns dos outros.

Target prefere:

```text
Community Organizer
= eligible

Session Organizer Assignment
= responsible for this Session
```

## N5.04.06.02 — Administrative override

Owner/Admin pode precisar de capability de override para recuperar uma Session abandonada, mas isso é governança de recuperação e não transforma Admin em Organizer esportivo permanente.

## N5.04.06.03 — Match control

```text
SessionOrganizerAssignment ≠ MatchController
```

Organizer pode assumir/obter Match control se elegível, mas controle corrente é `MatchControlLease`.

## N6.04.06 — Commands

```text
AssignSessionOrganizer
RemoveSessionOrganizerAssignment
TransferSessionOperationalResponsibility
AdministrativeTakeoverSessionResponsibility
```

nomes finais TBD.

## N8.04.06 — Security

Authorization deve resolver:

```text
Auth User
→ active Membership
→ ORGANIZER responsibility / admin override
→ Session community
→ SessionOrganizerAssignment
→ capability
```

Não confiar em `community_id` fornecido pelo client sem resolver a Session real.

## N10.04.06

- Organizer A cria Session; Organizer B não edita automaticamente só porque também é Organizer.
- Admin sem Organizer pode executar recovery override específico, mas não recebe avaliação esportiva automática.
- UUID de Session de outra Community não concede acesso.

```text
SessionCourt
├── id
├── session_id
├── label/name
├── order
├── status if needed
```

## N5.04.07 — Court não é Match

Court é recurso/local de execução.

```text
Court A
├── Match 1
```

## N5.04.07.02 — Concurrency

## N10.04.07

- Court 1 e Court 2 executam Matches simultâneas por controladores diferentes.
- Remover Court com Match ativa é bloqueado.


## N5.04.08.02 — Versioning

Snapshot registra:

```text

source_default_version? when useful
captured_at
```

## N10.04.08

- Community muda hard cap amanhã; Session criada ontem continua com snapshot antigo.
- Competition classification points não aparecem em SessionRulesSnapshot.

## N5.04.11.04 — Historical snapshot

## N10.04.11

- Waitlisted não aparece no solver.

- Player renomeado depois não corrompe participação histórica.

# 13. N3.04.12 — Roster Revisions

## N4.04.12.01 — Por que revisionar roster

Team Formation e Match preparation dependem de conjunto exato de participantes.

Por isso:

```text
RosterRevision R1
↓
Team CandidateSet C1
↓
Confirmed TeamDraw D1
```

Se roster muda:

```text
RosterRevision R2
```

então artefatos derivados de R1 ficam stale/incompatíveis.

## N5.04.12 — Provenance chain

Para Community Session:

```text
Registration revision
↓
Roster revision
↓
Balance input revision/snapshot
↓
CandidateSet / TeamDraw
↓
Match preparation / MatchRoster
```

Cada downstream sabe de qual upstream nasceu.

## N5.04.12.02 — Imutabilidade

RosterRevision publicada/materializada não é reescrita in-place.

Nova composição cria nova revision.

## N5.04.12.03 — Pre-start vs post-start

Antes do início, revisão pode invalidar TeamDraw e exigir regeneração.

Depois do início, mudanças devem passar por `SessionRosterAdjustment`/policy explícita e preservar história do roster usado nas Matches já iniciadas.

## N10.04.12

- Player sai depois do sorteio: D1 fica stale, não é silenciosamente reutilizado.
- Match já terminou com R1; R2 não reescreve MatchRoster histórico.
- Mesmo conjunto mas revision diferente mantém provenance auditável.

# 14. N3.04.13 — Session Readiness

## N4.04.13.01 — Readiness é derivada

```text
NO_EFFECTIVE_ROSTER

VOTING_STILL_OPEN
RULES_INVALID
COURT_CONFIGURATION_INVALID

COMPETITION_FIXTURE_NOT_READY
```

## N5.04.13 — Readiness Query

```text
GetSessionReadiness
→ ready: boolean
→ blockers[]
→ relevant revisions
```

UI usa blockers acionáveis.

## N5.04.13.02 — StartSession revalida

A query de readiness é UX; `StartSession` deve repetir as invariantes dentro da transaction/command path.

Não confiar em readiness calculada 30 segundos antes no browser.

## N10.04.13

- Tela mostra READY; roster muda em outra aba; StartSession revalida e rejeita stale draw.
- Voting fecha depois; readiness muda sem editar Session.status manualmente.

# 15. N3.04.14 — Start Session

## N4.04.14.01 — Semantic command

```text
StartSession(session_id, command_id, expected_revision?)
```

Não `PATCH status='active'`.

## N5.04.14 — Preconditions

Dependem do context, mas podem incluir:

- valid lifecycle transition;
- actor authorization;
- readiness;
- valid effective roster;
- TeamDraw resolved when required;
- configuration snapshot finalized.

## N5.04.14.02 — StartSession ≠ StartMatch

StartSession indica que o encontro operacional começou.

Cada Match:

```text
PrepareMatch
StartMatch
```

independentemente.

## N5.04.14.03 — Idempotency

Retry do mesmo command retorna estado já iniciado, sem duplicar side effects.

## N10.04.14

- Double-click Start gera um único started_at lógico.
- Match pode ser preparada após Session iniciar sem segunda transição da Session.
- Uma Session pode iniciar antes da primeira Match se readiness permitir.

# 16. N3.04.15 — Finish Session

## N4.04.15.01 — Semantic command

`FinishSession` finaliza o encontro operacional, não uma Match individual.

## N5.04.15 — Blockers

Por default, não finalizar se existem:

```text
LIVE Matches
PAUSED Matches ainda ativas no sentido operacional
pending critical Match reconciliation
```

Política para ABANDONED/CANCELLED deve ser explícita.

## N5.04.15.02 — Derived side effects

Após commit:

- stats/projections podem atualizar;
- report generation pode ocorrer;
- notifications podem ser emitidas.

Falha desses efeitos não reabre Session.

## N5.04.15.03 — Idempotency

Retry não gera múltiplos reports/notifications lógicos; downstream dedupe por source event.

## N10.04.15

- Push/report falha: Session continua COMPLETED.
- Match LIVE bloqueia finish.
- Response perdido após commit: retry retorna COMPLETED.

# 17. N3.04.16 — Session Cancellation

## N4.04.16.01 — Cancel ≠ delete

Cancellation preserva o registro e motivo/contexto necessário.

```text
Session status = CANCELLED
cancelled_at
cancelled_by
cancel_reason code/text as policy
```

## N5.04.16 — Consequências

Cancel pode:

- fechar/inutilizar Registration;
- invalidar reminders;
- impedir novas Matches;
- preservar entries/history existentes;
- notificar membros após commit.

## N5.04.16.02 — Active Session

Cancelar Session já IN_PROGRESS requer regras mais fortes:

- Matches live precisam ser canceladas/abandonadas explicitamente;
- história já capturada não é apagada.

## N5.04.16.03 — Delete

Hard-delete não é operação comum de produto para Session compartilhada com história.

## N10.04.16

- Cancelar Session publicada não apaga registrations.
- Cancelar durante Match live sem resolver Match é bloqueado ou exige workflow explícito.
- Restore de UI/cache não “des-cancela” Session.

# 18. N3.04.17 — Competition / Fixture Association

## N4.04.17.01 — Relação

Session pode hospedar Fixtures de Competition.

```text
Competition
  ↓
Fixture
  ↓ scheduled/hosted by
Session
  ↓
Prepare Match
  ↓
Match
```

## N5.04.17 — Session não é Competition round

Uma Session pode:

- hospedar várias Fixtures;
- hospedar Fixtures de rounds distintos;
- combinar atividades não competitivas, se policy permitir.

Não usar `Session.type=tournament` como substituto de Competition.

## N5.04.17.02 — Association entity

Pode existir relação explícita:

```text
SessionFixtureAssignment
```

ou FK adequada no Fixture, dependendo do desenho final de Competition.

O owner da relação semântica competitiva é Competition; Session apenas oferece contexto operacional/schedule/court.

## N5.04.17.03 — Reschedule boundary

Reschedule Session não deve alterar Fixture oficial sem passar pelas regras de Competition.

## N10.04.17

- Duas Fixtures no mesmo dia usam uma Session e courts diferentes.
- Session não competitiva não precisa criar Competition fake.
- Fixture cancelada não força hard-delete da Session.

| `selectedPlayerIds[]` | sem snapshot/FK/revision | `RosterRevision` + `SessionParticipant` |
| `teamIds[]` | resultado embutido | `CandidateSet` / `TeamDraw` |
| `TournamentConfig` dentro da Session | Competition acoplada | CompetitionRules/Stage/Fixture próprios |
| `FreePlayConfig` gigante | policy + runtime + balance | Rules + TeamFormationConfig + CourtRotationConfig |
| `cloudId/local_id` | identidade dual | UUID final |
| `syncStatus/sync_version` | sync genérico | domain revision + selective offline state |
| `owner_id auth cascade` | história ligada à conta | creator/actor refs não destrutivas |
| Session-level controller | não suporta multi-court bem | SessionOrganizerAssignment + per-Match lease |
| `deleted_at` sync tombstone | lifecycle ambíguo | CANCELLED/archival/retention semantics explícitos |

# 28. N10 — Adversarial / Acceptance Matrix

## SES-N10-001 — Quick without Community

Create and complete Quick Session with `community_id = null`.

## SES-N10-002 — Community offline creation

User offline attempts shared creation; only local draft exists, no fake committed Session.

## SES-N10-003 — Session type regression

Developer attempts `type='tournament'` to encode Competition; architecture/test review rejects target usage.

## SES-N10-004 — Status explosion

TeamDraw generation does not transition Session lifecycle to `teams_generated`.

## SES-N10-005 — Multi-court

Two Matches live in same Session on different courts with independent controllers.

## SES-N10-006 — Organizer isolation

Organizer B cannot edit Organizer A's assigned Session only because both have ORGANIZER responsibility.

## SES-N10-007 — Admin override

Admin recovery command can recover abandoned Session if authorized, without granting permanent Organizer responsibility.

## SES-N10-008 — Roster stale draw

R1 → D1; roster changes to R2; StartSession with D1 is rejected.

## SES-N10-009 — Historical Match roster

R2 after Match completion does not rewrite MatchRoster from R1.

## SES-N10-010 — Waitlist contamination

Waitlisted users never appear in SessionParticipant/solver until promoted/materialized.

## SES-N10-011 — Guest

Quick Guest is valid Participant without global Player.

## SES-N10-012 — Default mutation

Community changes default points target after Session creation; existing Session snapshot unchanged.

## SES-N10-013 — Start race

Two clients invoke StartSession concurrently; one logical transition, idempotent result.

## SES-N10-014 — Response loss

StartSession commits, response lost, retry same command ID returns IN_PROGRESS without duplicate side effects.

## SES-N10-015 — Readiness race

Client saw READY, another actor changes roster; StartSession revalidates and blocks.

## SES-N10-016 — Finish with live Match

FinishSession rejected while Match remains LIVE/PAUSED-active.

## SES-N10-017 — Provider failure

Notification provider fails after Finish; Session remains COMPLETED.

## SES-N10-018 — Cancellation

Cancel published Session preserves registration/history and suppresses future reminders.

## SES-N10-019 — Active cancellation

Cancellation cannot silently discard a live Match.

## SES-N10-020 — Competition linkage

Rescheduling host Session does not bypass Competition Fixture reschedule policy.

## SES-N10-021 — Old client

Legacy client tries PATCH `selected_player_ids` after new roster authority cutover; write rejected/routed through supported compatibility path.

## SES-N10-022 — Auth deletion

Session creator deletes account; historical Session remains.

## SES-N10-023 — Quick publish unknown outcome

## SES-N10-024 — Realtime gap

Client misses Session revision update; detects mismatch/refetches authoritative snapshot.

# 29. Decisions / Hypotheses / Open Questions

## DECIDED

- Session é distinta de Match, Competition, Fixture, RegistrationWindow e TeamDraw.
- Quick e Community usam o mesmo conceito de Session com políticas de autoridade diferentes.
- Quick pode existir sem Community.
- Community shared Session é server-authoritative.
- Lifecycle de Session será pequeno e não carregará fases de roster/teams/voting.
- `SessionType=tournament/free_play` não permanece como separação canônica.
- Competition será modelada fora de Session.
- `SessionParticipant` substitui selected Player arrays como conceito efetivo.
- Roster é revisionado e downstream registra provenance.
- Community defaults são snapshotados na Session.
- SessionOrganizerAssignment é distinto de MatchController.
- Match control será por Match no target.
- Readiness é derivada.
- `StartSession ≠ StartMatch`.
- Cancellation preserva história.

## STRONG HYPOTHESIS

- Lifecycle inicial: `DRAFT → SCHEDULED → IN_PROGRESS → COMPLETED`, com `CANCELLED` como saída alternativa.
- Play mode inicial separado em algo equivalente a `FREE_PLAY | STRUCTURED_MATCHES`.
- Uma Session terá 0..1 primary RegistrationWindow em V1, mas isso pertence N2.05.
- Administrative override para recuperação de Session será capability explícita de Owner/Admin.

## OPEN

- Nome final dos campos/enums `SessionContext` e `PlayMode`.
- Política exata de unpublish quando já existem registrations.
- Se Session possui um Organizer principal + auxiliares ou apenas assignments equivalentes em V1.
- Política detalhada de alteração de roster depois de Session IN_PROGRESS.
- Modelagem final de runtime Court Rotation para múltiplas courts.
- Se Session poderá hospedar simultaneamente Fixtures competitivas e free-play no mesmo evento.

# 31. Definition of Session Compliance

Uma implementação está alinhada a N2.04 quando:

1. Session representa evento operacional e não Match/Competition;
2. Quick e Community possuem políticas de autoridade explícitas;
3. lifecycle é pequeno e separado de publication/registration/team/voting states;
4. participants vivem em roster revisionado, não arrays autoritativos;
5. TeamDraw referencia roster exato;
6. rules/defaults são snapshots;
7. Organizer assignment é contextual;
8. multi-court não depende de controller global único;
9. readiness é calculada e revalidada no command;
10. StartSession e StartMatch são commands distintos;
11. Finish/Cancel preservam integridade de Matches/história;
12. Competition/Fixture association permanece separada;
13. shared Session usa server authority;
14. legacy cloud/local/sync fields não contaminam o target.
