## 0. Regra de leitura

Este documento define o **target canônico** de Registration.

A separação fundamental é:

```text
REGISTRATION ENTRY
= intenção/estado de inscrição

SESSION PARTICIPANT
= participação efetivamente materializada
```

Portanto:

```text
RegistrationEntry ≠ SessionParticipant
WAITLISTED ≠ PARTICIPANT
```

Registration é responsável por responder, de forma autoritativa e concorrente, perguntas como:

```text
A inscrição está aberta?
Este User/Player é elegível?
Ainda há vaga?
Quem está confirmado?
Quem está na fila?
Quem é promovido quando alguém sai?
Qual roster corresponde a qual revisão da inscrição?
```

Session consome o resultado materializado dessa capacidade; ela não deve reimplementar fila/capacidade por arrays locais.

# 1. Current State — evidência do repositório

## 1.1 Session atual usa seleção direta

O modelo atual de `Session` contém:

```text
selectedPlayerIds: string[]
```

junto de `teamIds[]`, config e lifecycle. Não há, nesse shape, distinção entre:

```text
pedido de entrada
confirmado
reserva
retirado
removido
```

O target substitui a seleção mutável direta por Registration + RosterRevision quando a Session é Community/shared.

## 1.2 Banco atual persiste `selected_player_ids[]`

A tabela `sessions` atual possui:

```text
selected_player_ids text[]
team_ids text[]
config jsonb
local_id
sync_version
```

Esse modelo não consegue representar corretamente FIFO, promoção transacional, revisão de roster ou corrida da última vaga sem lógica externa frágil.

## 1.3 `CommunityPresence` é um conceito diferente

O type atual define:

```text
CommunityPresence
├── communityId
├── date
└── items[]
    ├── playerId?
    ├── temporaryName?
    └── status:
        present | absent | maybe | unmarked | guest
```

Isso pode servir como presença/planejamento social, mas **não é RegistrationWindow autoritativa**.

`present` não deve ser reinterpretado silenciosamente como `CONFIRMED` em uma fila de capacidade limitada sem migração/policy explícita.

## 1.4 `community_presence` e WhatsApp drafts também são estruturas distintas

No banco atual existe:

```text
community_presence.items jsonb
whatsapp_list_drafts.main_slots jsonb
whatsapp_list_drafts.reserve_slots jsonb
```

Essas representações podem ajudar comunicação/planejamento, mas no target não serão fontes de verdade da fila.

## 1.5 Oportunidade de strangler

Como não existe um Registration bounded context consolidado que precise ser preservado como autoridade, o target pode nascer diretamente com:

```text
RegistrationWindow
RegistrationEntry
server-side commands
revision
FIFO sequence
```

O downstream legado pode receber `RosterRevision` materializada por adapter durante a migração.

# 2. N3.05.01 — Registration Window

## N4.05.01.01 — Definição

`RegistrationWindow` representa o período/política de inscrição de uma Session.

V1:

```text
Session 1 ── 0..1 primary RegistrationWindow
```

O modelo não deve impedir múltiplas windows futuras, mas não devemos introduzir complexidade sem requisito.

## N5.05.01 — Campos conceituais

```text
RegistrationWindow
├── id
├── session_id
├── status
├── capacity
├── opens_at?
├── closes_at?
├── revision
├── created_at
├── updated_at
└── policy snapshot / policy version as needed
```

A capacidade pertence à RegistrationWindow, não a uma lista local da UI.

## N5.05.01.02 — Session context

Quick Session normalmente não precisa de RegistrationWindow. Participantes são adicionados diretamente ao contexto local.

Community Session pode possuir RegistrationWindow compartilhada.

## N5.05.01.03 — Authority

```text
COMMUNITY REGISTRATION
= SERVER AUTHORITATIVE
```

Browser não decide sozinho quem ganhou a última vaga.

## N8.05.01 — Security

Toda operação resolve primeiro:

```text
window_id
→ session_id
→ community_id
```

E autoriza nesse contexto real. Payload não pode fornecer `community_id` alternativo para obter capability de outra Community.

## N10.05.01

- User conhece `window_id` de outra Community: não ganha leitura privada nem mutation.
- Window pertence a Session cancelada/archived context: command respeita lifecycle real.
- Dois clients com snapshots diferentes continuam convergindo pela revision autoritativa.

# 3. N3.05.02 — Registration Lifecycle

## N4.05.02.01 — Estados

Target V1:

```text
DRAFT
  ↓
OPEN
  ↓
CLOSED
  ↓
LOCKED
```

Possíveis desvios administrativos futuros devem ser explícitos, não booleans independentes.

## N5.05.02 — Semântica

### DRAFT

Configuração existe, mas membros ainda não entram.

### OPEN

Join/Leave funcionam conforme policy.

### CLOSED

Novos Joins ficam bloqueados. **Leave pode continuar permitido**, e enquanto não LOCKED a saída pode promover automaticamente waitlist.

### LOCKED

Roster de inscrição está congelado para finalização/materialização. Alterações exigem fluxo administrativo explícito.

## N5.05.02.02 — `closes_at`

Deadline não depende de cron pontual.

Command `JoinRegistration` verifica server time:

```text
now >= closes_at
→ join rejected/closed logically
```

Scheduler pode materializar status/notifications depois, mas não é autoridade temporal.

## N6.05.02 — Commands

```text
CreateRegistrationWindow
OpenRegistration
CloseRegistration
LockRegistration
```

Reopen, se permitido, será command explícito com regras próprias; não simples `status = OPEN` genérico.

## N10.05.02

- Join chega 1 ms após `closes_at`, cron ainda não rodou: server rejeita.
- CLOSED com waitlist e CONFIRMED saindo: promoção continua até LOCKED, conforme decisão V1.
- LOCKED impede saída casual que invalidaria roster sem fluxo administrativo.

# 4. N3.05.03 — Registration Entry

## N4.05.03.01 — Definição

`RegistrationEntry` representa a inscrição de um Player elegível em uma RegistrationWindow.

Campos conceituais:

```text
RegistrationEntry
├── id
├── registration_window_id
├── player_id
├── source
├── status
├── queue_sequence?
├── joined_at
├── status_changed_at
├── withdrawn_at?
├── removed_at?
├── removal_reason?
└── provenance/audit refs as needed
```

## N5.05.03 — Estados efetivos

Candidatos V1:

```text
CONFIRMED
WAITLISTED
WITHDRAWN
REMOVED
```

`PROMOTED` **não precisa ser status permanente**. Promoção é transição/fato:

```text
WAITLISTED → CONFIRMED
```

com audit/domain event apropriado.

## N5.05.03.02 — Source

Exemplos possíveis:

```text
SELF_JOIN
ORGANIZER_ADDED
MIGRATION
ADMIN_RESTORE
```

A existência de source não altera authorization automaticamente.

## N5.05.03.03 — Effective entry uniqueness

Não pode haver duas inscrições ativas efetivas para o mesmo Player na mesma Window.

Candidate DB invariant:

```text
partial unique index
(window_id, player_id)
WHERE status IN ('CONFIRMED','WAITLISTED')
```

A implementação exata será definida no schema C5.

## N5.05.03.04 — Rejoin

Se Player saiu (`WITHDRAWN`) e entra novamente enquanto OPEN:

```text
new effective join
→ goes to current end of queue / current capacity decision
```

Não recupera posição antiga automaticamente.

Para audit mais limpo, preferência inicial:

```text
new RegistrationEntry row
```

em vez de ressuscitar a entry antiga, salvo decisão posterior.

## N5.05.03.05 — Removed

`REMOVED` é diferente de `WITHDRAWN`.

- WITHDRAWN: saiu voluntariamente.
- REMOVED: ação operacional/administrativa.

Após REMOVED, reentrada automática pode ser bloqueada até Restore/explicit action.

## N10.05.03

- Double click gera command IDs diferentes: unique domain invariant impede duas active entries.
- User sai e volta: nova posição, não posição original.
- Organizer remove Player e ele tenta Join imediato: policy pode negar até restore.

# 5. N3.05.04 — Eligibility Resolution

## N4.05.04.01 — Self-join seguro

O client **não deve enviar um `player_id` arbitrário** para `JoinRegistration` e pedir que o server confie.

Fluxo de self-join:

```text
Auth User
↓
active CommunityMembership
↓
ACTIVE PlayerAccountLink
↓
CommunityPlayer / sports eligibility
↓
resolved Player
↓
Registration operation
```

## N5.05.04 — Eligibility factors

V1 pode exigir:

- User autenticado;
- Membership ativa na Community;
- User vinculado a Player;
- Player ativo no sports roster da Community;
- Session/Window disponível;
- Player não bloqueado/removido da Window;
- nenhuma active entry duplicada.

Futuras regras devem entrar em policy versionada, não `if` espalhado.

## N5.05.04.02 — Organizer-add

Organizer autorizado pode ter command distinto:

```text
AddPlayerToRegistration
```

Nesse caso target `player_id` é explícito, mas server verifica:

- Organizer assignment/capability;
- same Community;
- Player válido/eligible;
- window lifecycle.

## N5.05.04.03 — Guest

Community Registration digital V1 não precisa aceitar Guest sem Player persistente, a menos que requirement específico seja aprovado.

Quick Session continua aceitando Guest diretamente fora deste bounded context.

## N8.05.04 — Anti-BOLA

Conhecer Player UUID de outra Community não permite adicioná-lo a Window sem sports/context eligibility.

## N10.05.04

- User A manda `player_id` de B no self-join payload: server ignora/rejeita e resolve A.
- Admin sem Organizer capability não adiciona Player operacionalmente apenas por governance.
- Player global pertence a Community B, mas User está em A: não entra em A sem CommunityPlayer eligibility.

# 6. N3.05.05 — Capacity

## N4.05.05.01 — Definição

Capacity define o máximo de entries `CONFIRMED` simultâneas na Window.

```text
confirmed_count <= capacity
```

é invariante transacional.

## N5.05.05 — Não confiar em count client-side

UI pode exibir:

```text
11 / 12 vagas
```

mas isso é snapshot. Ao Join, server recalcula/serializa decisão.

## N5.05.05.02 — Capacity nullable/unlimited?

Decisão V1 preferida:

- capacity obrigatória para RegistrationWindow criada para lista limitada;
- se produto exigir “sem limite”, representar policy explícita em vez de número gigante mágico.

Essa parte fica como detalhe de schema em aberto.

## N5.05.05.03 — Capacity and roster

Capacity controla inscrições confirmadas. Roster final pode possuir ajustes administrativos posteriores, mas isso não deve reescrever a história da queue.

## N10.05.05

- Client vê 11/12 e 20 pessoas clicam Join: server mantém <=12 confirmed.
- Capacity inválida negativa/zero conforme policy é rejeitada por validation/constraint.

# 7. N3.05.06 — FIFO Queue

## N4.05.06.01 — Regra

Quando capacity está cheia:

```text
eligible Join
→ WAITLISTED
```

Fila é FIFO segundo **sequência monotônica autoritativa**, não timestamp de client.

## N5.05.06 — Queue sequence

Candidate:

```text
queue_sequence bigint
```

alocado server-side por Window.

A implementação pode usar counter na root Window ou mecanismo transacional equivalente.

## N5.05.06.02 — Por que não `created_at`

Dois requests podem ter timestamps próximos/iguais e client clocks não são confiáveis.

`updated_at` é ainda pior: edições não podem mover usuário na fila.

## N5.05.06.03 — Queue order after rejoin

Rejoin após withdrawal recebe nova sequence.

## N5.05.06.04 — Eligibility at promotion time

FIFO seleciona o primeiro **ainda elegível** no momento da promoção.

Se head da fila deixou Community/foi suspenso/ficou inelegível:

```text
skip according to explicit transition policy
```

sem bloquear todos atrás indefinidamente.

A entry inelegível deve receber estado/audit apropriado; não desaparecer.

## N10.05.06

- Timestamps idênticos: queue sequence ainda totaliza a ordem.
- User atualiza profile: não muda posição.
- Primeiro waitlisted perde Membership antes da promoção: próximo elegível é promovido, com reason preservado para o anterior.

# 8. N3.05.07 — Join Registration

## N4.05.07.01 — Command

```text
JoinRegistration
```

Entrada mínima conceitual:

```text
command_id
window_id
```

Self-join não precisa receber actor/player/community como autoridade.

## N5.05.07 — Transaction

Conceitualmente:

```text
BEGIN

authenticate
resolve window + Session + Community
lock RegistrationWindow
validate lifecycle/time
resolve eligibility
check active entry
count confirmed under lock / use authoritative counter

if space:
  create CONFIRMED
else:
  allocate queue_sequence
  create WAITLISTED

increment revision
write command receipt
write domain outbox if needed

COMMIT
```

## N5.05.07.02 — Result

Waitlist é **sucesso de command**, não technical/domain failure.

Resposta:

```text
CONFIRMED
or
WAITLISTED + authoritative position/data needed
```

## N5.05.07.03 — Idempotency

Mesmo `command_id` repetido deve devolver mesmo resultado lógico.

Distinct command IDs ainda são protegidos por active-entry uniqueness.

## N5.05.07.04 — Unknown outcome

Timeout depois do commit:

```text
client does NOT create second intention
retry same command_id
```

## N8.05.07 — Rate limiting

Join pode ter rate limit por User/IP/window sem comprometer fila legítima.

## N10.05.07

- Request commitou e resposta morreu: retry retorna a mesma entry/status.
- Mesmo command enviado simultaneamente duas vezes: uma execução lógica.
- Dois command IDs por double click: unique invariant evita duas vagas/positions.

# 9. N3.05.08 — Leave Registration

## N4.05.08.01 — Command

```text
LeaveRegistration
```

Self-leave resolve a própria active entry.

## N5.05.08 — Semântica

### WAITLISTED leaves

```text
WAITLISTED → WITHDRAWN
```

Não promove ninguém, pois nenhuma vaga confirmada surgiu.

### CONFIRMED leaves before LOCKED

```text
CONFIRMED → WITHDRAWN
↓
promote first eligible WAITLISTED
```

na **mesma transação**.

## N5.05.08.02 — Atomicity

Não pode existir intervalo permanente onde:

```text
capacity has free slot
+ eligible waitlist exists
```

por falha entre leave e promote.

## N5.05.08.03 — Result

Response pode incluir:

- entry final state;
- new window revision;
- promoção ocorrida (para UI relevante), sem vazar dados além do necessário.

## N10.05.08

- Exception artificial após WITHDRAWN antes de promoção: transaction rollback deixa ambos estados anteriores intactos.
- Leave e Join simultâneos respeitam FIFO; novo Join não fura waitlist existente.
- Same Leave command retried não promove duas pessoas.

# 10. N3.05.09 — Waitlist Promotion

## N4.05.09.01 — Trigger

Promoção pode ocorrer por:

```text
confirmed leave
confirmed removal
capacity increase
eligibility repair/restore where policy says
```

## N5.05.09 — `promote_next_eligible`

Conceitualmente é operação interna do Registration context, não endpoint de client que escolhe qualquer pessoa.

Algoritmo:

```text
ordered WAITLISTED by queue_sequence
↓
for each:
  revalidate eligibility
  first valid → CONFIRMED
```

## N5.05.09.02 — Event

Após commit pode emitir:

```text
RegistrationPromoted
```

para Notification/Realtime.

Notification failure não desfaz promoção.

## N5.05.09.03 — Privacy

Push/inbox para promovido deve conter mínimo necessário. Não é necessário notificar toda Community com dados privados da fila.

## N10.05.09

- First waitlisted suspended: second eligible promoted deterministically.
- Notification provider down: promotion continua committed.
- Worker processa Promotion event duas vezes: NotificationIntent deduplica.

# 11. N3.05.10 — Capacity Increase / Reduction

## N4.05.10.01 — Increase

Exemplo:

```text
capacity 12 → 15
waitlist 8
```

Na mesma operação ou processo transacional definido:

```text
promote first 3 eligible
```

preservando FIFO.

## N5.05.10 — Atomicity de increase

Preferência V1:

```text
capacity change + required promotions + revision
= one transaction
```

para capacities normais de Session.

## N4.05.10.02 — Reduction

Caso:

```text
capacity 12
confirmed 12
Organizer asks 10
```

Policy V1 preferida:

```text
BLOCK reduction below current confirmed count
```

Não rebaixar pessoas automaticamente.

Para reduzir, Organizer primeiro remove/ajusta explicitamente entries ou usa futuro command administrativo com política clara.

## N5.05.10.02 — Reason/audit

Capacity changes relevantes devem ser auditáveis como operação operacional de Session.

## N10.05.10

- Increase 12→15 com joins concorrentes não permite furar os três primeiros waitlisted.
- Reduction para 10 com 12 confirmed retorna conflict, sem escolher vítimas.
- Retry capacity increase não promove pessoas extras.

# 12. N3.05.11 — Close / Reopen / Lock

## N4.05.11.01 — Close

`CloseRegistration` impede novos joins.

V1:

```text
CLOSED still allows leave
and auto-promotion
until LOCKED
```

Isso evita prender confirmado que desistiu antes da materialização final.

## N4.05.11.02 — Lock

`LockRegistration` congela o estado de inscrição usado para `FinalizeSessionRoster`.

Lock deve validar preconditions apropriadas.

## N4.05.11.03 — Reopen

Reopen é **explicitly controlled**.

Possíveis regras:

- apenas antes de Session start;
- Organizer assigned/capability;
- roster downstream pode ficar stale;
- increment revision.

Se implementado, deve ser semantic command, não generic status patch.

## N5.05.11 — Downstream impact

Se roster já foi finalizado e Registration reabre/altera:

```text
new Registration revision
→ previous RosterRevision becomes source-stale
→ Team Candidate/Draw downstream may become stale
```

Nada é silenciosamente mutado.

## N10.05.11

- Reopen após TeamDraw confirmado exige invalidation/stale workflow, não mantém draw como se nada mudasse.
- Join concorre com Close: serialização decide antes/depois claramente; não estado ambíguo.

# 13. N3.05.12 — Registration Revision

## N4.05.12.01 — Objetivo

`revision` identifica a versão autoritativa do aggregate/window state relevante.

Incrementa em mutations que alteram visão relevante de Registration, por exemplo:

```text
join
leave
promotion
capacity
close/open/lock
remove/restore
```

## N5.05.12 — Não é timestamp

```text
revision != updated_at
```

Client usa revision para detectar gap/staleness.

## N5.05.12.02 — Downstream provenance

`RosterRevision` captura:

```text
source_registration_revision
```

Assim sabemos exatamente de qual estado de Registration aquele roster nasceu.

## N5.05.12.03 — Realtime

Eventos/deltas incluem revision final relevante.

Client que tem:

```text
revision 40
```

e recebe:

```text
revision 42
```

detecta gap e refetch.

## N10.05.12

- Realtime message #41 perdido: #42 causa resync.
- Duas writes serializadas produzem revisions distintas e monotônicas.
- `updated_at` igual não quebra detecção de mudança.

# 14. N3.05.13 — Finalize Session Roster

## N4.05.13.01 — Boundary

`FinalizeSessionRoster` é a ponte explícita:

```text
Registration
↓
Session roster
```

Ele materializa participação efetiva.

## N5.05.13 — Inputs

Conceitualmente:

```text
session_id
expected_registration_revision
command_id
```

## N5.05.13.02 — Preconditions

Candidatos:

- Window CLOSED ou LOCKED conforme policy final;
- Session ainda não iniciou;
- expected revision atual;
- confirmed entries elegíveis;
- actor com capability/SessionOrganizerAssignment apropriado.

## N5.05.13.03 — Output

Cria:

```text
RosterRevision
├── id
├── session_id
├── revision_number
├── source_registration_revision
├── created_at
└── entries
```

E as entries alimentam `SessionParticipant`/roster representation definida em N2.04.

## N5.05.13.04 — Snapshot

Roster é snapshot. Posterior mudança em:

```text
Player name
CommunityPlayer status
Membership
```

não reescreve aquela revisão.

## N5.05.13.05 — Idempotency

Retry do mesmo finalization command retorna mesma materialização lógica.

## N8.05.13 — Stale

Se expected registration revision não é atual:

```text
STALE_REGISTRATION
```

Não finaliza roster de snapshot velho silenciosamente.

## N10.05.13

- Organizer abre tela na revision 10; alguém sai e revision vira 11; finalize expected=10 é rejeitado.
- Retry after commit não cria RosterRevision duplicada.
- Waitlisted nunca aparece no roster final por acidente.

# 15. N3.05.14 — Post-start Roster Adjustments

## N4.05.14.01 — Regra

Depois que Session/Match iniciou, não reabrimos Registration como se o evento ainda estivesse na fase de inscrição.

Mudanças operacionais passam por entidade/command próprio:

```text
SessionRosterAdjustment
```

## N5.05.14 — Exemplos

```text
late arrival allowed by policy
confirmed player leaves due emergency
replacement
administrative correction
```

## N5.05.14.02 — Preserve history

Adjustment registra:

- actor;
- reason;
- before/after roster relation;
- timestamp;
- impact em Matches ainda não preparadas;
- non-impact em MatchRoster já frozen, salvo workflow próprio.

## N5.05.14.03 — TeamDraw impact

Roster adjustment depois de TeamDraw pode exigir:

```text
new TeamDraw revision
```

ou manual correction, conforme estágio.

Não mutar draw histórico in-place.

## N10.05.14

- Player substituído após Match 1: Match 1 history intacta; future Match preparation usa roster ajustado conforme policy.
- Late arrival não recebe queue_sequence fictícia retroativa.

# 16. N3.05.15 — Registration Realtime

## N4.05.15.01 — Objetivo

Realtime reduz latência de percepção, mas não decide fila.

Fluxo:

```text
Command
↓
DB transaction COMMIT
↓
Authoritative response
↓
Realtime event/invalidation
```

## N5.05.15 — Channel

Preferência:

```text
private Session/Registration channel
```

com authorization contextual.

## N5.05.15.02 — Payload

Transmitir mínimo:

```text
window_id
revision
change type
public/safe aggregate counters
self-relevant data when channel/query model allows
```

Não broadcast da fila inteira com dados pessoais sem necessidade.

## N5.05.15.03 — Snapshot protocol

```text
subscribe/buffer
↓
fetch authoritative snapshot
↓
discard <= snapshot revision
↓
apply contiguous
↓
gap → refetch
```

Reconnect sempre tolera perda de messages.

## N5.05.15.04 — Presence

Supabase Realtime Presence, se usado, não é CommunityPresence nem RegistrationEntry.

Viewer online ≠ registered.

## N10.05.15

- Broadcast perdido: snapshot/refetch converge.
- Fake client publica `REGISTRATION_PROMOTED`: DB não muda e client authoritative state não confia nisso.
- User de Community A não assina private registration B.

# 17. N3.05.16 — Registration Concurrency

## N4.05.16.01 — Hot aggregate

RegistrationWindow é um dos aggregates com maior risco de race.

Operações mutantes relevantes devem ser serializadas por Window.

Preferência Postgres:

```text
SELECT RegistrationWindow
FOR UPDATE
```

ou mecanismo equivalente que prove a mesma linearização.

## N5.05.16 — Races obrigatórias

### Last slot

```text
capacity = 12
confirmed = 11

A Join ─┐
        ├ simultaneously
B Join ─┘
```

Final:

```text
exactly one CONFIRMED
exactly one WAITLISTED
```

### Join vs Leave

Waitlist existente tem prioridade conforme FIFO; novo Join não aproveita gap transacional para furar fila.

### Join vs Close

Uma ordem linear é estabelecida pelo server.

### Vote/Team downstream

Registration revision protects later finalization from using stale state.

## N5.05.16.02 — No application mutex

Não confiar em mutex apenas dentro de uma Edge Function/process instance. Concorrência pode vir de múltiplas instances.

A garantia deve chegar ao banco/authoritative transactional layer.

## N5.05.16.03 — Deadlocks

Lock ordering deve ser documentado. Registration operations começam pela root Window antes de manipular entries relacionadas, reduzindo ciclos.

Deadlock/transient errors podem ser retried somente com command idempotency.

## N10.05.16

- 100 concurrent joins, capacity 12 → 12 CONFIRMED + 88 WAITLISTED.
- 50 concurrent leaves/promotions não produzem duplicate confirmed positions.
- Same command concurrent duas vezes → one logical result.
- Process crashes after acquiring lock before commit → transaction rollback/release, no partial queue state.

# 36. N10 — Adversarial / Acceptance Matrix

## REG-N10-001 — Last slot

Capacity 12, confirmed 11, A/B Join simultaneously → exactly one CONFIRMED, one WAITLISTED.

## REG-N10-002 — Mass join

100 simultaneous eligible Joins, capacity 12 → exactly 12 CONFIRMED and 88 WAITLISTED, all with deterministic unique queue order.

## REG-N10-003 — Same command concurrent

Same `command_id` received by two server instances → one logical Join result.

## REG-N10-004 — Double click different IDs

Two distinct command IDs from same User → at most one active entry; no double slot/queue position.

## REG-N10-005 — Response lost

Join commits but response is lost; retry same ID returns original CONFIRMED/WAITLISTED result.

## REG-N10-006 — Leave atomicity

Failure injected between withdrawing confirmed and promotion → rollback leaves original confirmed + waitlisted state intact.

## REG-N10-007 — Join versus Leave

Existing waitlist + confirmed leaves while new User joins → existing first eligible waitlisted gets vacancy before new Join.

## REG-N10-008 — Join versus Close

Concurrent Join and Close linearize cleanly; Join is either valid before Close or rejected after, never ambiguous partial.

## REG-N10-009 — Deadline

`closes_at` passed but scheduler delayed → Join rejected by server time.

## REG-N10-010 — Client clock manipulation

Client clock changed by hours → no effect on queue ordering/deadline authority.

## REG-N10-011 — FIFO timestamp collision

100 Joins share same millisecond timestamp → queue order remains unique via sequence.

## REG-N10-012 — Rejoin

Waitlisted User #2 withdraws and rejoins → receives new sequence at current tail, does not reclaim #2.

## REG-N10-013 — Removed rejoin

Organizer removes entry; self-join retry cannot bypass removal policy.

## REG-N10-014 — Ineligible queue head

First waitlisted loses active Membership before vacancy → promotion skips/handles it per explicit state and promotes next eligible without silent deletion.

## REG-N10-015 — Capacity increase

Capacity 12→15 with 10 waitlisted → first 3 eligible promoted, not arbitrary users.

## REG-N10-016 — Capacity race

Capacity increase runs while new Joins arrive → existing ordered waitlist maintains priority.

## REG-N10-017 — Capacity reduction

12 confirmed; Organizer requests capacity 10 → command rejected/conflict; no automatic demotion.

## REG-N10-018 — Stale finalize

Organizer fetched revision 40; Join/Leave produces 41; Finalize expected 40 → rejected.

## REG-N10-019 — Finalize retry

Roster finalization commits, response lost → same command returns same RosterRevision, not a second one.

## REG-N10-020 — Waitlist exclusion

Finalized roster contains only qualifying confirmed entries from source revision.

## REG-N10-021 — Cross-community BOLA

Organizer A sends Window B UUID → denied even if payload says `community_id=A`.

## REG-N10-022 — Arbitrary Player self-join

Member sends another Player UUID in request → server resolves own linked Player or rejects, never registers target arbitrarily.

## REG-N10-023 — Admin ≠ Organizer

Community Admin without Organizer responsibility/assignment cannot change capacity or remove entries merely due governance role.

## REG-N10-024 — Realtime gap

Client has revision 51, loses 52, receives 53 → detects gap and refetches; no permanent wrong queue.

## REG-N10-025 — Fake Realtime publish

Malicious client broadcasts “PROMOTED” → DB unchanged; authoritative read corrects UI.

## REG-N10-026 — Offline Join

User clicks Join while offline → UI does not create local CONFIRMED/WAITLISTED fact to replay automatically.

## REG-N10-027 — Cached stale capacity

Client cached `11/12`; real server is `12/12` → Join returns WAITLISTED, and UI accepts server result.

## REG-N10-028 — Notification outage

Promotion commits while push provider down → queue correct; notification retries independently.

## REG-N10-029 — Duplicate notification

Outbox worker retries Promotion → one effective NotificationIntent/delivery policy outcome per dedupe key.

## REG-N10-030 — Process crash under lock

Server process dies mid-transaction → Postgres rollback/releases lock; no half-promotion.

## REG-N10-031 — Deadlock retry

Transient DB deadlock occurs → idempotent command may retry with same ID; result remains one logical mutation.

## REG-N10-032 — CommunityPresence mismatch

Legacy `present` record exists but no RegistrationEntry → migration does not silently create historical confirmed slot without defined evidence/policy.

## REG-N10-033 — WhatsApp reserve order

Legacy reserve draft order differs from authoritative queue → communication draft does not override Registration sequence.

## REG-N10-034 — Post-start replacement

Session already started; Player replacement occurs → `SessionRosterAdjustment`, not mutation of old Registration queue/history.

## REG-N10-035 — Player deletion/link change

User loses PlayerAccountLink while waitlisted → promotion revalidates eligibility before confirmation.

# 37. Decisions / Hypotheses / Open Questions

## DECIDED

- Registration is a bounded context separate from Session.
- `RegistrationEntry ≠ SessionParticipant`.
- V1 uses at most one primary RegistrationWindow per Session.
- Shared Registration writes are online-only/server-authoritative.
- Self-join resolves User→Player server-side.
- Capacity and FIFO are authoritative DB concerns.
- FIFO uses monotonic sequence, not timestamps.
- Join serializes per RegistrationWindow.
- Leave of confirmed and promotion occur atomically before LOCKED.
- CLOSED blocks new Joins but permits Leave/auto-promotion until LOCKED in V1.
- Capacity increase auto-promotes according to FIFO.
- Capacity reduction below current confirmed count is blocked by default.
- Registration has domain revision.
- Roster finalization records source Registration revision.
- Waitlist does not create SessionParticipant.
- Post-start changes use SessionRosterAdjustment.
- Realtime uses snapshot+revision reconciliation.
- Communication drafts/CommunityPresence are not Registration authority.

## STRONG HYPOTHESIS

- Rejoin creates a new RegistrationEntry row instead of reviving the withdrawn row, improving audit/queue semantics.
- WAITLISTED requires `queue_sequence`; confirmed may or may not retain an original join sequence separately for analytics/audit.
- Reopen will exist only before Session start and will stale downstream roster/TeamDraw explicitly.
- Organizer-added players will use a separate semantic command rather than overloading self-join.

## OPEN

- Whether V1 needs an unlimited-capacity RegistrationWindow mode or simply omits Registration when capacity is irrelevant.
- Exact policy for a waitlisted entry that becomes temporarily ineligible: `REMOVED`, dedicated `INELIGIBLE`, or preserved WAITLISTED but skipped with reason/event.
- Whether Member sees exact numeric waitlist position or a coarser status in privacy-sensitive Communities.
- Whether Organizer can reserve protected slots/categories in future; **not V1**, because it complicates strict FIFO.
- Whether cancellation/refund/payment concepts will eventually attach to Registration; payment is out of current scope.
- Exact Reopen semantics after a roster revision exists.
