## 0. Regra de leitura

Este documento define o **target canônico** de Team Formation.

A regra esportiva mais importante deste contexto é não negociável:

```text
BALANCER INPUT
=
ATTRIBUTE VECTOR + EXPLICIT CONSTRAINTS

BALANCER NEVER USES
=
PLAYER OVERALL
```

`Overall` pode existir como valor derivado para display, ranking ou explicação em outras superfícies. Ele não pode participar de:

- ordenação inicial do solver;
- objective function;
- greedy initialization;
- simulated annealing acceptance;
- candidate ranking;
- tie-break entre candidates;
- hard-constraint validation;
- fallback de missing attributes;
- diagnostics usados para escolher solução.

A separação deve ser protegida por **tipo, código e testes**, não apenas por convenção.

Também são separações fundamentais:

```text
SkillProfile ≠ PlayerBalanceSnapshot
Hard Constraint ≠ Soft Objective
CandidateSolution ≠ TeamCandidate
TeamCandidateSet ≠ TeamDraw
TeamDraw ≠ MatchRoster
Solver search ≠ authoritative confirmation
```

# 1. Current State — evidência do repositório

## 1.1 O solver atual já é mais sofisticado que um sorteio aleatório

O código atual de balanceamento possui uma base que deve ser reaproveitada conceitualmente:

- cálculo multidimensional;
- pesos/configuração de balanceamento;
- distribuição por posições/composição;
- constraints de alocação;
- histórico/repetição;
- geração de múltiplas soluções;
- busca heurística;
- métricas de qualidade;
- testes que verificam cobertura de Players e distribuição.

Portanto a migração **não parte da premissa de que o algoritmo atual é descartável**.

## 1.2 O principal desvio atual é o uso de `overall`

A implementação atual ainda inclui `overall` em structures de peso/scoring/diagnóstico e em caminhos usados para avaliar ou ordenar soluções.

Isso conflita diretamente com a decisão de produto:

```text
O sorteio considera os atributos.
Não considera overall.
```

A correção target não é apenas colocar `overallWeight = 0`.

O campo deve sair do contrato de input do solver sempre que possível, porque um peso zero ainda permite regressão futura acidental.

## 1.3 O `Player` atual não é um BalanceInput adequado

O Player legado mistura:

- identity;
- attributes;
- overall;
- Community relations;
- physical/current state;
- sync/cloud metadata;
- evaluations.

Passar `Player[]` diretamente ao solver torna o algoritmo dependente de campos mutáveis e de conceitos que não pertencem a Team Formation.

O target usa um snapshot específico e imutável.

## 1.4 Os testes atuais são uma base importante

A suíte existente já cobre propriedades valiosas, entre elas:

- cada Player exatamente uma vez;
- tamanhos de Team equilibrados;
- assignments travados;
- perfis de composição como 5x1/6x0;
- diversidade entre soluções;
- diferenciação por fundamentos mesmo quando overall é igual.

Esses testes devem ser preservados e reforçados com uma propriedade mais forte:

```text
same attributes + different overall
→ identical solver behavior
```

## 1.5 Inputs legados de saúde/físico não permanecem automaticamente

O solver atual considera dimensões/penalidades como altura, gênero, lesão/limitação e repetição em algumas configurações.

No target:

- posição/composição pode continuar como policy explícita;
- altura pode ser utilizada se o produto decidir que é dimensão esportiva apropriada para aquela policy;
- gênero só entra com requisito e policy explícitos;
- saúde/lesão/limitação física **não** entra automaticamente, pois exige modelagem e revisão de privacidade próprias;
- repetição/histórico é policy versionada, não um comportamento oculto.

# 2. N3.06.01 — Balance Input Snapshot

## N4.06.01.01 — Objetivo

O solver nunca lê diretamente o estado mutável atual do Player durante a busca.

Antes da geração materializamos:

```text
RosterRevision
      ↓
ResolveBalanceInputs
      ↓
PlayerBalanceSnapshot[]
```

Cada snapshot representa exatamente o que o algoritmo podia conhecer e usar naquele sorteio.

## N5.06.01 — Modelo conceitual

```text
PlayerBalanceSnapshot
├── participant_id
├── player_id?                 # referência auxiliar quando existir
├── roster_revision_id
├── attribute_vector
├── positions / role profile
├── resolved constraints
├── confidence / maturity metadata
├── source_profile_version
├── rubric_version
├── resolver_version
├── captured_at
└── provenance metadata
```

`participant_id` é a identidade primária do solver porque o sorteio trabalha sobre o roster daquela Session, não sobre o catálogo global de Players.

## N5.06.01.02 — Imutabilidade

Depois de materializado, o snapshot não muda.

Se uma avaliação muda depois:

```text
old PlayerBalanceSnapshot
remains unchanged
```

Um novo sorteio precisa materializar novos inputs/revision.

## N5.06.01.03 — Fonte compartilhada confiável

Para Community/shared Session, o servidor deve resolver/materializar o snapshot a partir das fontes autoritativas, como:

```text
GlobalPlayerSkillProfile / contextual policy
RosterRevision
Session TeamFormationConfig snapshot
```

O browser não envia um vetor arbitrário e afirma que é o rating oficial do Player.

## N5.06.01.04 — Quick Session

Em Quick Session local-authoritative, o snapshot pode ser resolvido localmente a partir dos dados locais explicitamente disponíveis.

A provenance deve identificar que a origem é local/Quick.

## N10.06.01

- Evaluation muda após o sorteio: snapshot antigo permanece reproduzível.
- Browser modifica DevTools para aumentar ataque de um Player antes de publicar CandidateSet compartilhado: o servidor não aceita esse vetor como fonte autoritativa.
- RosterRevision muda: snapshots da revisão anterior não podem ser usados para confirmar novo draw.

# 3. N3.06.02 — Attribute Vector

## N4.06.02.01 — Definição

O vetor representa as dimensões esportivas usadas para comparar equilíbrio entre Teams.

Exemplo conceitual — nomes finais dependem do rubric canônico:

```text
attack
serve
reception
setting
block
defense
```

Outras dimensões podem existir se o Rating model as definir.

## N5.06.02 — Sem overall

Não existe dimensão:

```text
overall
```

no vetor canônico de otimização.

Um scalar `overall` derivado dos mesmos atributos pode existir em DTO de apresentação fora do solver, mas não é lido pelo engine.

## N5.06.02.02 — Normalização

Se dimensões usam escalas diferentes, o resolver/objective precisa normalizá-las de modo versionado antes de comparar spreads.

Não assumir que:

```text
attack 7
```

e:

```text
height 7
```

teriam significado comparável apenas por serem números.

## N5.06.02.03 — Missing

```text
missing ≠ 0
```

Resolver missing/cold-start acontece **antes** do solver.

Possíveis políticas pertencem ao Rating/Input Resolver:

- provisional estimate;
- neutral prior;
- Community baseline;
- explicit UNRATED handling;
- refusal to produce canonical shared draw quando insuficiente, se policy exigir.

O solver não inventa zero.

## N5.06.02.04 — Confidence

Confidence/maturity pode acompanhar o snapshot para diagnóstico e futura policy.

Na baseline target, confidence não altera silenciosamente o valor esportivo sem uma policy/version explícita.

## N10.06.02

- Mesmos atributos e overall diferente: resultado do solver é idêntico.
- Overall igual e atributos diferentes: solver pode produzir soluções diferentes.
- Um atributo ausente não vira zero e não cria falsa penalização extrema.

# 4. N3.06.03 — Hard Constraints

## N4.06.03.01 — Definição

Hard Constraint é uma condição que torna uma solução **inválida**, independentemente de quão bom seja seu score.

```text
if hard constraint violated
→ candidate invalid
```

Nunca:

```text
violate hard constraint
because objective improved
```

## N5.06.03 — Constraints estruturais obrigatórias

Sempre:

```text
Every roster participant appears exactly once.
No participant outside the roster appears.
No duplicate participant appears.
Team size follows formation policy.
```

## N5.06.03.02 — Constraints configuráveis

Exemplos possíveis:

```text
locked participant → Team X
must-play-together
must-not-play-together
specific position requirement
captain/role assignment
```

Uma regra só é hard se a policy disser explicitamente.

## N5.06.03.03 — Composition

5x1/6x0 e outras composições podem gerar constraints/requirements de roles.

Precisamos distinguir:

```text
required role coverage
```

de:

```text
preferred role balance
```

A primeira invalida; a segunda pontua.

## N10.06.03

- Solver encontra solução com score excelente, mas duplica Participant: rejeitada.
- Locked Player não pode ser movido por annealing.
- Role marcada apenas como preference não é tratada como impossibilidade.

# 5. N3.06.04 — Soft Objectives

## N4.06.04.01 — Definição

Soft Objective mede quão desejável é uma solução **entre soluções válidas**.

```text
valid candidates
      ↓
objective comparison
      ↓
better / worse
```

## N5.06.04 — Dimensões candidatas

### Skill balance

Principal objetivo:

```text
minimize imbalance
per attribute dimension
across Teams
```

### Position / composition quality

Quando policy trata como soft.

### Physical distribution

Somente dimensões explicitamente permitidas pelo produto/privacy model.

### Gender distribution

Somente se existir requisito legítimo e policy explícita.

### Repetition/history

Pode reduzir repetição excessiva de companheiros/adversários conforme policy versionada.

## N5.06.04.02 — Scalar objective ≠ Player Overall

É permitido que a **solução inteira** possua um scalar objective score:

```text
candidate.objective_score
```

Esse valor resume a qualidade da distribuição entre Teams.

Isso é conceitualmente diferente de:

```text
Player.overall
```

O primeiro avalia **uma assignment multidimensional**; o segundo seria um resumo individual e não pode ser input do solver.

## N5.06.04.03 — Objective policy

A fórmula exata precisa ser versionada.

Alternativas a avaliar:

- weighted normalized sum;
- minimax da pior dimensão;
- lexicographic priorities;
- combinação híbrida;
- portfolio/Pareto diagnostics.

A baseline final ainda é uma decisão a fechar com benchmarks e análise esportiva.

## N10.06.04

- Melhorar attack balance não pode compensar quebra de hard constraint.
- Alterar fórmula de overall não muda objective se attribute vectors não mudam.
- Mudar objective version pode gerar outro candidate, mas metadata deixa isso explícito.

# 6. N3.06.05 — Feasibility Precheck

## N4.06.05.01 — Objetivo

Antes de executar busca cara, validar se as hard constraints permitem alguma solução.

## N5.06.05 — Exemplos

```text
12 participants
2 teams of 6
→ structurally feasible
```

```text
3 locked setters
but policy requires exactly 1 setter per Team in 2 Teams
→ potentially infeasible
```

```text
Participant A must be with B
and A must not be with B
→ infeasible
```

## N5.06.05.02 — Output

```text
FeasibilityResult
├── feasible
├── blockers[]
├── warnings[]
└── checked_policy_version
```

Warnings representam baixa qualidade provável; blockers representam impossibilidade.

## N5.06.05.03 — UX

Não mostrar apenas:

```text
"Não foi possível sortear."
```

Mostrar blockers concretos quando puderem ser explicados com segurança.

## N10.06.05

- Constraint contraditória é detectada sem milhares de iterações inúteis.
- Insuficiência de uma posição hard retorna blocker específico.
- Preferência soft impossível não marca formação como infeasible.

# 7. N3.06.06 — Initial Solution

## N4.06.06.01 — Objetivo

Construir uma solução inicial válida e razoável antes da busca heurística.

## N5.06.06 — Multidimensional

A estratégia inicial não pode ser:

```text
sort by Player.overall
snake draft
```

como atalho principal.

Ela deve considerar:

- hard constraints;
- team capacity;
- role/composition requirements;
- multidimensional attribute deltas;
- deterministic seeded tie handling.

## N5.06.06.02 — Baseline comparison

Manter um baseline simples é útil para benchmark:

```text
Solver improvement
vs
multidimensional greedy baseline
```

Isso permite provar que a etapa heurística realmente melhora a solução.

## N10.06.06

- Trocar somente overall não altera ordem/alocação inicial.
- Initial solution sempre respeita locks/hard constraints antes do annealing.

## N4.06.07.01 — Boundary

O Application layer depende de uma porta conceitual:

```text
TeamFormationSolver
```

```text
solve(request, snapshots)
```

## N5.06.07 — Benefícios

- testar reference solver;
- trocar/experimentar algoritmos;

- manter DTO canônico independente da implementação.

## N5.06.07.02 — Não transformar em abstraction excessiva

Uma interface pequena basta.

Não criar uma plataforma genérica de optimization engines antes de necessidade real.

# 9. N3.06.08 — Simulated Annealing

## N4.06.08.01 — Estado

Simulated Annealing permanece uma **forte candidata/default inicial** porque já existe maturidade no código e se adapta bem a uma função de custo multidimensional com constraints.

Isso não significa torná-lo requisito eterno do domínio.

## N5.06.08 — Regras

- só opera sobre soluções hard-valid;
- mutation mantém/revalida invariantes;
- acceptance usa objective da assignment, nunca Player overall;
- random source é seeded/injetável;
- canonical generation usa iteration budget fixado/versionado;
- diagnostics registram iterações e outcome.

## N5.06.08.02 — Wall clock

Wall-clock pode ser usado para UX/timeout de segurança, mas não deve ser a única condição canônica de parada se queremos reproduzibilidade.

## N5.06.08.03 — Future replacement

Alternativas futuras podem incluir:

- local search;
- genetic search;
- integer programming para constraints específicas;
- exhaustive/branch-and-bound em rosters pequenos;
- hybrid solver.

Só entram com benchmark/correctness evidence.

# 10. N3.06.09 — Determinism / Seed

## N4.06.09.01 — Regra

```text
same canonical input
+ same algorithm version
+ same objective/policy versions
+ same seed
+ same iteration budget
=
same canonical result
```

## N5.06.09 — Randomness

Não usar `Math.random()` como dependência invisível do resultado canônico.

Usar PRNG seeded/versioned.

## N5.06.09.02 — Floating point

Se comparações numéricas puderem variar entre runtimes, definir:

- precision/rounding;
- stable ordering;
- deterministic tie-break.

## N5.06.09.03 — Input hash

TeamFormationRequest pode registrar um `input_hash` canônico derivado de:

```text
roster revision
snapshots
config
versions
seed
```

para diagnóstico/dedup/reproducibility.

## N10.06.09

- Repetir geração 100 vezes com mesmo input/seed produz mesmo portfolio.
- Alterar ordem acidental das rows retornadas pelo DB não muda resultado depois de canonical sorting.

# 11. N3.06.10 — Candidate Portfolio

## N4.06.10.01 — Objetivo

O produto pode oferecer múltiplas soluções de alta qualidade em vez de fingir que existe um único sorteio matematicamente perfeito.

Exemplo inicial:

```text
Candidate A
Candidate B
Candidate C
```

## N5.06.10 — Diversidade

Portfolio não deve ser:

```text
A = solução X
B = solução X com duas labels trocadas
C = solução X praticamente idêntica
```

Precisamos medir diversidade de assignments.

Candidate approach:

```text
participant assignment distance
/Hamming-like distance
```

com normalização para equivalência de Team labels.

A métrica/threshold final permanece aberta.

## N5.06.10.02 — Quality floor

Diversidade não pode justificar candidate obviamente ruim.

Portfolio selection equilibra:

```text
quality
+
diversity
```

sob policy versionada.

## N5.06.10.03 — Default count

Três opções é uma forte hipótese de UX inicial, não limite de domínio eterno.

# 12. N3.06.11 — Candidate Set

## N4.06.11.01 — Definição

`TeamCandidateSet` é o conjunto persistido/publicado de opções válidas para uma determinada revisão de roster/config.

```text
TeamCandidateSet
├── id
├── session_id
├── roster_revision_id
├── balance_input_snapshot_set_id / hash
├── formation_config_version
├── algorithm_version
├── objective_version
├── policy_version
├── status
├── generated_at
└── candidates[] / normalized relation
```

## N5.06.11 — Candidate

Cada candidate preserva:

```text
candidate_id
seed
team assignments
diagnostics
trusted objective score
assignment hash
rank/portfolio metadata
```

## N5.06.11.02 — Imutabilidade

Depois de publicado:

```text
CandidateSet immutable
```

Nova geração cria novo set/revision.

## N5.06.11.03 — Status

Candidatos:

```text
DRAFT
PUBLISHED
STALE
SELECTED
INVALIDATED / SUPERSEDED as needed
```

Não usar status para representar Voting lifecycle; VotingRound é separado.

## N5.06.11.04 — Browser trust

Em Community/shared flow, o browser pode executar a busca, mas ao publicar:

1. servidor identifica o authoritative BalanceInputSnapshot;
2. valida que todos os assignments usam exatamente o roster;
3. revalida hard constraints;
4. recomputa objective/diagnostics confiáveis com scorer canônico;
5. não confia em `score` enviado pelo browser;
6. persiste o CandidateSet autoritativo.

O servidor **não precisa necessariamente rerodar toda a busca heurística**.

Isso preserva performance local sem transformar o navegador em árbitro da verdade.

## N10.06.11

- Browser envia candidate com Player extra: rejeitado.
- Browser altera objective score para tornar C “melhor”: servidor recomputa.
- Browser envia assignment válida mas diferente da que o Worker teria encontrado: pode ser aceita como candidate/manual path se policy permitir, desde que provenance e constraints sejam verdadeiras; “optimality” não é security invariant.

# 15. N3.06.14 — Vote Eligibility

## N4.06.14.01 — Regra

Voter elegível deriva da revisão de roster congelada para o round.

Baseline:

```text
confirmed/effective roster participant
+
linked authenticated User
+
active eligible Community Membership
```

## N5.06.14 — Não elegíveis

```text
WAITLISTED
Participant removed before frozen eligibility
accountless Guest/Participant for digital vote
unrelated Community member
spectator
```

## N5.06.14.02 — Organizer proxy

Organizer não vota “em nome” de Participant que não possui conta.

Se o produto futuramente permitir votação presencial mediada, isso exige policy e audit próprios — não reutilizar `CastTeamVote` fingindo actor diferente.

## N5.06.14.03 — Frozen eligibility

Ao abrir VotingRound, eligibility snapshot precisa ser definida/versionada.

Roster mutation relevante pode invalidar o round em vez de recalcular silently quem tinha direito.

# 16. N3.06.15 — Voting State Machine

## N4.06.15.01 — Lifecycle

Candidate:

```text
DRAFT
  ↓
OPEN
  ↓
CLOSED
  ↓
TALLIED
  ↓
FINALIZED
```

Deviations:

```text
INVALIDATED
CANCELLED
```

## N5.06.15 — Effective vote

Uma baseline simples:

```text
unique effective vote
per (voting_round_id, user_id)
```

Durante `OPEN`, User pode alterar escolha conforme policy.

Isso atualiza/supersede o effective vote de maneira auditável, não cria peso adicional.

## N5.06.15.02 — Close race

`CastVote` × `CloseVoting` precisa ser serializado/linearizável no servidor.

Resultado precisa refletir uma ordem autoritativa clara.

## N5.06.15.03 — Roster invalidation

Roster relevante mudou:

```text
CandidateSet → STALE
VotingRound → INVALIDATED
```

Votes antigos podem ser preservados para audit/retention, mas nunca migrados para novo CandidateSet.

# 17. N3.06.16 — Tally / Tie-break

## N4.06.16.01 — Baseline

Primeira política candidata:

```text
plurality
```

Winner = Candidate com maior número de effective votes válidos.

## N5.06.16 — Tie

Forte hipótese inicial:

```text
tie
→ candidate with best trusted multidimensional objective score
```

Nunca:

```text
sum Player overall
```

## N5.06.16.02 — No votes

Forte hipótese inicial semelhante:

```text
0 valid votes
→ best trusted candidate objective
```

Alternativas futuras:

- Organizer decision;
- new round;
- deterministic random among tied candidates;
- configured policy.

Precisa ADR/policy antes de mudar.

## N5.06.16.03 — Quorum

Quorum é OPEN/optional.

Não assumir na V1 até requisito concreto.

## N5.06.16.04 — Results visibility

Baseline:

```text
AFTER_CLOSE
```

Enquanto OPEN:

- UI não mostra tally;
- read model não entrega tally;
- Realtime não transmite tally;
- telemetry não registra escolha individual.

## N10.06.16

- Tie entre A/B não consulta Player overall.
- Candidate objective enviado pelo client é adulterado: tally usa score recomputado/trusted.
- Results visibility AFTER_CLOSE não vaza pela API ou channel.

# 18. N3.06.17 — Team Draw

## N4.06.17.01 — Definição

`TeamDraw` é a **formação selecionada/materializada** para uma determinada Session/RosterRevision.

```text
TeamDraw
├── id
├── session_id
├── roster_revision_id
├── revision
├── source
│   ├── ORGANIZER_CANDIDATE
│   ├── VOTE_WINNER
│   └── MANUAL_EDIT
├── source_candidate_id?
├── source_voting_round_id?
├── assignments
├── validation metadata
├── confirmed_at?
└── confirmed_by?
```

## N5.06.17 — Não é MatchRoster

TeamDraw pode ainda ser alterado/revisionado antes da preparação da Match.

`MatchRoster` é snapshot específico da execução e não deve apontar para Team mutável.

## N5.06.17.02 — Provenance

Sempre preservar:

```text
which roster
which candidate/manual edit
which algorithm/config/version
which confirmation
```

# 19. N3.06.18 — Manual Editing

## N4.06.18.01 — Necessidade

O Organizer pode conhecer restrições da quadra que o solver não modela ou precisar ajustar uma solução.

Manual edit é legítimo.

## N5.06.18 — Regra de imutabilidade

Não modificar Candidate ou TeamDraw confirmado anterior in-place.

```text
existing draw
```

# 21. N3.06.20 — Hard-Constraint Revalidation

# 37. N10 — Adversarial / Acceptance Matrix

## BAL-N10-001 — Overall mutation

Given identical snapshots except a display overall field changed from 2 to 10, same seed/config produces identical candidates, objective and diagnostics.

## BAL-N10-002 — Same overall, different fundamentals

Two participants have equal overall but complementary attribute vectors; solver remains capable of distinguishing them.

## BAL-N10-003 — Tampered input vector

Browser alters attack=10 before publishing shared candidates. Server resolves authoritative snapshot and rejects/mismatches the tampered source.

## BAL-N10-004 — Tampered candidate score

Browser sends `objective_score = 0`. Server recomputes trusted objective.

## BAL-N10-005 — Duplicate participant

Candidate repeats Participant A twice. Validation rejects.

## BAL-N10-006 — Missing participant

Candidate omits one roster participant. Validation rejects.

## BAL-N10-007 — Extra participant

Candidate adds a Player not in RosterRevision. Validation rejects.

## BAL-N10-008 — Locked constraint

Participant locked to Team A cannot be moved by greedy, annealing or manual confirmation.

## BAL-N10-009 — Contradictory constraints

Precheck reports infeasible before long search.

## BAL-N10-010 — Soft conflict

Position preference impossible to satisfy does not reject all solutions when it is configured as soft.

## BAL-N10-011 — Deterministic replay

Same request run 100 times returns same canonical portfolio.

## BAL-N10-012 — DB row-order variation

Input rows arrive in different ordering; canonical sort/hash keeps result deterministic.

## BAL-N10-013 — Algorithm upgrade

v2 may produce different candidates from v1, but both remain historically reproducible from metadata.

## BAL-N10-014 — Roster changed after generation

Participant leaves after CandidateSet publication. Existing set becomes STALE and cannot be confirmed.

## BAL-N10-015 — Roster changed during voting

VotingRound is invalidated; votes are not silently applied to regenerated options.

## BAL-N10-016 — Waitlisted voter

Waitlisted User knows VotingRound ID and calls CastVote. Denied.

## BAL-N10-017 — Guest voter

Accountless Participant cannot impersonate another User to obtain a digital vote.

## BAL-N10-018 — Organizer proxy

Organizer cannot submit ballot with another participant as actor.

## BAL-N10-019 — Repeat vote

User changes A→B while OPEN. Tally counts one effective vote.

## BAL-N10-020 — Close/vote race

CastVote and CloseVoting race; transaction ordering yields a single deterministic outcome.

## BAL-N10-021 — Tie

A and B tie. Fallback uses trusted multidimensional candidate objective, never Player overall.

## BAL-N10-022 — Zero votes

No ballots are cast. Configured deterministic fallback runs without overall.

## BAL-N10-023 — Ballot privacy

Member queries round while OPEN. No individual choice/tally leak beyond policy.

## BAL-N10-024 — Manual invalid edit

Organizer moves Players into an assignment violating hard Team size/lock policy. Confirmation rejects.

## BAL-N10-025 — Manual valid lower-score edit

Organizer intentionally chooses a hard-valid solution with worse objective. It can be confirmed with diagnostics/provenance if policy permits; optimizer score is not absolute authority.

## BAL-N10-026 — Concurrent confirmation

Two different TeamDraw revisions are confirmed concurrently with same expected revision. At most one succeeds as current.

## BAL-N10-027 — Same-command retry

ConfirmTeamDraw response is lost. Retry with same command_id returns same logical confirmation.

## BAL-N10-028 — Candidate publish response loss

Publish committed but browser timed out. Retry does not create duplicate CandidateSet for same command.

## BAL-N10-029 — Stale SkillProfile

Balance input resolution detects profile source revision behind evaluations and recomputes/blocks per policy instead of silently snapshotting stale data.

## BAL-N10-030 — Missing attribute

Participant has no serve evaluation. Solver does not receive `serve=0` unless a specifically versioned resolver legitimately produces that value as an estimate with provenance.

## BAL-N10-031 — Overall formula changed

Product changes display overall formula. Existing attributes unchanged. Team candidates do not change because of the formula alone.

## BAL-N10-032 — Worker crash

Worker crashes mid-search. No partial solution becomes persisted authority; generation can restart from same snapshot/seed.

## BAL-N10-033 — Low-end device

Heavy generation takes seconds, but UI thread remains responsive and progress/cancel works.

## BAL-N10-034 — Incremental scorer regression

Optimized scorer differs from reference scorer on a generated mutation. Test fails; optimization cannot ship.

## BAL-N10-035 — Portfolio duplicates

Multiple seeds produce equivalent assignments under swapped Team labels. Portfolio canonicalization removes duplicates.

## BAL-N10-036 — History policy version

Repetition penalty policy changes. New candidates may differ only under explicit policy version; old draws remain explainable.

## BAL-N10-037 — Health data

Legacy `lesionado` flag exists on Player. New solver does not consume it automatically.

## BAL-N10-038 — Quick offline

Quick Session generates/edits/confirms teams fully offline using local frozen inputs.

## BAL-N10-039 — Community offline computation

Organizer loses network after obtaining trusted snapshot. Search may continue locally, but CandidateSet publish/TeamDraw confirmation waits for server revalidation.

## BAL-N10-040 — Client invents diagnostic

Browser claims “all hard constraints satisfied” while assignment violates one. Server validator rejects independent of diagnostic text.

# 38. Decisions / Strong Hypotheses / Open Questions

## DECIDED

- Solver uses individual attribute vector, never Player overall.
- Overall should be absent from canonical solver input.
- BalanceInput is an immutable participant-centric snapshot.
- Shared BalanceInput is resolved from authoritative server data.
- Hard constraints and soft objectives are distinct.
- Feasibility precheck precedes expensive search.
- Initial solution is multidimensional.
- Solver is behind an application/domain port.
- Canonical randomness is seeded/deterministic.
- CandidateSet is immutable after publication.
- Team selection supports `ORGANIZER_CHOICE | PARTICIPANT_VOTE`.
- Voting is online-authoritative and ballots are private.
- Roster change invalidates dependent candidate/voting artifacts.
- TeamDraw is revisioned and preserves provenance.
- Manual edit creates new revision.
- Shared publish/confirm revalidates roster and hard constraints server-side.
- Client score/diagnostics are not authoritative.
- MatchRoster freezes from confirmed TeamDraw.
- Algorithm/objective/policy versions are preserved.
- Reference scorer remains correctness baseline.
- Worker is execution infrastructure, not authority.

## STRONG HYPOTHESIS

- Simulated Annealing remains the initial default search algorithm.
- Default Candidate portfolio contains three options.
- Plurality is the first voting method.
- Tie/no-vote fallback initially selects the best candidate by trusted multidimensional objective.
- Weighted normalized objective is a plausible first baseline, but must be compared with minimax/lexicographic alternatives.
- Confidence begins primarily as diagnostic rather than hidden objective weight.

## OPEN

- Final canonical skill dimensions/rubric used by Team Formation.
- Exact objective aggregation formula and per-dimension weights.
- Whether the primary fairness objective should be weighted-sum, minimax, lexicographic or hybrid.
- Exact portfolio diversity metric and threshold.
- Voting quorum policy.
- Whether voters can change vote until close in every Community or if configurable.
- Exact tie/no-vote policy after product validation.
- Which position/composition rules are hard vs soft defaults.
- Whether gender/physical dimensions should participate and under which explicit policy.
- Final cold-start/missing attribute resolver.
- Future use of confidence in optimization.
- Conditions that would justify server-side full search instead of client Worker.

# 40. Definition of Team Formation Compliance

Uma implementação está alinhada a N2.06 quando:

1. `overall` não faz parte do optimization input nem da decisão do solver;
2. Team Formation recebe `PlayerBalanceSnapshot[]` imutável ligado a RosterRevision;
3. missing/cold-start é resolvido explicitamente antes do solver;
4. hard constraints nunca são trocadas por objective score;
5. same input/version/seed é determinístico;
6. CandidateSet persistido é immutable e versionado;
7. shared CandidateSet usa authoritative snapshots e server-side revalidation;
8. client-supplied objective/diagnostics não são authority;
9. Organizer Choice e Participant Voting usam o mesmo CandidateSet model;
10. Voting tem frozen eligibility, privacy e online authority;
11. roster changes invalidam downstream deterministicamente;
12. manual edits criam revisions e passam pelo mesmo hard validator;
13. ConfirmTeamDraw é idempotente, revision-checked e server-authoritative;
14. MatchRoster deriva de Confirmed TeamDraw;
15. algorithm/objective/policy metadata torna history explicável;
16. Worker melhora responsividade sem mudar a fonte de verdade;
17. property tests tornam regressões de overall, duplicates, constraints e determinismo bloqueantes.
