## 0. Regra de leitura

Este documento define o **target canônico** do motor de partida do Volley.

As regras centrais são:

```text
Fixture ≠ Match
Session ≠ Match
Organizer ≠ MatchController
MatchEvent ≠ MatchProjection
MatchResult ≠ OfficialCompetitionResult
Realtime ≠ source of truth
```

E, para qualquer Match compartilhado:

```text
CLIENT SENDS INTENT
        ↓
SERVER VALIDATES AUTH + LEASE + EPOCH + SEQUENCE + RULES
        ↓
SERVER APPENDS MATCH EVENT(S)
        ↓
SERVER UPDATES AUTHORITATIVE PROJECTION
        ↓
COMMIT
        ↓
ACK + REALTIME
```

Nunca:

```text
client computes official score
→ uploads final Game row
```

Nunca:

```text
last write wins
```

para placar, sets, winner, Match lifecycle, controller ou MatchResult.

# 1. Current State — evidência do repositório

## 1.1 O modelo atual mistura execução e projeção

O `Game` atual contém diretamente:

- `scoreA` / `scoreB`;
- `winnerTeamId` / `loserTeamId`;
- `status`;
- `startedAt` / `finishedAt`;
- `pointIds[]`;
- `sets` e `setTargets` em metadata;
- dados de torneio/round/stage.

`PointEvent`, por sua vez, carrega:

- `sequenceNumber`;
- `scoringTeamId` / `concedingTeamId`;
- attribution esportiva;
- `scoreBefore`;
- `scoreAfter`;
- timestamp;
- metadata de sync/conflict.

Isso cria múltiplas representações do mesmo estado esportivo sem uma regra estrutural forte dizendo qual é a fonte canônica.

## 1.2 O sync operacional atual trata Match como estado sincronizável genérico

`operationalCloudService.ts` faz mapping/upsert de `games` e `point_events` junto com várias outras entidades operacionais.

O target abandona a ideia de que um Match compartilhado pode ser corretamente reconciliado por generic CRUD/upsert/LWW.

## 1.3 Há uma boa separação entre criador e controlador

O repositório já possui `sessionOwnershipCloudService` e RPCs de claim/transfer.

A migration correspondente explicita que:

- quem controla não precisa ser quem criou a Session;
- `control_device_id` não é identidade de autorização;
- existe tomada explícita de controle.

Essas ideias são preservadas conceitualmente.

## 1.4 O lock atual está no nível errado para o target

Hoje:

```text
Session
└── controlled_by_user_id
```

Isso impede uma evolução natural para:

```text
Session
├── Court A → Match 1 → Controller A
└── Court B → Match 2 → Controller B
```

O target move exclusividade operacional para **MatchControlLease por Match**.

## 1.5 O próprio histórico do código demonstra o problema de dupla autoridade

A migration de heartbeat registra que os pontos durante a Session eram locais e não eram necessariamente sincronizados durante o jogo. Assim, a nuvem podia considerar a posse inativa mesmo enquanto o dispositivo continuava marcando placar.

Isso é evidência concreta de um problema arquitetural maior:

```text
local score authority
+
cloud control authority
+
generic later sync
=
ambiguous authority during failure
```

A solução target não é aumentar indefinidamente o heartbeat. É definir autoridade, epoch e protocolo de reconciliação.

# 3. N3.07.01 — Match Aggregate

## N4.07.01.01 — Responsabilidade

`Match` representa **uma execução esportiva concreta** entre lados definidos, sob regras congeladas, com lifecycle próprio.

Não representa:

- calendário;
- rodada competitiva;
- Session inteira;
- TeamDraw;
- ranking;
- resultado oficial de Competition.

## N5.07.01 — Identidade

```text
Match
├── id
├── session_id
├── fixture_id?              # opcional
├── court_assignment_id?
├── status
├── rules_snapshot_id
├── roster_id
├── current_projection_version
├── current_control_epoch
├── started_at?
├── finished_at?
├── finish_reason?
└── timestamps
```

UUID é final desde criação.

## N5.07.01.02 — Aggregate boundary

Operações live que alteram score/lifecycle serializam no Match, não na Session inteira.

Consequência:

```text
Match A point
```

não precisa bloquear:

```text
Match B point
```

em outra quadra.

## N10.07.01

- Dois Matches na mesma Session aceitam pontos simultaneamente sem lock global da Session.
- Um Match não pode referenciar MatchRoster de outra Session.
- Match finalizado não aceita AwardPoint normal.

# 4. N3.07.02 — Fixture vs Match

## N4.07.02.01 — Separação

```text
Fixture = intenção / pairing planejado
Match   = execução concreta
```

Quick/Free Play pode criar Match sem Fixture.

Competition normalmente cria Match a partir de Fixture.

## N5.07.02 — Cardinalidade

```text
Fixture 0..N Match executions
```

Motivos:

- replay;
- Match abandonado;
- execução invalidada;
- remarcação operacional;
- erro técnico que exige nova execução.

A Competition decide qual resultado é oficial; Match não faz essa escolha sozinho.

## N10.07.02

- Fixture cancelado antes de jogar tem zero Match.
- Replay cria novo Match, não apaga execução anterior.
- Match invalidado continua auditável.

# 5. N3.07.03 — Match Preparation

## N4.07.03.01 — Pipeline

```text
PrepareMatch
├── resolve Session / Fixture context
├── resolve confirmed teams
├── freeze MatchRoster
├── freeze MatchRulesSnapshot
├── assign court
├── initialize lineup if required
└── Match.status = PREPARING / READY
```

## N5.07.03 — Readiness

`READY` é permitido somente se blockers obrigatórios estiverem resolvidos.

Exemplos:

- dois lados válidos;
- roster válido;
- rules snapshot válido;
- nenhum TeamDraw stale quando origem é Team Formation;
- Fixture ainda executável quando existir;
- court requirement satisfeito quando policy exigir.

## N10.07.03

- Roster stale bloqueia Prepare/Ready.
- CandidateSet votado mas TeamDraw não confirmado não prepara Match.
- Regras mutáveis da Community não alteram Match já preparado.

# 7. N3.07.05 — Match Roster

## N4.07.05.01 — Snapshot histórico

`MatchRoster` congela quem pertence a cada lado naquela execução.

```text
MatchRoster
├── match_id
├── revision
├── source_type
├── source_id / revision
└── MatchRosterMember[]
```

`MatchRosterMember` deve preferir `participant_id` como referência histórica operacional e guardar snapshot mínimo necessário de exibição.

## N5.07.05 — Fonte

Possíveis fontes:

- confirmed TeamDraw;
- CompetitionTeam roster revision;
- Quick Session teams;
- explicit administrative preparation autorizada.

## N5.07.05.02 — Mutação

Antes de `READY`, alteração significativa pode gerar nova roster revision/preparation.

Depois de `LIVE`, não reescrever roster histórico.

A participação efetiva é modelada separadamente.

## N10.07.05

- Player muda nome após jogo: histórico continua inteligível.
- Team atual muda composição: Match antigo não muda.
- Participant não pertencente ao roster não pode receber attribution esportiva sem workflow explícito de ajuste.

# 10. N3.07.08 — Match Lifecycle

## N4.07.08.01 — Estados

Baseline:

```text
PREPARING
   ↓
READY
   ↓
LIVE ↔ PAUSED
   ↓
FINISHED
```

Terminais/desvios:

```text
CANCELLED
ABANDONED
INVALIDATED
```

## N5.07.08 — Semântica

- `CANCELLED`: não executado/encerrado administrativamente sem resultado técnico normal.
- `ABANDONED`: execução iniciou, mas não terminou segundo fluxo esportivo normal.
- `INVALIDATED`: execução preservada, porém declarada tecnicamente inválida para usos downstream.

## N5.07.08.02 — Session lifecycle

```text
StartSession ≠ StartMatch
FinishMatch ≠ FinishSession
```

Uma Session pode possuir vários Matches em diferentes estados.

## N10.07.08

- Pausar Session inteira não é atalho implícito para pausar todos os Matches.
- FinishSession deve detectar Match LIVE/PAUSED como blocker conforme policy.

## N4.07.09.01 — Responsabilidade

`MatchController` é o ator atualmente autorizado a emitir comandos live para um Match específico.

```text
Organizer eligibility
      ↓
Session/Match assignment + capability
      ↓
Acquire control
      ↓
MatchController for this Match
```

## N5.07.09 — Não é governance

- Community ADMIN não recebe controle esportivo automaticamente.
- Community ORGANIZER não significa controlador simultâneo de todos os Matches.
- CompetitionAdministrator não implica MatchController.

Override administrativo precisa ser explícito e auditado.

## N10.07.09

- Admin sem responsabilidade ORGANIZER não marca ponto.
- Organizer A pode controlar Court A enquanto Organizer B controla Court B.

# 12. N3.07.10 — Match Control Lease

## N4.07.10.01 — Modelo

```text
MatchControlLease
├── match_id
├── lease_id
├── controller_user_id
├── controller_device_id
├── control_epoch
├── acquired_at
├── heartbeat_at
├── expires_at
└── status
```

## N5.07.10 — Autoridade

`device_id` não autentica ninguém.

A autorização continua sendo:

```text
authenticated actor
+
capability/assignment
+
current lease
+
current epoch
```

Porém, a lease é vinculada a uma instância de dispositivo para impedir dois dispositivos do mesmo usuário emitindo comandos concorrentes sem coordenação.

Trocar de aparelho é suportado por takeover/transfer explícito que gera novo epoch.

## N5.07.10.02 — TTL

TTL e heartbeat são parâmetros operacionais medidos, não invariantes de domínio com um número mágico permanente.

O target exige apenas:

- lease expira sem heartbeat;
- heartbeat não altera score;
- takeover é explícito;
- expiry/takeover incrementa epoch ao conceder nova autoridade.

## N10.07.10

- Fechar navegador eventualmente libera lease.
- Mesmo usuário abre segundo aparelho: não existe escrita concorrente silenciosa.
- Outro usuário sem capability não consegue takeover apenas conhecendo Match ID.

# 13. N3.07.11 — Control Epoch

## N4.07.11.01 — Objetivo

Resolver o cenário mais perigoso:

```text
Controller A fica offline
Controller B assume
Controller A continua marcando localmente
Controller A reconecta
```

Sem epoch, os comandos antigos podem parecer válidos.

## N5.07.11 — Regra

Toda concessão/tomada de controle possui um `control_epoch` monotônico do Match.

Todo comando mutável live carrega:

```text
control_epoch
```

O servidor aceita somente o epoch atual.

## N5.07.11.02 — Takeover

```text
old epoch = 7
TakeoverMatchControl
new epoch = 8
```

Qualquer comando posterior com epoch 7 é rejeitado mesmo se for do antigo controlador legítimo.

## N10.07.11

- Pacote atrasado do controller antigo chega depois do takeover: rejeitado.
- Retry do controller atual com mesmo command_id/epoch: idempotente.

# 16. N3.07.14 — Award Point

## N4.07.14.01 — Command semântico

Baseline:

```text
AwardPoint
├── match_id
├── scoring_side_id
├── attribution?             # conforme CaptureMode
├── command_id
├── expected_last_sequence
└── control_epoch
```

O cliente não envia score oficial.

## N5.07.14 — Transaction

Em uma única transação:

```text
1. authenticate
2. resolve Match context
3. authorize controller
4. lock Match/critical projection
5. validate lease + epoch
6. validate expected sequence
7. validate status LIVE
8. validate scoring side
9. apply RulesSnapshot
10. append POINT_AWARDED
11. append SET_COMPLETED if triggered
12. append MATCH_FINISHED if triggered
13. update MatchProjection
14. create/update MatchResult if finished
15. save command receipt
16. commit
```

Só depois do commit realtime é emitido.

## N5.07.14.02 — Score snapshots

O servidor pode guardar valores calculados antes/depois dentro do payload do evento para auditoria/diagnóstico, mas eles são **outputs calculados**, não inputs confiados do browser.

## N10.07.14

- Dois AwardPoint concorrentes com mesmo expected sequence: apenas um ocupa aquela próxima sequência; o outro recebe stale conflict.
- Timeout depois do commit: retry do mesmo command_id não soma outro ponto.

# 18. N3.07.16 — Match Sequence

## N4.07.16.01 — Sequência autoritativa

Cada Match possui sequência estritamente crescente:

```text
1, 2, 3, ... N
```

Constraint:

```text
UNIQUE(match_id, sequence_no)
```

## N5.07.16 — Server assigned

O cliente pode informar `expected_last_sequence`, mas não escolhe a sequence oficial.

## N5.07.16.02 — Gap semantics

Para leitura/realtime:

```text
current snapshot last_seq = 81
received event seq = 83
→ gap detected
→ refetch/reconcile
```

Não aplicar 83 fingindo que 82 não importa.

## N10.07.16

- Nunca há duas seq 42 no mesmo Match.
- Matches diferentes podem ter seq 42 independentemente.

# 19. N3.07.17 — Match Projection

## N4.07.17.01 — Critical synchronous projection

`MatchProjection` representa estado atual necessário para processar o próximo comando rapidamente.

```text
MatchProjection
├── match_id
├── status
├── current_set
├── side_scores
├── completed_sets
├── winner_side_id?
├── last_sequence
├── projection_version
└── rules_interpreter_version
```

## N5.07.17 — Fonte

```text
MatchEvent[] = source facts
MatchProjection = rebuildable current state
```

## N5.07.17.02 — Synchronous

Diferentemente de career/statistics, esta projection é crítica para o próximo command e deve ser atualizada na mesma transação do evento live.

## N5.07.17.03 — Invariant

```text
replay(effective MatchEvents, MatchRulesSnapshot)
==
MatchProjection
```

## N10.07.17

- Corromper projection artificialmente é detectável por integrity check/replay.
- Rebuild em banco isolado chega ao mesmo last_sequence e score.

# 20. N3.07.18 — Set Resolution

## N4.07.18.01 — Rules-driven

Set não termina porque o cliente decidiu que `score == target`.

O Rules Engine determina:

- target;
- margin;
- hard cap;
- deciding set;
- quantos sets vencem Match.

## N5.07.18 — Atomic transition

Um `AwardPoint` pode causar, na mesma transação:

```text
POINT_AWARDED
SET_COMPLETED
MATCH_FINISHED
```

se as regras determinarem isso.

## N10.07.18

- 24x24 em win-by-2 não termina set de 25.
- Hard cap, quando configurado, encerra conforme snapshot.
- Deciding set usa target correto da versão congelada.

# 21. N3.07.19 — Match Finish

## N4.07.19.01 — Finish normal vs manual

Normalmente o Rules Engine pode finalizar automaticamente quando condição esportiva é atingida.

`FinishMatch` manual existe apenas para cenários/policies explícitos e registra motivo.

## N5.07.19 — Finish reason

Não limitar a string histórica a `auto|manual|walkover`.

Modelar enum versionável com semântica suficiente, por exemplo:

- `RULES_COMPLETED`;
- `MANUAL_CONFIRMED`;
- `ABANDONED`;
- `ADMINISTRATIVE` quando cabível no contexto técnico.

Walkover competitivo pertence primariamente à Competition/OfficialResult e não deve gerar pontos fictícios.

## N10.07.19

- Finish não pode existir com rules projection contraditória sem workflow manual explícito.
- AwardPoint depois de FINISHED é rejeitado.

# 22. N3.07.20 — Match Result

## N4.07.20.01 — Resultado técnico

`MatchResult` congela o resultado técnico derivado daquela execução.

```text
MatchResult
├── match_id
├── revision
├── source_last_sequence
├── winner_side_id?
├── loser_side_id?
├── set_score
├── point summaries
├── finish_reason
├── status CURRENT | SUPERSEDED
└── generated_at
```

## N5.07.20 — Competition boundary

```text
MatchResult
≠
OfficialCompetitionResult
```

A Competition pode:

- oficializar;
- rejeitar/invalidate;
- aplicar WO/penalty;
- exigir replay;
- corrigir resultado oficial via workflow próprio.

## N5.07.20.02 — Correção pós-finish

Se correção técnica válida alterar resultado, preservar revisão anterior e gerar nova MatchResult revision.

Não overwrite destrutivo.

## N10.07.20

- Official result continua referenciando a revisão oficialmente aceita até workflow de Competition tratar impacto.
- Rebuild técnico consegue explicar de qual `source_last_sequence` saiu o resultado.

# 23. N3.07.21 — Event Corrections / Reverts

## N4.07.21.01 — Append-oriented

Erro de marcação é inevitável. O sistema precisa corrigir sem apagar evidência.

Exemplo:

```text
seq 31 POINT_AWARDED side A
seq 32 POINT_REVERSED target_event_id=31
seq 33 POINT_AWARDED side B   # quando correção completa exige novo fato
```

Pode ocorrer dentro de um único command `CorrectPoint` que produz múltiplos events atomicamente.

## N5.07.21 — Attribution-only correction

Corrigir player/skill/fault sem alterar score pode usar evento específico de annotation correction ou revisão de metadata, mantendo audit trail.

## N5.07.21.02 — Pós-finish

Correção depois de `FINISHED` requer capability/policy mais forte e pode:

- criar nova projection/result revision;
- emitir impact event downstream;
- nunca alterar silenciosamente OfficialCompetitionResult já publicado.

## N10.07.21

- Undo não é `DELETE point_event`.
- Corrigir attribution não soma/subtrai ponto.
- Corrigir winner pós-oficialização gera conflito/impact workflow em Competition.

# 24. N3.07.22 — Capture Modes

## N4.07.22.01 — Modos

Baseline:

```text
SCORE_ONLY
BASIC_STATS
DETAILED
```

## N5.07.22 — Semântica

### SCORE_ONLY

Obrigatório apenas o lado que pontuou.

### BASIC_STATS

Pode exigir/permitir reason/player conforme policy.

### DETAILED

Pode registrar skill, fault, assist, lineup context e outras dimensões esportivas suportadas.

## N5.07.22.02 — Invariant

Capture mode altera **riqueza de dados**, não regra de placar.

```text
same scoring-side sequence
+ same rules
→ same score/result
```

independentemente do capture mode.

## N5.07.22.03 — Missing

Ausência de dado em SCORE_ONLY é `unknown/not captured`, nunca estatística zero falsa.

## N10.07.22

- Match SCORE_ONLY produz placar correto sem player attribution.
- Relatório não interpreta ausência de ace registrado como prova de zero aces quando capture coverage não permitia essa conclusão.

# 25. N3.07.23 — Offline Controller

## N4.07.23.01 — Quick Session

- somente commands permitidos;

- todos preservam `control_epoch` e base sequence;


## N10.07.23

- Quota error antes de persistir: ponto não é apresentado como durável.

# 27. N3.07.25 — Reconciliation

## N4.07.25.01 — Reconnect protocol

Ao reconectar:

```text
1. stop blind replay
2. fetch authoritative MatchProjection + current lease/epoch
3. compare server last_sequence
4. inspect local pending commands
5. if same epoch + compatible base sequence
     → ordered replay
   else
     → RECONCILIATION_REQUIRED
```

## N5.07.25 — No LWW

Nunca:

```text
local.updated_at > cloud.updated_at
→ overwrite cloud score
```

## N5.07.25.02 — Divergence

Se outro controller assumiu:

- eventos locais antigos permanecem preservados;
- não são autoaplicados;
- UI apresenta diferença de forma compreensível;
- operador autorizado decide como reconciliar, normalmente por correções semânticas sobre estado atual, não por replace do log.

## N10.07.25

- Controller A marca três pontos offline; B assume e marca cinco; A reconecta: nenhum dos três pontos é aplicado automaticamente com epoch antigo.
- Reconciliation não apaga evidência local antes de resolução.

# 29. N3.07.27 — Spectator Realtime

## N4.07.27.01 — Fonte

Spectator recebe **estado já committed**.

```text

→ DB commit
→ realtime transport
→ spectator
```

## N5.07.27 — Subscription protocol


Public spectator DTO é separado de controller/internal DTO.

## N10.07.27

- Spectator perde seq 91 e recebe 92: detecta gap e refaz snapshot.
- Realtime indisponível: controller ainda consegue command/ACK se API/DB estiverem disponíveis.

# 33. Concurrency model

## 33.1 Hot root = Match

Dentro de um Match, serialização é desejada.

A frequência de comandos de vôlei é pequena o suficiente para um row lock/transação curta por Match ser o baseline mais simples e correto.

Não distribuir um único Match entre múltiplos writers concorrentes apenas para parecer escalável.

## 33.2 AwardPoint race

```text
Controller command A expected=20
Controller command B expected=20
```

Servidor:

```text
A locks → appends 21 → commits
B locks → sees last=21 != expected=20 → stale conflict
```

## 33.3 Same command duplicate

```text
command_id X
```

executado duas vezes retorna o resultado já committed da primeira execução.

## 33.4 Different command IDs from accidental double tap

São semanticamente dois comandos distintos. Backend não pode adivinhar intenção e descartar um arbitrariamente.

Mitigações:

- UX debounce/feedback imediato;
- botão undo/correction eficiente;
- command_id estável durante retry do mesmo gesto.

# 34. Reliability / failure semantics

## 34.1 Success

```text
SUCCESS = transaction committed
```

Realtime delivery não participa da definição de success.

## 34.2 Unknown outcome

Se connection cai após commit e antes do response:

- UI considera outcome desconhecido;
- retry usa mesmo command_id;
- servidor devolve receipt/result existente.

## 34.3 Projection correctness

MatchProjection é rebuildable, mas crítica; gravação ocorre na mesma tx do evento.

Integrity check periódico:

```text
projection.last_sequence == max(match_events.sequence_no)
```

mais replay amostral/full onde operacionalmente apropriado.

## 34.4 No event compaction baseline

Partida possui volume naturalmente limitado. Não compactar/apagar MatchEvents para “performance” sem necessidade comprovada.

# 40. ADR candidates / decisions

## ADR-0078 — Universal Match Engine
Quick, Community e Competition usam o mesmo core de Match; diferem em authority/context/policies.

## ADR-0079 — Fixture is not Match
Planning/pairing e execução concreta são entidades separadas.

## ADR-0080 — MatchRoster is an immutable historical snapshot
Match não lê Team membership mutável para reconstruir passado.

## ADR-0081 — Match rules are frozen by snapshot
Mudanças de defaults/rulesets não reescrevem Match preparado/iniciado.

## ADR-0082 — MatchController is separate from Organizer
Organizer fornece elegibilidade operacional; controller representa autoridade atual de um Match.

## ADR-0083 — Control lease is scoped per Match
Remove session-wide scoring monopoly e habilita múltiplas quadras.

## ADR-0084 — Control epoch invalidates stale controllers
Todo takeover/reacquisition relevante gera epoch que protege contra comandos antigos/offline.

## ADR-0085 — MatchEvent log is authoritative for technical live facts
Estado corrente é projection, não source primária independente.

## ADR-0086 — Server computes authoritative score
Browser envia intenção esportiva, não placar final.

## ADR-0087 — MatchProjection is synchronous-critical and rebuildable
Atualizada na mesma tx porque o próximo command depende dela.

## ADR-0088 — Match uses per-aggregate authoritative sequence
Ordenação usa sequence server-side, não timestamps/LWW.

## ADR-0089 — Match corrections are append-oriented
Undo/correção preserva evento original e adiciona compensação/revision.

## ADR-0090 — Capture modes do not affect score semantics
SCORE_ONLY/BASIC/DETAILED mudam cobertura estatística, não regras.

## ADR-0091 — Community offline Match uses constrained outbox + reconciliation
Sem generic sync ou automatic merge.

## ADR-0092 — Quick Session may use local Match authority
Mesmo engine lógico; handoff explícito ao publicar.

## ADR-0093 — Realtime is committed transport with snapshot/sequence reconciliation
Não é command bus nem source of truth.

## ADR-0094 — Multiple courts have independent control domains
Cada Match possui lease/epoch/sequence próprios.

## ADR-0095 — MatchResult is distinct from OfficialCompetitionResult
Competition controla oficialização e impactos administrativos.

## ADR-0096 — Last-write-wins is forbidden for Match
Conflitos são resolvidos por sequence, epoch, command id e reconciliation explícita.

# 41. Open decisions que NÃO devem virar implementação acidental

1. **Community offline live scoring V1:** confirmar se entra no primeiro release do novo engine ou fica feature-gated após online path estabilizar.
2. **Lease TTL / heartbeat cadence:** medir em uso real; não congelar os atuais 10min/2min como verdade arquitetural eterna.
3. **Post-finish correction authority:** definir capabilities distintas para correção técnica comum vs alteração que muda winner/result.
4. **CaptureMode ownership:** decidir se default nasce em Community, Session e é congelado no Match, ou se Match pode escolher explicitamente antes do Start.
5. **Lineup depth V1:** ordem de saque/rotação/libero/substituição completa pode ser staged sem contaminar score engine básico.
6. **Spectator visibility:** definir public/community-only/private por Session/Competition policy e DTO correspondente.
7. **Manual finish:** fechar casos legítimos em que é permitido finalizar fora do Rules Engine.
8. **Event taxonomy:** manter pequena; só adicionar eventos necessários para regra, auditoria, estatística ou recovery.

# 42. Definition of Done — C2.07

C2.07 pode ser considerado arquiteturalmente materializado quando as próximas fases preservarem simultaneamente:

```text
semantic commands
+ server authoritative score
+ immutable event history
+ synchronous rebuildable projection
+ per-Match sequence
+ per-Match control lease
+ control_epoch fencing
+ idempotent command retry
+ frozen rules/roster
+ append-oriented correction
+ explicit offline reconciliation
+ committed-only realtime
+ MatchResult / OfficialResult separation
```

Se uma implementação futura simplificar qualquer item acima por `upsert Game`, `updated_at`, `pointIds[]`, `syncStatus` ou LWW, ela deve ser tratada como **regressão arquitetural**, não como detalhe de implementação.
