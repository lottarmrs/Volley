## 0. Regra de leitura

Este documento define o **target canônico** do contexto Competition.

As separações centrais são:

```text
Competition ≠ Session
CompetitionTeam ≠ SessionTeam
Round ≠ Fixture
Fixture ≠ Match
MatchResult ≠ OfficialCompetitionResult
OfficialCompetitionResult ≠ StandingsProjection
Penalty ≠ fake MatchEvent
BYE ≠ fake Match
```

O produto pode usar labels como:

```text
Campeonato
Liga
Torneio
Copa
```

sem obrigar engines independentes. O core é composto por `Competition + Stages + Fixtures + Matches + Official Results`.

# 1. Current State — evidência do repositório

## 1.1 `Championship` atual foi criado para liga multi-data

O design existente introduziu `Championship` para agrupar várias Sessions ao longo de semanas/meses, com roster fixo, agenda recorrente e standings acumulados.

Essa intenção é preservada.

O target apenas generaliza o conceito para `Competition`, capaz de representar também estruturas com stages/groups/knockout sem criar outra engine paralela.

## 1.2 `ChampionshipRound` atual mistura Round e Fixture

O type atual contém:

```text
round
teamAId
teamBId
scheduledDate
skipped
sessionId
```

Logo uma row representa, na prática, um confronto agendado.

A primeira migration inclusive usava:

```text
unique (championship_id, round)
```

mas uma correção posterior precisou remover essa constraint para “preserve every fixture in rounds that contain more than one match”.

Isso evidencia a separação correta:

```text
Round
contains
0..N Fixtures
```

## 1.3 Competition Team já é conceitualmente separado de Session Team

O legado possui `ChampionshipTeam` independente de Session e cria `Team` de Session com `championshipTeamId` quando materializa o confronto.

Essa é uma boa direção.

No target:

```text
CompetitionTeam
        ↓ snapshot/materialization
MatchRoster / execution teams
```

sem depender de copiar arrays mutáveis de player IDs como source-of-truth permanente.

## 1.4 Standings atual consome `Game` diretamente

`calculateTournamentStandings()` considera `Game` com status `finished | walkover` e lê winner, score e sets diretamente.

No target isso muda para:

```text
OfficialCompetitionResult[]
+ Penalty[]
↓
StandingsProjection
```

porque Match tecnicamente finalizada ainda pode não estar homologada, e resultado oficial pode receber correção administrativa sem inventar eventos de jogo.

## 1.5 Walkover atual é representado como Game com score artificial

`createWalkoverResult()` atualmente transforma um Game em `walkover`, define score e winner.

No target, WO administrativo é resultado de Competition e não exige MatchEvent nem Match real.

Um score regulamentar pode existir no `OfficialCompetitionResult` quando necessário para tiebreaks, mas não como fato esportivo fictício de Match.

## 1.6 CRUD atual não protege lifecycle complexo

`championshipCloudService` faz `select('*')` e `upsert()` direto em championships/teams/rounds.

Isso não é suficiente para operações como:

- start Competition;
- freeze ruleset;
- generate fixtures;
- resolve dependent bracket slot;
- officialize result;
- correct official result;
- apply penalty;
- finalize stage.

O target usa Commands semânticos e transações apropriadas.

# 2. N3.08.01 — Competition Aggregate

## N4.08.01.01 — Definição

`Competition` representa uma edição competitiva concreta.

Campos conceituais:

```text
id
scope/community_id
name
status
competition_type/product_label optional
current_ruleset_version_id
created_at
started_at?
completed_at?
archived_at?
```

Não deve conter arrays de Teams, Fixtures ou Results.

## N5.08.01 — Boundary

Competition é dona de:

- estrutura competitiva;
- entries;
- competition rosters;
- stages/groups/rounds/fixtures;
- official results;
- penalties;
- standings/bracket projections;
- awards competitivos.

Não é dona de:

- Match execution internals;
- Session lifecycle;
- Player identity;
- Notification delivery.

---

# 3. N3.08.02 — Competition Series / Edition

## N4.08.02.01 — Não supermodelar V1

Uma competição anual recorrente pode futuramente ter:

```text
CompetitionSeries
  ├── 2026 edition
  ├── 2027 edition
  └── 2028 edition
```

Mas `CompetitionSeries` não é obrigatória no V1.

O aggregate principal continua sendo a edição concreta `Competition`.

## N5.08.02 — Regra

Não criar hierarquia:

```text
Program → Tournament → Championship → Season → Edition
```

sem requirement real.

`CompetitionSeries` só entra quando recorrência entre edições exigir identidade própria.

# 4. N3.08.03 — Competition Organizer Scope

Competition deve possuir scope explícito.


# 15. N3.08.14 — Fixture

## N4.08.14.01 — Definição

`Fixture` é um confronto planejado.

```text
Fixture
├── competition_id
├── stage_id
├── round_id?
├── slot_a_source
├── slot_b_source
├── resolved_entry_a_id?
├── resolved_entry_b_id?
├── scheduled_at?
├── status
└── venue/court refs optional
```

## N5.08.14 — Fixture ≠ Match

Uma Fixture pode ter:

```text
0 Match executions
1 normal Match
N executions in replay/invalidated cases
```

Match nunca é a única identidade do confronto planejado.

## N5.08.14.02 — Lifecycle candidato

```text
PENDING_SLOTS
SCHEDULED
READY
IN_EXECUTION
AWAITING_OFFICIAL_RESULT
COMPLETED
CANCELLED
```

Estados finais exatos serão fechados no C3/C5.

# 16. N3.08.15 — Fixture Slot Source

Slots podem vir de fontes diferentes:

```text
DIRECT_ENTRY
GROUP_POSITION
STAGE_POSITION
FIXTURE_WINNER
FIXTURE_LOSER
SEED
BYE
```

Exemplo:

```text
Semifinal 1
A = GROUP_A_POSITION_1
B = GROUP_B_POSITION_2
```

ou:

```text
Final
A = WINNER(Fixture semifinal 1)
B = WINNER(Fixture semifinal 2)
```

## N5.08.15 — Resolution

Slot só é resolvido quando sua source está oficial e estável segundo ruleset.

Não resolver baseado apenas em MatchProjection ou MatchResult ainda não homologado quando Competition exige officialization.

# 18. N3.08.17 — Fixture Execution

## N4.08.17.01 — Bridge para Session/Match

Uma Fixture pode ser hospedada em uma Session existente ou gerar preparação operacional.

```text
Fixture
   ↓
PrepareFixtureExecution
   ↓
Session context / Court
   ↓
PrepareMatch
```

Uma Session pode hospedar:

```text

```

## N5.08.17 — No one-session-per-round assumption

O target não assume:

```text
Round = Session
```

Isso evita a limitação do legado multi-data.

## N4.08.18.01 — MatchResult

Fato técnico produzido por Live Match.

- winner;

- score;
- finish reason;
- event/log provenance.

## N4.08.18.02 — OfficialCompetitionResult

Fato oficial do contexto Competition.

Pode originar-se de:

```text

```

## N5.08.18 — Regra

```text
Match finished
DOES NOT necessarily mean
Competition result official
```

# 20. N3.08.19 — Official Competition Result

## N4.08.19.01 — Source fact

`OfficialCompetitionResult` é source fact competitivo.

Modelo conceitual:

```text
id
fixture_id
version
status/current marker
source_type
source_match_result_id?
winner_entry_id?
loser_entry_id?
official_score snapshot
reason
officialized_by
officialized_at
supersedes_result_id?
```

## N5.08.19 — Current result

Deve existir no máximo um `CURRENT` official result por Fixture.

Correção cria nova versão e supersede a anterior.

## N6.08.19 — Commands

```text
OfficializeMatchResult
CreateAdministrativeResult
CorrectOfficialResult
InvalidateOfficialResult
```

## N8.08.19 — Concurrency

Dois administradores officializando simultaneamente:

```text
one current result
other receives authoritative conflict/result
```

Nunca dois currents.

# 21. N3.08.20 — Walkover / Administrative Result

## N4.08.20.01 — WO não gera história falsa

```text
Walkover
≠
Match with invented PointEvents
```

Se ruleset define placar administrativo, armazená-lo no OfficialResult.

Exemplo:

```text

```

## N5.08.20 — No fake Match requirement

Pode existir OfficialResult para Fixture sem nenhuma Match execution.

# 23. N3.08.22 — Tie-break Policies

## N4.08.22.01 — Ordem determinística

Ruleset deve registrar ordem explícita, por exemplo:

```text
classification_points
point_difference
head_to_head
wins
points_for
points_against
```

A ordem atual do tournament calculator pode servir de baseline, mas não deve ficar hard-coded universalmente para todos os formatos.

## N5.08.22 — Multi-team ties

Confronto direto de empate entre 3+ equipes exige policy explícita; não reutilizar silenciosamente lógica binária.

## N10.08.22

Mesmos official results + mesma ruleset version + mesmo calculation version produzem mesma classificação.

```text
├── reason
```

# 25. N3.08.24 — Bracket Dependency Graph

## N4.08.24.01 — Graph

Knockout é dependency graph:

```text
Quarterfinal A ─┐
                ├→ Semifinal 1 ─┐
Quarterfinal B ─┘               │
                                ├→ Final
Quarterfinal C ─┐               │
                ├→ Semifinal 2 ─┘
Quarterfinal D ─┘
```

Dependencies vivem em `FixtureSlotSource`.

## N5.08.24 — Idempotent propagation

Quando OfficialResult upstream muda de PENDING para CURRENT:

- resolver dependents deterministicamente;
- não duplicar Fixtures;
- não sobrescrever downstream que já entrou em estado incompatível.

## N8.08.24 — Conflict

Se upstream é corrigido depois de downstream Match já iniciar:

```text
MANUAL IMPACT REVIEW REQUIRED
```

Não trocar silenciosamente participante da Match em andamento/concluída.

# 26. N3.08.25 — Qualification Rules

Qualification é policy de Stage.

Exemplos:

```text
top N per group
best K third-place teams
rank 1..4 to playoffs
winner advances
```

Resolution usa standings/facts oficiais, não provisional live score.

# 27. N3.08.26 — Finalize Stage

`FinalizeStage` valida:

- Fixtures necessárias possuem Current OfficialResult;
- pending corrections/invalidation relevantes inexistem;
- qualification determinística pode ser resolvida;
- dependencies downstream podem ser materializadas.

É command explícito/idempotente quando a estrutura exigir freeze.

Não depende apenas de “todas Game.status=finished”.

# 28. N3.08.27 — Retroactive Result Correction

## N4.08.27.01 — Append/version, não rewrite

```text
OfficialResult v1
↓ superseded by
OfficialResult v2
```

Nunca destruir silenciosamente o fato de que v1 foi anteriormente oficial.

## N5.08.27 — Impact analysis

Antes de correction, calcular dependências afetadas:

```text
standings
qualification
resolved fixture slots
future scheduled fixtures
already-started downstream matches
awards
notifications/reports
```

## N6.08.27 — Commands

```text
PreviewOfficialResultCorrectionImpact
CorrectOfficialResult
```

## N8.08.27 — Automatic vs manual

Pode auto-rebuildar:

- standings projection;
- qualification ainda não executada;
- future unresolved slots.

Não auto-reescreve:

- downstream Match já iniciada;
- OfficialResult downstream;
- relatório oficial já emitido sem versioning.

# 34. Offline Policy

Competition mutations compartilhadas são:

```text
ONLINE_AUTHORITATIVE
```

Não enfileirar offline:

- officialization;
- penalty;
- reschedule;
- roster mutation;
- stage finalization.

Cached reads podem funcionar offline.

A Match executada em modo offline segue N2.07/N2.12; Competition só recebe resultado técnico depois da reconciliação/commit do Match.

# 35. Reliability / Transaction Boundaries

## 35.1 Officialize

Atomicidade mínima:

```text
lock Fixture
validate MatchResult/current state
insert OfficialCompetitionResult
mark prior result superseded if correction flow
update Fixture official state
write command receipt
write outbox/domain event
COMMIT
```

Projection de standings pode ser eventual, desde que OfficialResult já esteja durável.

## 35.2 Stage finalization

Quando dependências são simples, resolução de slots pode ocorrer na mesma transaction.

Quando extensa, usar durable outbox/worker idempotente.

## 35.3 At-least-once

Projection rebuild e bracket propagation devem aceitar execução repetida.

# 36. Performance / Scale

Competition geralmente possui volume muito menor que MatchEvents.

Otimizar primeiro:

- indexes por competition/stage/fixture;
- current official result lookup;
- projection de standings;
- bracket read model;
- cursor pagination em histórico longo.

Não introduzir graph database para bracket V1; Postgres relacional representa dependency graph adequadamente.

# 37. Current → Target Mapping

| Current | Target |
|---|---|
| `Championship` | `Competition` edition |
| `ChampionshipTeam.playerIds[]` | `CompetitionTeam + RosterRevision + entries` |

# 38. Migration Strategy Anchor

```text
1. Introduce Competition tables alongside Championship legacy
2. Map Championship → Competition
3. Map ChampionshipTeam → CompetitionTeam + roster rev
4. Split each ChampionshipRound row into Round grouping + Fixture
5. Preserve scheduled_date/session bridge as Fixture execution metadata
6. Introduce OfficialCompetitionResult
7. During compatibility, materialize official result from eligible legacy finished Game exactly once
8. Build new standings from OfficialResults
9. Compare legacy standings vs target projection on migrated cohorts
10. Switch reads to target
11. Switch admin writes to semantic commands
```

# 43. Definition of Competition Compliance

Uma implementação está alinhada a N2.08 quando:

1. Competition possui structure própria e não é Session longa;
2. Teams/rosters competitivos preservam identidade entre Sessions;
3. Round contém Fixtures em vez de representar um único confronto;
4. Fixture e Match têm lifecycle e identidade diferentes;
5. MatchResult técnico não é standings source direto;
6. OfficialCompetitionResult é versionado/current por Fixture;
7. WO/penalty não inventam fatos esportivos;
8. standings/bracket são rebuildable projections;
9. ruleset/tiebreak/qualification são versionados e determinísticos;
10. retro corrections fazem impact analysis e não reescrevem downstream ativo silenciosamente;
11. Competition capabilities não vazam de Organizer/Admin/Captain sem policy explícita;
12. critical writes são semantic commands server-authoritative.
