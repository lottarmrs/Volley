## 0. Regra de leitura

Este documento define o **target canônico** de History / Statistics.

A separação estrutural é:

```text
FACTUAL SPORTS HISTORY
≠
SUBJECTIVE PLAYER EVALUATION
≠
SKILL PROFILE
≠
OVERALL
≠
REPORT PRESENTATION
```

Em particular:

```text
MatchParticipation + MatchEvent + MatchResult
        ↓
statistical contribution
        ↓
statistics / career / rankings
```

é um pipeline diferente de:

```text
PlayerEvaluation
        ↓
CommunityPlayerSkillProfile
        ↓
GlobalPlayerSkillProfile
        ↓
Derived Overall
```

Não existe atualização automática de Rating a partir de Stats neste target.

Não existe atualização automática de Stats a partir de Rating.

Se no futuro houver um modelo de inferência esportiva que use fatos de jogo para sugerir avaliação, ele será outro bounded policy/ADR e nunca uma mistura silenciosa destes dois pipelines.

# 1. Current State — evidência do repositório

## 1.1 `calculatePlayerStats()` ainda reconstrói participação usando Team atual

A implementação atual de `src/logic/statistics.ts` recebe:

```text
PointEvent[]
Game[]
Team[]
Player[]
```

Para descobrir `gamesPlayed`, ela procura Games cujos `teamAId/teamBId` apontam para Teams em que `team.playerIds.includes(player.id)`.

Isso significa que o cálculo histórico depende do shape mutável de Team atual.

Esse modelo não é suficiente para o target porque:

```text
historical participation
MUST NOT depend on
current Team membership
```

O target usa `MatchParticipation` / `MatchRoster` histórico como fonte.

## 1.2 `CareerEvent` atual é uma agregação por Session, não uma contribuição factual por Match

O modelo atual possui:

```text
CareerEvent
├── playerId
├── sourceSessionId
├── sourceFingerprint
├── status: confirmed | provisional
├── values
├── occurredAt
└── sourceUpdatedAt
```

`buildCareerEvent()` agrega Games de uma Session e produz um único conjunto de valores.

A ideia de separar `confirmed` e `provisional` é útil e será preservada conceitualmente.

Porém, a unidade canônica muda para Match porque:

- correções acontecem naturalmente em Match;
- Match possui event sequence própria;
- Competition oficializa Match/Fixture;
- uma Session pode conter múltiplas Matches;
- uma contribuição por Match facilita rebuild incremental e dedupe.

## 1.3 `CareerEvent.values.rating` mistura dois domínios

O `CareerValues` atual contém:

```text
rating
```

E `buildCareerEvent()` usa `stats.rating?.overall ?? 0` para preenchê-lo.

Isso mistura uma projeção subjetiva/derivada com fatos de jogo dentro da carreira factual.

No target:

```text
rating / overall
DO NOT belong to
factual PlayerMatchStatContribution
```

Se um relatório histórico quiser mostrar “rating exibido na época”, isso deve ser um snapshot de apresentação explicitamente versionado, e não um componente agregado da estatística factual.

## 1.4 `0` atual pode esconder ausência de captura

O modelo atual usa números como `0` para várias dimensões.

Mas o Match Engine target possui modos de captura diferentes:

```text
SCORE_ONLY
BASIC_STATS
DETAILED
```

Se uma Match ocorreu em `SCORE_ONLY`, não registrar recepções não significa:

```text
receptions = 0
```

Significa:

```text
receptions = UNKNOWN / NOT_CAPTURED
```

Essa distinção é obrigatória no target.

## 1.5 Career Cloud atual é CRUD direto de projection-like data

`careerCloudService.ts` faz upsert/fetch/delete direto de `career_events`, inclusive com conflito por `(player_id, source_session_id)`.

Isso reflete o modelo local-first/sync atual.

No target, shared career/statistics são projections server-side derivadas de fatos autoritativos. O browser não upserta totais de carreira como source of truth.

## 1.6 Tournament/Competition stats atuais leem Games/PointEvents diretamente

O código atual de torneio calcula standings, MVP, scorers e awards diretamente sobre `Game[]`, `PointEvent[]`, Teams e Players.

Partes das funções puras podem ser reaproveitadas, mas o target altera as fontes:

```text
historical participation
→ MatchParticipation

factual events
→ MatchEvent

competition eligibility/result
→ OfficialCompetitionResult
```

E não Team atual / Game mutável como autoridade histórica.

# 2. N3.09.01 — Factual vs Subjective Data

## N4.09.01.01 — Factual sports data

Fatos são observações/decisões registradas sobre algo que aconteceu no contexto esportivo.

Exemplos:

```text
Player P participou da Match M
P marcou um ponto de saque
Match terminou 2 sets a 1
Team A venceu
Fixture F foi oficializada com resultado R
```

Fontes principais:

```text
MatchParticipation
MatchEvent
MatchResult
OfficialCompetitionResult
CompetitionPenalty
```

## N4.09.01.02 — Subjective evaluation data

Avaliação responde outra pergunta:

> Como um Organizer/evaluator avalia a habilidade do Player em determinadas dimensões?

Fonte:

```text
PlayerEvaluation
```

Projeções:

```text
CommunityPlayerSkillProfile
GlobalPlayerSkillProfile
Derived Overall
```

## N5.09.01 — Regra de separação

```text
Stats never mutate PlayerEvaluation.
PlayerEvaluation never mutates MatchStats.
Overall never becomes a stat fact.
```

UI pode apresentar essas informações próximas visualmente, mas os pipelines de dados permanecem distintos.

## N10.09.01

- Player marca 20 aces em Matches: isso não altera automaticamente `serve` evaluation.
- Organizer muda `serve` de 7 para 9: career aces permanece exatamente igual.
- Fórmula do overall muda: historical factual stats permanecem idênticas.

# 3. N3.09.02 — Match Participation

## N4.09.02.01 — Fonte histórica de participação

A pergunta:

> Este Player participou desta Match?

é respondida por `MatchParticipation` / `MatchRoster`, não pelo estado atual de Team.

Modelo conceitual:

```text
MatchParticipation
├── id
├── match_id
├── participant_id
├── player_id nullable
├── team_side / match_roster_entry_id
├── participation_status
├── started_as / lineup role if captured
├── source
└── historical snapshot references
```

## N5.09.02 — Player vs Guest

```text
player_id != null
→ contribution may aggregate into persistent Player career

player_id = null
→ Guest contribution remains contextual
```

Guest pode possuir estatística por Match/Session sem obrigatoriamente gerar Player global.

## N5.09.02.02 — Participation eligibility

Estar no roster não significa necessariamente ter participado esportivamente se o domínio no futuro diferenciar:

```text
ROSTERED
ENTERED_MATCH
PLAYED
DID_NOT_PLAY
```

V1 pode usar regra mais simples, mas o schema não deve reconstruir participação depois a partir do Team atual.

## N8.09.02 — Historical integrity

Mudanças em:

```text
Player name
Player position
CommunityPlayer status
current Team
PlayerAccountLink
```

não alteram a existência da MatchParticipation histórica.

## N10.09.02

- Player muda de Team depois da Match: gamesPlayed histórico não muda.
- Community remove Player: participações antigas continuam.
- Player merge mantém contribution history sem contar source+target duas vezes.

# 4. N3.09.03 — Stat Contribution

## N4.09.03.01 — Unidade canônica

A unidade básica do pipeline estatístico é uma contribuição derivada por participação em uma Match.

Nome canônico, fechado por C7 R5:

```text
PlayerMatchStatContribution
```

A semântica e o nome arquitetural estão fechados. O nome físico de tabela continua responsabilidade do Data Catalog/schema e não altera esta identidade de domínio/projection.

## N4.09.03.02 — Modelo candidato

```text
PlayerMatchStatContribution
├── id
├── match_id
├── match_participation_id
├── player_id nullable
├── session_id
├── community_id nullable
├── competition_id nullable
├── fixture_id nullable
├── source_last_sequence
├── capture_coverage
├── stat_definition_version
├── calculation_version
├── eligibility_state
├── metrics
├── computed_at
└── projection_revision
```

Core metrics importantes devem preferir colunas/estrutura tipada em vez de um blob sem contrato. JSONB pode ser usado para payload versionado/metrics extensíveis quando justificado.

## N5.09.03 — Derivada, não source fact

Essa contribuição é uma **projection rebuildable**.

Sua verdade deriva de:

```text
MatchParticipation
+
MatchEvents effective at sequence N
+
MatchResult / eligibility context
```

Portanto pode ser substituída/recalculada quando os fatos mudam.

## N5.09.03.02 — Dedupe

Uma Match efetiva contribui no máximo uma vez para uma mesma participação e versão corrente da projection.

Não criar:

```text
Career contribution via Session
+
Career contribution via Match
```

para o mesmo fato.

## N10.09.03

- Rebuild 100 vezes produz a mesma contribuição lógica.
- Worker processa o mesmo MatchFinished duas vezes: não duplica career.
- Player participa de duas Matches na mesma Session: duas contribuições, não uma colapsada indevidamente.

# 5. N3.09.04 — Match Stats

## N4.09.04.01 — Métricas factuais

Exemplos candidatos, sujeitos ao que o Match Event schema realmente captura:

```text
points_won
attack_points
block_points
aces
counter_attack_points
opponent_error_points
receptions
perfect_receptions
digs
sets_played
match_played
match_won
```

Não devemos publicar uma métrica que o capture mode não suporta com semântica clara.

## N5.09.04 — Definição explícita

Cada stat precisa responder:

```text
What counts?
What does not count?
Which events feed it?
What capture mode supports it?
How are corrections handled?
What is unknown?
```

## N5.09.04.02 — Points vs actions

Um point event que diz “ponto ganho por ataque” permite contar `attack_points`.

Ele **não** necessariamente permite inferir:

```text
attack attempts
attack efficiency percentage
```

se tentativas que não geraram ponto não foram capturadas.

## N8.09.04 — No invented denominator

Não calcular percentual de recepção/ataque se o sistema não registrou todas as tentativas necessárias para o denominador.

## N10.09.04

- SCORE_ONLY Match retorna score/game outcome, mas detailed player metrics ficam unknown.
- BASIC_STATS com apenas point-winning skills não produz “attack efficiency” falsa.
- Correction que reverte um ace reduz a contribuição derivada após rebuild.

# 6. N3.09.05 — Session Scope

## N4.09.05.01 — Agregação

Session stats são agregados das Match contributions elegíveis daquela Session.

```text
Session
├── Match A contributions
├── Match B contributions
└── Match C contributions
```

## N5.09.05 — Não recalcular do estado atual de Session Team

O aggregate usa IDs/snapshots/contributions históricas.

## N5.09.05.02 — Multiple matches

Uma pessoa que joga três Matches na Session pode ter:

```text
games = 3
```

Não `games = 1` apenas porque existe um CareerEvent por Session no modelo antigo.

## N10.09.05

- Uma Session com três Matches gera três contributions por Player quando elegível.
- Uma Match cancelada não aumenta gamesPlayed.
- Uma Match invalidada depois é removida do aggregate após recompute.

# 7. N3.09.06 — Community Scope

## N4.09.06.01 — Definição

Community stats agregam Match contributions cuja Match pertence/contextualiza aquela Community e é estatisticamente elegível.

## N5.09.06 — Player global, stats contextuais

Mesmo Player pode ter:

```text
Community A stats
Community B stats
Global stats
```

sem duplicação do Player.

## N5.09.06.02 — Privacy

Community aggregate não significa que qualquer Member pode ver qualquer stat individual. Read policy decide visibilidade.

## N10.09.06

- Match da Community A nunca aparece no scope B por ID mix-up.
- Player em A e B vê aggregates separados corretamente.
- Community archived preserva history conforme retention policy.

# 8. N3.09.07 — Competition Scope

## N4.09.07.01 — Competition eligibility

Para stats oficiais de Competition, não basta uma Match ter terminado.

A relação competitiva deve estar validada por:

```text
Fixture
+
current OfficialCompetitionResult
+
statistical eligibility
```

## N5.09.07 — Fato técnico vs oficial

Os MatchEvents continuam sendo os fatos técnicos do jogo.

Mas para classificar uma contribuição como oficial daquela Competition, o sistema considera o OfficialResult corrente.

## N5.09.07.02 — Replay / invalidation

Se Fixture teve:

```text
Match A invalidated
Match B official replay
```

Competition stats oficiais devem incluir apenas a execução elegível segundo policy.

## N5.09.07.03 — Walkover

Walkover sem Match events pode gerar:

```text
competition result / standings contribution
```

mas não inventa player point stats.

## N10.09.07

- Match finished mas não officialized: não entra em official Competition ranking quando policy exige homologação.
- WO soma standings conforme rule, mas nenhum Player recebe 25 pontos fictícios.
- Replay oficial substitui execução invalidada sem double counting.

# 9. N3.09.08 — Global Career

## N4.09.08.01 — Definição

Global Career é uma projeção agregada das contribuições elegíveis vinculadas ao Player global.

```text
Player
   ↓
eligible Match contributions
   ↓
PlayerCareerProjection
```

## N5.09.08 — Não é um event source

Career projection pode ser deletada e reconstruída a partir das contribuições/fatos.

Não deve ser usada como única prova de participação histórica.

## N5.09.08.02 — Scopes

Query pode aceitar:

```text
GLOBAL
COMMUNITY
COMPETITION
SESSION
DATE_RANGE
```

sem necessariamente persistir uma tabela separada para cada combinação desde V1.

## N5.09.08.03 — Player merge

Merge deve evitar contar duas vezes contributions que já representam a mesma participação.

## N10.09.08

- Apagar PlayerCareerProjection e rebuildar produz mesmo resultado.
- Community filter não altera global source data, apenas scope.
- Player merge não duplica Match já referenciada pelo canonical target.

# 10. N3.09.09 — Statistical Eligibility

## N4.09.09.01 — Por que existe

Nem toda Match record deve contribuir para Stats.

Exemplos:

```text
CANCELLED
INVALIDATED
ABANDONED
TEST/IMPORT anomaly
REPLAY superseded
```

Precisamos de policy explícita.

## N5.09.09 — Modelo conceitual

```text
StatisticalEligibility
├── source match/result
├── scope
├── eligible boolean/state
├── reason
├── policy_version
└── evaluated_at
```

Pode ser derivada deterministicamente e/ou materializada como projection para performance/audit.

## N5.09.09.02 — Candidatos iniciais

```text
FINISHED valid Match
→ eligible

CANCELLED
→ not eligible

INVALIDATED
→ not eligible

ABANDONED
→ policy-dependent

WALKOVER without play
→ result/standings eligible,
   player-event stats absent
```

## N5.09.09.03 — Scope dependency

Uma Match casual pode ser elegível para global/community career enquanto uma execução competitiva invalidada pode não ser elegível para Competition official stats.

Eligibility pode variar por scope, mas não arbitrariamente.

## N10.09.09

- Invalidating Match removes contribution after rebuild.
- Abandoned Match does not silently count as full played Match without policy.
- Competition result superseded does not leave old official aggregate active.

# 11. N3.09.10 — Capture Coverage

## N4.09.10.01 — Problema

Stats só são confiáveis quando sabemos o que foi capturado.

## N5.09.10 — Match capture mode

O Match Engine define snapshot de captura, por exemplo:

```text
SCORE_ONLY
BASIC_STATS
DETAILED
```

A contribuição estatística guarda essa informação.

## N5.09.10.02 — Coverage por dimensão

Um mode global pode não ser suficiente no futuro. Algumas métricas podem ter coverage própria:

```text
NOT_CAPTURED
PARTIAL
COMPLETE
```

Não precisamos materializar complexidade máxima no V1, mas o contrato deve permitir distinguir pelo menos `known` de `unknown`.

## N5.09.10.03 — Historical imports

Legacy import pode ser:

```text
SCORE_ONLY_LEGACY
POINT_WINNERS_ONLY_LEGACY
UNKNOWN_COVERAGE
```

conforme evidência.

Não promovemos import parcial para `DETAILED`.

## N10.09.10

- Legacy Game tem placar mas sem PointEvents: score conhecido, player skills unknown.
- MatchDetailed com event stream completo pode afirmar zero aces se nenhum ace ocorreu.
- MatchScoreOnly não pode afirmar zero aces.

# 12. N3.09.11 — Stat Definition Versioning

## N4.09.11.01 — Definição

A mesma palavra pode mudar de significado se mudarmos taxonomia/algoritmo.

Portanto contribution registra:

```text
stat_definition_version
calculation_version
```

## N5.09.11 — Diferença

### Stat definition version

Muda quando muda o significado da métrica.

Exemplo:

```text
V1: counterattack counted only explicit skill X
V2: includes reason Y under clarified rule
```

### Calculation version

Pode mudar implementação sem mudar significado.

Exemplo:

```text
same result
faster projector
```

## N5.09.11.02 — Historical comparability

Se definição muda materialmente, precisamos decidir:

- rebuild histórico usando nova definição quando source events permitem;
- manter cohorts versionados;
- apresentar compatibility note.

Não misturar números semanticamente diferentes como se fossem idênticos.

## N10.09.11

- Deploy de projector otimizado com mesma definição não muda totals.
- Mudança semântica incrementa definition version.
- Historical rows sem source suficiente não são “recalculadas” inventando detalhe.

# 13. N3.09.12 — Corrections

## N4.09.12.01 — Match event correction

Correção append-oriented em Match altera a sequência efetiva.

Pipeline:

```text
MatchEvent correction/reversal
↓
MatchProjection updated
↓
source_last_sequence changes
↓
recompute affected PlayerMatchStatContribution
↓
update affected aggregates
```

## N5.09.12 — Bounded recompute

Uma correção em uma Match não deve exigir varrer todos os MatchEvents de toda a carreira no browser.

Preferência:

```text
recompute Match contribution
↓
recompute/incrementally adjust aggregates
```

## N5.09.12.02 — Official result correction

Correction de OfficialCompetitionResult pode alterar:

- Competition standings;
- win/loss outcome contributions;
- official eligibility.

Não altera player skill events técnicos a menos que a Match também seja corrigida.

## N8.09.12 — No silent rewrite of official reports

Se report oficial já foi emitido, correction cria nova revisão/supersedes em vez de mutar o documento histórico silenciosamente.

## N10.09.12

- Revert ace → Match contribution loses one ace.
- Official winner corrected sem MatchEvent correction → standings/win outcome muda, raw point event stats não.
- Correction processed twice remains idempotent.

# 14. N3.09.13 — Rebuild

## N4.09.13.01 — Propriedade obrigatória

Toda projection estatística crítica deve ser documentadamente rebuildable.

Para cada projection devemos saber:

```text
source facts
source revision/sequence
calculation version
rebuild command/job
integrity invariant
```

## N5.09.13 — Hierarquia

```text
Match facts
↓
PlayerMatchStatContribution
↓
Session/Community/Competition/Global aggregates
```

Rebuild pode ocorrer bottom-up.

## N5.09.13.02 — Rebuild scope

Suportar:

```text
single Match
single Player
date range
single Community
single Competition
full rebuild
```

conforme operação.

## N5.09.13.03 — Idempotência

Rebuild repetido produz estado equivalente.

## N10.09.13

- Delete projection row → rebuild restores.
- Full rebuild and incremental pipeline converge.
- Worker crashes halfway → rerun safely continues/replaces deterministic rows.

# 15. N3.09.14 — Projection Staleness

## N4.09.14.01 — Source-based freshness

Não medir freshness por:

```text
projection.updated_at seems recent
```

Usar:

```text
source_last_sequence
source_revision
calculation_version
```

## N5.09.14 — Match contribution stale

Se:

```text
MatchProjection.last_sequence = 105
PlayerMatchStatContribution.source_last_sequence = 103
```

contribution está stale.

## N5.09.14.02 — Aggregate stale

Aggregate guarda source checkpoint/revision compatível para permitir detecção.

## N8.09.14 — UI

Normalmente usuário não precisa ver números técnicos de revision, mas a plataforma deve evitar apresentar projection stale como definitiva quando a diferença for relevante.

## N10.09.14

- Correction commit succeeds but async career worker fails: stale metric/health check detects.
- Timestamp novo por touch não mascara source sequence atrasada.

# 16. N3.09.15 — Unknown vs Zero

## N4.09.15.01 — Regra fundamental

```text
0
=
metric captured and no occurrence

UNKNOWN
=
metric not captured / insufficient evidence
```

Esses valores nunca são intercambiáveis.

## N5.09.15 — API representation

Possibilidades:

```text
nullable value + coverage metadata
```

ou:

```text
StatValue {
  value?: number
  coverage: COMPLETE | PARTIAL | NOT_CAPTURED
}
```

A escolha exata é de contrato, mas `?? 0` não pode apagar a semântica.

## N5.09.15.02 — Aggregation

Somar metrics precisa preservar coverage.

Exemplo:

```text
Match A complete: 2 aces
Match B score-only: unknown aces
```

Career não pode afirmar simplesmente:

```text
2 aces across all matches
```

sem indicar que coverage é parcial.

Pode mostrar:

```text
2 recorded aces
coverage: partial
```

ou limitar denominador a Matches completas.

## N10.09.15

- One complete + one unknown match does not produce false complete aggregate.
- Zero in a DETAILED Match remains zero.
- Import pipeline never converts null/missing metric to 0 automatically.

# 18. N3.09.17 — Reports

## N4.09.17.01 — Report não é source fact

Relatório é uma representação derivada/publicada do estado em determinado momento.

Exemplos:

```text
MatchReport
SessionReport
CompetitionReport
PlayerCareerReport
```

## N5.09.17 — Report snapshot

Report relevante deve registrar:

```text
report_revision
source scope
source checkpoints
stat_definition_version
generated_at
generator_version
status
```

## N5.09.17.02 — Lifecycle candidato

```text
DRAFT
OFFICIAL
SUPERSEDED
```

Nem todo relatório precisa de formalização `OFFICIAL`; isso vale especialmente para documentos/exports que representem resultado oficial.

## N5.09.17.03 — Corrections

Se report oficial precisa mudar:

```text
revision N remains historical
revision N+1 supersedes N
```

Não editar PDF/row anterior sem provenance.

## N8.09.17 — Privacy

Export/report pode amplificar exposição porque congela dados fora da UI.

Antes de gerar:

- scope de acesso;
- dados permitidos;
- finalidade;
- retenção/export policy.

## N10.09.17

- Correction after official CompetitionReport creates new revision.
- User without access cannot generate private player report by UUID enumeration.
- Report snapshot does not embed raw evaluation unless explicit product requirement and authorization.

# 19. N3.09.18 — Rankings

## N4.09.18.01 — Metric-specific

Ranking precisa responder:

> ranking de quê?

Exemplos:

```text
most aces
most attack points
win rate
recorded points
```

Não usar um genérico:

```text
best player
```

sem definição explícita.

## N5.09.18 — Overall exclusion

`Derived Overall` pertence ao rating/display pipeline e não é estatística factual.

Se existir ranking por overall na UI, é outro ranking de SkillProfile, não um History/Statistics ranking.

## N5.09.18.02 — Eligibility threshold

Rankings podem precisar de:

```text
minimum matches
```

# 37. Decisions / Hypotheses / Open Questions

## DECIDED

- Factual Stats are separate from subjective Evaluation, SkillProfile and Overall.
- Historical participation comes from immutable/current-at-time participation records, not current Team state.
- Match is the primary contribution unit.
- Shared stats/career are server-derived rebuildable projections.
- Capture coverage is first-class semantics.
- Unknown is not zero.
- Corrections trigger bounded recompute.
- Quick local stats may appear as provisional overlay.
- Publish must dedupe/replace the provisional representation.
- Guest contextual stats are allowed without creating Player.
- Rankings are metric-specific.
- Official reports are revisioned rather than silently overwritten.
- Postgres remains the initial statistics platform.

## STRONG HYPOTHESIS

- `PlayerMatchStatContribution` will be the canonical persisted contribution name/entity.
- V1 will store a practical mixture of typed core metric columns plus versioned metadata rather than EAV for every stat.
- Shared career projection will be materialized for hot global/player scopes; some less common filters may remain query-time over contributions.
- `StatisticalEligibility` will be a deterministic policy with materialized current result/checkpoint where operationally useful.

## OPEN

- Exact V1 stat taxonomy supported by BASIC_STATS vs DETAILED capture.
- Exact definition of `gamesPlayed` when Player is rostered but never enters court, if lineup/substitution capture becomes richer.
- Abandoned Match eligibility by reason and scope.
- Which player stats, if any, become public profile fields by default.
- Minimum sample/coverage rules for each ranking type.
- Whether historical display should show current Player identity or snapshot display name in each UI surface.
- Whether official reports need cryptographic/signature/export immutability beyond database revisioning.

# 39. Definition of History / Statistics Compliance

Uma implementação está alinhada a N2.09 quando:

1. Stats e Ratings são pipelines independentes;
2. MatchParticipation é a fonte de quem jogou;
3. contribuição estatística é por Match e rebuildable;
4. capture coverage permite distinguir zero de unknown;
5. corrections reprocessam apenas scopes necessários sempre que possível;
6. source sequence/revision detecta projection stale;
7. shared career é calculada no servidor;
8. Quick offline usa overlay provisional sem double counting após publish;
9. Guests podem ter stats contextuais sem Player global;
10. Competition stats oficiais respeitam OfficialCompetitionResult e eligibility;
11. WO/legacy imports não inventam eventos pessoais;
12. reports oficiais são versionados/superseded;
13. rankings declaram métrica, scope, coverage e eligibility;
14. UI não precisa baixar toda história para mostrar career;
15. legacy `CareerValues.rating` não sobrevive dentro do factual pipeline.
