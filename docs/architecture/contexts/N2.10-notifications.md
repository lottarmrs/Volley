## 0. Regra de leitura

Este documento define o **target canônico** de Notifications.

A regra mais importante é:

```text
A NOTIFICAÇÃO NÃO É O FATO DE DOMÍNIO.
```

Exemplos:

```text
"Sua inscrição foi aceita"
≠
RegistrationEntry CONFIRMED

"Você saiu da lista de espera"
≠
Waitlist promotion transaction

"O sorteio foi confirmado"
≠
Confirmed TeamDraw

"Resultado oficial publicado"
≠
OfficialCompetitionResult
```

O fato é persistido pelo bounded context proprietário.

Notifications reage **depois** do commit do fato.

Pipeline canônico:

```text
Committed Domain Transaction
        ├── domain facts/current state
        └── app_private.domain_outbox
                    ↓
            NotificationPolicy
                    ↓
       NotificationIntent per recipient
              ├── Inbox state
              └── Channel delivery
                    ↓
             DeliveryAttempt[]
```

Outra regra estrutural:

```text
DOMAIN SUCCESS
MUST NOT depend on
PUSH / EMAIL / WHATSAPP / EXTERNAL PROVIDER SUCCESS
```

A pessoa pode não receber Push e a inscrição continuar confirmada.

A pessoa pode não receber Email e o resultado continuar oficial.

# 1. Current State — evidência do repositório

## 1.1 Não existe ainda um Notifications bounded context canônico

O serviço operacional atual importa e sincroniza em conjunto:

```text
Session
Team
Game
PointEvent
GameReport
SessionReport
CommunityPresence
WhatsAppListDraft
```

O mesmo `OperationalSyncPayload` possui `drafts: WhatsAppListDraft[]`, e `whatsapp_list_drafts` é tratado como uma das tabelas genéricas sincronizadas pelo `operationalCloudService`.

Isso mostra que o conceito existente mais próximo de comunicação ao usuário ainda é um **draft operacional de compartilhamento**, e não um pipeline de notificação orientado a eventos de domínio.

## 1.2 `WhatsAppListDraft` atual é conteúdo de compartilhamento, não delivery

O mapper atual de `WhatsAppListDraft` persiste informações como:

```text
template_id
title
date
location
start_time
end_time
value
pix_key
pix_holder
pix_bank
payment_deadline
setters
main_slots
reserve_slots
extra_text
```

Isso é semanticamente muito diferente de:

```text
NotificationIntent
NotificationDelivery
DeliveryAttempt
```

Um draft preparado para copiar/compartilhar no WhatsApp não prova que:

- uma mensagem foi enviada;
- um destinatário específico recebeu;
- houve um provider automático;
- houve retry;
- houve delivery receipt;
- houve read receipt;
- o estado de domínio ainda era relevante no momento do compartilhamento.

Portanto o target **preserva a utilidade do draft**, mas o remove do papel de substituto de Notifications.

## 1.3 O sync genérico atual não deve ser reutilizado como mecanismo de notificação

O serviço atual faz `fetchAll()` de várias tabelas operacionais e usa upsert genérico por `owner_id,local_id`.

Notifications tem semântica diferente:

- intents precisam de dedupe semântico;
- delivery é eventual;
- attempts são histórico técnico append-oriented;
- scheduled reminders precisam revalidar estado;
- push endpoints pertencem a dispositivos/usuários;
- Inbox é recipient-owned;
- provider secrets não podem passar pelo browser.

Logo, Notifications não será apenas mais uma coleção dentro de um `OperationalSyncPayload` genérico.

# 2. N3.10.01 — Boundary e responsabilidade

## N4.10.01.01 — O que pertence a Notifications

Notifications responde:

> Dado que um fato autoritativo aconteceu, existe uma comunicação útil para algum User e, se existir, como torná-la disponível e tentar entregá-la pelos canais permitidos?

Pertencem ao contexto:

```text
NotificationPolicy
NotificationIntent
NotificationInboxState
NotificationDelivery
NotificationDeliveryAttempt
NotificationTemplateVersion
UserPushEndpoint
UserNotificationPreference
scheduled relevance evaluation
provider adapters
```

## N4.10.01.02 — O que NÃO pertence a Notifications

Não pertencem:

```text
Registration state
Membership state
Session lifecycle
Match state
TeamDraw selection
Voting truth
OfficialResult
PlayerEvaluation
Stats
Community authorization
```

Notifications pode referenciar esses aggregates, mas não é dona deles.

## N5.10.01 — Consequência

Se Notifications estiver completamente indisponível:

```text
core domain commands may continue
```

desde que o Postgres/transação autoritativa consiga registrar o fato e sua saída durável para processamento posterior.

## N10.10.01

- Push provider cai: `JoinRegistration` ainda pode confirmar a vaga.
- Worker de Notifications para: `OfficializeCompetitionResult` continua sendo verdade.
- Inbox temporariamente indisponível para leitura: Match não volta de FINISHED para LIVE.

# 3. N3.10.02 — DomainEvent e Transactional Outbox

## N4.10.02.01 — Evento após fato, mas outbox na mesma transação

O ponto de integração é um registro durável escrito junto ao commit de domínio:

```text
BEGIN
  validate domain command
  mutate authoritative domain state
  append/record domain event semantics
  INSERT app_private.domain_outbox (...)
  commit
END
```

Não significa que um provider externo seja chamado dentro da transação.

Significa que, se o domínio commitou, existe uma intenção durável de processar os efeitos externos correspondentes.

## N4.10.02.02 — Modelo conceitual de outbox

```text
DomainOutboxItem
├── id
├── event_id
├── event_type
├── aggregate_type
├── aggregate_id
├── aggregate_revision / sequence nullable
├── schema_version
├── occurred_at
├── payload_minimal
├── processing_status
├── available_at
├── attempt_count
├── lease_owner nullable
├── lease_expires_at nullable
├── processed_at nullable
└── last_error_class nullable
```

O outbox não precisa conter um dump do aggregate.

Payload deve ser mínimo e versionado.

## N5.10.02 — Por que não chamar provider na transação

Alternativa rejeitada:

```text
Domain RPC
  → provider Push
  → provider Email
  → commit DB
```

Problemas:

- provider aumenta duração da transação;
- falha de provider pode rollbackar um fato válido;
- timeout gera outcome desconhecido;
- provider pode aceitar e resposta se perder;
- acopla disponibilidade do produto à infraestrutura externa;
- dificulta retry e rate-limit handling.

## N6.10.02 — Por que não deixar o frontend enviar

Alternativa rejeitada:

```text
browser receives success
→ browser calls push/email provider
```

Problemas:

- browser pode fechar;
- browser não é confiável;
- secrets não podem ficar no cliente;
- cliente malicioso poderia escolher destinatários;
- duplicação e perda são inevitáveis;
- reminders futuros não funcionam sem browser aberto.

## N10.10.02

- Domain tx rollbacka: nenhum outbox item válido deve existir.
- Domain tx commita e resposta HTTP se perde: outbox continua processável.
- Worker cai depois de ler item mas antes de marcar processado: lease expira e item é retomado idempotentemente.

# 4. N3.10.03 — NotificationPolicy

## N4.10.03.01 — Nem todo DomainEvent deve notificar

Erro a evitar:

```text
DomainEvent = Notification
```

A relação correta é:

```text
DomainEvent
   ↓
NotificationPolicy
   ├── no-op
   ├── one recipient
   └── many recipient intents
```

A política decide:

- se há comunicação;
- categoria;
- urgência;
- destinatários;
- template;
- canais candidatos;
- agendamento;
- expiração;
- regra de revalidação.

## N4.10.03.02 — Exemplos candidatos

Eventos potencialmente notificáveis:

```text
CommunityJoinApproved
CommunityJoinRejected
RegistrationOpened
RegistrationPromotedFromWaitlist
RegistrationRemoved
SessionCancelled
TeamVoteOpened
TeamVoteClosed
TeamDrawConfirmed
MatchStartingSoon
OfficialCompetitionResultPublished
```

Mas o fato de existir esse evento não obriga notification em todos os produtos/categorias.

## N5.10.03 — Policy version

Políticas que alteram comportamento de forma relevante devem ser versionáveis/auditáveis quando necessário.

Não precisamos transformar toda condição simples em um motor de regras genérico V1.

Preferência:

```text
explicit typed policies in application/domain code
```

em vez de:

```text
user-programmable rule engine
```

## N10.10.03

- `MatchPointAwarded` acontece 100 vezes: não cria 100 Pushes por padrão.
- `RegistrationOpened` numa comunidade silenciosa pode gerar somente Inbox, conforme política.
- `RegistrationPromotedFromWaitlist` pode ser URGENT porque requer ação rápida.

# 5. N3.10.04 — Recipient Resolution

## N4.10.04.01 — Recipient é User

NotificationIntent automática é dirigida a um usuário autenticável:

```text
recipient_user_id
```

Não a:

```text
email string supplied by browser
phone supplied by browser
arbitrary player_id
```

O Player pode ser usado como origem para resolver um User via `PlayerAccountLink`, mas o delivery target continua sendo uma identidade de comunicação autorizada.

## N4.10.04.02 — Resolver no contexto correto

Exemplo `RegistrationPromotedFromWaitlist`:

```text
RegistrationEntry
→ Session
→ Community
→ registered Player
→ authorized account link
→ eligible User
```

A resolução deve impedir BOLA/cross-community leakage.

## N5.10.04 — Fan-out é assíncrono

Para eventos como `RegistrationOpened`:

```text
Domain transaction
MUST NOT synchronously insert/send
thousands of provider messages
```

O outbox registra o evento de origem; worker/policy materializa intents em lotes.

## N10.10.04

- Community tem 5.000 membros: abrir lista não transforma a command transaction em fan-out de 5.000 inserts externos.
- Member é removido antes de um reminder futuro: revalidação bloqueia delivery contextual.
- Payload malicioso envia `recipient_user_id` de outra pessoa: campo não é aceito para notification automática.

# 6. N3.10.05 — NotificationIntent

## N4.10.05.01 — Semântica

`NotificationIntent` representa:

> Esta comunicação específica foi materializada para este destinatário por causa desta origem.

Modelo candidato:

```text
NotificationIntent
├── id
├── recipient_user_id
├── source_event_id
├── source_event_type
├── source_aggregate_type
├── source_aggregate_id
├── source_revision nullable
├── notification_type
├── category
├── urgency
├── template_key
├── template_version
├── locale
├── rendered_title
├── rendered_body
├── navigation_target nullable
├── scheduled_for nullable
├── expires_at nullable
├── relevance_policy_version nullable
├── created_at
└── materialization_version
```

## N4.10.05.02 — Intent é semântica, não tentativa

Uma intent pode gerar:

```text
1 Inbox item
0..N Push deliveries
0..N Email deliveries
future provider deliveries
```

Não criar uma nova `NotificationIntent` a cada retry.

## N5.10.05 — Imutabilidade semântica

Após materializada, os campos históricos essenciais da intent não são reescritos para simular outra notificação.

Mudanças de read/archive e delivery ficam em estruturas separadas.

## N10.10.05

- User possui 3 dispositivos: uma intent, até 3 Push deliveries.
- Push falha 4 vezes: uma intent, um delivery lógico por endpoint, múltiplos attempts.
- User abre Inbox e lê: isso não transforma provider status em DELIVERED.

# 7. N3.10.06 — Dedupe e Idempotência

## N4.10.06.01 — Chave semântica

Candidate default:

```text
UNIQUE (
  source_event_id,
  recipient_user_id,
  notification_type
)
```

Casos que precisem mais de uma notificação do mesmo tipo por evento devem possuir uma semantic discriminator explícita.

## N4.10.06.02 — Diferenciar command idempotency de notification dedupe

```text
CommandReceipt
```

protege repetição da command.

```text
NotificationIntent semantic uniqueness
```

protege materialização duplicada.

```text
Provider idempotency key / delivery uniqueness
```

protege tentativa externa quando suportado.

São camadas diferentes.

## N5.10.06 — Exactly-once

Não prometer:

```text
distributed exactly-once delivery
```

O target é:

```text
durable at-least-once processing
+
idempotent materialization/effects
+
provider-specific dedupe where available
```

## N10.10.06

- Mesmo outbox item é consumido duas vezes: uma intent.
- Mesmo domínio é acionado por dois command_ids distintos, mas constraint de domínio impede segundo fato: não surge segunda notification sem fato novo.
- Provider aceitou request e response se perdeu: retry usa idempotency key quando provider oferecer suporte; caso contrário registra outcome incerto sem corromper o domínio.

# 8. N3.10.07 — Persistent Inbox

## N4.10.07.01 — Inbox independente de Push

Push é best-effort.

Inbox é a experiência persistente de comunicação dentro do app.

Fluxo:

```text
NotificationIntent
      ↓
NotificationInboxState
```

A pessoa pode descobrir a comunicação ao abrir o app mesmo que:

- permissão de Push esteja desativada;
- dispositivo esteja offline;
- token esteja inválido;
- provider tenha falhado.

## N4.10.07.02 — Estado de apresentação

Modelo candidato:

```text
NotificationInboxState
├── notification_intent_id
├── recipient_user_id
├── read_at nullable
├── archived_at nullable
└── updated_at
```

Se performance e simplicidade indicarem, `read_at`/`archived_at` podem fisicamente coexistir na tabela de intent, desde que semanticamente continuem separados de delivery state. A arquitetura não exige table split dogmático.

## N4.10.07.03 — Unread badge

Unread count é derivável:

```text
count(active inbox items where read_at is null)
```

Pode existir projection/cache para performance, mas não deve virar uma fonte de verdade impossível de reconstruir.

## N10.10.07

- Push token inválido: item continua na Inbox.
- User lê em dispositivo A: dispositivo B eventualmente reflete via authoritative query/realtime invalidation.
- Badge corrompe: rebuild/query corrige sem alterar intents.

# 9. N3.10.08 — Templates e Conteúdo Histórico

## N4.10.08.01 — Template versionado

Modelo:

```text
NotificationTemplateVersion
├── template_key
├── version
├── locale
├── title_template
├── body_template
├── variable_schema
├── created_at
└── retired_at nullable
```

## N4.10.08.02 — Rendered snapshot

Ao materializar a intent, guardar:

```text
template_key
version
locale
rendered_title
rendered_body
```

Assim, alterar template amanhã não reescreve silenciosamente a Inbox de ontem.

## N5.10.08 — Variáveis tipadas/permitidas

Não aceitar template arbitrary code.

Cada template possui schema de variáveis.

Exemplo:

```text
registration_promoted.v2
variables:
  session_name
  community_name
  deadline_text?
```

Dados devem ser escaped/sanitizados de acordo com a superfície de renderização.

## N6.10.08 — Não persistir URL efêmera

Não congelar signed URL curta dentro do body histórico.

Persistir alvo semântico:

```text
media_asset_id
navigation_target
```

E resolver acesso quando necessário.

## N10.10.08

- Template v12 muda para v13: notification antiga continua mostrando snapshot v12.
- Community se chama `<script>...`: conteúdo é tratado como texto, não executado.
- Signed avatar URL expira: Inbox continua navegável porque não depende dela como identificador durável.

# 10. N3.10.09 — Localization

## N4.10.09.01 — Locale no momento da materialização

A intent registra o locale usado.

Candidate selection:

```text
User preferred locale
→ supported locale fallback
→ product default
```

## N4.10.09.02 — Histórico não é reescrito

Se User muda idioma amanhã:

```text
new notifications → new locale preference
old rendered notifications → unchanged
```

Uma UI pode futuramente oferecer re-render explicitamente se houver requisito, mas isso não é default.

## N10.10.09

- User em `pt-BR` recebe item; depois muda para `en`: item histórico permanece pt-BR, próximos são English.
- Template locale inexistente: fallback determinístico e observável, nunca corpo vazio silencioso.

# 11. N3.10.10 — Scheduling e Reminders

## N4.10.10.01 — Reminder não é uma promessa cega de envio

Ao agendar:

```text
schedule candidate delivery
```

No horário de processamento:

```text
re-read authoritative state
→ revalidate relevance
→ evaluate expiry/preferences/urgency
→ send or suppress
```

## N4.10.10.02 — Server time

`scheduled_for` e `expires_at` usam tempo autoritativo do servidor.

Browser clock não decide vencimento compartilhado.

## N4.10.10.03 — Exemplos de revalidação

### Session reminder

Não enviar “sessão começa em 1h” se:

```text
Session CANCELLED
Session start changed to tomorrow
recipient no longer eligible
```

### Waitlist promotion

Não enviar reminder de promoção se:

```text
entry WITHDRAWN
entry REMOVED
registration source revision invalidated
```

### Vote reminder

Não enviar “vote agora” se:

```text
VotingRound CLOSED
VotingRound INVALIDATED
user no longer eligible voter
```

## N10.10.10

- Reminder foi criado segunda, Session cancelada terça, scheduled_for quarta: SUPPRESSED_NOT_RELEVANT.
- Worker ficou fora 4h e reminder expirou: SUPPRESSED_EXPIRED, não envia avalanche atrasada sem contexto.
- Horário da Session mudou: relevance policy usa estado atual, não texto antigo para decidir envio.

# 12. N3.10.11 — TTL, Expiry e Suppression

## N4.10.11.01 — Expiração explícita

Notifications sensíveis ao tempo podem possuir:

```text
expires_at
```

Após isso, delivery externo não é mais útil.

## N4.10.11.02 — Suppression é resultado válido

Estados candidatos:

```text
PENDING
PROCESSING
DELIVERED
FAILED_RETRYABLE
FAILED_PERMANENT
SUPPRESSED_EXPIRED
SUPPRESSED_NOT_RELEVANT
SUPPRESSED_BY_PREFERENCE
```

A nomenclatura física final pode variar, mas “não enviar porque ficou irrelevante” não deve aparecer como erro técnico.

## N5.10.11 — Inbox vs external TTL

Uma notification pode expirar para Push e ainda permanecer como histórico na Inbox, dependendo da policy.

Exemplo:

```text
"Você foi promovido da reserva"
```

Mesmo que o alerta Push tenha perdido a utilidade operacional, o item histórico pode explicar o que ocorreu.

## N10.10.11

- Push atrasado de “vote agora” não é enviado depois do voto fechar.
- Provider volta após 12h: processor checa TTL antes de retry.

# 13. N3.10.12 — Channels e Provider Adapters

## N4.10.12.01 — Channel é infraestrutura de entrega

Canais candidatos:

```text
IN_APP
PUSH
EMAIL
future WHATSAPP_AUTOMATED
```

O domínio não deve importar SDK de provider.

Interface conceitual:

```text
NotificationChannelAdapter
  send(deliveryRequest)
    → ProviderDeliveryResult
```

## N4.10.12.02 — Provider substituível

Não persistir conceitos específicos de Firebase/Expo/OneSignal/Resend/Twilio/etc. como semântica central do domínio.

Guardar metadados necessários:

```text
provider_key
provider_message_id nullable
provider_status_code_class nullable
```

como infraestrutura.

## N4.10.12.03 — Escolha inicial

Postgres + transactional outbox + worker é suficiente para V1.

Não introduzir Kafka/RabbitMQ/SQS por princípio antes de carga/operational need justificar.

Isso preserva possibilidade de migração futura porque a fronteira:

```text
DomainOutbox → processor
```

já existe.

## N10.10.12

- Troca de provider Push: intents históricas não precisam mudar de schema.
- Email provider cai: Push e Inbox podem continuar.
- Um provider aplica rate limit: apenas deliveries daquele provider sofrem backoff.

# 14. N3.10.13 — Push Endpoints

## N4.10.13.01 — Endpoint por instalação/dispositivo

Modelo candidato:

```text
UserPushEndpoint
├── id
├── user_id
├── installation_id
├── provider
├── token_ciphertext / protected token
├── platform
├── app_version nullable
├── status
├── registered_at
├── last_seen_at nullable
├── disabled_at nullable
└── disable_reason nullable
```

Um User pode ter vários endpoints.

## N4.10.13.02 — Ownership server-side

`RegisterPushEndpoint` resolve:

```text
auth.uid() → user_id
```

O cliente não cadastra token em nome de outro User.

## N4.10.13.03 — Endpoint inválido

Provider pode indicar token definitivamente inválido.

Nesse caso:

```text
disable endpoint
≠
delete NotificationIntent
≠
mark Inbox item read
```

## N5.10.13 — Logout / account switch

O aplicativo deve evitar endpoint permanecer indevidamente associado ao usuário anterior em dispositivo compartilhado.

Fluxo de logout deve desregistrar/desabilitar a associação quando possível; servidor também precisa suportar token rotation/re-registration segura.

## N10.10.13

- User A logout, User B login no mesmo aparelho: Push de A não deve ser entregue ao contexto de B.
- Token rotaciona: novo endpoint/credencial substitui a anterior sem duplicação permanente.
- Um dos três dispositivos morre: somente endpoint inválido é desabilitado.

# 15. N3.10.14 — Preferences

## N4.10.14.01 — Preferência não é autorização

`UserNotificationPreference` controla comunicação, não acesso ao domínio.

Exemplo:

```text
UserNotificationPreference
├── user_id
├── category
├── channel
├── enabled
├── quiet_hours_policy nullable
└── updated_at
```

## N4.10.14.02 — Categorias

Candidate taxonomy:

```text
REGISTRATION
SESSION
TEAM_SELECTION
MATCH
COMPETITION
COMMUNITY
ACCOUNT_SECURITY
```

Marketing/promotional communication, se existir no futuro, deve ser separada das comunicações transacionais/operacionais e receber análise jurídica própria.

## N4.10.14.03 — Não construir permission-builder

V1 não precisa de:

```text
IF community=X AND organizer=Y AND event=Z AND hour...
```

como regra configurável arbitrária pelo usuário.

Preferências simples por categoria/canal são mais previsíveis e testáveis.

## N5.10.14 — Momento da avaliação

Para delivery futuro, preferência deve ser reavaliada próximo ao envio.

Assim, se User desativa Push depois do agendamento e antes do envio, a escolha recente pode ser respeitada.

## N10.10.14

- User desativa Push para Session reminders: Inbox pode continuar conforme política de produto, Push é suprimido.
- Preference muda durante fila: worker usa estado atual permitido pela policy, não snapshot antigo cego.

# 16. N3.10.15 — Urgency e Quiet Hours

## N4.10.15.01 — Urgency semântica

Candidate:

```text
LOW
NORMAL
TIME_SENSITIVE
SECURITY_CRITICAL
```

Não usar “URGENT” como desculpa para tudo.

## N4.10.15.02 — Quiet hours

Quiet hours são política de entrega, não de criação do fato.

Comunicações não críticas podem ser postergadas.

Alguns alertas time-sensitive podem bypassar quiet hours se a política do produto disser explicitamente.

Exemplo a decidir por produto:

```text
promoted from waitlist
with confirmation deadline in 20 minutes
```

pode justificar comportamento diferente de:

```text
weekly community summary
```

## N5.10.15 — Não inventar decisão legal/produto

Quais categorias podem bypassar quiet hours deve ser decisão explícita documentada, não inferida pelo provider ou pelo frontend.

## N10.10.15

- Reminder normal cai às 03:00: posterga conforme preference.
- Security-critical account event: policy pode ignorar quiet hours.
- Evento atrasado ultrapassa TTL enquanto espera quiet hours: suppress, não envia depois sem utilidade.

## N4.10.16.01 — Separar delivery lógico de attempt físico

NotificationDelivery
├── id

├── endpoint_id nullable

Porém não guardar eternamente payloads completos/sensíveis só para debug.

## N5.10.16 — Delivery state não é read state

User read the content

## N10.10.16

# 18. N3.10.17 — Workers, Lease e At-Least-Once

## N4.10.17.01 — Processing model

Workers assumem at-least-once.

Postgres pode inicialmente atuar como fila durável.

Claim pattern candidato:

```text
SELECT eligible jobs
FOR UPDATE SKIP LOCKED
→ assign lease
→ commit claim
→ process
→ persist outcome
```

ou mecanismo equivalente com leases.

## N4.10.17.02 — Lease recuperável

Worker pode morrer.

Logo:

```text
PROCESSING forever
```

não é um estado aceitável.

Lease expira e outro worker pode retomar de maneira idempotente.

## N4.10.17.03 — Batching

Fan-out grande e provider APIs podem ser processados em lotes controlados.

Batch size/concurrency são parâmetros operacionais, não semântica de domínio.

## N10.10.17

- Worker A claim 100 jobs e morre no job 32: leases expiram e backlog é retomado.
- Worker A e B competem pelo mesmo job: lock/lease impede processamento simultâneo normal; idempotência protege duplicação residual.
- Deploy reinicia todos workers: backlog durável permanece.

# 19. N3.10.18 — Retry, Backoff e Poison Messages

## N4.10.18.01 — Classificar falha

Não retryar tudo indiscriminadamente.

Classes:

```text
TRANSIENT
RATE_LIMITED
PERMANENT_ENDPOINT
PERMANENT_PAYLOAD
AUTH_PROVIDER_CONFIGURATION
UNKNOWN
```

## N4.10.18.02 — Backoff bounded + jitter

Transient:

```text
retry with bounded exponential backoff + jitter
```

429:

```text
respect Retry-After when trustworthy
```

Permanent endpoint:

```text
disable endpoint
stop retries for that delivery
```

## N4.10.18.03 — Poison isolation

Após limite finito:

```text
FAILED_PERMANENT / DEAD-LETTER-LIKE STATE
```

Um item venenoso não pode bloquear o resto da fila.

V1 não precisa de broker especializado: status + erro + manual reprocess pode cumprir a semântica.

## N5.10.18 — Manual retry

Operador reprocessa o **mesmo delivery/intent**, não fabrica um novo fato de domínio para forçar mensagem.

## N10.10.18

- Provider retorna 500 por 20min: backoff evita retry storm.
- Payload inválido determinístico: não executar 100 retries inúteis.
- Um template quebrado para um recipient não bloqueia 10.000 outras notifications.

# 20. N3.10.19 — Transações e Atomicidade

## N4.10.19.01 — Atomicidade de origem

Obrigatório:

```text

```

na mesma transação lógica quando o evento requer integração externa durável.

## N4.10.19.02 — Materialização de intents

Materializar várias recipient intents pode ocorrer fora da source transaction.

Cada lote deve possuir dedupe e checkpoint/progress confiável.

## N4.10.19.03 — Delivery externo nunca dentro de DB transaction longa

Claim deve ser curto.

Chamada externa ocorre fora de lock de longa duração.

Outcome é persistido depois com ownership/lease validation.

## N10.10.19

- 20s de latência no Email provider não segura lock na RegistrationWindow.
- Crash após provider call e antes de persistir result: outcome incerto é tratado pelo delivery idempotency strategy, sem desfazer source fact.

# 22. N3.10.21 — Offline e Local Cache

## N4.10.21.01 — Inbox local é cache

No modelo online-first:

```text
server Inbox = authority
IndexedDB Inbox = cache
```

Não existe merge arbitrário de notification content criado offline.

## N4.10.21.02 — Mark read offline

`MarkNotificationRead` é candidato a command offline segura porque:

- afeta somente estado de apresentação do próprio actor;
- é monotônica/idempotente se semântica for `read_at = min(existing, requested?)` ou server-time first-read;
- não altera direito de terceiros;
- não altera fatos esportivos.

Decision detail:

```text
client queues: MarkNotificationRead(intent_id, command_id)
server resolves actor from auth
if already read → success idempotent
```

`MarkUnread` é mais complexo porque deixa de ser monotônico e pode precisar de explicit last-write semantics; pode ficar online-only ou usar revision se existir.

## N4.10.21.03 — Push registration online-only

Cadastro/rotação de endpoint é server-authoritative e requer auth válida.

## N10.10.21

- User lê notification offline e fecha app: local command persiste e sincroniza depois.
- Outro usuário faz login no mesmo aparelho: cache e pending read commands são user-scoped e não vazam.
- Item foi removido/retido antes do replay de MarkRead: safe no-op/not-found semantics, sem criar item fantasma.

# 23. N3.10.22 — Segurança

## N4.10.22.01 — Threat model específico

Ameaças:

- cliente tenta notificar outro User;
- cross-community recipient leak;
- endpoint token roubado/exposto;
- provider secret no bundle;
- deep link usado como autorização;
- template injection/XSS;
- Push lock-screen expondo informação privada;
- webhook de provider forjado;
- enumeration por Notification IDs;
- mass assignment em preferences/endpoints.

## N4.10.22.02 — Authorization

Inbox:

```text
auth.uid() == recipient_user_id
```

com RLS/Query boundary apropriada.

Automatic intent creation:

```text
internal processor only
```

Não expor genericamente:

```text
POST /notifications { recipientUserId: arbitrary }
```

para browser.

## N4.10.22.03 — Push payload minimization

Lock screen pode ser visível a terceiros.

Preferir payload mínimo e adequado à classificação da informação.

Informação sensível/contextual pode usar:

```text
"Você tem uma nova atualização"
```

mais um identifier/deep-link seguro, e buscar corpo autenticado dentro do app.

## N4.10.22.04 — Deep link não autoriza

Abrir:

```text
/community/C/session/S
```

não concede acesso.

Query/command de destino reexecuta autorização normal.

## N4.10.22.05 — Secrets

Provider API keys/private signing secrets:

```text
server/secret store only
NEVER VITE_*
NEVER browser bundle
NEVER localStorage
```

## N4.10.22.06 — Webhooks

Se provider webhooks forem adicionados:

- verificar assinatura/autenticidade;
- replay protection/idempotência;
- validar schema;
- não confiar em IDs sem lookup contextual;
- registrar apenas diagnóstico necessário.

## N10.10.22

- Malicious member tenta alterar `recipient_user_id` num MarkRead: query/command resolve actor e bloqueia.
- Push aponta para community que User deixou: deep link abre, mas read query retorna acesso negado ao recurso privado.
- Community name contém HTML: template escaping evita execução.

# 28. N3.10.27 — Fan-out e Escalabilidade

## N4.10.27.01 — Evitar fan-out na write transaction

Uma comunidade grande não deve tornar `OpenRegistrationWindow` proporcional ao número de membros.

Source transaction permanece aproximadamente O(1) em relação a recipient fan-out:

```text
registration mutation + one outbox event
```

Depois:

```text
recipient resolution in pages
→ batch intent inserts
→ delivery queue
```

## N4.10.27.02 — Backpressure

Workers precisam de limites por:

- provider;
- tenant/community se necessário;
- job type;
- global concurrency.

Isso evita um broadcast grande bloquear alerts time-sensitive.

## N4.10.27.03 — Priority

Pode haver filas/prioridade lógica:

```text
TIME_SENSITIVE
NORMAL
BULK_LOW
```

sem criar três brokers diferentes no início.

## N5.10.27 — Não otimizar para 10M sem evidência

Primeiro target:

- query shapes corretos;
- cursor pagination;
- bounded batches;
- indexes dos hot paths;
- observabilidade de backlog/latência;
- adapters claros.

Depois escalar infraestrutura com evidência.

## N10.10.27

- Evento fan-out 50k não bloqueia Match alert urgente: prioridade/backpressure reservam capacidade.
- Backlog cresce: `oldest_pending_age` sinaliza antes de falha silenciosa.
- Um community broadcast gigante não consome memória do browser porque clients não recebem fan-out raw via one giant payload.

# 30. N3.10.29 — Reliability / Disaster / Restore

## N4.10.29.01 — Capability tier

Notifications é majoritariamente:

```text

```

Inbox e time-sensitive alerts são importantes, mas provider failure não pode corromper REL-TIER-1/2 facts.

## N4.10.29.02 — Restore

Após restore de backup:

- outbox pode conter jobs antigos;
- scheduled notifications podem ter vencido;
- source state pode ter avançado diferentemente;
- provider delivery pode já ter ocorrido antes do snapshot.

Portanto não executar replay cego.

Pipeline pós-restore:

```text
revalidate schedule
revalidate source relevance
honor dedupe/idempotency
suppress expired
process only eligible
```

## N4.10.29.03 — Provider outage

Provider externo indisponível:

```text
source domain unaffected
Inbox can still be created
channel delivery accumulates bounded backlog
retry/backpressure active
```

## N10.10.29

- Backup restaurado com reminder de ontem: não dispara hoje só porque voltou a PENDING.
- Push provider indisponível 6h: Registration correctness segue intacta.
- Inbox projection/cache perdido: rebuild/refetch a partir de intents/state.

# 32. Alternatives / Trade-offs

## 32.1 Provider call inside domain transaction

**Rejected.**

Prós:

- parece simples em happy path.

Contras dominantes:

- acopla disponibilidade;
- aumenta lock duration;
- outcome incerto;
- rollback indesejado;
- provider side effect não é transacional com Postgres.

## 32.2 Browser sends after success

**Rejected.**

É inseguro, não durável e impossível para reminders/background confiáveis.

## 32.3 Transactional outbox + async worker

**Chosen.**

Melhor equilíbrio V1 entre:

- durability;
- idempotency;
- operational simplicity;
- provider isolation;
- future scale.

## 32.4 Kafka/RabbitMQ immediately

**Deferred / rejected for V1.**

Pode ser útil no futuro, mas hoje adicionaria:

- broker operations;
- credentials/networking;
- local/dev complexity;
- delivery semantics adicionais;
- observability extra.

Sem evidência de throughput que exija isso.

## 32.5 Realtime as notification bus/source

**Rejected.**

Realtime é loss-tolerant transport; usuário offline perderia eventos sem durable Inbox.

## 32.6 Push-only product

**Rejected.**

Push permission/provider/device são best-effort.

## 32.7 One giant mutable notification row

**Rejected as semantic model.**

Misturaria:

- immutable communication identity;
- user read state;
- channel delivery state;
- N provider attempts.

Physical co-location de alguns campos pode ser otimização futura, mas boundaries permanecem explícitas.

## 32.8 Render template only at read time

**Rejected by default.**

Mudaria conteúdo histórico silenciosamente.

## 32.9 Store only rendered text, no provenance

**Rejected.**

Perde template/version/locale traceability.

## 32.10 Automated WhatsApp now

**Deferred.**

O legado atual é manual share draft. Provider automation exige novo adapter, política, credenciais, compliance e operação.

# 35. ADRs — C2.10

## ADR-0132 — Notifications are downstream of committed domain facts

**Decision:** notification delivery never defines whether a domain operation succeeded.

## ADR-0133 — Transactional domain outbox is the durable integration entry point

**Decision:** source transaction writes the domain mutation and corresponding outbox record atomically when asynchronous effects are required.

## ADR-0134 — NotificationPolicy maps events to recipient-specific intents

**Decision:** not every DomainEvent notifies; typed policies decide recipient, category, urgency, template and channel eligibility.

## ADR-0135 — NotificationIntent is per recipient and semantically deduplicated

**Decision:** one logical communication is not recreated on retries or per device.

## ADR-0136 — Persistent Inbox is independent from transport delivery

**Decision:** Push/Email failure must not eliminate in-app history.

## ADR-0137 — Read state and delivery state are separate dimensions

**Decision:** `read_at` does not mean provider delivered and provider delivered does not prove the user read.

## ADR-0138 — Scheduled notifications revalidate source state and expiry

**Decision:** delayed work never blindly sends stale reminders.

## ADR-0139 — Templates are versioned and rendered content is frozen per intent

**Decision:** later copy changes do not rewrite notification history.

## ADR-0140 — Channels use provider adapters; Postgres + worker is initial infrastructure

**Decision:** do not introduce a dedicated message broker before workload evidence requires it.

## ADR-0141 — Workers are at-least-once, idempotent and poison-isolating

**Decision:** leases, semantic dedupe, bounded retry and terminal failure states protect the queue.

## ADR-0142 — Push endpoints are per User/installation and credentials remain server-side

**Decision:** token ownership is derived from authenticated context and provider secrets never reach browser code.

## ADR-0143 — Realtime only accelerates Inbox visibility

**Decision:** durable Inbox/query remains authority; Realtime messages are loss-tolerant invalidations/updates.

## ADR-0144 — Notification content follows recipient-only authorization and privacy minimization

**Decision:** RLS/query boundary prevents cross-user access; lock-screen/provider payloads contain only necessary data.

## ADR-0145 — WhatsAppShareDraft remains separate from automated WhatsApp delivery

**Decision:** manual share artifact is not a NotificationDelivery. A future provider integration attaches through channel adapter semantics.

## ADR-0146 — Preferences, category and urgency are delivery policy, not source-domain state

**Decision:** notification preference can suppress/delay communication without rewriting Registration/Session/Match/Competition facts.

# 37. Definition of Done — Notifications foundation

C2.10 pode ser considerado implementado no target somente quando:

- [ ] pelo menos um domain command crítico produz transactional outbox atomicamente;
- [ ] duplicate processing não duplica NotificationIntent;
- [ ] Inbox é persistentemente consultável por recipient;
- [ ] RLS/authorization impede leitura cross-user;
- [ ] Push endpoint não pode ser registrado para outro User;
- [ ] provider secrets estão ausentes do bundle/browser;
- [ ] provider failure não altera source domain success;
- [ ] scheduled reminder revalida source state e TTL;
- [ ] stale reminder é suprimido com razão explícita;
- [ ] template version + locale + rendered snapshot são preservados;
- [ ] worker crash é recuperável por lease/reclaim;
- [ ] poison item não bloqueia fila;
- [ ] backoff/rate-limit behavior possui testes;
- [ ] Realtime outage não perde Inbox item;
- [ ] logout/account switch isola endpoint/cache/pending read state;
- [ ] provider payload/logging passa revisão de privacidade;
- [ ] observabilidade mede backlog age, failures e suppression;
- [ ] restore drill/replay não dispara blindly reminders expirados;
- [ ] `WhatsAppShareDraft` não é tratado como proof of delivery;
- [ ] N10 matrix possui testes automatizados nos cenários aplicáveis.
