## 0. Regra de leitura

Este documento define o **target canônico** de Media.

A separação fundamental é:

```text
UNTRUSTED UPLOAD
≠
SANITIZED MEDIA ASSET
≠
MODERATION DECISION
≠
DOMAIN ATTACHMENT
≠
DELIVERY URL
```

Um arquivo recebido do browser não se torna avatar simplesmente porque:

- o nome termina em `.jpg`;
- `File.type` diz `image/jpeg`;
- o browser conseguiu exibir a imagem;
- o upload para Storage terminou;
- existe uma URL pública;
- um humano decidiu aprovar o conteúdo.

O pipeline canônico é:

```text
CreateMediaUploadIntent
        ↓
private incoming object
        ↓
FinalizeMediaUpload
        ↓
server-side technical processing
  ├── object/path/intent verification
  ├── actual format / magic / decode
  ├── byte-size limits
  ├── dimensions / decoded pixel limits
  ├── malformed/truncated rejection
  ├── metadata / EXIF removal
  ├── orientation normalization
  ├── animation policy
  └── canonical re-encode
        ↓
MediaAsset READY
        ↓
optional moderation policy
        ↓
Attach / Replace on domain entity
        ↓
public or authorized delivery
```

A segunda regra fundamental é:

```text
MediaAsset.id
=
domain identity

Storage bucket/path/URL
=
infrastructure location
```

O domínio não deve carregar uma URL de Storage como identidade do arquivo.

# 1. Current State — evidência do repositório

## 1.1 O fluxo atual de avatar faz processamento principal no browser

`src/infra/supabase/avatarStorageService.ts` possui `toWebp()` que:

- carrega a imagem no browser;
- limita a maior dimensão a 256 px;
- desenha em `canvas`;
- tenta gerar WebP com qualidade 0.85;
- em caso de falha, retorna o arquivo original.

A intenção de otimizar largura de banda e cache é boa.

Mas o fallback é relevante:

```text
browser processing failed
→ original file may still be uploaded
```

Portanto o processamento client-side atual não pode ser tratado como boundary de segurança.

## 1.2 A validação inicial confia em propriedades do arquivo fornecidas ao browser

O fluxo verifica:

```text
file.type.startsWith('image/')
file.size <= 5 MB
```

Depois escolhe extensão por tipo do blob ou extensão do nome original.

Isso é uma boa validação de UX, mas não prova server-side:

- formato real;
- decode seguro;
- dimensões efetivas;
- quantidade de pixels após decode;
- ausência de metadados sensíveis;
- ausência de conteúdo malformado;
- que o arquivo recebido corresponde à policy esperada.

No target, validação client-side permanece como feedback rápido, nunca como controle de confiança.

## 1.3 O bucket `avatars` atual é público

A migration `20260624133117_player_avatars_approval.sql` configura:

```text
bucket: avatars
public: true
file_size_limit: 5 MB
allowed MIME:
- image/webp
- image/jpeg
- image/png
```

E cria policy de SELECT para o bucket `avatars`.

O client faz upload de candidatos em:

```text
proposals/{playerId}/{candidateId}.{ext}
```

antes da decisão final de aprovação.

Logo, no modelo atual, **o candidate object ainda não aprovado está em uma trust zone pública**.

Isso não é o target.

No target:

```text
pending/untrusted candidate
MUST NOT be publicly deliverable
```

## 1.4 O domínio atual guarda URL de infraestrutura

O modelo atual possui:

```text
Player.avatarUrl?: string
```

A migration adiciona:

```text
public.players.avatar_url text
```

E `PlayerAvatarProposal` possui:

```text
imageUrl: string
```

No target, esses campos são substituídos conceitualmente por referências como:

```text
players.avatar_asset_id
```

A URL final é resolvida para leitura/entrega e não é a identidade persistente do MediaAsset.

## 1.5 A RPC recebe `p_image_url` como dado de negócio

`propose_player_avatar(p_player_id, p_image_url)` recebe uma string e a registra em `player_avatar_proposals`.

Quando há autoaprovação ou aprovação posterior, essa string é promovida para `players.avatar_url`.

A RPC autoriza quem pode propor/aprovar, mas o contrato de domínio continua sendo:

```text
approve this URL
```

em vez de:

```text
approve/attach this known READY MediaAsset
```

O target fecha essa lacuna.

## 1.6 Sanitation e moderation estão misturados conceitualmente

O fluxo atual possui um approval workflow útil:

```text
pending
approved
rejected
superseded
```

Mas aprovação humana responde principalmente:

> Este conteúdo pode ser usado como foto deste Player?

Ela não deve significar:

> Este arquivo foi tecnicamente validado, metadata foi removida e os bytes são seguros.

No target:

```text
technical processing
≠
content moderation/approval
```

## 1.7 A autorização atual usa “player admin” baseado também em governance de Community

`current_user_is_player_admin()` considera:

- criador/owner atual do Player; ou
- owner/admin de uma Community em que o Player esteja ativo.

Isso pertence ao current state e será migrado junto com o modelo de Identity/Community.

O target não assume que `Community ADMIN` possui automaticamente autoridade sobre a mídia global de um Player.

Capabilities e contexto real devem decidir.

## 1.8 Há uma inconsistência útil como sinal arquitetural

O client aceita extensão candidata `gif` em fallback, mas o bucket atual declara MIME permitido apenas para WebP/JPEG/PNG.

Isso mostra por que policy de media não deve ficar espalhada entre:

```text
browser extension list
+
Storage MIME policy
+
RPC approval
```

O target centraliza a policy técnica em contrato versionado server-side.

# 2. N3.11.01 — MediaAsset

## N4.11.01.01 — Definição

`MediaAsset` representa um artefato de mídia conhecido e controlado pelo sistema após passar pelo lifecycle apropriado.

Modelo candidato:

```text
MediaAsset
├── id UUID
├── purpose
├── uploaded_by_user_id nullable
├── processing_state
├── visibility
├── processing_policy_version
├── canonical_mime_type nullable
├── canonical_width nullable
├── canonical_height nullable
├── canonical_byte_size nullable
├── canonical_checksum nullable
├── created_at
├── uploaded_at nullable
├── processing_started_at nullable
├── ready_at nullable
├── rejected_at nullable
├── failure_code nullable
└── retired_at nullable
```

Campos exatos serão fechados no Data Catalog. A semântica é obrigatória.

## N5.11.01 — Storage não é identidade

Não persistir no aggregate consumidor:

```text
https://<provider>/storage/v1/object/public/avatars/...
```

como identidade.

Persistir:

```text
avatar_asset_id = <uuid>
```

Consequências:

- troca de bucket não muda domínio;
- troca de CDN não muda domínio;
- signed URL pode expirar sem alterar `MediaAsset`;
- variantes podem mudar por policy;
- asset pode ser reprocessado sem reescrever Player.

## N5.11.01.02 — Não criar uma entidade por provider

Evitar:

```text
SupabaseAvatar
S3Image
CloudinaryPhoto
```

no domínio.

Adapters de infraestrutura resolvem MediaAsset para Storage.

## N10.11.01

- Bucket muda de nome: `players.avatar_asset_id` não muda.
- Signed URL expira: Player continua apontando para o mesmo asset.
- CDN hostname muda: nenhum histórico de Player é reescrito.

# 3. N3.11.02 — Media Purpose

## N4.11.02.01 — Finalidade é parte da policy

Um upload deve declarar sua finalidade.

Exemplos iniciais:

```text
PLAYER_AVATAR
COMMUNITY_AVATAR
COMMUNITY_COVER
COMPETITION_AVATAR
COMPETITION_COVER
```

Não usar um upload genérico sem purpose e tentar inferir depois pelo local onde a URL apareceu.

## N5.11.02 — Policy por purpose

Purpose pode definir:

```text
allowed formats
max upload bytes
max decoded dimensions
max decoded pixels
canonical master format
required variants
crop/aspect policy
moderation requirement
allowed visibility
retention policy
```

## N5.11.02.02 — Purpose compatibility

Um asset processado como:

```text
PLAYER_AVATAR
```

não deve ser anexado arbitrariamente como:

```text
COMPETITION_COVER
```

sem policy explícita.

Isso reduz mass-assignment e bypass de regras de dimensão/moderação.

## N10.11.02

- Browser cria PLAYER_AVATAR e tenta anexar em Community cover: reject.
- Policy futura aumenta resolução de Competition cover: assets antigos permanecem válidos pela versão com que foram processados até migração explícita.

# 4. N3.11.03 — Media Upload Intent

## N4.11.03.01 — Por que existe UploadIntent

O browser não escolhe livremente:

```text
bucket
object path
owner
purpose
visibility final
```

Ele pede autorização para iniciar um upload específico.

Modelo candidato:

```text
MediaUploadIntent
├── id UUID
├── created_by_user_id
├── purpose
├── target_context_type nullable
├── target_context_id nullable
├── incoming_object_key
├── allowed_mime_policy
├── max_upload_bytes
├── processing_policy_version
├── status
├── expires_at
├── created_at
├── uploaded_at nullable
└── finalized_at nullable
```

## N5.11.03 — Estados

Candidate lifecycle:

```text
CREATED
  ↓
UPLOADED
  ↓
FINALIZED

or

EXPIRED
CANCELLED
FAILED
```

UploadIntent não é o MediaAsset final.

## N6.11.03 — Commands

```text
CreateMediaUploadIntent
FinalizeMediaUpload
CancelMediaUploadIntent
```

`CreateMediaUploadIntent`:

1. autentica actor;
2. resolve capability para purpose/context;
3. cria key aleatória controlada pelo servidor;
4. registra limites/policy version;
5. devolve autorização de upload limitada àquele objeto.

## N7.11.03 — Direct upload vs proxy de bytes

Duas alternativas foram consideradas.

### A — bytes passam pelo nosso API/Edge Function

Prós:

- controle central imediato.

Contras:

- duplica bandwidth;
- aumenta latência;
- aumenta custo;
- pode atingir limites de memória/body/function;
- faz app server virar proxy de blob.

### B — browser faz upload direto para Storage privado com autorização restrita

Prós:

- melhor throughput;
- menor custo de aplicação;
- provider lida com upload;
- mantém app fora do hot path de bytes.

Condição obrigatória:

```text
upload destination is private/untrusted
+
server verifies/processes before use
```

**Target V1: B.**

## N8.11.03 — Replay/expiry

Upload authorization deve ser:

- curta;
- escopada ao key esperado;
- sem poder listar bucket;
- sem poder sobrescrever outros objetos;
- invalidada logicamente após finalize/expiry.

## N10.11.03

- URL/token de upload vaza: só permite o objeto/escopo e expira.
- Intent expirou antes do upload: finalize não promove.
- Mesmo intent finalizado duas vezes: segunda chamada é idempotente ou retorna estado autoritativo, nunca cria dois assets.
- Browser troca `target_context_id` no finalize: servidor usa contexto registrado no intent.

# 5. N3.11.04 — Incoming Asset

## N4.11.04.01 — Zona de confiança

Todo upload externo entra como **não confiável**.

Recommended trust zones:

```text
media-incoming-private
media-private
media-public
```

Nomes físicos finais podem variar.

A decisão arquitetural é separar trust/delivery zones, não necessariamente esses nomes literais.

## N5.11.04 — Incoming nunca é público

Objeto em incoming:

```text
MUST NOT
be served as application media
```

Mesmo que seja imagem aparentemente válida.

## N5.11.04.02 — Object key sem PII

Não usar:

```text
matheus-rodrigues-cpf-...jpg
player-name@email.com.png
```

Preferir:

```text
incoming/{intent_uuid}/{random_object_uuid}
```

O nome original pode ser descartado ou mantido apenas se houver finalidade explícita; não é necessário para avatar.

## N7.11.04 — Bucket separado vs prefixos

É tecnicamente possível usar:

```text
one bucket
/incoming
/private
/public
```

Mas um erro de policy em bucket público pode expor incoming.

Para trust zones distintas, buckets separados reduzem blast radius e tornam review mais claro.

**Preferência target:** buckets separados por trust/delivery zone.

## N10.11.04

- Candidate pending não pode ser obtido por public URL.
- Usuário A não consegue ler incoming de B.
- Nome original contendo `<script>` nunca vira object key/renderização de HTML.

# 6. N3.11.05 — Server Validation

## N4.11.05.01 — Browser é não confiável

Não confiar em:

```text
Content-Type do request
File.type
file extension
client canvas output declaration
original filename
client dimensions
```

## N5.11.05 — Allowlist V1

Para imagens visuais do produto, target inicial:

```text
JPEG
PNG
WebP
```

Outros formatos exigem decisão explícita.

### SVG

Rejeitado V1.

Razões:

- é documento ativo/complexo, não simples raster;
- pode conter scripts/referências/recursos externos dependendo do pipeline;
- sanitation segura é mais complexa;
- não há necessidade de produto que justifique ampliar a superfície agora.

### GIF/animated images

Rejeitar V1, salvo ADR futura.

Motivos:

- animation bombs/frames;
- custo variável de decode;
- UX inconsistente para avatar;
- pipeline de variantes mais complexo.

### HEIC/AVIF

Não habilitar apenas porque celulares produzem esses formatos.

Podem ser adicionados quando houver codec server-side seguro, observável e testado.

## N5.11.05.02 — Magic/decoder truth

Formato é aceito pelo decoder controlado do servidor, não pela extensão.

Fluxo:

```text
read bounded header
→ detect supported format
→ decode under limits
→ verify successful raster
```

## N8.11.05 — Malware

Para **raster images estritamente decoded e re-encoded**, o principal boundary V1 é:

```text
allowlist + bounded decode + discard original + canonical re-encode
```

Não introduzir antivírus genérico apenas por reflexo.

Se o produto futuramente aceitar:

```text
PDF
Office documents
ZIP
arbitrary attachments
```

isso exige nova threat model e provavelmente malware scanning.

## N10.11.05

- `.jpg` com bytes executáveis: reject.
- `image/jpeg` declarada com payload não decodificável: reject.
- SVG renomeado para `.png`: reject.
- GIF animado com MIME falso: reject.

# 7. N3.11.06 — Decode / Dimension Validation

## N4.11.06.01 — Byte size não basta

Arquivo comprimido pequeno pode decodificar para imagem enorme.

Precisamos limitar pelo menos:

```text
compressed bytes
width
height
width * height decoded pixels
```

## N5.11.06 — Pixel bomb protection

Cada MediaPurpose define limites máximos coerentes.

Exemplo conceitual, sem congelar números aqui:

```text
PLAYER_AVATAR_POLICY
├ max_upload_bytes
├ max_source_width
├ max_source_height
└ max_source_pixels
```

Números finais são configuration/policy benchmarks e não devem ser inventados sem testes reais de UX/dispositivos.

## N5.11.06.02 — Decoder bounds

Worker deve possuir:

- timeout apropriado;
- memory limit;
- bounded concurrency;
- decode library atualizada;
- rejection para dimensões absurdas antes de alocar desnecessariamente quando o formato permitir header inspection.

## N8.11.06 — OOM isolation

Um arquivo malicioso não deve derrubar todos os workers.

Processing concurrency precisa considerar custo de memória por decode.

## N10.11.06

- 2 MB que decodifica 100.000 × 100.000: reject antes de processamento perigoso.
- header diz uma dimensão e arquivo quebra no decode: FAILED/REJECTED técnico, nunca READY.
- 50 uploads grandes simultâneos não iniciam 50 decodes sem concurrency budget.

# 8. N3.11.07 — Metadata / EXIF Removal

## N4.11.07.01 — Metadata não necessária é descartada

Fotos podem carregar:

```text
GPS/location
camera model
capture timestamp
orientation
software tags
comments
thumbnails
other EXIF/XMP/IPTC metadata
```

Para avatar/capa, a maioria não é necessária.

Target:

```text
read orientation if needed for normalization
→ rasterize/normalize
→ re-encode without source metadata
```

## N5.11.07 — EXIF stripping é privacy by default

Não persistir localização do arquivo original apenas porque veio junto.

Isso está alinhado ao princípio de minimização.

## N5.11.07.02 — Raw incoming retention

O raw upload pode conter metadata sensível.

Após sucesso de processamento:

```text
raw incoming object
→ delete asynchronously
```

salvo finalidade explícita que justifique retenção.

Para os purposes iniciais, não existe essa justificativa.

## N10.11.07

- JPEG com GPS: variante final não contém GPS.
- EXIF orientation 6: imagem final aparece corretamente orientada, mas tag original não é preservada.
- Falha de GC após READY não torna o raw público; ele continua privado até retry.

# 9. N3.11.08 — Normalization / Re-encode

## N4.11.08.01 — Canonical sanitized master

Após decode, produzir um artefato controlado.

Modelo:

```text
untrusted raw
→ decoded raster
→ orientation/crop policy
→ canonical re-encode
→ SANITIZED_MASTER
```

O sanitized master fica privado.

## N5.11.08 — Por que manter master saneado

Alternativa 1:

```text
keep only avatar_256
```

é simples, mas impede gerar no futuro uma variante maior sem voltar ao raw inseguro.

Alternativa 2:

```text
retain sanitized master
+
derive variants
```

custa storage adicional, mas permite:

- novas variantes;
- mudança de CDN;
- reprocessing;
- qualidade futura;

sem preservar o arquivo cru/EXIF.

**Target:** sanitized master privado + variantes necessárias.

## N5.11.08.02 — Processing policy version

Registrar:

```text
processing_policy_version
```

para saber com qual pipeline o asset foi produzido.

Alterar encoder/quality não reescreve silenciosamente a história.

## N10.11.08

- Policy V2 aumenta tamanho de avatar: V1 continua válido; reprocess opcional gera nova variant version.
- Encoder muda resultado binário: checksum muda, MediaAsset identity pode permanecer se semântica for reprocess da mesma mídia; variant metadata registra versão.

# 10. N3.11.09 — Media Lifecycle

## N4.11.09.01 — Processing state

Candidate states:

```text
PENDING_UPLOAD
UPLOADED
PROCESSING
READY
REJECTED
FAILED
RETIRED
```

`REJECTED` significa conteúdo/arquivo não aceito por policy técnica.

`FAILED` significa erro operacional/processamento não conclusivo e potencialmente retryable.

## N5.11.09 — READY não significa aprovado para qualquer domínio

```text
READY
=
technically safe/normalized according to processing policy
```

Não significa automaticamente:

```text
approved as this Player's avatar
```

Essa segunda decisão pertence à attachment/moderation policy.

## N5.11.09.02 — State monotonicity

Evitar transformar o lifecycle em um `status` genérico onde qualquer transição é aceita.

Exemplos inválidos:

```text
REJECTED → READY by browser update
RETIRED → PROCESSING without explicit reprocess flow
PENDING_UPLOAD → READY without validated object
```

## N10.11.09

- Worker cai em PROCESSING: lease/retry retoma de forma idempotente.
- Object desapareceu antes do processing: asset FAILED com reason; não gera attachment.
- Retry de erro transitório produz um único set efetivo de variants.

# 11. N3.11.10 — Media Variants

## N4.11.10.01 — Modelo candidato

```text
MediaVariant
├── id
├── media_asset_id
├── variant_kind
├── processing_policy_version
├── storage_zone
├── object_key
├── mime_type
├── width
├── height
├── byte_size
├── checksum
├── created_at
└── retired_at nullable
```

Candidate kinds:

```text
SANITIZED_MASTER
AVATAR_SMALL
AVATAR_MEDIUM
COVER_STANDARD
```

Não gerar 15 variantes preventivamente.

## N5.11.10 — Immutable object keys

Uma variant publicada não é sobrescrita in-place.

Preferir:

```text
asset/{asset_id}/{variant_revision_or_hash}.webp
```

em vez de:

```text
player/{player_id}/avatar.webp  # overwrite forever
```

Benefícios:

- CDN/browser caching seguro;
- rollback de attachment;
- evita imagem antiga em URL com conteúdo novo;
- rastreabilidade.

## N5.11.10.02 — Variants são infraestrutura derivada

Se uma variant for perdida mas sanitized master continuar íntegro:

```text
variant can be regenerated
```

Ela não é source fact esportivo.

## N10.11.10

- Variante 256 corrompe: regenerate sem alterar Player.
- Replacement cria URL/key diferente; cache antigo não mostra bytes incorretos sob a mesma key.

# 12. N3.11.11 — Player Avatar

## N4.11.11.01 — Attachment canônico

Player guarda referência:

```text
players.avatar_asset_id nullable
```

FK para `MediaAsset` READY/attachable conforme command semantics.

Não guardar URL como vínculo autoritativo.

## N5.11.11 — Global Player ≠ Community-owned image

Como Player é identidade esportiva global, a autoridade de alteração de avatar global precisa ser compatível com Identity/PlayerAccountLink e políticas próprias.

Não herdar automaticamente:

```text
Community OWNER/ADMIN
→ global player avatar control
```

A Community pode futuramente possuir apresentação contextual de um CommunityPlayer, mas isso é outro attachment e não muda silenciosamente o avatar global.

## N5.11.11.02 — Player sem account

Player pode existir sem User.

Então o produto precisa suportar policy explícita para quem pode propor mídia desse Player.

Possibilidades:

- responsável/criador legado durante migração;
- Organizer com capability específica;
- Community contextual proposal;
- platform-mediated resolution.

A decisão final de capability será fechada junto do modelo de Identity, sem reintroduzir “admin alto o bastante”.

## N6.11.11 — Commands

```text
ProposePlayerAvatar
ApprovePlayerAvatarProposal
RejectPlayerAvatarProposal
AttachPlayerAvatar
ReplacePlayerAvatar
DetachPlayerAvatar
```

A UI pode colapsar algumas dessas etapas conforme policy, mas o modelo mantém semântica.

## N8.11.11 — Concurrent replace

Dois replacements simultâneos usam:

```text
expected player/profile revision
```

ou semantic uniqueness/current proposal rules.

Não decidir pelo último `updated_at` de client.

## N10.11.11

- Player tem avatar A; upload B falha: A continua ativo.
- B fica READY, mas attach falha por revision: A continua ativo; B vira unattached candidate/orphan elegível a cleanup depois do grace period.
- Dois tabs substituem avatar: um vence via revision/command semantics, o outro recebe conflict; nenhum LWW silencioso.

# 13. N3.11.12 — Community Media

## N4.11.12.01 — Attachments explícitos

Candidate fields:

```text
communities.avatar_asset_id
communities.cover_asset_id
```

Não criar um polymorphic `owner_type/owner_id` genérico para tudo quando FKs tipadas são possíveis.

## N10.11.12

# 16. N3.11.15 — Visibility / Public Delivery

## N4.11.15.01 — Visibility semântica

Candidate enum:

```text
PRIVATE
CONTEXTUAL
PUBLIC
```

`CONTEXTUAL` significa visível apenas mediante autorização do domínio correspondente, por exemplo Community.

Não confundir com bucket físico.

## N5.11.15 — Hybrid delivery

Duas alternativas extremas:

### Tudo público

Prós:

- cache/CDN simples;
- baixa latência.

Contras:

- impossível controlar assets privados/contextuais;
- pending candidates podem vazar se modelados mal;
- revogação é fraca.

### Tudo por signed URL

Prós:

- autorização explícita;
- melhor revogação lógica.

Contras:

- overhead de geração;
- cache público menos eficiente;
- mais dependência de auth/API para assets realmente públicos.

### Target híbrido

```text
PUBLIC approved deliverable variant
→ public delivery/CDN allowed

PRIVATE/CONTEXTUAL variant
→ authorized/signed delivery

INCOMING/PENDING
→ never public
```

## N5.11.15.02 — Signed URL nunca é identidade persistente

Não persistir signed URL em Player/Community.

Ela é efêmera.

## N5.11.15.03 — Public → private não é revogação perfeita

Se um asset já foi publicado na Internet:

- pode estar em cache;
- pode ter sido copiado;
- terceiros podem ter salvo.

Ao mudar visibilidade:

1. remover/retirar variante pública;
2. interromper novas entregas públicas;
3. usar delivery privado daí em diante;
4. aceitar que cópias externas passadas não são tecnicamente recuperáveis.

Produto/privacidade não deve prometer apagamento retroativo da Internet.

## N5.11.15.04 — Entity privacy caps media visibility

Mídia não amplia visibilidade da entidade.

Exemplo:

```text
private/contextual Player profile
+
asset marked PUBLIC accidentally
```

não autoriza UI/query a revelar o Player.

Attachment/delivery policy deve considerar o contexto consumidor.

## N10.11.15

- Pending avatar URL não existe como public deliverable.
- Signed URL expira e nova pode ser emitida sem alterar MediaAsset.
- Asset público é alterado para private: old public representation é retirada, novas queries exigem autorização.

# 17. N3.11.16 — Replacement / Detach

## N4.11.16.01 — Replacement é criação + troca de ponteiro

Fluxo:

```text
Current Asset A attached
        ↓
Upload/process Asset B
        ↓
B READY (+ moderation if required)
        ↓
atomic domain command
A attached → B attached
        ↓
A becomes unattached/retained until cleanup policy
```

Não fazer:

```text
overwrite bytes of Asset A
```

## N5.11.16 — Failure safety

Se qualquer etapa antes do pointer switch falhar:

```text
A remains active
```

Isso reduz broken avatars.

## N5.11.16.02 — Detach

Detach remove a referência do domínio.

Não precisa synchronously deletar blobs dentro da mesma transaction.

```text
BEGIN
  authorize
  detach FK
  record audit/outbox if needed
COMMIT
↓
GC later
```

## N8.11.16 — Idempotência

`ReplacePlayerAvatar`/equivalentes usam `command_id`.

Timeout após commit:

```text
retry SAME command_id
→ same authoritative result
```

## N10.11.16

- Storage delete de A falha depois de B attached: B continua correto; A vira orphan para retry/GC.
- Response do replace se perde: retry não cria nova promoção.
- Detach chamado duas vezes: estado final é sem avatar, sem double side effect perigoso.

# 18. N3.11.17 — Orphan Cleanup

## N4.11.17.01 — Orphan é estado técnico, não delete imediato

Assets podem ficar sem attachment por:

- upload abandonado;
- processing concluído mas user desistiu;
- proposal rejeitada;
- replacement conflict;
- old asset após replacement;
- falha entre Storage e DB.

Não deletar imediatamente ao menor sinal de ausência.

## N5.11.17 — Grace period

GC exige:

```text
unattached
+
not protected by pending proposal
+
not referenced by domain/audit retention requirement
+
older than grace threshold
```

Threshold final é policy operacional, não número inventado neste documento.

## N5.11.17.02 — Raw incoming sweeper

Separado do final orphan GC:

```text
expired upload intents
→ delete incoming objects

successful processing
→ delete raw incoming after safe checkpoint
```

## N5.11.17.03 — Idempotent GC

Deletion deve tolerar:

```text
object already absent
worker duplicate
retry after timeout
```

## N8.11.17 — DB ↔ object integrity

Precisamos de auditoria periódica:

```text
DB variant says object exists, Storage missing
Storage object exists, DB has no valid reference
```

A resposta difere:

- missing derived variant → regenerate se master existe;
- missing master/public asset → alert/recovery;
- orphan object → quarantine/delete após policy.

## N10.11.17

- Worker processa orphan twice: segunda delete é harmless.
- Asset acabou de ser criado e ainda será attached: grace evita race com GC.
- Manual deletion no Storage remove variante ativa: integrity check detecta.

# 20. Cross-cutting — Processing Architecture

## N4.11.19 — Onde o processing executa

Não introduzir um Media microservice independente V1 sem necessidade.

Arquitetura inicial preferida:

```text
Application/API
  → creates upload intent

Supabase Storage
  → receives private raw object

Server-side worker / controlled function
  → decode/sanitize/re-encode
  → writes MediaAsset/MediaVariant state
```

A implementação pode usar Edge Function, worker server-side ou runtime adequado aos codecs/limites necessários.

A escolha depende de benchmarks de:

- memory;
- CPU;
- timeout;
- image library availability;
- concurrency;
- operational simplicity.

Não congelar Edge Function se a carga de image processing ultrapassar seus limites reais.

## N5.11.19 — Explicit finalize vs Storage webhook

Duas estratégias:

### Storage event/webhook only

Prós:

- processing automático mesmo se browser fechar.

Contras:

- delivery/event duplicado precisa ser tratado;
- debugging mais indireto;
- acoplamento a event integration do provider.

### Explicit `FinalizeMediaUpload` + sweeper/recovery

Prós:

- command/application flow explícito;
- fácil correlacionar intent;
- fácil idempotência;
- menor complexidade inicial.

Contras:

- browser pode fechar após upload sem finalize.

**Target V1:** explicit finalize + sweeper/recovery para uploaded-but-unfinalized objects.

Storage event pode ser adicionado depois como acelerador/recovery, nunca como fonte única sem idempotência.

## N8.11.19 — Processing idempotency

Processor identifica trabalho por:

```text
asset_id
+
source object/checksum
+
processing_policy_version
```

Duplicate execution não cria variants conflitantes.

# 24. Cross-cutting — Reliability / Failure Modes

## N4.11.23 — Storage outage

Se Storage estiver indisponível:

```text
Media operations degrade
core Registration/Match/Competition facts remain operational
```

Media não deve ser dependência síncrona de comandos esportivos críticos.

## N5.11.23 — Failure matrix

### Upload falha

- intent permanece/expira;
- attachment atual não muda.

### Upload completa, finalize falha

- incoming object permanece privado;
- retry same command/idempotency;
- sweeper identifica stale unfinalized.

### Processing falha transient

- `FAILED`/retryable technical state;
- retry bounded.

### Processing rejeita arquivo

- `REJECTED` domain-technical result;
- não retry infinito.

### Processou, DB update response se perdeu

- worker/idempotency reconcilia estado.

### Variant upload falhou depois do master

- retry gera variant;
- MediaAsset só vira attachable READY quando required variants estiverem consistentes.

### Delete orphan falhou

- retry/GC posterior;
- não rollbackar attachment novo.

## N5.11.23.02 — Poison processing

Após número bounded de retries técnicos:

```text
FAILED_PERMANENT / manual or policy review
```

Não deixar um asset ruim bloquear a fila inteira.

## N5.11.23.03 — Backup ≠ object durability

DB backup não garante que blobs estão restauráveis.

Recovery drills devem validar:

```text
DB references
↔
Storage objects
↔
regenerable variants
```

## N10.11.23

- Postgres restaurado para ponto anterior e Storage contém objetos mais novos: integrity job identifica orphans.
- Storage restaurado faltando variant derivada: regenerate do master quando possível.
- Storage perde sanitized master e public variant existe: alert; não fingir que DB backup resolveu blob loss.

# 31. Migração do fluxo atual

## N4.11.30 — Problema da migração

Hoje existem:

```text
players.avatar_url
player_avatar_proposals.image_url
public avatars bucket
proposals/* public objects
```

Não podemos simplesmente trocar o tipo de coluna e perder imagens existentes.

## N5.11.30 — Estratégia expand → migrate → switch → contract

### Fase A — Expand

Criar:

```text
media_assets
media_variants
media_upload_intents
player avatar_asset_id
new processing path
```

Mantendo `avatar_url` legível temporariamente.

### Fase B — Inventory

Classificar URLs existentes:

```text
known avatars bucket
external/unknown URL
missing object
invalid URL
```

Não assumir que todo `avatar_url` é um objeto válido do bucket apenas pelo prefixo esperado.

### Fase C — Import known legacy media

Para cada asset legado controlado:

1. ler bytes server-side;
2. processar com policy de migração;
3. produzir sanitized master/variant;
4. criar MediaAsset;
5. preencher `avatar_asset_id`;
6. manter legacy field durante compatibility window.

### Fase D — Unknown/external URLs

Não baixar automaticamente qualquer URL arbitrária sem SSRF controls.

Options:

- exigir reupload;
- importar por allowlist controlada;
- manter legacy read fallback temporário.

Decisão por inventory.

### Fase E — Switch write path

Novos avatars só passam pelo Media pipeline.

Bloquear novas gravações de `avatar_url`.

### Fase F — Verify

Comparar:

```text
legacy players with avatar
vs
new players with valid asset attachment
```

Smoke test visual + integrity checks.

### Fase G — Contract

Remover:

```text
avatar_url write path
legacy public proposal upload
legacy proposal URL contract
```

Após compatibility window.

## N8.11.30 — Existing public candidates

Pending/rejected candidates já publicados merecem cleanup específico após migração e retention review.

Não deixar `proposals/` público indefinidamente apenas porque era legado.

## N10.11.30

- Legacy URL aponta objeto inexistente: migration registra anomaly, não cria READY asset falso.
- Legacy URL externa: não faz server-side fetch irrestrito.
- Migration interrompe no meio: backfill é resumable/idempotent.
- Old frontend durante compatibility window continua lendo fallback; não consegue gravar novo unsafe URL após switch.

# 32. N10 — Adversarial / Failure Acceptance Matrix

Os cenários abaixo devem virar testes automatizados, integration tests, security tests ou operational drills conforme a camada.

## N10.11.01 — Format spoofing

1. `.jpg` contém bytes não-image → reject.
2. `Content-Type: image/png` contém outro formato não permitido → reject.
3. SVG renomeado para `.png` → reject.
4. GIF animado com extensão `.jpg` → reject.
5. arquivo truncado → reject.

## N10.11.02 — Resource exhaustion

6. compressed image pequena com decoded pixels gigantes → reject por pixel budget.
7. width aceitável e height absurda → reject.
8. muitos uploads simultâneos → bounded processing concurrency.
9. user repete arquivo malicioso → rate-limit/abuse signal.
10. processor OOM/crash → lease expira, fila continua; asset não vira READY.

## N10.11.03 — Metadata/privacy

11. EXIF GPS → absent final media.
12. camera serial/model → absent se não necessário.
13. original filename com PII → não entra em public object key.
14. rejected raw asset → nunca publicamente entregue.

## N10.11.04 — Upload intent

15. expired intent → cannot finalize/promote.
16. replay same finalize with same command → one logical asset/result.
17. wrong object key → reject.
18. wrong purpose on finalize → server ignores/rejects mutation against registered intent.
19. user B guesses user A intent → reject.
20. leaked signed upload authorization → bounded key/scope/TTL.

## N10.11.05 — Authorization/BOLA

21. user guesses MediaAsset UUID of another Community → cannot attach/read private variant.
22. Organizer tries Community cover update without governance capability → reject.
23. Community Admin tries global Player avatar action without player-media capability → reject.
24. Session Organizer tries Competition logo update → reject.
25. browser direct-write to public delivery bucket → reject.

## N10.11.06 — Processing/moderation separation

26. human approves raw incoming object → impossible; proposal requires READY asset.
27. auto-approval path receives PROCESSING asset → waits/rejects, never bypasses.
28. technically safe asset rejected by moderation → remains unattached.
29. technically invalid asset cannot be manually overridden into READY via ordinary UI.

## N10.11.07 — Replacement/concurrency

30. current avatar A, B upload fails → A stays.
31. B READY but attach conflict → A stays.
32. two concurrent replacements → optimistic conflict, no timestamp LWW.
33. response lost after successful replace → retry same command returns same result.
34. old public A remains cached → B uses immutable different key; domain points to B.

## N10.11.08 — Worker/idempotency

35. same process job executes twice → one effective set of variants.
36. worker dies after writing variant before DB ack → retry reconciles/dedupes.
37. poison asset retries bounded then isolates.
38. bad asset does not block later assets in queue.

## N10.11.09 — Garbage collection

39. raw incoming after successful processing → eventually deleted.
40. abandoned upload intent → incoming removed after expiry/grace.
41. unattached READY asset younger than grace → not deleted.
42. pending proposal asset → protected from orphan GC.
43. duplicate GC execution → harmless.
44. delete provider timeout → retry; active domain state unchanged.

## N10.11.10 — Integrity/recovery

45. DB references missing variant → alert/regenerate if possible.
46. Storage contains DB-orphan object → quarantine/delete after policy.
47. DB restore older than Storage → orphan scan catches newer blobs.
48. Storage restore loses derived variant but master survives → regenerate.
49. master missing → no silent success; operational incident/anomaly.

## N10.11.11 — Visibility

50. private asset has no permanent public URL.
51. public asset can use long immutable caching.
52. public → private removes future public delivery, without promising erasure of copies already made.
53. signed URL expiry does not invalidate MediaAsset.

## N10.11.12 — Account/privacy lifecycle

54. uploader account deleted → attached asset does not disappear by auth cascade.
55. avatar detached on privacy request where applicable → sports facts remain.
56. Player merge does not duplicate raw media or rewrite Match history; attachment resolution follows merge policy.
57. archived Community retains/deletes media according to lifecycle/retention, not universal `deleted_at`.

## N10.11.13 — Offline/client

58. offline preview never changes shared avatar.
59. browser canvas sanitizes successfully → server still validates.
60. browser canvas fails and sends raw original → server policy still protects system.

## N10.11.14 — Policy evolution

61. old asset processed under V1 remains labeled V1.
62. V2 changes encoder → no silent claim that V1 was processed by V2.
63. codec CVE discovered → assets by affected policy/version can be identified for quarantine/reprocess.
64. new file format support requires explicit policy/version/tests.

# 34. ADRs congelados neste contexto

## ADR-0147 — `MediaAsset` é a identidade canônica de mídia

Domain consumers referenciam `MediaAsset.id`, não URL.

## ADR-0148 — Storage URL/path é infraestrutura, não identidade de domínio

Delivery descriptors são resolvidos na query/infrastructure layer.

## ADR-0149 — Todo upload entra em zona incoming privada

Pending/raw candidates nunca ficam em public delivery zone.

## ADR-0150 — Validação/decode/saneamento/re-encode server-side são obrigatórios

Browser processing não é boundary de confiança.

## ADR-0151 — Client resize/compression é somente otimização

Pode permanecer para bandwidth/UX sem substituir processing do servidor.

## ADR-0152 — V1 aceita raster allowlist e rejeita SVG/animação

Base: JPEG/PNG/WebP; outros formatos exigem ADR/policy explícita.

## ADR-0153 — Technical processing e content moderation são lifecycles separados

`READY` não significa automaticamente `APPROVED AS AVATAR`.

## ADR-0154 — Attachments centrais usam FKs tipadas em vez de ownership polymorphic genérico

Player/Community/Competition mantêm referências explícitas.

## ADR-0155 — Media publicada é imutável; replacement cria novo asset/variant

Nunca sobrescrever bytes sob a mesma identidade/cache key para simular nova mídia.

## ADR-0156 — Delivery usa modelo híbrido por visibilidade

PUBLIC aprovado pode ser público/CDN; PRIVATE/CONTEXTUAL usa autorização/signed delivery.

## ADR-0157 — Signed URLs não são persistidas como identidade

São artefatos efêmeros de entrega.

## ADR-0158 — Sem cross-user content-addressed dedupe V1

Checksum serve integridade/idempotência; não cria ownership compartilhado global.

## ADR-0159 — Raw incoming é descartado; sanitized master pode ser retido privadamente

Permite reprocessar variantes sem preservar EXIF/raw inseguro.

## ADR-0160 — Orphan cleanup é eventual, idempotente e protegido por grace/reference checks

Delete de blob não participa da transação crítica de replacement.

## ADR-0161 — Quotas e rate-limits fazem parte do lifecycle de upload

Bucket file-size limit sozinho não controla abuse/custo.

## ADR-0162 — V1 usa Storage adapter + processing server-side, sem Media microservice obrigatório

Separação lógica não exige serviço distribuído prematuro.

## ADR-0163 — Mídia de apresentação é independente da história esportiva

Match/Session history não congela avatar por padrão.
