# 2. W0 — Safety / Inventory / Executable Foundations

## XS-W0-01 — Freeze architecture-risk expansion

### Goal

Prevent new work from deepening paths already marked for retirement.

### Required repository guardrails

Add/revise architecture fitness rules so new target code does not introduce:

```text
new shared-domain dependency on syncService
new target entity cloudId/local_id pair
new target generic syncStatus state
new target direct critical browser table CRUD
new authorization derived from client role text
new use of updated_at as conflict resolver
new broad domain localStorage key
new Overall dependency in balancing objective
```

### Important nuance

Do not make legacy tests fail merely because legacy still exists.

Fitness rule should distinguish:

```text
LEGACY ALLOWLISTED PATH
vs
NEW TARGET PATH
```

and include an explicit removal trigger.

### Evidence

- architecture test/ESLint/import-rule where practical;
- PR review template references C6 slice/authority;
- C7 later checks stale allowlists.

### Exit gate

New code cannot accidentally expand the largest known legacy coupling without an explicit exception.

## XS-W0-05 — Introduce command execution foundation

```text

```

```text

```


### Persistence foundation


```text

CONFLICT
TECHNICAL_FAILURE
OFFLINE_UNAVAILABLE
UNKNOWN_OUTCOME
```

### Exit gate

At least one non-destructive target command can execute end-to-end through Application→RPC with server-derived actor, stable result and retry semantics.

W2 is the first major shared-state authority migration.

## XS-W2-01 — Safe account↔Player relation expansion

### Target

Introduce explicit `PlayerAccountLink` relation rather than treating direct `players.user_id` as permanent ownership semantics.

### Schema expand

Conceptually:

```text
player_account_links
├── id
├── player_id
├── user_id
├── status
├── provenance/source
├── created_at
└── reviewed/activated metadata where needed
```

Do not finalize multi-profile constraints until `HYP-ID-001`/relevant Open Decisions are ready. Initial constraints may reflect the accepted V1 assumption only if documented as such.

### Backfill

Only explicit trustworthy current links become active target links.

Ambiguous legacy links:

```text
migration anomaly
not guessed active link
```

### Command path

Target commands:

```text
Propose/ClaimPlayerAccountLink
ApprovePlayerAccountLink (policy dependent)
Reject/Cancel link request
Unlink according to privacy/history policy
```

Exact approval authority remains blocked by `OPEN-ID-001` before broad claim flow.

### Compatibility

Read adapter may prefer target active link and fall back to direct field for not-yet-migrated legacy rows. New target writes do not create new direct-link authority.

### Exit gate

Target authorization/identity lookup for migrated cohort does not require `players.user_id` as authority.

## XS-W2-02 — Split CommunityMembership from CommunityPlayer

### Schema expand

Target relations:

```text
community_memberships
community_players
community_join_requests
```

Where:

```text
CommunityMembership
= User access/governance

CommunityPlayer
= Player sports relationship

CommunityJoinRequest
= pending approval intent
```

### Migration

Classify legacy rows by what source data actually proves.

Never infer:

```text
admin account must be Player
Player must have account
pending join is effective Membership
legacy player/guest role is governance
```

### Constraints

At minimum:

- effective Membership uniqueness per Community/User;
- CommunityPlayer uniqueness per Community/Player;
- one pending JoinRequest per Community/User where policy requires;
- FK delete semantics preserving historical relationships appropriately.

### Exit gate

Tests cover:

```text
Admin not Player
accountless CommunityPlayer
User+Player with both relations
JoinRequest without Membership
```

### Target


## XS-W2-04 — Community ownership invariant

### Target command

```text
CreateCommunity
TransferCommunityOwnership
LeaveCommunity
RemoveMember
SuspendMember
```

### Transaction rules

`CreateCommunity` commits root + OWNER Membership atomically.

`TransferCommunityOwnership` preserves exactly one active Owner after commit.

Current owner cannot leave/be removed/suspended in a way that produces ownerless active Community.

### Database evidence

Use DB constraints where expressible plus semantic transaction checks.

### Concurrency tests

Two transfers racing must not yield:

```text
0 owners
2 owners
```

### Exit gate

Community authority for migrated cohort uses target semantic commands and membership state, not generic `communityCloudService.upsert()`.
