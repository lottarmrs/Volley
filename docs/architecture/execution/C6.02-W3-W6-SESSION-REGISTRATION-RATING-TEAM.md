# 0. Goal

W3–W6 moves the core pre-Match workflow from broad mutable Session/Team arrays into explicit authoritative artifacts:

```text
Session
→ RegistrationWindow
→ RegistrationEntry
→ RosterRevision
→ PlayerBalanceSnapshot
→ CandidateSet
→ optional VotingRound
→ TeamDraw
→ confirmed TeamDraw
→ Match preparation
```

The pack is complete only when **new target Sessions no longer require `selectedPlayerIds[]`, `teamIds[]`, generic cloud mutation or Player Overall authority to progress through this flow**.

### Decisão de escopo (2026-09-10, verificada em 2026-09-13)

Inserida depois da XS-W3-07 porque a cadeia W3 → W6 pressupunha Session target que nada no cliente
criava. Implementada conforme o
[spec da W3-08](../../superpowers/specs/2026-09-10-xs-w3-08-target-cohort-reachability-design.md), na
branch `exec/c6-w3-08-target-cohort-reachability`, **não integrada**. Alcançabilidade re-derivada em
[`C6-REACHABILITY-MAP.md`](C6-REACHABILITY-MAP.md).

Entregou, em commits `d4ad525`, `139bd51`, `da7fd16`, `8a4af23`, `04fd199`, `fd3f1e2` e `88e3475`:
`read_target_session` devolvendo `current_roster_revision_id` com a mesma definição de "corrente" da
captura; o marcador local `Session.authorityModel`; o upload deixando de subir a raiz marcada; o
`syncNow` lendo por id cada Session marcada; `set_community_organizer`, que concede e revoga
`ORGANIZER`; e o sync criando pelo `create_target_session` a Session nova de comunidade com o modelo de
avaliação ativado, sem cair para o legado quando a criação falha ou quando a consulta de ativação
falha.

A review final de branch inteira abriu uma rodada de correção: `fe131b0` preserva o `communityId`
local no merge da leitura por id; `25992d4` faz a criação adotar a Session por leitura quando
`create_target_session` responde `23505` (`sessions_pkey`) — comportamento observado contra o banco
real, sem replay idempotente — o que cobre tanto a cópia obsoleta que perdeu marcador e `cloudId`
quanto a resposta perdida depois do commit; e `95656c2` filtra para UUID os ids enviados à consulta de
ativação, para que um id local de comunidade não derrube a consulta de todas as Sessions; e `67ac1af`
deixa de chamar `softDelete` ao excluir uma Session target — um no-op filtrado pela RLS que o sync
registrava como sucesso — e reporta um problema naquela rodada.

**O cutover da XS-W3-07 não tem alvo neste app.** A ligação de `transition_legacy_session_to_target` a
um botão foi implementada e revertida (`2fae047` → `a320106`): uma Session só entra em `sessions` via
`confirmDivision`, que grava `teams_generated` e cria times, e fica bloqueada por `NOT_DRAFT` e
`HAS_TEAM_EVIDENCE`; o rascunho do wizard nunca sobe; e `buildManualSessionDraft`, o único caminho
que produziria um rascunho sem times, não tem chamador. Os comandos do cutover continuam corretos e
testados no banco, sem nada real contra o que rodar.

**Fronteiras que esta fatia não cruza:** não liga captura (`capture_balance_input_snapshot`) nem
publicação de candidatos — isso é a XS-W6-03, e a captura continua inalcançável. Nenhuma tela chama
`set_community_organizer`, então a criação target só alcança os organizadores do backfill de
`20260827150000`; quem é promovido pela interface não ganha `ORGANIZER`. Times e jogos de Session
target continuam no sync genérico. Nada muda para comunidade não ativada.

**Problemas conhecidos:**

- um membro de comunidade ativada sem `ORGANIZER` que cria Session localmente recebe `42501` de
  `create_target_session` a cada sync, sem saída pela interface. Sem perda de dado; a Session fica
  pendente;
- a Session target é invisível em outro aparelho: o download em lote filtra `sessions` para legado
  (`operationalCloudService.ts:72`) e a leitura target só acontece por um `cloudId` guardado
  localmente. `teams` e `games` são baixados sem esse filtro e chegam sem a Session-pai;
- excluir uma Session target não se propaga: o upload não chama `softDelete` para ela (a policy de
  update só casa linha legada e o filtraria em silêncio, com sucesso falso) e reporta um problema
  naquela rodada; a Session local é removida pelo filtro `visible` do retorno e a linha continua viva
  no servidor. Mantê-la pendente exigiria trocar esse filtro, o que muda também o legado;
- promover a organizador pelo app ainda não concede `ORGANIZER`: `set_community_organizer` não tem
  chamador em `src/`.

# 3. W4 — Registration / Waitlist

Registration is largely additive, which allows a cleaner target-first implementation.

---

## XS-W4-01 — Registration schema and invariants

### Target tables

```text
registration_windows
registration_entries
```

Possible supportive audit/event structures only when needed; do not implement full event sourcing by default.

### Window fields

Conceptually:

```text
id
session_id
capacity
status
revision
opened_at/closed_at/locked_at
```

### Entry fields

Conceptually:

```text
id
window_id
player_id / resolved participant identity as policy requires
status = CONFIRMED | WAITLISTED | WITHDRAWN | REMOVED
queue_sequence nullable/required by waitlist status
source
created_at
```

`PROMOTED` is event/action/provenance, not enduring status.

### Constraints/indexes

At minimum:

```text
one active effective entry per window/player
queue_sequence unique where authoritative waitlist position applies
indexes for first eligible waitlisted entry
```

Capacity invariant is enforced by serialized command transaction, not a naive standalone CHECK over multiple rows.

### Exit gate

Schema can support last-slot race without client-side counting.

---

## XS-W4-02 — Open/Close/Lock Registration lifecycle

### Target commands

```text
CreateRegistrationWindow
OpenRegistration
CloseRegistration
ReopenRegistration (only after OPEN-REG-006 closes)
LockRegistration
ChangeRegistrationCapacity
```

### Baseline lifecycle

```text
DRAFT → OPEN → CLOSED → LOCKED
```

`CLOSED` blocks new Join but may still allow existing confirmed Leave + automatic promotion until `LOCKED`, according to N2.05.

### Capacity reduction

Default target behavior blocks capacity reduction below confirmed count rather than silently demoting participants.

### Exit gate

No UI row update can bypass lifecycle/capacity policy.

---

## XS-W4-03 — JoinRegistration authoritative transaction

### Input

Client sends intent, not arbitrary Player identity for self-join.

Server resolves:

```text
auth User
→ active Membership
→ linked Player
→ CommunityPlayer / eligibility
→ RegistrationWindow
```

### Transaction

```text
BEGIN
lock RegistrationWindow
revalidate OPEN + eligibility
check existing active entry
if confirmed_count < capacity
  create CONFIRMED
else
  allocate monotonic queue_sequence
  create WAITLISTED
increment revision
save command receipt where required
COMMIT
```

### Response

Return authoritative result:

```text
CONFIRMED | WAITLISTED
revision
minimal relevant counts/status
```

`WAITLISTED` is a successful business outcome.

### Tests

Two simultaneous users for last slot:

```text
exactly one CONFIRMED
other WAITLISTED
```

100-user burst must preserve capacity and FIFO sequence uniqueness.

### Offline

`ONLINE_AUTHORITATIVE`; no generic outbox replay.

---

## XS-W4-04 — LeaveRegistration + promotion atomicity

### Transaction

```text
BEGIN
lock window
mark confirmed entry WITHDRAWN
find first eligible WAITLISTED by queue_sequence
revalidate eligibility
promote within same transaction if candidate exists
increment revision
COMMIT
```

If first waiter became ineligible, apply the explicit skip/remove policy once `OPEN-REG-002` is resolved enough for implementation. Do not silently grant a later user while losing audit of why earlier candidate was skipped.

### Critical invariant

No asynchronous notification/provider step occurs between Leave and promotion.

### Tests

- failure injection between withdrawal/promotion rolls back both;
- concurrent new Join cannot bypass an existing eligible waiter;
- capacity increase promotes in FIFO order.

# 5. W6 — Team Formation / Voting

## XS-W6-01 — PlayerBalanceSnapshot resolver

### Scoped implementation decision (2026-09-08)

Implemented for target COMMUNITY Sessions only, as a private immutable artifact plus two semantic
RPCs, per the
[W6-01 spec](../../superpowers/specs/2026-09-08-xs-w6-01-balance-input-snapshots-design.md).
The user's explicit missing-score policy is versioned as `v0-global-roster-mean-5`: a dimension the
evaluated roster never observed is resolved by the roster mean of observed values, and by 5 when the
roster has no observation at all. Estimates never feed the mean and never overwrite an observed
value; every estimated dimension is listed explicitly. The private W5-04 global profile is the only
evaluation source — no legacy attribute, self-evaluation, Overall, form or display rating enters the
vector.

**Boundaries this slice does not cross:** the trusted input resolver exists, but the legacy wizard's
sorter stays on its prior path, candidate publication is not integrated, and the broad W5-05 source
cutover is not claimed. A returned snapshot stays tied to its original roster; downstream candidate
publication must revalidate the current roster and configuration independently. The local Quick
resolver described below is untouched.

### Target

For one `RosterRevision`, resolve immutable participant-centric snapshots containing only canonical solver inputs and provenance.

Conceptually:

```text
participant_id
player_id optional
attribute vector by rubric/version
positions/roles
explicit constraints
confidence/coverage diagnostics
source profile versions
captured_at
```

### Rules

- Overall absent from canonical solver contract;
- missing never silently becomes zero;
- current Player mutation after snapshot does not change existing generation.

### Shared authority

For Community/shared Session, server produces/authorizes trusted snapshot. Client may compute with it.

### Quick

Local resolver is allowed for local-owned Quick using locally frozen data; handoff/publish later revalidates according to target policy.

## XS-W6-02 — TeamFormationRequest / deterministic solver port

### Scoped implementation decision (2026-09-09)

Implemented per the
[W6-02 spec](../../superpowers/specs/2026-09-09-xs-w6-02-team-formation-port-design.md). The port
defines its own normalized `TeamFormationRequest`, independent of both the local snapshot shape and
the W6-01 authorized snapshot, with two adapters translating each into it. Accepting only the
server artifact would have excluded Quick Session and any cloudless session, and would have
performed the W5-05 source cutover this slice does not claim.

Both existing call sites — `useSessionWizard`'s Worker path and `sessionLifecycleUseCases`'s direct
path — now route through the port, producing the same options as before: no behavior change for any
user. The feasibility precheck detects only mechanical contradiction in the request itself (empty
roster, `teamCount < 1`, fewer participants than teams, a pair marked both together and separated, a
`pairsTogether` pair naming a participant absent from the roster, or a locked index for a present
participant outside range) — never difficulty. An id in `pairsSeparated` or `lockedPlayerIdxs` that
is absent from the roster is tolerated, not refused: the engine already handles that case correctly
(see the facts below). Whether a satisfiable but demanding combination should be refused is product
policy, still open.

The parity exit gate — direct driver and Worker driver agree on the canonical fingerprint for the
same input — is proven by invoking the Worker module's own `onmessage` handler against a stubbed
`self`, not by a real browser Worker. jsdom has no `Worker` implementation, so the gate covers the
Worker's code path (contract, serialization, routing) and not the browser runtime itself.

**Boundaries this slice does not cross:** no source cutover (the wizard does not consume the
authorized snapshot yet), no candidate publication, no voting, no UI change, no new hard constraint.

**Facts that came out of execution, not the plan:**

- The engine was already deterministic before this slice: `createSeededRandom` drives the search
  from `config.balanceSeed`, the budget is an iteration count, and `Date.now()` only fills the
  reported `BalanceCandidate.runtimeMillis`, which never controls the search. This slice gave the
  engine a contract; it did not make it deterministic.
- The spec's algorithm guard, as first written, compared `algorithmVersion` against the `algorithm`
  string the engine reports — that field is `'Simulated Annealing (Smart Balance Engine)'`, a display
  string, so the comparison was unimplementable. The design was corrected to compare against the
  exported `BALANCE_ALGORITHM_VERSION` constant instead, and that guard shipped in the first version
  of this slice. It was then **deleted entirely** in the branch-wide review's fix wave (`6247b9d`):
  both adapters stamp `BALANCE_ALGORITHM_VERSION` onto the request themselves, and the port is the
  only production caller, so the comparison checked the constant against itself and could not fail
  without a hand-written caller. There is no `ALGORITHM_VERSION_MISMATCH` refusal any more.
  `algorithmVersion` still exists on the request and still enters the fingerprint as provenance, but
  nothing validates it at runtime. Closing that for real needs `BalanceCandidate` to carry a
  machine-readable version beside its display string, or a caller outside the two adapters — neither
  exists yet.
- The first version of the precheck refused any `hardConstraints` id absent from `participants`,
  including `pairsSeparated` and `lockedPlayerIdxs`. That was a real regression: the engine already
  tolerates an orphan id in those two (`buildInitialSolution` guards placement with `if (athlete)`,
  the lock penalty and `isFeasible` skip a lock whose id resolves to `currentIdx === -1`, and an
  orphaned `pairsSeparated` pair is vacuously satisfied), so the precheck was refusing requests the
  engine could satisfy fine — and the wizard reaches exactly that state whenever someone locks a
  player, goes back a step, and deselects them. The branch-wide review caught it before integration;
  the fix (`471e81b`) narrowed the precheck to refuse only an orphan in `pairsTogether`, which has no
  such tolerance.
- A precheck refusal on the synchronous direct path used to resolve to a silent no-op in the wizard:
  no message, no status reset — only a thrown refusal surfaced a message. Fixed in the same fix wave
  (`396fc47`): the synchronous path now resets the generating state and shows the same pt-BR message
  the Worker path shows, and the Worker forwards the refusal's own code instead of collapsing every
  refusal to `INFEASIBLE_CONSTRAINTS`.

### Application port

Introduce domain/application solver interface independent of UI and current `Player[]` shape.

Input includes:

```text
roster revision/snapshot set
team count/size
hard constraints
soft objective policy/version
algorithm version
seed
fixed iteration/work budget
```

### Existing engine reuse


### Eligibility

Voter is derived from frozen eligible confirmed roster + linked User/active membership policy.

Waitlisted and accountless Guest cannot cast authenticated ballot by impersonation.

### Privacy

### One effective vote

Unique effective ballot per VotingRound/User; update/change while OPEN only if chosen product policy allows.

### Exit gate

Direct table insert or actor override cannot create a valid foreign ballot.
