# 0. Goal

W3–W6 moves the core pre-Match workflow from broad mutable Session/Team arrays into explicit authoritative artifacts:

```text
Session
→ RegistrationWindow
→ RegistrationEntry
→ RosterRevision
→ PlayerBalanceSnapshot
→ CandidateSet
→ optional VotingRound
→ TeamDraw
→ confirmed TeamDraw
→ Match preparation
```

The pack is complete only when **new target Sessions no longer require `selectedPlayerIds[]`, `teamIds[]`, generic cloud mutation or Player Overall authority to progress through this flow**.

# 2. W3 — Session normalized backbone

## XS-W3-01 — Introduce target Session root and semantic dimensions

### Target model

Separate:

```text
SessionContext
→ QUICK | COMMUNITY

PlayMode
→ semantic equivalent of FREE_PLAY | STRUCTURED_MATCHES

Competition
→ external bounded context, not Session.type
```

Final enum names remain governed by `OPEN-SES-001`; schema should not freeze ambiguous legacy `tournament/free_play` semantics as the target model.

### Schema expand

Conceptually introduce/add:

```text
sessions
  id UUID final
  context/play-mode fields
  lifecycle status
  planned scheduling fields
  actual started/finished timestamps
  publication state where modeled separately
  community_id nullable for Quick/local handoff semantics as target requires
```

Do not drop legacy columns yet.

### Compatibility

Target Session read mapper may emit legacy `type` for old UI temporarily, but mapping direction is:

```text
target semantic fields
→ compatibility type
```

not target authority inferred repeatedly from old enum.

### Exit gate

A newly created target Session can be read/updated through semantic commands without requiring legacy `type` to decide Competition semantics.

### Target

# 3. W4 — Registration / Waitlist

Registration is largely additive, which allows a cleaner target-first implementation.

---

## XS-W4-01 — Registration schema and invariants

### Target tables

```text
registration_windows
registration_entries
```

Possible supportive audit/event structures only when needed; do not implement full event sourcing by default.

### Window fields

Conceptually:

```text
id
session_id
capacity
status
revision
opened_at/closed_at/locked_at
```

### Entry fields

Conceptually:

```text
id
window_id
player_id / resolved participant identity as policy requires
status = CONFIRMED | WAITLISTED | WITHDRAWN | REMOVED
queue_sequence nullable/required by waitlist status
source
created_at
```

`PROMOTED` is event/action/provenance, not enduring status.

### Constraints/indexes

At minimum:

```text
one active effective entry per window/player
queue_sequence unique where authoritative waitlist position applies
indexes for first eligible waitlisted entry
```

Capacity invariant is enforced by serialized command transaction, not a naive standalone CHECK over multiple rows.

### Exit gate

Schema can support last-slot race without client-side counting.

---

## XS-W4-02 — Open/Close/Lock Registration lifecycle

### Target commands

```text
CreateRegistrationWindow
OpenRegistration
CloseRegistration
ReopenRegistration (only after OPEN-REG-006 closes)
LockRegistration
ChangeRegistrationCapacity
```

### Baseline lifecycle

```text
DRAFT → OPEN → CLOSED → LOCKED
```

`CLOSED` blocks new Join but may still allow existing confirmed Leave + automatic promotion until `LOCKED`, according to N2.05.

### Capacity reduction

Default target behavior blocks capacity reduction below confirmed count rather than silently demoting participants.

### Exit gate

No UI row update can bypass lifecycle/capacity policy.

---

## XS-W4-03 — JoinRegistration authoritative transaction

### Input

Client sends intent, not arbitrary Player identity for self-join.

Server resolves:

```text
auth User
→ active Membership
→ linked Player
→ CommunityPlayer / eligibility
→ RegistrationWindow
```

### Transaction

```text
BEGIN
lock RegistrationWindow
revalidate OPEN + eligibility
check existing active entry
if confirmed_count < capacity
  create CONFIRMED
else
  allocate monotonic queue_sequence
  create WAITLISTED
increment revision
save command receipt where required
COMMIT
```

### Response

Return authoritative result:

```text
CONFIRMED | WAITLISTED
revision
minimal relevant counts/status
```

`WAITLISTED` is a successful business outcome.

### Tests

Two simultaneous users for last slot:

```text
exactly one CONFIRMED
other WAITLISTED
```

100-user burst must preserve capacity and FIFO sequence uniqueness.

### Offline

`ONLINE_AUTHORITATIVE`; no generic outbox replay.

---

## XS-W4-04 — LeaveRegistration + promotion atomicity

### Transaction

```text
BEGIN
lock window
mark confirmed entry WITHDRAWN
find first eligible WAITLISTED by queue_sequence
revalidate eligibility
promote within same transaction if candidate exists
increment revision
COMMIT
```

If first waiter became ineligible, apply the explicit skip/remove policy once `OPEN-REG-002` is resolved enough for implementation. Do not silently grant a later user while losing audit of why earlier candidate was skipped.

### Critical invariant

No asynchronous notification/provider step occurs between Leave and promotion.

### Tests

- failure injection between withdrawal/promotion rolls back both;
- concurrent new Join cannot bypass an existing eligible waiter;
- capacity increase promotes in FIFO order.

---

## XS-W4-05 — FinalizeSessionRoster

### Input

```text
registration_window_id
expected registration revision
command_id
```

### Output

New immutable `RosterRevision` with:

```text
source_registration_revision
confirmed participants only
provenance
```

WAITLISTED never enters roster.

### Staleness

Registration change after finalize marks downstream roster-dependent artifacts stale according to explicit revision comparison; do not mutate prior roster revision.

### Exit gate

Team Formation reads exact RosterRevision, not live Registration rows and not selected-player arrays.

---

## XS-W4-06 — Legacy Session Registration introduction

An upcoming legacy Session can opt into target Registration only via explicit transition.

Record:

```text
starting confirmed roster source
capacity
window status
initial registration revision
legacy queue chronology = UNKNOWN unless proven
```

### Forbidden mapping

```text
CommunityPresence
WhatsApp reserve list
selectedPlayerIds[] timestamp
updated_at
```

cannot be treated as historical FIFO evidence.

### Exit gate

All future Join/Leave actions after transition use target queue sequence; no legacy sync path mutates the target window.

# 4. W5 — Rating / Skill Profile hierarchy

W5 separates subjective evaluation source facts from derived profiles and factual statistics.

---

## XS-W5-01 — Versioned PlayerEvaluation source model

### Target

Evaluation is scoped by:

```text
community
player
evaluator User
rubric/version
attribute dimensions
revision/effective state
```

One evaluator can have one effective evaluation contribution for a Player/Community while historical revisions remain traceable.

### Migration

Current evaluation without trustworthy Community:

```text
LEGACY_UNSCOPED_EVALUATION
```

Preserve as evidence; exclude from official target Community aggregate until explicit attribution.

Do not infer Community merely because Player belongs to one or more Communities.

### Exit gate

New evaluation writes require contextual `player.evaluate` capability and explicit Community scope.

---

## XS-W5-02 — Skill rubric/dimension contract

### Goal

Create a versioned attribute contract without freezing an unresolved final sports rubric silently.

`OPEN-BAL-001` remains blocking for final production-stable dimension set.

Implementation may support an experimental/versioned rubric only if:

```text
version explicit
missing semantics explicit
Overall excluded from source dimensions
migration provenance explicit
```

### Exit gate

Team snapshot resolver can request dimensions by rubric/version instead of reading arbitrary mutable Player fields.

---

## XS-W5-03 — CommunityPlayerSkillProfile projection

### Source

Effective PlayerEvaluation revisions for one Community/Player.

### Projection

Attribute-by-attribute aggregate plus:

```text
source revision/checkpoint
aggregation policy version
confidence/coverage metadata
calculated_at
```

Exact robust estimator remains `OPEN-RATING-001`; do not hide a permanent arithmetic mean as architecture fact.

### Rebuild

Projection can be recomputed from retained source evaluations.

### Exit gate

Projection integrity test compares rebuild to stored result for fixture data.

---

## XS-W5-04 — GlobalPlayerSkillProfile projection

### Source hierarchy

```text
Organizer evaluations
→ Community profile
→ Global profile by Community
```

Not:

```text
all individual evaluators globally averaged
```

This prevents a Community with many evaluators from dominating purely by evaluator count.

### Community credibility

No hidden credibility weighting until `OPEN-RATING-002` closes.

### Derived Overall

Overall may be calculated/displayed from Global profile with explicit formula version, but is not mutable source and not solver input.

### Exit gate

Changing only Overall formula does not alter underlying attribute vector or Team Formation candidate.

---

## XS-W5-05 — Shadow recompute and cutover

### Sequence

1. build target projections in shadow;
2. compare attribute values/coverage against expected fixture/manual reference;
3. investigate legacy differences without forcing parity where legacy semantics are wrong;
4. cut target reads for Team Formation snapshot resolver;
5. keep legacy rating display adapter only if needed.

### Exit gate

Target BalanceSnapshot resolver no longer reads legacy direct/global aggregate path.

# 5. W6 — Team Formation / Voting

---

## XS-W6-01 — PlayerBalanceSnapshot resolver

### Target

For one `RosterRevision`, resolve immutable participant-centric snapshots containing only canonical solver inputs and provenance.

Conceptually:

```text
participant_id
player_id optional
attribute vector by rubric/version
positions/roles
explicit constraints
confidence/coverage diagnostics
source profile versions
captured_at
```

### Rules

- Overall absent from canonical solver contract;
- missing never silently becomes zero;
- current Player mutation after snapshot does not change existing generation.

### Shared authority

For Community/shared Session, server produces/authorizes trusted snapshot. Client may compute with it.

### Quick

Local resolver is allowed for local-owned Quick using locally frozen data; handoff/publish later revalidates according to target policy.

---

## XS-W6-02 — TeamFormationRequest / deterministic solver port

### Application port

Introduce domain/application solver interface independent of UI and current `Player[]` shape.

Input includes:

```text
roster revision/snapshot set
team count/size
hard constraints
soft objective policy/version
algorithm version
seed
fixed iteration/work budget
```

### Existing engine reuse

`src/logic/balancing.ts` and Worker remain reusable infrastructure after contract/objective cleanup.

### Hard vs soft

Feasibility precheck rejects contradictory hard constraints before expensive search.

### Exit gate

Direct solver and Worker solver produce identical canonical fingerprints for same normalized input/version/seed/budget.

---

## XS-W6-03 — CandidateSet publication

### Target concepts

```text
TeamCandidateSet
CandidateSolution[]
```

Candidate set records:

```text
session_id
roster_revision_id
snapshot/input fingerprint
algorithm/objective/policy versions
candidate fingerprints
status
published_at
```

Published set is immutable.

### Server trust boundary

Client may search locally, but publish command revalidates:

```text
roster revision still current/allowed
snapshot identity
hard constraints
trusted objective diagnostics as required
candidate assignment membership
```

Client text claiming “valid” is not trusted.

### Exit gate

A forged candidate that violates hard constraint cannot be published/confirmed.

## XS-W6-04 — Organizer Choice path

Target command:

```text
SelectTeamCandidate
ConfirmTeamDraw
```

`TeamDraw` becomes a revisioned result/provenance artifact.

Manual edit:

```text
creates new draw revision
preserves provenance
must remain hard-valid
```

A hard-valid manually chosen solution may be worse by optimizer score and still be confirmable if policy allows; optimizer is recommendation, not governance authority.

### Concurrency

Two confirmations against same expected draw/roster revision: at most one current confirmation succeeds.

---

## XS-W6-05 — Voting schema and lifecycle

### Target

```text
voting_rounds
ballots
```

Lifecycle:

```text
DRAFT → OPEN → CLOSED → TALLIED → FINALIZED
with INVALIDATED/CANCELLED paths
```

### Eligibility

Voter is derived from frozen eligible confirmed roster + linked User/active membership policy.

Waitlisted and accountless Guest cannot cast authenticated ballot by impersonation.

Organizer cannot submit ballot as another User.

### Privacy

Ballots remain private. Results visibility follows configured policy; default target from C2 favors no individual ballot leakage.

### One effective vote

Unique effective ballot per VotingRound/User; update/change while OPEN only if chosen product policy allows.

### Exit gate

Direct table insert or actor override cannot create a valid foreign ballot.

---

## XS-W6-06 — Close/Tally/Finalize Voting

### Transactional race

`CastVote` racing `CloseVoting` produces one deterministic ordered outcome under DB transaction/lock/revision rules.

### Tie/no-vote

Exact policy remains `OPEN-BAL-007`; current multidimensional-objective fallback is a hypothesis, not a permanent hidden rule.

### Finalization

```text
FinalizeTeamVote
→ validates candidate set still current
→ chooses policy result
→ creates/identifies TeamDraw revision
→ closes logical voting outcome atomically
```

### Roster change

If roster revision changes:

```text
CandidateSet → STALE
VotingRound → INVALIDATED
old ballots preserved as historical evidence
```

No ballots are silently transferred to regenerated options.

---

## XS-W6-07 — ConfirmTeamDraw authority cutover

For target Session:

```text
BEFORE
legacy Teams / team_ids[] can act as mutable authority

AFTER
Confirmed TeamDraw revision
= authority for team formation result
```

Compatibility adapter may render `Team[]` for old UI/read code, but old Team mutation cannot alter target confirmed assignment.

### Match handoff

Match preparation freezes a `MatchRoster` from confirmed TeamDraw; later TeamDraw changes do not rewrite a started Match.

# 8. W3–W6 rollback / forward-fix

## Session/Registration after cutover

Do not revert a target Session to legacy selected-player/team-array authority.

Pause new target Session creation if needed; preserve target authority for already created target Sessions.

## Player Skill Profile projection defect

Because source evaluations remain facts:

```text
fix aggregation version
rebuild projection
```

rather than mutate evaluation history.

## Solver defect

Do not rewrite historical TeamDraw. Ship new algorithm/policy version; regenerate only where workflow allows.

## Voting defect

Do not reassign old ballots to new CandidateSet. Invalidate affected round and run explicit replacement workflow.
