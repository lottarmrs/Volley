# 0. Regra de leitura

Architecture Governance não existe para adicionar cerimônia a toda mudança.

Existe para impedir quatro falhas recorrentes:

```text
1. decisões importantes existirem apenas em conversa/memória;
2. código contradizer arquitetura silenciosamente;
3. legado ganhar novas dependências depois de já ter substituto target;
4. uma otimização/local convenience desfazer invariantes globais.
```

A regra central é:

```text
ARCHITECTURE
=
DECISIONS + CONSTRAINTS + EVIDENCE + OWNERSHIP + EVOLUTION RULES
```

Não apenas diagramas.

E:

```text
GOVERNANCE
≠
CENTRAL TEAM APPROVES EVERY PR
```

O modelo preferido é federado:

```text
bounded-context owner
      ↓
owns local domain decisions
      ↓
within global principles/invariants/contracts
      ↓
architecture review only when trigger/risk requires
```

Uma decisão local pode ser tomada localmente enquanto não altera contrato global, source of truth, security boundary, persistence authority, dependency direction, cross-context semantics ou operational risk material.

# 2. N3.23.01 — Architecture Principles

## N4.23.01 — Papel dos princípios

Princípios são constraints de alta estabilidade que moldam várias decisões.

Eles não devem conter detalhes facilmente mutáveis como:

```text
exact timeout
exact provider
exact table name
exact UI route
exact worker technology
```

Eles devem conter regras como:

```text
one authority per aggregate
Overall never enters canonical solver
shared critical state is server-authoritative
facts and projections are distinct
```

## N4.23.01 — Mudança de princípio

Modificar princípio exige:

1. problema concreto;
2. impacto cross-context analisado;
3. alternatives;
4. consequences;
5. affected invariants;
6. migration strategy;
7. test/fitness-function impact;
8. explicit architecture review;
9. ADR que explique a mudança material.

Não editar um princípio apenas para fazer o código atual “ficar conforme”.

## N5.23.01 — Violation handling

Se implementação precisa violar princípio temporariamente:

```text
Exception Record
+ scope
+ reason
+ compensating controls
+ owner
+ expiry/review trigger
```

Se a violação deve ser permanente, não é exception: é proposta de mudança arquitetural.

# 3. N3.23.02 — Architecture Source of Truth

## N4.23.02 — Não existe uma única ordem total para todos os tipos de verdade

A pergunta correta é:

> “Qual artefato é autoridade para este tipo de decisão?”

### Authority matrix

| Pergunta | Source of truth |
|---|---|
| Termo significa o quê? | `GLOSSARY.md` |
| Quais constraints globais governam design? | `PRINCIPLES.md` |
| Por que decisão arquitetural foi tomada e qual status? | ADR canônico |
| Qual target/contract de um bounded context? | documento N2 canônico |
| Qual N2/N3 existe e quem possui? | `EAP-MASTER.md` |
| Qual schema DB é aplicado? | migrations versionadas |
| Qual API/DTO executável existe? | contrato/schema/code validado + tests |
| Qual invariant é obrigatório? | global/context invariant catalog + owning N2 |
| Qual comportamento está realmente implantado? | deployed code/schema + telemetry |
| Qual plano de transição atual? | migration plan/runbook ligado ao N2.22 |

## N4.23.02 — Conflict protocol

Se duas sources canônicas aparentemente divergem:

```text
DO NOT
pick newest file
pick latest timestamp
pick code automatically
pick opinion of current implementer
```

Fazer:

```text
1 identify conflict class
2 identify owning contexts
3 block irreversible decision if needed
4 open contradiction record
5 resolve through ADR/doc correction
6 update tests/fitness functions
7 close traceability
```

## N4.23.02 — Code vs docs

Código pode estar incorreto ou arquitetura pode ter evoluído.

Portanto:

```text
CODE CONTRADICTS CANONICAL ARCHITECTURE
→ bug OR architecture-change proposal
```

Nunca silêncio.

## N4.23.02 — Canonical status during consolidation

Enquanto C2/C3/C4/C5/C6/C7 não estiverem concluídos:

```text
DRAFT-CANONICAL
```

significa:

- preferred source for target design;
- ainda sujeito a contradiction audit/canonicalization;
- não equivale a “already deployed”.

Após aprovação/audit:

```text
CANONICAL
```

# 4. N3.23.03 — Bounded Context Ownership

Ownership principal no EAP é conceitual e independe do tamanho atual da equipe.

Cada context owner é responsável por:

```text
ubiquitous language
invariants
commands/queries
state ownership
cross-context contracts
security/privacy requirements
migration strategy
operational behavior
observability
quality evidence
deprecation
canonical documentation
```

## N4.23.03 — Ownership não significa isolamento total

Exemplo:

```text
Match owns MatchEvent semantics
Security owns global auth constraints
Data owns DB policy
Operations owns deploy mechanics
```

Uma mudança em Match pode exigir review de Security/Data/Operations, mas Match continua dono da regra esportiva.

## N4.23.03 — Shared decisions

Quando dois contexts compartilham boundary:

```text
producer owns meaning of published contract
consumer owns use of contract
cross-context invariant has named primary owner
```

Evitar “everyone owns it”, que na prática significa ninguém possuir.

# 5. N3.23.04 — Module Ownership

## N4.23.04 — Target dependency shape

```text
src/app
   ↓ composition
src/ui
   ↓ intents/view models
src/application
   ↓ ports + orchestration
src/domain

src/infra
   ↑ implements ports

src/shared
   = stable primitives/contracts only
```

## N4.23.04 — Rules

### Domain

Não depende de:

- React;
- Supabase SDK;
- browser storage;
- provider client;
- UI components;
- direct network.

### Application

Pode depender de:

- domain;
- command/query contracts;
- ports;
- deterministic policy abstractions.

Não deve depender de UI.

### Infrastructure

Implementa ports e contém:

- Supabase adapters;
- provider adapters;
- IndexedDB adapters;
- transport serialization;
- persistence mapping.

Não é owner de regra de domínio apenas porque executa SQL/API.

### UI

Consome application/view models e emite intentions.

Não deve administrar table rows diretamente.

### Shared

Não é pasta de “coisas usadas em dois lugares”.

Um tipo com owner de domínio continua pertencendo ao context owner mesmo se vários contexts consumirem projection/DTO dele.

## N4.23.04 — Legacy coexistence

Legacy modules podem permanecer fora da estrutura target durante strangler.

Criar target module não exige mover todo repositório.

Mas:

```text
NO NEW TARGET FEATURE
MAY TAKE A DEPENDENCY
ON A DEPRECATED LEGACY PERSISTENCE CONTRACT
WHEN TARGET CONTRACT EXISTS
```

# 6. N3.23.05 — ADR Governance

ADR registra decisão arquitetural material, não toda implementação.

## N4.23.05 — Quando ADR é necessário

Candidatos:

- source of truth/authority;
- cross-context boundary;
- new persistence model;
- security model change;
- offline authority change;
- Realtime protocol change;
- high-cost infrastructure adoption;
- durable provider lock-in;
- major data migration strategy;
- exception becoming permanent;
- principle change;
- irreversible/expensive tradeoff.

Não precisa ADR para:

- trivial refactor;
- copy;
- rename local sem semantic impact;
- implementation detail already constrained by accepted architecture.

## N4.23.05 — ADR record

Canonical ADR deve possuir no mínimo:

```text
ID
Title
Status
Date
Owner
Contexts
Problem
Decision
Alternatives Considered
Why
Consequences
Security/Privacy Impact
Reliability/Operational Impact
Migration Impact
Testing/Fitness Functions
Reversibility / Exit Strategy
Revisit Triggers
Related Principles
Related Invariants
Supersedes / Superseded By
```

## N4.23.05 — C3 canonicalization

C2 working anchors serão processados no C3 para:

- deduplicar;
- resolver overlaps;
- detectar contradições;
- definir title/status;
- construir supersession graph;
- preservar rationale;
- estabelecer IDs canônicos.

C2.23 não cria uma nova sequência numérica paralela.

# 7. N3.23.06 — ADR Lifecycle

Status baseline:

```text
PROPOSED
ACCEPTED
REJECTED
SUPERSEDED
DEPRECATED
```

Opcionalmente:

```text
TRIAL
```

somente quando há experimento arquitetural controlado e exit criteria.

## N4.23.06 — Material change

Depois de `ACCEPTED`, não editar materialmente rationale/decision para fingir que sempre foi outra coisa.

Mudança material:

```text
new ADR
→ supersedes old ADR
```

Correções editoriais podem ser feitas com changelog quando necessário.

## N4.23.06 — Rejected decisions are retained

`REJECTED` permanece registrado para evitar repetir discussão sem novo contexto/evidência.

Nova evidência pode gerar nova proposta, não apagar a decisão anterior.

```text
Question

Affected Contexts
```

## N4.23.07 — Rules

- se não bloqueia, safe default precisa ser explícito;
- open decision sem owner/review trigger tende a virar dívida invisível;
- fechar decisão material gera ADR ou atualização canônica apropriada.

# 9. N3.23.08 — Hypotheses

Hypothesis é claim testável, não decisão.

Exemplo:

```text
HYP:
local Supabase stack reproduz adequadamente DB/RLS behavior

EVIDENCE:
CI integration results
provider delta inventory

REVISIT:
when Realtime/Auth/Storage divergence appears
```

Record mínimo:

```text
HYP-ID
Claim
Why It Matters
Evidence Expected
Measurement
Owner
Review Trigger
Outcome
```

## N4.23.08 — Critical rule

```text
UNVALIDATED HYPOTHESIS
CANNOT BE THE ONLY CONTROL
PROTECTING A CRITICAL INVARIANT
```

Exemplo: “provavelmente ninguém terá dois devices” não pode proteger Match correctness.

# 10. N3.23.09 — Global Invariants

Global invariant atravessa múltiplos contexts.

Exemplos:

```text
one authority per aggregate
actor identity server-resolved
shared critical state not LWW
Overall never canonical balancing input
account deletion does not erase sports facts
Realtime never source of truth
external provider never blocks domain commit
```

C4 criará catálogo global único.

## N4.23.09 — Ownership

Cada global invariant terá:

```text
ID
Statement
Primary owner
Affected contexts
Enforcement layers
Executable evidence
Related principles/ADRs
Violation severity
```

## N4.23.09 — Duplicate local invariants

Contexts podem repetir uma global invariant para legibilidade, mas C4 registra a relação:

```text
GLOBAL-INV-X
→ MATCH-INV-Y
→ API-INV-Z
→ SEC-INV-W
```

Não devem existir versões semanticamente divergentes da mesma regra.

# 11. N3.23.10 — Context Invariants

Cada bounded context mantém invariants locais no documento canônico.

Rules:

- ID estável depois de canonicalization;
- mudança material exige impact review;
- invariant crítico deve ter executable evidence;
- remover invariant exige rationale/ADR quando a semântica mudou;
- implementation detail não deve ser promovido a invariant sem necessidade.

## N4.23.10 — Invariant severity

Sugestão conceitual:

```text
I0 — safety/security/data integrity
I1 — domain correctness
I2 — contract/operational correctness
I3 — maintainability/performance guard
```

A classificação final será consolidada no C4/C5.

# 12. N3.23.11 — Traceability

Target trace graph:

```text
Product Rule / Risk
      ↓
Principle
      ↓
ADR
      ↓
Invariant
      ↓
Command / Data / Contract
      ↓

      ↓
```

## N4.23.11 — Traceability artifact

Exact implementation remains `OPEN`:

- markdown catalog;
- generated index;
- YAML/JSON manifest;
- code metadata.

Não introduzir plataforma de architecture management sem necessidade.

# 13. N3.23.12 — Dependency Rules

## N4.23.12 — Layer direction

Baseline:

```text
UI → Application → Domain
Infrastructure → Application Ports / Domain types as allowed
App → composition of all
```

Forbidden target dependencies include:

```text
Domain → Supabase SDK
Domain → React
Application → concrete UI
UI → direct critical table mutation
Context A → private table/module of Context B as implicit API
```

## N4.23.12 — Context-to-context

Contexts integrate via explicit:

- IDs;
- immutable snapshots;
- query/read contracts;
- domain events;
- commands/use cases where ownership permits.

Avoid shared mutable entity model where ownership is ambiguous.

## N4.23.12 — Database dependency

A context não deve ler/escrever private implementation table de outro context apenas porque ambos estão no mesmo Postgres.

Cross-context DB join pode ser uma deliberate read model/query optimization, com owner e contract explícitos.

# 14. N3.23.13 — Architecture Fitness Functions

Fitness function é executable architecture constraint.

## N4.23.13 — Categories

### F0 — static structure

- forbidden imports;
- folder/layer boundaries;
- no direct Supabase import from UI for migrated flows;
- no browser service-role secret;
- no new `cloudId/localId/syncStatus` in canonical domain models;
- no new legacy sync payload members after deprecation.

### F1 — semantic code

- solver canonical input excludes Overall;
- commands carry `command_id` where required;
- Realtime authoritative event types not publishable from client path;
- offline outbox has allowlist.

### F2 — database/security

- migrations from zero;
- RLS matrix;
- privileged function hardening;
- no dangerous Auth cascade to sports facts;
- partial uniques/constraints;
- critical transaction concurrency.

### F3 — operational

- deployed security headers;
- restore drill;
- projection rebuild integrity;
- compatibility/deprecation telemetry;
- migration authority checks.

## N4.23.13 — Fitness-function lifecycle

Cada fitness function registra conceitualmente:

```text
intent
owner
protected invariant
scope
failure meaning
legacy/target status
removal trigger
```

Um teste que protege um caminho legacy deve desaparecer quando o caminho é contractado.

## N4.23.13 — Avoid false architecture certainty

Passar um alias test não prova correta domain boundary.

Fitness function precisa provar a regra que importa, não apenas a forma atual da pasta.

# 17. N3.23.16 — API Governance

API/application contract segue N2.15.

Governance rules:

- semantic Commands, not generic critical CRUD;
- actor resolved server-side;
- stable product error codes;
- explicit revision/sequence/epoch where needed;
- runtime validation at untrusted boundaries;
- DTO ≠ DB Row ≠ Domain ≠ ViewModel;
- additive compatibility before breaking change;
- public/private DTO separation;
- idempotency contract documented;
- deprecation window measured.

## N4.23.16 — Breaking change trigger

Requires architecture/application review when changing:

- command semantics;
- idempotency scope;
- authorization context;
- error meaning;
- event envelope;
- compatibility window;
- source of truth.

Simple additive field may not require ADR if semantics are local/obvious.

# 18. N3.23.17 — Data Governance

Follows N2.14/N2.21:

```text
versioned migrations = schema authority
```

Every new durable dataset declares:

```text
owner context
classification: FACT / CURRENT STATE / SNAPSHOT / PROJECTION
identity/key strategy
FK/delete semantics
retention/lifecycle
privacy classification
rebuildability if projection
migration strategy
```

## N4.23.17 — Database review triggers

Review required for:

- new cross-context FK;
- Auth cascade;
- new JSONB core relation;
- new array-of-IDs relation;
- partitioning;
- material denormalization;
- SECURITY DEFINER;
- public schema exposure;
- destructive contract;
- new global table without owner.

# 19. N3.23.18 — Security Governance

Security model is cross-cutting and follows N2.16.

Changes requiring Security review include:

- capability matrix;
- privileged RPC;
- RLS/grants;
- public read expansion;
- service-role use;
- MFA/AAL requirement;
- account linking/merge;
- public Realtime/Storage;
- external provider receiving personal data;
- production privileged tooling.

## N4.23.18 — Security exception

“Temporary bypass” is still a security design decision.

Requires scope, compensating control and expiry.

No hidden backdoor.

# 20. N3.23.19 — Privacy Governance

Every new personal-data processing must answer:

```text
purpose
categories
subjects
visibility
legal basis / applicable justification
retention
recipients/providers
international transfer if applicable
rights workflow impact
security classification
```

Privacy review trigger includes:

- new personal/sensitive field;
- new public profile exposure;
- new provider/data recipient;
- new retention policy;
- analytics/telemetry with identifiers;
- export/deletion behavior;
- media/biometric use change.

`Global Player` never means `public global directory` automatically.

# 21. N3.23.20 — Offline Governance

Every mutation/use case declares one class from N2.12:

```text
ONLINE_AUTHORITATIVE
OFFLINE_OWNED
CACHED_READ
LOCAL_DRAFT
CONDITIONALLY_OFFLINE_COMMAND
```

No new shared mutation may enter generic outbox without explicit policy.

Governance questions:

1. who is authority offline?
2. how ordering is preserved?
3. can two devices act?
4. what happens on logout/account switch?
5. how retry is idempotent?
6. what happens on divergence?
7. what data is locally irreplaceable?

If these are unanswered, offline support is not designed.

# 22. N3.23.21 — Realtime Governance

Realtime contract must declare:

```text
channel scope
subscription authorization
payload DTO
revision or sequence semantics
snapshot/reconnect protocol
privacy exposure
schema version
publisher authority
```

Rules:

- committed transport only;
- authoritative publish path trusted;
- browser cannot fabricate domain event;
- Presence is ephemeral;
- missed messages are recoverable;
- public spectator DTO separate from internal DTO.

Changing Realtime payload must not silently expose DB row schema.

# 23. N3.23.22 — Reliability Governance

Each critical flow declares:


# 34. N3.23.33 — Risk Classification

Architecture risk classification is independent of Operations O0–O3 but can map to it.

### AR0 — local / reversible

No cross-context semantics, no durable data/security impact.

### AR1 — bounded-context contract

Changes domain API or data shape but remains local/reversible.

### AR2 — cross-context / durable / security relevant

Changes authority, shared contract, durable migration, authorization, offline/realtime protocol.

### AR3 — critical / irreversible or high blast radius

Examples:

- destructive data transformation;
- identity merge;
- global auth model;
- Match source facts protocol;
- Registration ordering semantics;
- privacy/public exposure;
- major platform adoption;
- production reset.
