# 0. Command contract baseline

A target mutation is normally expressed as:

```text
SemanticCommand
├── command_id
├── payload allowlisted for the command
├── expected_revision when relevant
├── expected_last_sequence when relevant
└── control_epoch when relevant
```

Server derives:

```text
actor_user_id
actual resource context
current capability
current Membership/assignment/lease
server time
```

A successful critical command means:

```text
AUTHORITATIVE TRANSACTION COMMITTED
```

not merely:

```text
request accepted by browser
optimistic local object changed
provider call succeeded
Realtime event observed
```

Retry of the same logical mutation reuses the same `command_id`.

# 1. Common transaction/result vocabulary

## Transaction profile

```text
T0 — no mutation / pure local compute
T1 — one aggregate/current row transaction
T2 — aggregate + dependent rows atomically
T3 — source fact + synchronous critical projection
T4 — source mutation + domain outbox atomically
T5 — local durable IndexedDB transaction
```

Profiles can combine, e.g. `T2+T4`.

## Result profile

```text
R-AUTH
returns authoritative current state/revision needed by caller

R-EFFECT
returns identity/result of created source fact

R-QUEUED
source committed; downstream async work pending

R-LOCAL
local durable result only

R-RECONCILE
cannot safely auto-apply; explicit reconciliation needed
```

## Conflict profile

```text
REVISION_STALE
SEQUENCE_STALE
CONTROL_LOST
CAPACITY_RACE
ALREADY_EXISTS
NOT_ELIGIBLE
STATE_TRANSITION_INVALID
AUTHORIZATION_DENIED
UNKNOWN_OUTCOME
RECONCILIATION_REQUIRED
```

### Last-slot rule

Two concurrent `JoinRegistration` transactions against one remaining slot must yield:

```text
one CONFIRMED
one WAITLISTED
```

never two confirmed, regardless of client clocks or request arrival timestamps observed outside the serialized transaction.

### Match command rule

The client does **not** submit authoritative:

```text
score_after
winner
set_winner
last_sequence
control owner
```

as mutable facts. It submits sporting intent and concurrency context; server/rules derive the outcome.

# 12. Error / recovery matrix

| Condition | Product/application result | Automatic retry? | Required next action |
|---|---|---:|---|
| normal full capacity Join | `WAITLISTED` success | no | display authoritative waitlist status |
| validation rejection | stable domain code | no blind retry | fix input/state |
| authorization denial | authorization code | no | refresh identity/capability only when relevant; never retry loop |
| stale revision | conflict code | not blind | refetch current aggregate; user/system decides reapply |
| stale Match sequence | Match stale conflict | not generic retry | fetch/reconcile contiguous state |
| lost Match control/old epoch | `MATCH_CONTROL_LOST` / reconcile | no auto-apply | fetch lease/epoch; reconcile/discard according to protocol |
| DB retryable deadlock before known commit | technical retryable | bounded same logical command | retry with same `command_id` |
| HTTP timeout after possible commit | `UNKNOWN_OUTCOME` | yes, same `command_id` | command receipt/idempotent recovery |
| provider timeout after domain commit | downstream delivery unknown | worker/provider policy | reconcile/retry provider effect; domain remains success |
| Realtime gap | convergence gap | yes via refetch/range | authoritative snapshot/range recovery |
| IndexedDB failure before offline critical acknowledgement | local durability failure | no fake success | fail closed; free space/recover/export |
| Quick publish response lost | `HANDOFF_UNKNOWN` | same command_id | freeze ambiguous local authority; resolve server ownership |
| legacy migration ambiguity | migration anomaly | no guess/retry as truth | quarantine/manual resolution or preserve evidence |

# 14. C5.02 exit criteria

Implementation planning must be able to answer for every critical mutation:

1. what semantic command expresses the intent;
2. who owns it;
3. what aggregate/rows are locked;
4. what transaction boundary exists;
5. which revision/sequence/epoch/uniqueness primitive applies;
6. how `command_id` protects retries;
7. whether it is allowed offline;
8. what authoritative result is returned immediately;
9. which side effects occur only after commit;
10. which Realtime event is secondary;
11. what stable recovery class applies;
12. what executable evidence is required.
