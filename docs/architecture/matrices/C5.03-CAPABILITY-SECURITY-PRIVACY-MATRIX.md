# 0. Governing authorization chain

For every protected operation:

```text
JWT / authenticated principal
        ↓
server derives actor User
        ↓
resolve requested resource by canonical ID
        ↓
resolve ACTUAL resource context
        ↓
load current Membership / responsibility / assignment / lease / competition authority
        ↓
derive capability
        ↓
step-up/AAL requirement if policy says so
        ↓
domain state/eligibility validation
        ↓
ALLOW or DENY
```

Never:

```text
payload.community_id
payload.owner_id
payload.role
payload.isAdmin
localStorage.role
raw_user_meta_data.organizer
```

as authorization authority.

| Media uploader | actor allowed to upload for a target/purpose | right to attach to arbitrary target or publish raw bytes |

# 2. Capability naming rule

The strings below are semantic capability concepts for matrices/API policy. C5 does not require a persisted ACL table.

Target baseline prefers:

```text
current DB state
+ small static/contextual capability rules
+ explicit assignments
```

rather than a per-Community arbitrary permission builder.

`HYP-COM-003` remains the assumption that a small static contextual map is sufficient initially.

# 8. AAL / step-up matrix

AAL2 is an accepted security mechanism for selected high-impact operations; the **exact final set remains OPEN** in Security.

| Operation class | Baseline architectural posture | Why |
|---|---|---|
| ordinary read/query | normal authenticated/context authorization | low mutation impact |
| normal Join/Leave Registration | AAL1 may be sufficient subject policy | user self-service, domain transaction protects fairness |
| ordinary Organizer Session mutation | contextual auth; step-up not automatically required | operational frequency/UX |
| Community ownership transfer | strong candidate / target high-impact step-up | single-owner governance blast radius |
| Player Merge | strong candidate | irreversible identity/history impact |
| conflicted PlayerAccountLink approval | strong candidate | account hijack risk |
| platform/security break-glass | strong MFA/step-up | exceptional privilege |
| bulk privacy deletion / destructive repair | strong step-up | irreversible personal-data/data integrity impact |
| ordinary Match point command | lease/epoch is mandatory; AAL2 per point would be inappropriate by default | court usability; session auth already established |

Rule:

```text
UI step-up prompt
≠
security enforcement
```

The server/RPC policy must verify required assurance where the final Security policy mandates it.

# 10. Public DTO / internal DTO separation

| Resource | Public/spectator DTO may contain | Must not contain |
|---|---|---|
| Player minimal public profile if enabled | allowed display name/avatar/public stats only | email, memberships list, raw evaluations, private skill profile, auth IDs |
| Community public card | name/description/approved media/discovery metadata | member private data, JoinRequests, internal settings, audit |
| Session public view if enabled | schedule/public title/status/safe roster depending policy | waitlist identities, organizer security metadata, internal revisions not needed |
| Match spectator | score, sets, team display, sporting event meaning, status | actor_user_id, device_id, control_epoch details, command_id, private participant data |
| Competition public | stage/fixture/result/standings fields intended by product | admin assignments, correction notes/security metadata, private rosters if not public |
| Media public descriptor | immutable delivery URL/path descriptor + dimensions/type as safe | incoming path, internal bucket credentials, uploader secret metadata |

Public DTO is an explicit read contract. It is never obtained by exposing an internal row and “hiding a few fields in React”.

# 12. SECURITY DEFINER / RPC matrix

Target privileged RPC rules:

```text
SECURITY DEFINER where actually required
SET search_path = ''
fully-qualified object names
minimal EXECUTE grants
explicit auth.uid()/JWT assurance checks
actual resource context resolution
allowlisted inputs
stable product error translation
transaction/locks inside command boundary
no service role in browser
```

| Command class | Why RPC/DB-local transaction is preferred |
|---|---|
| Registration Join/Leave/capacity | row serialization + FIFO + multi-row atomicity |
| Community ownership transfer | exactly-one owner transition |
| Voting Cast/Close/Finalize | race ordering + ballot uniqueness/privacy |
| AwardPoint / Match control state | sequence/epoch/lease + projection atomicity |
| Officialize/Correct Competition result | official fact + dependency/projection coordination |
| critical Player link/merge pieces | uniqueness/context/history integrity where DB-local |

External HTTP/provider work belongs after commit, usually worker/Edge/server adapter, not inside these locks.

# 13. Storage / Media trust-zone matrix

| Zone | Read | Write | Trust | Promotion rule |
|---|---|---|---|---|
| `incoming-private` conceptual zone | uploader/internal only | scoped upload intent | untrusted bytes | processor must decode/validate/sanitize |
| sanitized master | internal/authorized only | processor | trusted normalized source | may generate variants |
| private/contextual variant | authorized delivery only | processor | technically safe | visibility/domain authorization required |
| public variant | public only when asset + owning entity policy permit | processor/trusted publisher only | technically safe + explicitly public eligible | immutable key; browser cannot upload arbitrary final object |

A public bucket/object path is an infrastructure delivery choice, not media identity or authorization logic.

# 15. Privacy processing matrix

Each real processing activity must eventually have a privacy inventory record containing:

```text
purpose
personal-data categories
data subjects
controller/operator role
legal basis
recipients/providers
international transfer mechanism if applicable
retention
security class
rights workflow
```

C5 does not invent legal basis values.

| Processing family | Likely personal data | Architecture control | Open/legal dependency |
|---|---|---|---|
| Account/Auth | email, identifiers, MFA/security metadata | provider + least privilege + no token logging | controller/provider mapping |
| Player identity/discovery | name, username, avatar | minimal discovery, rate limiting, contextual visibility | `OPEN-ID-002`, minors policy |
| Membership/Community | community association, roles/status | contextual RLS/capability | retention category |
| Player Evaluation | subjective sports assessments | contextual access, revision history, not telemetry | evaluated Player visibility/legal purpose policy |
| Match participation | identity + sporting history | immutable factual history, privacy-minimal snapshots | public spectator/profile exposure policy |
| Statistics | derived personal sporting performance | purpose-specific projections/read DTOs | public profile/ranking `OPEN-STAT-004/005` |
| Notifications | recipient/message/read state/device endpoint | recipient-only Inbox, provider minimization | provider/legal basis/retention |
| Media | image/avatar metadata | private raw, EXIF removal, explicit visibility | exact retention/moderation limits |
| Audit/Security | actor/action/resource/security events | semantic/minimized, internal least privilege | retention/legal requirements |
| Telemetry | pseudonymous operational identifiers/signals | bounded cardinality/redaction/purpose retention | vendor/retention policy |

# 16. Account deletion / privacy-rights matrix

| Data class | Account deletion default architectural effect | Why |
|---|---|---|
| Auth account/session | revoke/delete according to account workflow | authentication access ends |
| UserProfile personal fields | delete/anonymize/retain only where justified | privacy purpose/retention |

| CommunityMembership | lifecycle/removal/anonymization policy | governance relation separate from sports history |

# 17. Security negative-test matrix

Every privileged target path needs at least one explicit denial proving each applicable class:

| Negative class | Example |
|---|---|
| unauthenticated | caller guesses Session UUID |
| cross-context BOLA | Member of Community A uses resource UUID from B |
| actor spoofing | payload says `actor_user_id=B` |
| role spoofing | payload/localStorage/raw metadata says `admin=true` |
| hierarchy confusion | Admin invokes `AwardPoint` without Match control |
| responsibility confusion | Organizer invokes `TransferCommunityOwnership` |
| stale membership | removed User uses old JWT/socket |
| direct table bypass | client INSERTs RegistrationEntry/MatchEvent directly |
| mass assignment | generic status/owner/officialized_by fields submitted |
| channel bypass | unauthorized private Realtime topic subscription |
| Storage BOLA | guessed private object key |
| media trust bypass | raw upload manually approved without READY processing |
| service credential leak | bundle contains service-role/provider secret |
| MFA bypass | AAL1 caller invokes step-up RPC directly |

# 19. C5.03 exit criteria

C5.03 is complete when implementation can answer:

1. which actor concept is being used;
2. which contextual capability authorizes the action;
3. which roles explicitly do **not** imply it;
4. how actual resource scope is resolved;
5. whether RLS/RPC/lease/AAL/Storage policy adds enforcement;
6. which DTO/data fields the audience may receive;
7. which data is public/contextual/recipient-only/internal/private;
8. which security/privacy Open Decision blocks broader exposure;
9. what negative test proves BOLA/hierarchy/mass-assignment resistance;
10. how account deletion/privacy workflow avoids destroying shared sports history.
