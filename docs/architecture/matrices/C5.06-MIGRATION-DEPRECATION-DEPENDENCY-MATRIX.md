# 0. Governing migration rule

```text
TWO IMPLEMENTATIONS MAY COEXIST
BUT
TWO AUTHORITIES FOR THE SAME AGGREGATE MAY NOT
```

Migration is transfer of authority, not synchronization of two equally valid models.

```text
LEGACY AUTHORITY
→ EXPAND TARGET
→ SHADOW / ADAPTER / VERIFY
→ CUTOVER A COHORT
→ TARGET AUTHORITY
→ RETIRE LEGACY READ/WRITE
→ CONTRACT
```

For an aggregate already cut over:

```text
feature flag OFF
≠
return authority to stale legacy state
```

A flag may stop new cohorts or disable optional surfaces, but it cannot reverse committed authority without an explicit migration/recovery protocol.

### Ambiguity rule

```text
legacy role/title/name similarity
≠
proof of target capability
```

Ambiguous mappings become `MigrationAnomaly`, not automatic privilege escalation.

| Legacy representation | Target | Backfill/adapter | New write switch | Critical non-mapping |

| no RegistrationWindow | target RegistrationWindow | only upcoming Session can explicitly transition/import starting confirmed roster | Join/Leave/Open/Close target RPCs | no historical FIFO invented |

### Registration introduction gate

A legacy upcoming Session may start target Registration only after an explicit transition records:

```text
starting confirmed roster source
starting target window revision
capacity/status
whether historical queue ordering is UNKNOWN
```

If old data cannot prove waitlist chronology:

```text
WAITLIST SEQUENCE STARTS WITH TARGET ACTIONS
```

rather than fabricated timestamps.

### Historical import classes

```text
LEGACY_COMPLETE_ENOUGH
score/result + ordered point evidence trustworthy

LEGACY_PARTIAL
score/result trustworthy; some event detail incomplete

SCORE_ONLY
final score/result trustworthy; no trustworthy detailed event history

AMBIGUOUS
source conflicts / ownership/order cannot be proven
```

Never manufacture PointEvents to make `SCORE_ONLY` look complete.

### Sync subtraction order

```text
1 stop TARGET writes through generic sync
2 stop TARGET reads through generic sync
3 freeze remaining legacy-only surfaces
4 remove entity from sync payload
5 remove merge/remap/tombstone logic for that entity
6 remove service dependency from consumers
7 contract legacy DB fields/indexes later
```

Do not delete the service before steps 1–6 are verified.

# 16. Rollback / forward-fix matrix

| Situation | Safe response | Unsafe response |
|---|---|---|
| frontend bug after additive DB migration | rollback frontend if compatible; flag new cohort | run destructive DB down migration automatically |
| target write cutover bug before any target writes | stop new cohort; fix before transfer | continue shadow as if correct |
| target aggregate already accepted writes | forward-fix target; stop new cohorts; preserve authority | switch authority back to stale legacy copy |
| projection bug | serve previous valid projection if available / rebuild/fix calculation version | mutate source facts to match buggy projection |
| backfill bug | stop/checkpoint, fix idempotent job, repair mapped cohort | rerun unbounded destructive script blindly |
| Match V2 issue with active target Match | use protocol/runbook/reconciliation; feature-gate new starts | migrate active Match back to legacy Game/LWW |
| provider integration issue | kill/disable delivery worker/channel while source domain remains | roll back committed Registration/Match facts |

Database recovery preference is forward-fix/additive compatibility rather than assuming reversible down migrations.

# 17. Removal gate matrix

A legacy artifact can be removed only when all applicable gates are true.

| Gate | Question |
|---|---|
| writer gate | can any current/new/old supported client still mutate through legacy path? |
| reader gate | does any route/hook/job/report still read legacy representation? |
| cohort gate | are any active resources still legitimately executing under legacy protocol? |
| migration gate | are all eligible rows/backfills/import anomalies resolved or explicitly quarantined? |
| local-data gate | can old devices still hold irreplaceable residual data needing importer/recovery? |
| telemetry gate | supported client/version usage of legacy contract is zero/below explicit removal rule |
| DB gate | views/functions/RLS/triggers/indexes/constraints no longer depend on legacy column/table |
| worker gate | no scheduler/job/outbox consumer references legacy shape |
| Storage gate | no policy/object lifecycle needs legacy path |
| test gate | architecture/unit/integration/E2E tests no longer encode old contract as desired behavior |
| documentation gate | old specs/runbooks are archived/marked legacy and do not claim authority |
| recovery gate | restore/rollback/runbook does not require removed artifact |

Text search alone is not sufficient proof of safe removal.

# 20. C5.06 exit criteria

C5.06 is complete when C6 can turn every target slice into an executable migration plan answering:

1. what current representation/path exists;
2. what target replaces it;
3. what wave/prerequisites apply;
4. what the cutover unit/cohort is;
5. how identity/provenance is preserved;
6. what compatibility adapter is temporary;
7. exactly when write authority transfers;
8. which old writer is blocked after cutover;
9. how semantic parity/invariants are verified;
10. how ambiguous legacy data is quarantined rather than guessed;
11. how rollback/forward-fix works after target writes exist;
12. what telemetry/tests/data checks prove removal safety;
13. which schema/code/docs/tests/services are deprecated;
14. what Open Decision genuinely blocks a slice versus what can remain deferred;
15. how active execution cohorts are protected from mid-protocol migration.
