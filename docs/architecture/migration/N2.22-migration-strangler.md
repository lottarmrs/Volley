# 0. Regra de leitura

A regra central deste capítulo é:

```text
TWO IMPLEMENTATIONS MAY COEXIST
BUT
TWO AUTHORITIES FOR THE SAME AGGREGATE MAY NOT
```

A migração não é uma refatoração de pastas nem uma substituição de tabelas isolada.

É uma transferência controlada de autoridade:

```text
LEGACY AUTHORITY
      ↓
EXPAND TARGET
      ↓
SHADOW / VERIFY
      ↓
CUTOVER ONE MIGRATION UNIT
      ↓
TARGET AUTHORITY
      ↓
RETIRE LEGACY COMPATIBILITY
```

Consequentemente:

```text
DUAL COMPATIBILITY
≠
DUAL AUTHORITY
```

Podemos manter dois readers, dois DTOs ou um adapter antigo e um novo durante uma janela. Não podemos permitir que browser A considere `localStorage` a verdade e browser B considere Postgres a verdade para o mesmo RegistrationWindow, Match ou Membership.

Outra regra:

```text
MIGRATION COMPLETION
≠ NEW CODE EXISTS
≠ BACKFILL FINISHED
≠ OLD FILE DELETED
```

Migração só termina quando autoridade, dados, contratos, testes, observabilidade, operação e legado foram fechados de forma verificável.

O repositório já possui:


Isso é evidência operacional útil, mas entra em conflito com a necessidade atual de evoluir um produto com história esportiva real.

Decisão deste C2:

```text
RESET
IS NOT
THE DEFAULT MIGRATION STRATEGY
```

Um reset destrutivo futuro só pode ocorrer como decisão extraordinária de produto, explicitamente aprovada, com escopo, usuários afetados, backup/restore, comunicação e compliance próprios.

O strangler canônico preserva fatos e proveniência por default.

# 2. N3.22.01 — Migration Principles

## N4.22.01 — Vertical slices

Migrar por capability/end-to-end behavior, não por camada horizontal inteira.

Preferir:

```text
Registration
├── schema
├── RPCs
├── RLS
├── Application use cases
├── UI adapter
├── Realtime
├── tests
└── observability
```

antes de:

```text
refactor all TypeScript types
then all DB
then all UI
then hope they fit
```

## N4.22.01 — One authority

Cada aggregate possui exatamente uma autoridade efetiva por instante.

Podem existir cópias/shadows, mas somente uma aceita decisões autoritativas.

## N4.22.01 — Preserve facts

Source Facts C0 não são reescritos silenciosamente para “caber” no target.

Se o legado não contém informação suficiente:

```text
MIGRATE AS UNKNOWN / LEGACY EVIDENCE
OR
QUARANTINE FOR REVIEW
```

Nunca inventar dado.

## N4.22.01 — Preserve IDs where semantics match

Se uma entidade antiga e target representam a mesma identidade, preservar UUID.

Se uma entidade antiga se divide em várias novas, registrar mapeamento explícito.

## N4.22.01 — Forward-compatible rollback

Rollback primário é:

```text
stop next cohorts
flag off target path where still safe
serve compatible old reader/adapter
forward-fix target
```

Não é restaurar automaticamente dados antigos sobre writes target já confirmados.

## N4.22.01 — No hidden migration

Nenhuma conversão irreversível ocorre implicitamente ao abrir uma tela.

Migração precisa de run id, status e observabilidade quando altera autoridade ou dados persistentes.

# 4. N3.22.03 — Target-State Mapping

Cada legacy concept deve ter um destino explícito.

| CURRENT | TARGET | Migration note |
|---|---|---|
| authenticated account/profile | User/Auth identity | preserve auth UUID |
| `Player.user_id` direct link | PlayerAccountLink | backfill explicit link |
| `community_members` mixed role semantics | CommunityMembership + operational responsibility | split Organizer from governance |
| `community_players.role` legacy | CommunityPlayer sports relation | do not use as governance |
| Session selected IDs | RosterRevision entries | preserve roster provenance |
| Session team IDs | TeamDraw/assignments | snapshot historical membership |
| CommunityPresence | availability/presence concept | never auto-convert to Registration |
| WhatsApp list draft slots | share artifact | never auto-convert to authoritative roster |
| generic `Game` | Match | finished history may backfill; live stays legacy |
| PointEvent | MatchEvent where evidence allows | preserve original ID/sequence/provenance |
| Championship | Competition | derive stage only from supported semantics |
| ChampionshipRound | Fixture-like planned pairing | do not call it Round blindly |
| current career projections/events | legacy statistical evidence | rebuild target projections from canonical facts where possible |
| player evaluation aggregate/overall | PlayerEvaluation revisions + profiles | never copy overall into solver authority |
| avatar URL/proposal | MediaAsset + attachment | sanitize before READY pointer |
| local sync metadata | migration-only compatibility | retire after authority cutover |

Mapping status must distinguish:

```text
EXACT
SPLIT
MERGE
DERIVED
NO_EQUIVALENT
AMBIGUOUS
RETIRED
```

`AMBIGUOUS` blocks automatic destructive conversion.

# 5. N3.22.04 — Dependency Graph

Canonical dependency ordering:

```text
Identity
  ↓
Community + Authorization
  ↓
Session backbone
  ├──────────────→ Registration
  │                    ↓
  │               RosterRevision
  │                    ↓
  ├→ Rating → Team Formation → Voting
  │                         ↓
  └──────────────────────→ Match
                               ↓
                    ┌──────────┴──────────┐
                    ↓                     ↓
               Competition            Statistics
                    ↓                     ↓
                    └──────────┬──────────┘
                               ↓
                         Notifications

Media attaches across Identity/Community/Competition but is not authority for sports flow.
Realtime follows authoritative commands.
```

Important constraints:

- Registration cannot become authoritative before Membership/Player eligibility is trustworthy.

- Voting cannot exist before immutable CandidateSet.
- Match cannot consume target TeamDraw before MatchRoster snapshot path exists.
- Statistics target should not derive from current mutable Team arrays.
- Global sync retirement waits for all affected contexts.

# 7. N3.22.06 — Expand

Expand introduces target structures while old behavior keeps working.

Examples:

- new normalized tables;
- nullable target references;
- new RPCs;
- new read models;
- new Application ports;
- compatibility views/adapters;
- indexes required by target;
- internal migration/provenance tables.

Rules:

```text
EXPAND MUST BE
backward compatible
non-destructive
observable
testable from zero
```

A table being present does not transfer authority.

---

# 8. N3.22.07 — Shadow

Shadow means target logic executes without becoming source of truth.

Examples:

```text
legacy balancer result
+ target solver result
→ compare diagnostics
→ only current authoritative result exposed
```

or:

```text
legacy standings
+ target projection rebuilt from imported facts
→ compare
```

Shadow must never:

- send user-visible provider effects twice;
- mutate authoritative result;
- promote waitlist;
- cast votes;
- create official MatchEvent;
- leak hidden/private data.

Shadow mismatches become structured migration evidence.

---

# 9. N3.22.08 — Dual Compatibility

Dual compatibility allows old and new consumers during transition.

Preferred direction:

```text
ONE AUTHORITATIVE WRITE MODEL
          ↓
compatibility adapter/projection
          ↓
legacy reader
```

Avoid:

```text
legacy writer ─┐
               ├→ same semantic aggregate
new writer ────┘
```

If temporary dual-write is unavoidable, exactly one command path owns the transaction and writes both representations atomically or via a reliable derived projection. Two independent clients never write both models.

---

# 10. N3.22.09 — Cohort Cutover

Cut over bounded cohorts instead of all data simultaneously.

Possible cohort rules:

- newly created resources only;
- selected test Community;
- selected organizers/internal accounts;
- Sessions created after timestamp/version;
- existing DRAFT resource meeting migration preconditions;
- finished historical resources through backfill.

Never migrate an aggregate mid-critical execution merely because a global flag changed.

Critical rule:

```text
LIVE MATCH
→ remains on its authority/protocol until terminal/reconciled
```

Likewise, an active legacy Competition should not have its bracket semantics switched mid-round without explicit migration procedure.

# 11. N3.22.10 — Backfill

Backfill converts stored legacy evidence into target structures.

Properties:

```text
idempotent
bounded batches
checkpointed
resumable
provenance-aware
observable
safe under retry
```

## N4.22.10 — Backfill run

```text
migration_run
├── migration_name
├── code_version
├── source_checkpoint
├── started_at
├── completed_at
├── rows_examined
├── rows_migrated
├── anomalies
└── verification_status
```

## N4.22.10 — No silent guesses

If source lacks required context, create anomaly/review state.

Examples:

- old evaluation has no Community scope;
- legacy Session type cannot distinguish competition structure from play mode;
- PointEvents are incomplete but Game score exists;
- local-only shared Session has unknown authoritative ownership.

Do not synthesize certainty.

# 12. N3.22.11 — Verification

Verification is semantic.

Not enough:

```text
source rows = target rows
```

Need assertions such as:

```text
exactly one active Community owner
confirmed registration <= capacity
roster membership preserved
historical participant references resolve
Match event sequences contiguous where claimed
finished result agrees with source evidence
TeamDraw participant union equals roster revision
competition dependency graph acyclic
projection rebuild equals stored projection
no cross-Community authorization leakage
```

## N4.22.11 — Reconciliation report

Every backfill/cutover produces:

```text
PASS
PASS_WITH_DECLARED_LOSSINESS
BLOCKED_AMBIGUOUS
FAILED
```

`PASS_WITH_DECLARED_LOSSINESS` requires explicit field-level documentation, e.g. historical Match has result but detailed event coverage is unknown.

# 13. N3.22.12 — Read Cutover

Read cutover normally follows target population and verification.

Pattern:

```text
legacy writer remains authority temporarily
→ target shadow maintained
→ target read model verified
→ selected readers switch
```

Read cutover must not cause the UI to show target state that legacy writer cannot correctly maintain.

If target view depends on facts unavailable from legacy writes, write cutover must precede or happen atomically with read cutover.

---

# 14. N3.22.13 — Write Cutover

Write cutover is the authority transfer.

Required gate:

```text
authorization ready
constraints ready
idempotency ready
observability ready
rollback/forward-fix ready
compatible readers ready
```

After target write cutover for a unit:

```text
legacy UI may still exist
BUT
it must call target-compatible application contracts
or become read-only/blocked
```

It may not continue persisting independently to legacy state.

---

# 15. N3.22.14 — Contract

Contract removes obsolete compatibility structures only after evidence.

Examples:

- drop old array column;
- remove legacy RPC;
- remove table mirror;
- remove `local_id` unique indexes;
- remove DTO field;
- delete facade;
- retire localStorage key importer.

Contract gate includes:

```text
no active legacy writers
no supported client relies on contract
backfill verified
rollback window considered
telemetry says legacy path zero/acceptable
DB dependency scan clean
```

Contract is often a separate release from cutover.

---

# 16. N3.22.15 — Rollback

Rollback semantics depend on authority state.

## Before write cutover

Safe baseline:

```text
disable shadow/target reader
continue legacy authority
```

## After write cutover but before legacy contract

Possible:

```text
rollback frontend
→ old-compatible adapter reads target
```

or stop new cohort migrations while target aggregate remains target-owned.

Do not move a target-owned aggregate back to legacy automatically if target-only writes cannot be represented losslessly.

## After contract

Recovery is forward-fix or restore/DR procedure, not casual rollback.

---

# 17. N3.22.16 — Feature Flags

Flags route cohorts and behavior; they do not define truth by themselves.

Use cases:

```text
create new Sessions as V2
use target Registration UI
enable target read model
publish target Realtime
allow Match V2 starts
```

Rules:

- server authoritative for shared flow;
- flag evaluation observable;
- no security semantics;
- stable cohort assignment where needed;
- persisted authority marker wins after irreversible cutover.

# 18. N3.22.17 — Legacy Adapters

Legacy adapters are temporary anti-corruption layers.

Examples:

```text
legacy Session view
← TargetSessionReadModel adapter
```

or:

```text
old component intent
→ Application Use Case
→ target command
```

Adapters must:

- live at explicit boundary;
- be marked deprecated;
- expose no new target-only feature through legacy model;
- have owner/wave/removal gate;
- emit usage telemetry where useful.

Do not let legacy DTO become the permanent canonical domain because “the adapter already works”.

# 20. N3.22.19 — Identity Migration

Target from N2.02:

```text
Auth User
   ↓ explicit link
Player
```

with Guest/Participant distinct.

## N4.22.19 — Existing direct links

Existing trusted `players.user_id` relationships can seed `PlayerAccountLink`, preserving Player UUID where semantics match.

Do not create a new Player merely because the target table exists.

## N4.22.19 — Duplicate/conflicting players

Do not let generic semantic dedupe silently decide identity during cutover.

## N4.22.19 — Guests

Legacy guest/temporary names do not automatically become persistent Players.

## N4.22.19 — Account deletion

Migration must first eliminate FK/cascade patterns that could delete sports history when Auth account is deleted.

# 21. N3.22.20 — Community Migration

Target separates:

```text
CommunityMembership
≠
CommunityPlayer
```

## N4.22.20 — Governance state

Backfill active Membership state from the authoritative current membership source.

Join/pending semantics that currently share a table may be split into `CommunityJoinRequest` + Membership only when source status supports an exact mapping.

## N4.22.20 — Sports relation

Legacy `community_players.role` does not become governance automatically.

## N4.22.20 — Ownership

## N4.22.20 — Archive/lifecycle

Do not translate generic `deletedAt` blindly into `ARCHIVED`; lifecycle meaning must be supported by source evidence.

# 22. N3.22.21 — Organizer Migration

Critical semantic correction:

```text
Organizer
=
operational sports responsibility
```

not Community governance.

Legacy role mapping must be explicit.

Examples:

```text
legacy owner → governance OWNER
legacy admin → governance ADMIN
legacy organizer → operational responsibility ORGANIZER
```

If a legacy row combines meanings, split them intentionally.

Do not grant Community Admin to an Organizer merely to preserve current UI access.

After eligibility is migrated, new/target Sessions use `SessionOrganizerAssignment` where required.

Existing active legacy Session ownership/control remains legacy until Session/Match cutover rules allow migration.

# 23. N3.22.22 — Session Migration

Target Session removes authority from arrays and overloaded `type`.

## N4.22.22 — Normalize participants

Legacy:

```text
Session.selected_player_ids[]
```

Target:

```text
RosterRevision
└── RosterRevisionEntry[]
```

Historical migration preserves original Session ID and records source revision/provenance.

## N4.22.22 — Normalize teams

Legacy `team_ids[]` and Team `player_ids[]` become immutable historical TeamDraw/assignment evidence when sufficient data exists.

If solver input/version/seed are absent, do not invent them. Mark historical draw provenance as incomplete/legacy.

## N4.22.22 — Session type

Legacy `tournament | free_play` cannot be copied directly into the target dimensions because Competition structure and Session play mode are separate concepts.

Mapping must inspect associated Championship/competition evidence. Ambiguous cases are migrated with explicit legacy classification, not guessed.

## N4.22.22 — Active sessions

Never migrate an active execution in place during the first cutover.

Preferred initial policy:

```text
new Session → target
legacy active Session → legacy until terminal
legacy finished Session → historical backfill
eligible legacy draft → explicit migration after validation
```

# 24. N3.22.23 — Registration Introduction

Registration is mostly a new bounded context.

Important non-mappings:

```text
CommunityPresence
≠ RegistrationEntry

WhatsAppListDraft slot
≠ RegistrationEntry

Session.selectedPlayerIds
≠ proof of FIFO registration history
```

Therefore:

- new target Community Sessions may create RegistrationWindow;
- legacy upcoming Session can adopt Registration only through explicit organizer transition/import with a declared starting roster/queue;
- no historical FIFO sequence is fabricated;
- current selected roster may seed confirmed entries only if the organizer explicitly chooses an import policy and the migration records `source=LEGACY_ROSTER_IMPORT`;
- waitlist ordering begins from authoritative target actions after introduction unless exact source ordering exists.

This prevents a convenience migration from inventing fairness history.

## N4.22.24 — Overall

Never backfill target balancing authority from old overall.

Target profiles are recomputed attribute-by-attribute.

# 26. N3.22.25 — Team Formation Migration

Team Formation can be strangled earlier than some storage because much logic is pure TypeScript.

## N4.22.25 — First correction

Remove `overall` from the canonical solver contract/objective before target shared confirmation.

This is suitable for W1 pure-domain correction behind compatible UI.

## N4.22.25 — Solver port

Introduce target solver port consuming `PlayerBalanceSnapshot[]`.

Legacy UI can call adapter until target TeamFormation use case is complete.

## N4.22.25 — Historical divisions

Local `bestDivisions` are not automatically permanent TeamCandidateSets.

Only persisted/confirmed historical team assignments needed for sports history are migrated.

Missing algorithm version/seed/objective metadata remains `UNKNOWN_LEGACY`, not synthesized.

## N4.22.25 — Shared confirmation

Once `ConfirmTeamDraw` is target-authoritative, old UI must call that command. It cannot persist Teams directly.

# 27. N3.22.26 — Voting Introduction

Voting has no valid legacy equivalent merely because several draw options existed.

```text
three generated divisions
≠
three published vote candidates
```

Therefore:

- no historical ballots are fabricated;
- target CandidateSet must be immutable and tied to roster revision;
- VotingRound begins only after target CandidateSet publication;
- old organizer-choice sessions continue without voting;
- Community default voting policy applies only to target/new Sessions or explicit migrated configuration.

# 28. N3.22.27 — Match Migration

Match is the highest-risk cutover.

## N4.22.27 — Historical finished Game

A finished legacy Game may be imported as Match + MatchResult.

If PointEvents provide trustworthy ordering, import them preserving IDs/sequence where possible.

If detailed events are incomplete but final score/result is reliable:

```text
MatchResult = preserved factual result
capture_coverage = LEGACY_PARTIAL / SCORE_ONLY
```

Do not manufacture PointEvents to make the log “look complete”.

## N4.22.27 — Active Game

Initial rule:

```text
ACTIVE LEGACY GAME
DO NOT LIVE-MIGRATE
```

Finish/reconcile under legacy controller, then import terminal history.

## N4.22.27 — New Match V2

New target Match starts with:

```text
MatchRoster
RulesSnapshot
MatchControlLease
control_epoch
MatchEvent.sequence
MatchProjection
```

and never participates in generic sync/LWW.

## N4.22.27 — Session control transition

Session-level control remains only for legacy sessions. Target Match control is per Match/court.

Compatibility UI may translate “session controller” intent into Match control only where semantics are explicit.

# 29. N3.22.28 — Offline Migration

Offline migration follows operation classification, not entity type alone.

## N4.22.28 — Quick

Legacy local-only Quick-like Session can be imported to target IndexedDB as `LOCAL_OWNED` when no evidence says cloud/shared authority exists.

Preserve final UUID where valid.

## N4.22.28 — Shared local ambiguity

A local Session with `communityId` but no authoritative cloud state is not automatically published.

Classify, for example:

```text
LEGACY_UNRESOLVED_SHARED_LOCAL
```

and require explicit import/review.

## N4.22.28 — Match outbox

Do not convert generic pending sync records into Match commands unless command type, command_id, epoch and base sequence are known.

Legacy unsent PointEvents require dedicated reconciliation/import procedure.

## N4.22.28 — Account scope

Existing cache-owner protection is preserved. Unknown/other-account local data is sealed, never replayed under the currently logged-in account.

# 30. N3.22.29 — Realtime Migration

Realtime follows write authority.

Migration order:

```text

→ authoritative read model exists
→ snapshot protocol exists
→ semantic Broadcast enabled
→ client subscription cut over
```

Do not introduce Broadcast as a second write/sync path.

Legacy contexts may continue manual refresh/generic sync until their own cutover.

Target channel event must include revision/sequence checkpoint required by N2.13.

During coexistence, UI must not subscribe to both legacy and target sources and apply both as independent mutations to one aggregate.

# 31. N3.22.30 — Competition Migration

## N4.22.30 — Teams

# 32. N3.22.31 — Statistics Migration

# 34. N3.22.33 — Media Migration

# 35. N3.22.34 — Sync Retirement

Global sync is retired by subtraction.

## N4.22.34 — Per-context retirement ledger

For every entity currently in `LocalSyncPayload` / `OperationalSyncPayload` record:

```text
legacy upload used?
legacy download used?
target read path?
target write path?
local policy?
cutover cohort?
remaining consumers?
```

## N4.22.34 — Retirement order

```text
1 stop target writes through generic sync
2 stop target reads through generic sync
3 freeze legacy-only surfaces
4 remove entity from payload
5 remove merge/remap logic
6 remove service dependency
7 remove dead schema fields/indexes later
```

Never delete `syncService` first and then discover that one screen still depends on it.

## N4.22.34 — Exit gate

Global sync can disappear only when:

- no shared target aggregate relies on local/cloud merge;
- no critical pending mutation is stored only as `syncStatus=pending`;
- Quick is explicitly local-owned;
- Match uses typed outbox/reconciliation;
- shared data uses commands/queries;
- caches are recreatable;
- migration import paths for residual legacy local data are handled.

# 43. Client Compatibility During Cutover

A long-lived SPA/PWA means deployment and cutover are separate.

Strategy:

```text
SERVER ADDITIVE FIRST
→ support old contract window
→ deploy new client
→ measure old client usage
→ block/upgrade ancient mutating clients if needed
→ contract later
```

For critical writes, server may return:

```text
CLIENT_VERSION_UNSUPPORTED
UPGRADE_REQUIRED
```

rather than accepting an old payload that cannot express target invariants.

An old client is never allowed to resurrect a legacy writer for a target-owned aggregate.

# 52. Resultado canônico do C2.22

O target não é:

```text
LEGACY APP
→ BIG REWRITE
→ TARGET APP
```

É:

```text
LEGACY
  ↓
W0 safety + inventory
  ↓
small vertical target slices
  ↓
shadow / prove
  ↓
cut authority by aggregate/cohort
  ↓
legacy becomes compatibility only
  ↓
retire generic sync/localStorage authority
  ↓
contract
  ↓
TARGET
```

A arquitetura aceita temporariamente mais código para reduzir risco, mas exige que cada adapter, shadow e compatibility path possua **motivo, owner, telemetry e condição de remoção**.

A meta não é “migrar rápido”.

A meta é:

```text
MOVE AUTHORITY
WITHOUT LOSING FACTS,
WITHOUT INVENTING HISTORY,
WITHOUT DUPLICATING EFFECTS,
AND WITHOUT MAKING THE LEGACY PERMANENT.
```
