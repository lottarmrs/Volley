# 0. Regra de leitura

```text
SOURCE CHANGE
≠
SAFE PRODUCTION CHANGE
```

Uma mudança operacionalmente concluída precisa de caminho controlado para:

```text
build
→ verify
→ deploy compatible change
→ observe
→ backfill/migrate when needed
→ verify again
→ enable behavior
→ recover/forward-fix
→ contract legacy only when safe
```

Portanto:

```text
DEPLOYMENT
≠ git push
≠ build succeeded
≠ migration executed
```

O target otimiza simultaneamente:

```text
correctness
security
recoverability
observability
reproducibility
change velocity
cost discipline
```

sem transformar a infraestrutura numa plataforma maior que o produto.

## 1.1 CI

O único workflow em `.github/workflows` roda em PR/push para `main`:

```text
npm ci
npm run typecheck
npm run lint:eslint
npm run format:check
npm test
npm run build
```

Não existe nesse diretório um CD versionado. Isso não prova ausência de deploy externo; prova que o repositório não controla/documenta CD por GitHub Actions hoje.

## 1.2 Runtime/package

- `.nvmrc`: Node 22.
- Docker build: `node:22-alpine`.
- `package.json` aceita faixa de Node mais ampla.
- package manager: npm.
- lock: `package-lock.json` v3.
- CI/Docker já usam `npm ci`.

Target: uma política canônica de runtime/package para local + CI + build.

## 1.3 Serving

Docker multi-stage:

```text
Node build
→ Vite dist
→ nginx static server
```

nginx roda non-root. Preservar.

Tags amplas como `node:22-alpine` e `nginx:alpine` são mutáveis; supply-chain/reprodutibilidade precisa de política explícita.

## 1.4 Headers/cache

`nginx.conf` já tem:

- SPA fallback;
- gzip;
- cache longo de assets;
- `X-Frame-Options`;
- `X-XSS-Protection`;
- `X-Content-Type-Options`.

Target moderno inclui, conforme compatibilidade:

- CSP;
- `frame-ancestors`;
- Referrer-Policy;
- Permissions-Policy;
- HSTS no edge TLS;
- cache explícito de HTML;
- headers consistentes por location.

`X-XSS-Protection` não é controle principal de XSS.

## 1.5 Configuration/secrets

`.env.example` contém apenas public build config Supabase:

```text
VITE_SUPABASE_URL
VITE_SUPABASE_PUBLISHABLE_KEY
VITE_SUPABASE_ANON_KEY # legacy fallback
```

Regra target:

```text
VITE_* = public
SECRET MUST NOT BE VITE_*
```

## 1.6 Schema/migrations

O README orienta migrations cronológicas, mas existe também `supabase/migrations/schema.sql` como retrato consolidado.

A documentação operacional atual admite que esse snapshot pode divergir silenciosamente; o drift check descrito hoje é manual e não cobre integralmente tables/columns/RLS/grants/indexes/triggers/event triggers.

Target elimina ambiguidade:

```text
VERSIONED MIGRATION CHAIN = AUTHORITATIVE HISTORY
CONSOLIDATED SNAPSHOT = DERIVED / VERIFIED ARTIFACT
```

## 1.7 Rehearsal

O reset/cutover atual já foi ensaiado em projeto Supabase separado porque Supabase Branching dependia de capability/plano pago.

Decisão:

```text
ENVIRONMENT ISOLATION
MUST NOT DEPEND
ON PAID SUPABASE BRANCHING
```

Branching pode ser otimização futura, nunca requisito arquitetural.

## 1.8 Produção manual

Há checklist de Auth, schema drift e break-glass/cutover. Isso é melhor que conhecimento tribal, porém procedimentos privilegiados manuais devem ser exceção, não deployment path normal.

# 3. N3.21.01 — Environment Model

Ambientes representam níveis de confiança/isolamento, não apenas URLs.

```text
LOCAL
CI
PREVIEW
STAGING / REHEARSAL
PRODUCTION
```

Nem todo ambiente precisa ser persistente desde o início.

## N4 — Environment contract

Cada ambiente declara conceitualmente:

```text
environment_id
data_class
backend_project
frontend_origin
auth_origins
storage_namespace
provider_mode
secrets_scope
telemetry_scope
deploy_policy
retention_policy
```

O conceito é `isolated environment capability`, não `Supabase Branch`.

Implementações válidas:

- Supabase CLI/local containers;
- projeto dedicado;
- projeto temporário;
- Supabase Branching;
- provider equivalente futuro.

```text
PRODUCTION DATA
MUST NOT
BECOME ROUTINE TEST DATA
```

# 4. N3.21.02 — Local Environment

Target:

```text
Vite local
+
local Supabase stack for DB-sensitive work
+
provider fakes/sandboxes
```

Dois modos:

### UI/domain-only

- Vite;
- IndexedDB/cache/drafts;
- fake adapters.

### Full-stack

- Vite;
- local PostgreSQL/Supabase;
- migrations from zero;
- local Auth/Storage/Realtime onde suportado.

Seeds:

- sintéticos;
- determinísticos;
- versionados;
- idempotentes quando possível;
- separados de production migrations.

`.env` local é ignored, least privilege e não usa prod credentials por default.

# 5. N3.21.03 — CI Environment

CI é descartável e reproduzível:

```text
checkout
→ deterministic install
→ static gates
→ tests
→ fresh DB/migrations
→ RLS/RPC/constraint/concurrency tests
→ build
→ evidence
→ teardown
```

CI não depende de:

- production DB;
- production service role;
- production Storage;
- production provider secrets.

Preferência inicial para DB:

```text
Supabase CLI/local containers
```

porque reduz custo/shared-state flakes e não exige branching pago.

Se alguma capability não for fiel localmente, usar projeto CI isolado de escopo mínimo.

Preservar artifacts de falha: Playwright traces, test reports, migration logs, schema diff, selected query plans.

# 6. N3.21.04 — Preview Environment

Preview valida um commit antes do merge; não é clone de produção.

### Frontend-only preview

Aceitável para UI-only/contract-compatible changes.

### Backend-aware preview

Mudanças de schema/RPC/auth precisam backend compatível.

Alternativas:

```text
shared staging backend
+ cheap/simple
- cross-PR interference/schema mismatch
```

versus

```text
isolated backend per preview
+ fidelity/isolation
- cost/provisioning/cleanup
```

Decisão: não exigir backend cloud por PR inicialmente. Isolar quando o risco justificar.

Production Auth não libera wildcard amplo de preview origins por conveniência. Preferir preview ligado a staging Auth/controlled allowlist.

# 7. N3.21.05 — Staging

Staging/rehearsal production-like:

- separate Supabase project;
- separate Auth users;
- separate Storage;
- sandbox/fake external providers;
- separate telemetry;
- same configuration shape as production.

Pode começar `on-demand` em vez de 24/7.

Evoluir para persistent staging quando deploy frequency, team size, provider integration ou rehearsal cost justificar.

Nunca clone rotineiramente production PII.

# 8. N3.21.06 — Production

Único ambiente autorizado a servir shared state real:

- dedicated backend;
- production Auth;
- production Storage;
- DNS/TLS;
- real provider credentials;
- backups;
- restricted admin access;
- release identifiers;
- alerting.

Mudança permanente de schema/config crítica deve ser versionada/reconciliável.

Dashboard-only settings inevitáveis precisam checklist + verification + change record até automação segura existir.

# 9. N3.21.07 — Environment Isolation

Isolamento em quatro dimensões:

```text
DATA
IDENTITY
SECRETS
EXTERNAL EFFECTS
```

Nunca:

```text
preview → production write
CI → production write
staging cleanup → production resources
```

Production users não são test fixtures.

Cada environment tem secret scope próprio.

CI/staging não enviam uncontrolled real email/message/webhook/media side effect.

Recursos devem carregar environment identifier quando o provider permitir.

Separar:

```text
PUBLIC BUILD CONFIG
SERVER SECRET CONFIG
DOMAIN POLICY
RUNTIME OPERATIONAL CONFIG
```

Tudo em `VITE_*` é público.

Não esconder domain rules críticas em env vars opacas quando deveriam ser policies versionadas.

# 11. N3.21.09 — Secrets Management

Regra absoluta:

```text
SERVICE ROLE
PROVIDER SECRET
SMTP SECRET
OAUTH CLIENT SECRET
SIGNING SECRET
MUST NOT ENTER CLIENT BUNDLE
```

Secrets ficam em secret store de CI/runtime/provider.

Nunca em:

- source;
- real `.env.example` values;
- logs;
- test snapshots;
- localStorage/IndexedDB.

Preferir scoped GitHub Environments e short-lived/OIDC credentials onde houver suporte.

Cada secret tem owner, rotation, dependents, revoke e verification procedure.

Leak response:

```text
revoke first
→ rotate
→ assess exposure
→ remove from future code
→ record incident
```

Git history cleanup não substitui revogação.

# 12. N3.21.10 — Runtime Versioning

Target:

```text
ONE NODE MAJOR POLICY
across local + CI + Docker build
```

Estado atual converge em Node 22 na `.nvmrc`/Docker; reconciliar `package.json` mais permissivo.

Trade-off:

- major-only: fácil security patch, menor reprodução;
- exact patch/digest: reprodução forte, mais manutenção.

Decisão: pin canonical LTS major agora + drift checks; digest/exact patch em production build quando tooling facilitar updates. Exact patch policy permanece `OPEN`.

Browser support matrix também deve ser explícita/testada.

# 17. N3.21.15 — Database Migrations

```text
VERSIONED MIGRATIONS
ARE AUTHORITATIVE SCHEMA HISTORY
```

`schema.sql`, se mantido, é generated bootstrap/review/documentation artifact, não second writable truth.

Ideal:

```text
migration chain
→ fresh DB
→ generated/introspected snapshot
→ drift verification
```

Migration qualities:

- ordered;
- deterministic;
- reviewed;
- bounded lock impact;
- compatible with deploy ordering;
- tested fresh and upgrade path.

No casual destructive DDL.

High-risk DDL avalia table size, lock mode, rewrite risk, index build, statement timeout e maintenance-window need.

Verification inclui RLS, policies, grants, function security/search_path, triggers/event triggers, constraints/indexes.

---

# 18. N3.21.16 — Backfills

Separar:

```text
SCHEMA EXPANSION
DATA BACKFILL
CONSTRAINT ENFORCEMENT
LEGACY CONTRACT
```

Backfill deve ser:

- resumable;
- idempotent/checkpointed;
- bounded batch;
- observable;
- cancelable;
- retry-safe;
- accompanied by semantic verification.

Evitar giant transaction em hot tables.

Dual-write, se necessário, é time-boxed, observable, reconcilable e já nasce com removal plan.

# 19. N3.21.17 — Deployment Ordering

Canonical high-risk order:

```text
1 precheck
2 backup/restore confidence where required
3 DB expand backwards-compatibly
4 server/RPC/worker compatible with old+new
5 frontend compatible deploy
6 verify
7 backfill
8 verify data
9 enable feature/cohort
10 observe
11 contract legacy later
```

Exemplo: substituir `sessions.selected_player_ids[]` por roster normalizado:

```text
add new tables
→ deploy old/new adapter
→ backfill safe cohorts
→ cut writes
→ verify parity
→ cut reads
→ wait client window
→ stop legacy writes
→ drop array later
```

SPA tabs antigos continuam abertos durante deploy; server contracts precisam compatibility window explícita ou safe upgrade-required rejection.

# 20. N3.21.18 — Rollback

Rollback difere por component.

### Frontend

Previous immutable artifact pode voltar rápido se DB continua backward-compatible.

### Database

```text
DO NOT ASSUME DOWN MIGRATION IS SAFE
```

Preferir forward-fix. Reverse destructive migration pode perder writes feitos no novo schema.

### Behavior

Flag/kill switch pode desligar behavior mantendo expanded schema.

### Domain irreversibility

Sent notification, official result ou historical fact não são “rolled back” como deployment artifact; exigem domain correction semantics.

# 21. N3.21.19 — Feature Flags

```text
FEATURE FLAG
≠ AUTHORIZATION
≠ DOMAIN VALIDATION
```

Usos:

- gradual rollout;
- migration cutover;
- beta;
- algorithm version cohort;
- read-model switch;
- UI exposure.

Scopes só quando necessários: global/environment/cohort/community/entity.

Critical mutation flag é checked server-side.

Cada flag tem owner, purpose, safe default e expected removal.

---

# 22. N3.21.20 — Kill Switches

```text
feature flag → rollout
kill switch → stop harm quickly
```

Candidate switches:

- external notification delivery;
- media uploads/processing;
- new Quick→Cloud publication;
- new Competition officialization;
- new Registration joins under systemic risk;
- Match takeover;
- creation/start of new shared Matches.

Live Match caution: bloquear novos starts/takeovers é preferível a abandonar Match já LIVE. Emergency state deve ser authenticated, audited, observable e reversible.

# 23. N3.21.21 — Background Workers

Async work que não deve alongar critical user transaction:

- notifications;
- media;
- non-critical projections;
- cleanup;
- exports;
- some backfills.

```text
DOMAIN TX
→ OUTBOX/JOB FACT
→ WORKER
→ SIDE EFFECT / PROJECTION
```

Default current-scale: managed/serverless worker where practical; dedicated always-on fleet só com throughput/latency evidence.

Provider/scheduler sits behind ports.

Assume:

```text
AT LEAST ONCE
```

Handlers são idempotent. No false exactly-once claim.

---

# 24. N3.21.22 — Scheduled Jobs

Usos possíveis:

- reminders;
- orphan media cleanup;
- lease diagnostics/cleanup;
- integrity checks;
- retention;
- rollups.

Canonical concept é `ScheduledJob`, não `pg_cron`.

Adapters possíveis: pg_cron, provider scheduler, external scheduler.

Time-triggered job revalida source state no momento da execução.

Jobs non-overlap usam lease/advisory lock/checkpoint quando necessário.

# 25. N3.21.23 — Outbox Processing

Loop target:

```text
claim bounded batch
→ lease/lock
→ execute handler
→ record attempt
→ success ack
or retry/backoff
or terminal/poison handling
```

Domain mutation + outbox insert = same transaction.

Provider call = outside transaction.

Concurrent claim usa safe DB pattern (`SKIP LOCKED` equivalent when appropriate).

No infinite hot loop.

Metrics:

- pending;
- oldest age;
- retries;
- terminal failures;
- handler latency.

# 32. N3.21.30 — PWA Deployment

Target N2.12:

```text
SERVICE WORKER
FOR APP SHELL / STATIC ASSETS
NOT GENERAL DOMAIN SYNC ENGINE
```

Service worker não pode prender cliente indefinidamente em old code.

- versioned caches;
- old cache cleanup;
- update UX;
- backend compatibility window.

Não blindly cache mutation responses, auth-sensitive API, Realtime ou one-time auth callbacks.

# 33. N3.21.31 — Backup

Segue N2.17 criticality:

```text
C0 source facts → strongest durability
C1 snapshots → durable
C2 projections → rebuildable
C3 ephemeral → no backup requirement
```

Use managed backup/PITR where plan actually supports and RPO justifies. Não assumir paid capability.

Se indisponível, supplemental logical backup/export conforme escala.

DB backup não implica Storage media backup.

Backup job green não prova restore.

---

# 34. N3.21.32 — Restore

Sempre primeiro em isolated environment:

```text
freeze external effects
→ provision target
→ restore DB
→ restore/verify Storage
→ integrity checks
→ rebuild selected projections
→ verify auth/resource isolation
→ reapply privacy deletion/anonymization obligations if needed
→ app compatibility
→ record actual RTO/RPO evidence
```

Restored rehearsal não envia historical notifications/production provider calls.

Disaster restore não pode ressuscitar permanentemente data que deveria permanecer deleted/anonymized.

# 35. N3.21.33 — Disaster Recovery

Initial scenarios:

- frontend hosting failure;
- bad frontend release;
- bad DB migration;
- credential compromise;
- Supabase outage;
- Storage loss/corruption;
- operator destructive error;
- DNS/account loss;
- provider/region incident.

Não exigir multi-region active-active Postgres agora. Custo/conflict/replication complexity só entra com business RTO/RPO evidence.

Backend outage preserves offline Quick/cache where safe, mas shared Registration/roles/votes never fake success.

# 36. N3.21.34 — Production Access

Least privilege. Conceptual classes:

```text
RELEASE OPERATOR
READ-ONLY DIAGNOSTIC
DATABASE PRIVILEGED
SECURITY/BREAK-GLASS
PROVIDER ADMIN
```

Uma pessoa pode inicialmente acumular responsabilidades, mas capabilities continuam separadas conceitualmente.

Normal debugging prefere telemetry/scoped reads/operator tools, não unrestricted SQL browsing.

Privileged accounts usam MFA onde suportado. Operator tooling minimiza PII.

---

# 37. N3.21.35 — Break Glass

Para cenários onde normal auth/automation não consegue recuperar com segurança.

Properties:

- documented;
- rare;
- strong-auth protected;
- minimally scoped;
- time-bounded;
- externally recorded when possible;
- followed by credential/session rotation review;
- post-action incident/change record.

Two-person approval é desejável quando team size permite, mas não é requisito fictício para operação de uma pessoa. Sem peer: predefined procedure + explicit incident record + post-review.

Nunca criar hidden app backdoor para emergency.

---

# 38. N3.21.36 — Data Repair

Hierarchy:

```text
1 semantic correction command
2 versioned repair job/script
3 scoped migration/backfill
4 privileged manual SQL only as emergency exception
```

Repair script:

- dry-run where practical;
- explicit target scope;
- idempotent/checkpointed;
- precondition assertions;
- before/after counts;
- invariant verification;
- audit/change record.

Immutable sports history usa correction/revision semantics, não silent fact mutation.

Emergency SQL deve ser captured and reconciled into versioned prevention/history.

# 39. N3.21.37 — Incident Operations

```text

→ CLASSIFY
→ ASSIGN OWNER
→ STOP THE BLEED
→ PRESERVE EVIDENCE
→ MITIGATE
→ RECOVER
```

# 41. N3.21.39 — Change Management

Risk-based, não ceremony uniforme.

### O0 — low

copy/UI/non-critical refactor.

### O1 — medium

additive query/projection/provider template/reversible rollout.

### O2 — high

RLS/RPC, Registration concurrency, Match control/events, officialization, identity linking, schema backfill/data repair.

### O3 — critical/destructive

production reset, destructive contract, ownership/auth recovery, bulk privacy deletion, restore/cutover.

Higher risk adds design review, DB tests, rehearsal, backup confidence, explicit owner, observation, flag and recovery plan.

Do not apply O3 ceremony to O0 changes.

# 54. Final architectural statement

```text
LOCAL/CI ARE REPRODUCIBLE
PREVIEW/STAGING ARE ISOLATED BY RISK
PRODUCTION IS PRIVILEGED

MIGRATIONS ARE VERSIONED
BACKFILLS ARE RESUMABLE
DEPLOYS ARE COMPATIBLE
FLAGS CONTROL ROLLOUT, NOT AUTH
ROLLBACK RESPECTS IRREVERSIBILITY

EXTERNAL EFFECTS ARE ASYNC
WORKERS ARE AT-LEAST-ONCE
RESTORES ARE TESTED
BREAK-GLASS IS EXCEPTIONAL
POST-DEPLOY VERIFICATION IS PART OF DEPLOY
```

O objetivo não é máxima sofisticação de infraestrutura. É tornar o Volley evolutivo e operável com segurança enquanto o sistema sai do formato atual de SPA/Supabase para shared state mais crítico, sem transformar cada futura mudança de schema, segurança ou domínio numa aposta operacional.
