## 0. Regra de leitura

Este documento define o **target canônico** para o funcionamento online/offline do Volley.

A regra mais importante é:

```text
OFFLINE IS AN OPERATION POLICY
NOT AN APPLICATION-WIDE DATA SYNCHRONIZATION MODE
```

O Volley não será classificado globalmente como:

```text
online-first
```

ou:

```text
local-first
```

sem qualificação.

Cada operação pertence explicitamente a uma das classes:

```text
ONLINE_AUTHORITATIVE
OFFLINE_OWNED
CACHED_READ
LOCAL_DRAFT
CONDITIONALLY_OFFLINE_COMMAND
```

A consequência estrutural é:

```text
shared mutable truth
→ server-authoritative

local-only product flow
→ may be offline-owned

read convenience
→ cache

unfinished user input
→ draft

special continuity protocol
→ conditionally-offline command
```

Não existe uma regra genérica:

```text
edit anything locally
→ sync later
→ merge somehow
```

Outra regra fundamental:

```text
OFFLINE CAPABILITY
MUST NOT create
DUAL AUTHORITY
```

Quando um aggregate possui uma autoridade, uma segunda cópia mutável não pode disputar a mesma verdade sem um protocolo específico.

# 1. Current State — evidência do repositório

## 1.1 O app atual é descrito como local-first com Supabase opcional

`AGENTS.md` declara explicitamente:

```text
Local-first React 19 + Vite 6 app.
Optional Supabase sync.
All data persists to localStorage unless cloud sync is configured.
```

Essa decisão foi útil para tornar o produto funcional sem backend obrigatório e para permitir trabalho offline desde cedo.

Entretanto, o domínio atual cresceu para incluir conceitos que não podem ser reconciliados de forma segura por uma sincronização genérica, como:

```text
Community governance
Membership
Registration capacity / waitlist
shared TeamDraw selection
participant voting
Match control
Competition officialization
```

Esses conceitos possuem concorrência, autorização e ordenação próprias.

## 1.2 `localStorageRepository` persiste praticamente todo o domínio

O arquivo atual possui chaves para:

```text
players
sessions
teams
games
points
reports
communities
communityPresence
communityRules
championships
championshipTeams
championshipRounds
championshipRequests
WhatsApp drafts/templates
sync issue ledger
```

Portanto `localStorage` hoje é mais que preferência/cache: ele funciona como banco operacional principal do browser.

Também já existe uma proteção importante:

```text
LOCAL_CACHE_OWNER_KEY
```

junto de `validateCacheOwner()` e `clearLocalDomainCache()`, para evitar que dados da conta anterior sejam enviados pela conta seguinte.

Esse objetivo de isolamento será preservado no target, mas com armazenamento estruturado e escopo explícito.

## 1.3 `CloudSyncStatus` é um metadado transversal

O tipo atual é:

```text
'local' | 'pending' | 'synced' | 'conflict' | 'error'
```

E diversos domain models carregam campos como:

```text
cloudId
syncStatus
lastSyncedAt
deletedAt
```

Isso demonstra que a infraestrutura de sincronização penetrou no shape das entidades.

No target:

```text
sync metadata
!=
domain lifecycle
```

Uma RegistrationEntry não será `pending` porque “ainda não sincronizou”; ela será PENDING/CONFIRMED/WAITLISTED conforme seu domínio.

Uma Quick Session poderá ser local-authoritative sem precisar se declarar genericamente `syncStatus='local'`.

## 1.4 `operationalCloudService` trata muitas entidades como um payload sincronizável

`OperationalSyncPayload` reúne:

```text
sessions
teams
games
pointEvents
gameReports
sessionReports
presenceRecords
drafts
```

Os mappers persistem `local_id`, `deleted_at`, timestamps e metadados de sync.

O serviço também possui leitura paginada de tabelas inteiras e paths de upsert genérico.

Isso funciona para um modelo de replicação de coleções, mas não expressa corretamente commands como:

```text
JoinRegistration
LeaveRegistration
TransferOwnership
AwardPoint
CastTeamVote
ConfirmTeamDraw
OfficializeCompetitionResult
```

## 1.5 `syncService` já precisou criar reconciliação semântica e dedupe por timestamp

O serviço atual possui:

```text
communitySemanticKey()
playerSemanticKey()
getSyncTimestamp()
dedupeByLatest()
reference remapping
soft-delete marking
semantic duplicate consolidation
```

Isso é evidência de que uma sincronização global passou a resolver problemas que pertencem a Identity, Data Architecture e aos bounded contexts.

Em particular, `dedupeByLatest()` e timestamps podem ser úteis para dados não críticos, mas não podem decidir:

```text
quem ficou com a última vaga
qual voto é válido após o fechamento
qual MatchEvent vem depois
quem é Owner
qual resultado é oficial
```

## 1.6 `useCloudSync` já conhece o custo dos conflitos de controle

O hook atual:

- monta o payload completo;
- faz upload/download/sync bidirecional;
- possui lock de operação com TTL em `localStorage`;
- registra falhas parciais em um ledger;
- tenta novamente após reconexão;
- limpa dados quando detecta cache de outra conta;
- detecta Session control conflicts;
- marca eventos locais conflitantes para resolução posterior.

Essas proteções são valiosas.

O target preserva os princípios de:

```text
account isolation
idempotent retry
failure visibility
conflict explicitness
```

mas remove a necessidade de reconciliar a maior parte do domínio depois do fato.

## 1.7 A conectividade atual já não confia cegamente em `navigator.onLine`

`logic/connectivity.ts` documenta corretamente que Wi-Fi conectado pode não possuir internet e que uma requisição real é evidência melhor que `navigator.onLine`.

Essa decisão será preservada e ampliada para distinguir:

```text
network reachability
backend reachability
auth readiness
data freshness
operation availability
```

# 2. N3.12.01 — Authority Model

## N4.12.01.01 — Uma autoridade por aggregate

Para qualquer aggregate mutável, deve ser possível responder:

> Quem tem autoridade para aceitar a próxima mutation agora?

Exemplos:

```text
Community
→ server

RegistrationWindow
→ server

VotingRound
→ server

Competition
→ server

published/shared Session
→ server

unpublished Quick Session
→ local device

LIVE Match with connectivity
→ server under MatchControlLease

LIVE Match during approved offline continuation
→ local controller records commands provisionally,
   server remains final reconciliation authority
```

Não usar:

```text
cloud copy
+
local copy
+
latest timestamp wins
```

como authority model.

## N4.12.01.02 — Authority é diferente de storage location

Ter uma cópia no IndexedDB não torna o browser autoridade.

Exemplo:

```text
cached Community
lives locally
but authority = server
```

Da mesma forma:

```text
Quick Session local
may later be uploaded to cloud
but before successful handoff
its authority = device
```

## N5.12.01 — Authority transition must be explicit

Uma mudança de autoridade precisa de um protocolo identificável.

Principal exemplo:

```text
Quick LOCAL_OWNED
→ PublishQuickSession
→ SERVER_OWNED
```

Não ocorre apenas porque a internet voltou.

## N10.12.01

- Internet volta enquanto Quick está ativa: a Session não passa para cloud automaticamente.
- Cache recebe atualização do servidor: cache não ganha authority.
- Um timestamp local mais recente não sobrescreve Registration server-side.

# 3. N3.12.02 — Operation Classification

## N4.12.02.01 — Classes canônicas

### `ONLINE_AUTHORITATIVE`

Mutation só pode ser aceita pela autoridade remota atual.

Offline:

```text
fail closed
```

sem criar “sucesso local”.

### `OFFLINE_OWNED`

Aggregate nasce e permanece local-authoritative até handoff explícito.

### `CACHED_READ`

Uma cópia local pode ser mostrada sem declarar que é atual.

### `LOCAL_DRAFT`

Input ainda não submetido pode ser persistido localmente.

Draft não altera shared state.

### `CONDITIONALLY_OFFLINE_COMMAND`

Uma command normalmente remota possui um protocolo explícito de continuidade offline, com constraints adicionais e posterior reconciliation.

V1 principal:

```text
Match controller
```

## N4.12.02.02 — Matriz inicial de operações

| Capability / operação | Classe target |

| Criar Quick Session local | OFFLINE_OWNED |
| Configurar Quick local | OFFLINE_OWNED |

| Registrar Match local de Quick | OFFLINE_OWNED |
| Publicar Quick | ONLINE_AUTHORITATIVE handoff command |
| Ler Community previamente visitada | CACHED_READ |
| Criar Community efetiva | ONLINE_AUTHORITATIVE |

| Criar shared Community Session | ONLINE_AUTHORITATIVE |

## N5.12.02 — Policy é por command/query, não por entidade inteira

Uma mesma área pode conter operações de classes diferentes.

Exemplo:

```text
Team Formation
├── read BalanceInputSnapshot → CACHED_READ
├── run solver → local computation
└── ConfirmTeamDraw → ONLINE_AUTHORITATIVE
```

## N10.12.02

- Offline solver funciona com snapshot válido; confirmação compartilhada não.
- Draft de avaliação pode ser escrito offline; `SubmitEvaluation` não finge sucesso.
- Community page abre de cache; `RemoveMember` permanece indisponível.

# 4. N3.12.03 — Online-Authoritative Operations

## N4.12.03.01 — Shared mutable state

São online-authoritative por padrão:

```text
Community governance
Membership
JoinRequest
Registration
Voting
shared TeamDraw confirmation
Competition administration
OfficialCompetitionResult
Match takeover/control transfer
PlayerAccountLink critical mutations
Media attachment shared state
```

## N5.12.03 — Offline UX

Quando offline, a UI pode:

- mostrar o último snapshot cacheado;
- explicar que a ação exige conexão;
- manter input em draft quando semanticamente seguro;
- permitir refresh/retry quando a rede voltar.

Não pode:

```text
optimistically mark as committed
and promise to reconcile later
```

para uma operação não autorizada offline.

## N5.12.03.02 — Por que Registration não entra em outbox genérica

Exemplo:

```text
12:00 user offline clicks Join
12:01 last slot taken online
12:15 device reconnects
```

Se o clique offline fosse tratado como vaga confirmada, o cliente teria mentido.

Se fosse apenas enfileirado silenciosamente, a ordem temporal/FIFO também seria ambígua.

Portanto:

```text
JoinRegistration offline
→ OFFLINE_UNAVAILABLE
```

O mesmo princípio vale para Voting e governance.

## N10.12.03

- Dois usuários offline tentam última vaga: nenhum recebe confirmação local falsa.
- Vote após deadline enquanto dispositivo estava offline não é retroativamente aceito.
- Owner offline não transfere ownership por fila tardia.

# 5. N3.12.04 — Offline-Owned Data

## N4.12.04.01 — Significado

Offline-owned significa:

> Enquanto este aggregate não passou por authority handoff, o dispositivo é sua fonte primária de verdade operacional.

Principal capability:

```text
Quick Session
```

Pode incluir:

```text
QuickSession local state
local roster/participants
local TeamDraw
local Matches
local MatchEvents
local derived reports
```

## N5.12.04 — Persistência antes de confirmação visual

Para eventos críticos locais:

```text
write durable local state
→ commit IndexedDB transaction
→ then show action as persisted
```

Não:

```text
update React state
→ maybe persist later
```

quando a perda significaria apagar pontos de uma partida.

## N8.12.04 — Local storage failure

Se IndexedDB falhar/quota estourar durante uma Match offline:

```text
fail closed for new critical events
```

A UI deve dizer que não consegue garantir persistência.

Não continuar registrando placar apenas em memória.

## N10.12.04

- Browser fecha depois do ponto: ao reabrir, ponto persistido reaparece.
- IndexedDB write falha: UI não declara ponto salvo.
- React component remonta: authority não depende de component memory.

# 6. N3.12.05 — Cached Reads

## N4.12.05.01 — Cache é conveniência

Cache pode guardar snapshots de:

```text
Community summary
upcoming Sessions
recent history
Competition bracket/standings
Player public/contextual profile
Notification Inbox subset
```

conforme privacy policy.

Cache nunca é fonte para decidir shared mutation sem revalidação server-side.

## N4.12.05.02 — Cache envelope

Modelo conceitual:

```text
CachedSnapshot<T>
├── cache_key
├── owner_scope
├── resource_type
├── resource_id
├── data
├── server_revision / sequence nullable
├── schema_version
├── fetched_at
├── validated_at
└── visibility_context
```

## N5.12.05 — Bounded cache

Não baixar toda a história do usuário/comunidade por padrão.

Preferir:

```text
active context
recent pages
explicitly opened resources
```

com paginação e eviction de dados recriáveis.

## N8.12.05 — Privacy

Dados de alta sensibilidade contextual não entram em cache apenas porque tecnicamente cabem.

Caching deve obedecer allowlist/purpose.

Exemplos que exigem cuidado especial:

```text
individual evaluations
private ballots
admin-only membership data
security/audit data
```

## N10.12.05

- Usuário offline abre Community visitada ontem: vê snapshot marcado como possivelmente desatualizado.
- Cache sem revision não é usado para um command que exige expectedRevision atual.
- Eviction remove cache antigo sem tocar Quick local/outbox.

# 7. N3.12.06 — Local Drafts

## N4.12.06.01 — Draft não é aggregate publicado

Draft pode existir para:

```text
Community creation form
Session form
Competition configuration form
PlayerEvaluation form
media crop/preview state
message/share drafts
```

Sem produzir shared mutation.

## N5.12.06 — Explicit submission

A transição é:

```text
LOCAL_DRAFT
→ Submit/Create command online
→ authoritative server response
→ draft archived/deleted
```

## N5.12.06.02 — No automatic multi-device merge V1

Um draft local não será transformado em collaborative document.

V1:

```text
draft = device/local-scope
```

Se futuramente drafts compartilhados forem necessários, serão outro modelo server-side.

## N10.12.06

- Usuário edita Session form offline: draft persiste.
- Reconecta: nada é criado sem submit explícito.
- Mesmo usuário abre outro dispositivo: draft local não aparece como se tivesse sido sincronizado.

# 8. N3.12.07 — Conditional Offline Commands

## N4.12.07.01 — Exception, não default

Uma command só entra nessa classe se houver protocolo explícito para:

```text
prior authority proof
ordering
idempotency
conflict detection
reconciliation
failure recovery
```

V1 principal:

```text
Match control continuity
```

## N4.12.07.02 — Match prerequisites

Antes da perda de rede, o controller deve possuir contexto autoritativo suficiente, por exemplo:

```text
match_id
controller identity
control_epoch
base last_sequence
rules snapshot
roster snapshot
local device id
```

Exact lease/offline-grace semantics pertencem ao N2.07, mas este contexto impõe:

```text
no epoch
→ no offline continuation
```

## N5.12.07 — Reconnect protocol

```text
1. stop blind replay
2. fetch authoritative Match snapshot
3. compare epoch
4. compare last_sequence/base chain
5. if compatible → replay ordered idempotent commands
6. server applies/rejects each command
7. if incompatible → RECONCILIATION_REQUIRED
```

Nunca:

```text
merge two scores by updated_at
```

## N5.12.07.02 — Takeover remains online-only

Um dispositivo offline não pode decidir que tomou controle porque não vê o estado atual.

## N10.12.07

- Controller perde rede e registra 5 pontos: comandos ficam duráveis e ordenados.
- Outro controller toma controle online: epoch muda; comandos antigos não são autoaplicados.
- Reconnect com mesmo epoch/sequence: replay em ordem.
- Replay duplicado: command IDs impedem efeito duplicado.

# 9. N3.12.08 — Quick Session Authority

## N4.12.08.01 — Quick nasce independente da nuvem

Quick Session não exige Community e pode nascer:

```text
LOCAL_OWNED
```

com UUID final gerado no cliente.

Ela não recebe um ID temporário que depois precisa ser substituído por `cloudId`.

## N5.12.08 — Final IDs

```text
session_id = UUID final
match_id = UUID final
participant_id = UUID final
match_event_id / command_id = UUID final
```

quando gerados localmente.

O servidor pode aceitar esses IDs no handoff após validação.

## N5.12.08.02 — Local provenance

Quick local deve carregar provenance suficiente para distinguir:

```text
LOCAL_QUICK
```

de um aggregate compartilhado.

Isso é melhor que inferir por ausência de `cloudId`.

## N8.12.08 — Multi-tab local writer

Duas abas do mesmo browser não devem editar a mesma Quick silenciosamente.

Usar:

```text
local aggregate revision
+
local writer coordination/lease
```

Web Locks/BroadcastChannel/IndexedDB lease podem ser usados como implementação, com fallback apropriado.

Esse lock é coordenação local, não autorização de segurança.

## N10.12.08

- Quick é criada sem internet e recebe IDs finais.
- Reload preserva a Session.
- Segunda aba tenta controlar a mesma Quick: recebe read-only/conflict ou assume após protocolo local; não grava em paralelo silenciosamente.

# 10. N3.12.09 — Quick Publication / Authority Handoff

## N4.12.09.01 — Handoff explícito

Comando conceitual:

```text
PublishQuickSession
```

O objetivo não é “sincronizar diferenças”.

É:

> Transferir uma Session coerente que até agora era local-authoritative para o servidor, passando a obedecer às regras server-authoritative.

## N4.12.09.02 — State machine de authority

Modelo conceitual:

```text
LOCAL_OWNED
   ↓ PublishQuickSession(command_id)
HANDOFF_IN_FLIGHT
   ├── confirmed failure before acceptance → LOCAL_OWNED
   ├── outcome unknown → HANDOFF_UNKNOWN
   └── authoritative ACK → SERVER_OWNED
```

`HANDOFF_UNKNOWN` é obrigatório conceitualmente porque:

```text
request timeout
!=
server rollback
```

O servidor pode ter commitado e a resposta ter se perdido.

Enquanto outcome for desconhecido:

```text
freeze local authority-changing mutations
retry/query with SAME command_id
```

para não criar duas autoridades.

## N5.12.09 — One-way handoff

Depois de `SERVER_OWNED`:

```text
old local aggregate
→ cache/projection only
```

Ele não volta automaticamente a ser local-owned quando a rede cai.

Uma Match dentro dele pode usar o protocolo condicional de N2.07, mas isso é outra capability.

## N5.12.09.02 — Safe handoff boundary

V1 deve preferir handoff em limites seguros:

```text
before live shared execution
or
after local Quick completion
```

Handoff de uma Match local já LIVE com eventos concorrentes não entra no Publish genérico.

Se essa experiência for necessária no futuro, exige protocolo/ADR específico.

## N5.12.09.03 — Server validation

O servidor não aceita blob local cegamente.

Valida:

```text
actor
payload/schema version
IDs
referential integrity
session lifecycle
participant snapshots
team snapshot invariants
match/event sequence
allowed provenance
idempotency
```

## N5.12.09.04 — Historical provenance

Uma Quick importada pode contribuir para history conforme policy, mas permanece identificável como origem Quick/local import.

Ela não se torna OfficialCompetitionResult por publicação.

## N10.12.09

- Publish timeout depois do commit: local entra `HANDOFF_UNKNOWN`; retry igual retorna o mesmo server result.
- Usuário não consegue continuar editando como local e simultaneamente ter server copy autoritativa.
- Publish repetido 10 vezes com mesmo command ID não duplica Session/history.
- Mesma Session UUID publicada por command diferente encontra domain uniqueness/conflict, não cria clone silencioso.

# 11. N3.12.10 — Command Outbox

## N4.12.10.01 — Outbox local é allowlist

Não existe:

```text

```

Existe:

```text
explicit offline-capable command policies
```

Principal caso:

```text

```

Possíveis casos seguros adicionais no futuro exigem review próprio.

## N4.12.10.02 — Modelo conceitual

```text
CommandOutboxItem
├── id
├── owner_scope
├── command_id
├── command_type
├── aggregate_type
├── aggregate_id
├── payload_version
├── payload
├── expected_revision nullable
├── expected_last_sequence nullable
├── control_epoch nullable
├── actor_user_id nullable
├── device_id
├── created_at_local
├── status
├── attempt_count
├── next_attempt_at nullable
├── last_error_class nullable
```

Candidate status:

```text
PENDING
IN_FLIGHT
ACKNOWLEDGED
REQUIRES_RECONCILIATION
FAILED_PERMANENT
SEALED_ACCOUNT_MISMATCH
```

## N5.12.10 — Time-sensitive shared commands excluded

Não entram na outbox genérica:

```text
JoinRegistration
LeaveRegistration
CastVote
TransferOwnership
ApproveJoinRequest
ChangeMembershipRole
ConfirmTeamDraw
MatchTakeover
OfficializeCompetitionResult
```

## N8.12.10 — Crash safety

Outbox item é gravado antes de UI declarar comando offline protegido.

## N10.12.10

- Browser crash depois de enfileirar: item reaparece.
- Logout/login como outro User: item não é reexecutado.
- Worker/replay duplica envio: command_id preserva idempotência.

# 12. N3.12.11 — Idempotent Retry

## N4.12.11.01 — Retry depende do tipo de falha

### Safe automatic retry

```text
idempotent reads
explicitly idempotent commands with same command_id
```

### Refresh/reconciliation required

```text
REVISION_CONFLICT
SEQUENCE_CONFLICT
CONTROL_EPOCH_CHANGED
HANDOFF_OUTCOME_UNKNOWN
```

### No retry without user/domain change

```text
AUTHORIZATION_DENIED
VALIDATION_FAILED
DOMAIN_RULE_REJECTED
RESOURCE_ARCHIVED
```

## N5.12.11 — Same logical operation, same command ID

Se a resposta se perder:

```text
retry SAME command_id
```

Não gerar novo ID a cada click/reconnect.

## N5.12.11.02 — Backoff

Retries automáticos usam:

```text
bounded exponential backoff
+
jitter
```

sem loop agressivo de reconexão.

## N8.12.11 — Auth refresh

Token expirado pode exigir refresh de Auth antes de reenviar a mesma command.

O actor continua sendo resolvido server-side; outbox não concede identidade.

## N10.12.11

- HTTP response perdida após commit: retry obtém receipt/result sem segundo efeito.
- Authorization denied não entra em loop infinito.
- Stale revision não é sobrescrita por retry cego.

# 13. N3.12.12 — IndexedDB

## N4.12.12.01 — Por que substituir `localStorage` como banco de domínio

`localStorage` é:

- síncrono;
- string/JSON-oriented;
- pouco adequado para event logs e consultas indexadas;
- ruim para transações estruturadas;
- fácil de transformar em grandes blobs regravados.

O target usa IndexedDB para estado local estruturado.

## N4.12.12.02 — Stores conceituais

Candidate baseline:

```text
local_quick_sessions
local_quick_participants
local_quick_team_draws
local_quick_matches
local_quick_match_events
local_drafts
remote_cache_snapshots
command_outbox
local_recovery_metadata
```

A decomposição física final pode variar, mas os tipos de durabilidade não podem ser misturados sem distinção.

## N5.12.12 — Recreateable vs irreplaceable

Cada store/record deve ser classificado:

```text
RECREATEABLE
├── remote cache
├── derived local projection
└── static resource cache

IRREPLACEABLE_LOCAL
├── unpublished Quick
├── unacknowledged offline Match commands
└── unsent local drafts where user expects persistence
```

Essa classificação governa eviction, migration e recovery.

## N5.12.12.02 — `localStorage` target

Pode permanecer para dados pequenos/não críticos, por exemplo:

```text
theme
UI preferences
dismissed hints
non-authoritative device id
small feature/UI metadata
```

Não para event log de Match ou dataset de domínio inteiro.

## N8.12.12 — Persistence API

A aplicação pode solicitar browser persistent storage quando houver dados locais críticos, como melhoria best-effort.

Isso não é garantia de durabilidade e não substitui recovery/monitoring.

## N10.12.12

- Eviction policy remove remote cache, nunca unpublished Quick primeiro.
- Storage estimate baixo dispara warning antes de Match offline crítica quando possível.
- `localStorage` cheio não derruba event log porque ele já não é seu backend principal.

# 14. N3.12.13 — User-scoped Local Data

## N4.12.13.01 — Scope obrigatório

Todo dado local ligado a account possui:

```text

```

conceitualmente equivalente a:

```text
user:<authenticated-user-id>
```

O repository local nunca executa consultas de user data sem scope explícito.

## N5.12.13 — Account switch

Ao trocar de User:

```text
1. stop active replay/workers
2. close/rebind scoped repositories
3. clear in-memory state
4. load only new scope cache/data
5. never upload previous scope
```

## N8.12.13 — Sensitive cache

Não confiar em “está no IndexedDB” como privacy control.

XSS executando na origem pode acessar dados que o app acessa.

A proteção principal é:

```text
minimize cached sensitive data
scope it correctly
purge/restrict on lifecycle
harden XSS surface
```

Browser-side encryption pode ser adicionada onde houver threat model claro, mas não deve ser apresentada como defesa mágica contra XSS se a chave também estiver disponível à aplicação.

## N10.12.13

- User A logout, User B login: nenhuma Session/cache A aparece para B.
- Pending command A nunca roda com token B.
- Cache-owner metadata corrompido: fail safe para mutation, não cross-upload.

# 18. N3.12.17 — Local DB Migration

# 34. N10 — Adversarial / Failure Acceptance Matrix

Os cenários abaixo devem virar testes unitários, integration, browser storage, concurrency, E2E ou recovery drills conforme a camada.

## N10.12.34.01 — Authority

1. Shared Community mutation offline → blocked, no local success.
2. Registration Join offline → no confirmed/waitlisted local state.
3. Vote offline → no queued ballot.
4. Ownership transfer offline → no queued governance mutation.
5. Quick offline → fully usable within local policy.
6. Internet returns → Quick authority does not change automatically.
7. Cached entity newer local timestamp → cannot override server authority.

## N10.12.34.02 — Quick handoff

8. Publish succeeds → authority becomes SERVER_OWNED.
9. Publish definite validation failure → remains LOCAL_OWNED.
10. Publish response lost after server commit → HANDOFF_UNKNOWN.
11. HANDOFF_UNKNOWN blocks continued local authority mutation.
12. Retry same command ID resolves to one server Session.
13. Different command ID same Session UUID cannot duplicate source.
14. Server rejects malformed sequence/reference graph.
15. Live local Match mid-game is not generic handoff V1.

## N10.12.34.03 — Outbox

16. Match command persisted before UI ack.
17. Browser crash preserves pending command.
18. Duplicate replay produces one logical event.
19. Outbox item with old epoch → reconciliation required.
20. Outbox item with stale expected sequence → reconciliation required.
21. Unauthorized replay → rejected, not infinite retry.
22. Registration command cannot be inserted through generic outbox API.
23. Vote cannot be inserted through generic outbox API.

## N10.12.34.04 — Account scope

24. User A data never appears after User B login.
25. User A pending command never executes with B auth.
26. Logout stops workers/replay before token/account swap.
27. Sealed pending A data can be resumed only by A/recovery policy.
28. Anonymous data does not auto-claim to first login.

## N10.12.34.05 — Connectivity

29. `navigator.onLine=true` but backend unreachable → capability unavailable.
30. RPC reachable, Realtime down → degraded, not globally offline.
31. Storage down → media degraded only.
32. Auth refresh in progress → shared command waits/fails appropriately without becoming local mutation.

## N10.12.34.06 — Freshness

33. Cached Registration state labelled stale/last-known offline.
34. Cached admin role does not authorize server command after revocation.
35. Reconnect revalidates active screen snapshot.
36. Realtime gap triggers refetch/reconciliation.

## N10.12.34.07 — Local durability

37. IndexedDB transaction failure → no critical UI success.
38. Quota exceeded → new offline Match event blocked with recoverable UX.
39. Cache eviction never deletes unpublished Quick first.
40. Browser restart rebuilds local projection from source events when needed.
41. In-memory React state loss does not lose durable point.

## N10.12.34.08 — Local migrations

42. Upgrade with old tab open → blocked/versionchange UX.
43. Migration failure preserves irreplaceable old store.
44. Cache-only incompatible store may reset independently.
45. Migration re-run is idempotent.
46. localStorage → IndexedDB copy verified before source removal.
47. Legacy shared-local unresolved data is not uploaded silently.

## N10.12.34.09 — Ordering / clocks

48. Modified device clock does not win FIFO.
49. Modified device clock does not extend vote deadline.
50. Match offline client timestamp does not replace epoch/sequence ordering.
51. Same local aggregate two tabs → writer/revision conflict, no silent parallel writes.

## N10.12.34.10 — History / stats

52. Local Quick stats marked provisional.
53. Published Quick server projection does not double count local overlay.
54. Failed publish leaves provisional local stats intact.
55. Competition official stats never derive from unpublished Quick.

## N10.12.34.11 — Security

56. Cached data does not grant capability.
57. Old JWT role metadata does not bypass current server authorization.
58. Outbox actor field cannot impersonate another User; server uses auth identity.
59. Recovery export excludes auth tokens/secrets.
60. Next account cannot inspect sealed prior-account payload through ordinary UI.

## N10.12.34.12 — Legacy sync retirement

61. Aggregate migrated to semantic commands is no longer written by generic sync.
62. Generic sync cannot resurrect removed target state using newer local timestamp.
63. `cloudId` removal does not change canonical UUID references.
64. Old tombstone is not automatically interpreted as new domain archive/cancel state.
65. Reconnect after full migration does not upload/download whole operational dataset.

# 36. ADRs congelados neste contexto

## ADR-0164 — Offline policy é definida por operação

Toda command/query relevante é classificada como `ONLINE_AUTHORITATIVE`, `OFFLINE_OWNED`, `CACHED_READ`, `LOCAL_DRAFT` ou `CONDITIONALLY_OFFLINE_COMMAND`.

## ADR-0165 — Shared mutable state é server-authoritative

Governance, Registration, Voting, shared confirmation e Competition não usam local merge como autoridade.

## ADR-0166 — Quick Session é offline-owned até handoff explícito

Quick preserva experiência offline real sem transformar Community state em local-first.

## ADR-0167 — Quick authority handoff é one-way e usa IDs finais

`PublishQuickSession` transfere autoridade; não cria `cloudId` paralelo nem inicia sync bidirecional.

## ADR-0168 — Generic bidirectional domain sync será aposentado

O target não possui sucessor universal de `LocalSyncPayload + merge`.

## ADR-0169 — Local command outbox é allowlist-only

Somente commands explicitamente modeladas como offline-capable podem ser persistidas para replay.

## ADR-0170 — Registration, Voting e Governance não são offline queued

Time/order/capacity/capability tornam o replay tardio semanticamente inseguro como default.

## ADR-0171 — Match offline usa protocolo dedicado de epoch/sequence/reconciliation

Match é exceção condicionada, não justificativa para generic sync.

## ADR-0172 — IndexedDB é o storage estruturado target

Quick, MatchOutbox, drafts e cache estruturado deixam de depender de grandes JSON blobs no `localStorage`.

## ADR-0173 — `localStorage` fica restrito a preferências/metadados pequenos

Não é o source store de Match events ou dataset de domínio.

## ADR-0174 — Local data é explicitamente user-scoped

Account switching nunca pode reutilizar cache/outbox de outra identidade.

## ADR-0175 — Anonymous local data exige claim/import explícito

Login não faz merge automático de dados device-local.

## ADR-0176 — Connectivity é multidimensional; `navigator.onLine` é hint

Request outcome/dependency state prevalecem para operation availability.

## ADR-0177 — Cache carrega freshness/version metadata

FRESH/STALE/UNKNOWN são distintos de online/offline.

## ADR-0178 — LWW é limitado a dados local-only de baixo risco

Não se aplica a shared domain state.

## ADR-0179 — Server primitives governam shared ordering/time

Queue sequence, Match sequence, revision e server deadlines substituem client timestamps.

## ADR-0180 — Não existe multi-device local draft merge V1

Draft local continua device-scoped até submit.

## ADR-0181 — Service Worker V1 cuida de app shell/assets, não de domain mutation replay

Background sync crítico exige ADR futuro específico.

## ADR-0182 — Offline stats usam provisional overlay separado

Local Quick history não é confundida com CareerProjection confirmada e não duplica após publish.

## ADR-0183 — Migração para o modelo target usa strangler por capability

Cada bounded context troca seu mutation path e depois sai do generic sync; não há big-bang obrigatório.

# 38. Exit Criteria C2.12

11. Como Quick funciona 100% offline?

20. Como anonymous local data é tratada?
