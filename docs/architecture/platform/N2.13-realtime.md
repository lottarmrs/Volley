## 0. Regra de leitura

Este documento define o **target canônico** para atualização em tempo real no Volley.

A regra central é:

```text
REALTIME
=
LOW-LATENCY TRANSPORT OF COMMITTED INFORMATION

REALTIME
≠
SOURCE OF TRUTH
≠ COMMAND BUS
≠ DATABASE
≠ OFFLINE SYNC
≠ RELIABLE HISTORY
```

A arquitetura correta é:

```text
Client Command
      ↓
Authoritative server transaction
      ↓
COMMIT
      ↓
Authoritative command response
      +
Realtime signal/event
      ↓
Other connected clients update sooner
```

Se o Realtime desaparecer completamente, o sistema deve ficar **mais lento para convergir**, não semanticamente incorreto.

# 1. Current State — evidência do repositório

## 1.1 Estado operacional atual depende principalmente de sync

O fluxo atual possui um `OperationalSyncPayload` que transporta em lote:

```text
sessions
teams
games
pointEvents
gameReports
sessionReports
presenceRecords
WhatsApp drafts
```

As entidades são mapeadas entre estado local e tabelas Supabase com `cloudId`, `local_id`, `syncStatus`, `lastSyncedAt` e tombstones.

A convergência compartilhada atual ocorre predominantemente por upload/download/sync, não por um protocolo canônico de `snapshot + revision/sequence + realtime`.

## 1.2 `useCloudSync` já revela os custos do modelo atual

O hook atual precisa:

- construir um payload global;
- detectar owner do cache local;
- impedir sync concorrente;
- registrar um ledger de falhas;
- reconciliar resultado inteiro;
- detectar conflitos de Session control depois de conhecer estado cloud;
- diferenciar eventos já existentes na nuvem de eventos locais ainda não enviados.

Isso não será substituído por “mais Realtime”.

O target remove o sync genérico e usa Realtime apenas como acelerador de leitura do estado autoritativo.

## 1.3 `CommunityPresence` atual não é Supabase Presence

O `CommunityPresence` do domínio atual é um registro persistido de presença/planejamento por Community/data.

Ele **não** deve ser confundido com `Realtime Presence`, que é estado efêmero de sockets/clients.

Durante a migração, o nome persistido deve ser revisto (`CommunityAttendance`, `AvailabilityRecord` ou termo final do contexto) para reduzir ambiguidade.

## 1.4 Controle atual é RPC + sync, não protocolo Realtime

`sessionOwnershipCloudService` já usa RPC para claim/transfer, uma direção correta de autoridade server-side.

Porém o modelo atual de atualização de score/eventos ainda depende da arquitetura local/sync e do controle no nível de Session.

C2.07 substitui isso por `MatchControlLease + control_epoch + MatchEvent.sequence`; C2.13 apenas transporta os commits para outros clients.

## 1.5 Connectivity já possui uma decisão correta a preservar

O código atual trata `navigator.onLine` como pista, não veredito, e permite que o resultado de requests reais ajuste o estado de conectividade.

O Realtime target deve manter essa distinção:

```text
WebSocket disconnected
≠
backend unavailable
```

# 2. Provider Direction — Supabase Realtime

Como decisão de implementação atual para Supabase:

```text
DEFAULT FOR DOMAIN UPDATES
→ Broadcast from trusted server/database path

NOT DEFAULT
→ raw Postgres Changes subscriptions from every client
```

Motivação:

- Broadcast permite payload semântico/minimizado;
- topic boundaries podem acompanhar aggregates/contexts;
- private channels usam Realtime Authorization;
- não precisamos expor shape de row para todo subscriber;
- reduz coupling entre schema físico e frontend;
- escala de fan-out é mais apropriada que Postgres Changes para a maioria dos fluxos;
- políticas de envio/recebimento podem ser separadas.

A documentação atual do Supabase recomenda Broadcast para a maioria dos casos quando escalabilidade e segurança importam; Postgres Changes permanece uma opção mais simples para casos limitados.

Isso é uma **provider implementation decision**, não regra de domínio eterna. Se o provider mudar, o protocolo `snapshot/revision/sequence/reconcile` permanece.

# 3. N3.13.01 — Realtime Role

## N4.13.01.01 — Responsabilidade

Realtime possui somente estas responsabilidades:

```text
1. reduzir tempo entre commit e percepção por outros clients;
2. sinalizar invalidação/alteração;
3. entregar deltas semânticos quando seguro;
4. transportar estado efêmero de Presence quando necessário.
```

Não possui responsabilidade por:

```text
autorização de command
persistência autoritativa
idempotência de command
recovery histórico
ordenação de Registration
score calculation
vote tally authority
notification durability
```

## N5.13.01 — Command response é primário para o actor

Quem executa um command não deve esperar seu próprio Broadcast para saber se funcionou.

```text
AwardPoint
↓
command response = authoritative outcome
```

Realtime é principalmente para:

- espectadores;
- outro device autorizado;
- outras telas abertas;
- cache invalidation.

## N10.13.01

- Realtime cai durante `JoinRegistration`: command pode concluir normalmente; actor recebe response; outros clients convergem por refetch/polling/reconnect.
- Broadcast chega antes da UI processar o command response: response e envelope compartilham revision/sequence e não geram double apply.

# 4. N3.13.02 — Broadcast vs Postgres Changes

## N4.13.02.01 — Default

Usar **Broadcast semântico** como padrão para mudanças de domínio relevantes.

Exemplos:

```text
registration.changed
team_selection.candidates_published
team_selection.voting_closed
match.event_committed
competition.official_result_changed
notification.intent_created
```

Evitar expor genericamente:

```text
INSERT table X
UPDATE row Y
DELETE row Z
```

como contrato público do frontend.

## N5.13.02 — Quando Postgres Changes pode ser aceitável

Somente quando todos forem verdadeiros:

- baixo volume/fan-out conhecido;
- baixo risco de expor row shape;
- simplicidade operacional claramente superior;
- RLS e performance medidos;
- não se torna contrato arquitetural de longo prazo;
- ADR/exception documenta o uso se for uma capacidade crítica.

## N5.13.02.02 — No schema coupling

Frontend não deve depender de:

```text
payload.new.database_column_name
```

como API de domínio estável.

Realtime payload é DTO versionado.

## N10.13.02

- Renomear uma coluna física não quebra spectators se o event contract não mudou.
- Adicionar coluna privada a uma tabela não a transmite automaticamente.

# 5. N3.13.03 — Private Channels

## N4.13.03.01 — Baseline

Channels de domínio são privados por padrão.

Candidatos:

```text
community:<community_id>
session:<session_id>
registration:<window_id>
team-selection:<session_id>
match:<match_id>
competition:<competition_id>
user:<user_id>:notifications
```

Nomes exatos podem mudar, mas os scopes devem ser derivados de resources reais.

## N5.13.03 — Public spectators são exceção explícita

Se houver Match pública no futuro:

```text
match-public:<match_id>
```

ou boundary equivalente usa **public DTO próprio**.

Não abrir o channel privado existente apenas mudando uma flag.

## N5.13.03.02 — Project setting

Preferência operacional: desabilitar public channels globalmente quando o produto não precisar deles.

Se public channels forem necessários futuramente, o escopo permitido deve ser explícito e mínimo.

## N10.13.03

- Usuário conhece `match_id` de Community privada: channel join continua negado.
- Feature pública futura não recebe actor IDs/control metadata do channel administrativo.

# 6. N3.13.04 — Channel Authorization

## N4.13.04.01 — Regra

Autorização de channel responde somente:

> este principal pode receber/enviar esta classe de mensagem neste topic?

Não responde:

> ele pode executar o command de domínio correspondente?

Commands sempre revalidam capability no servidor.

## N5.13.04 — Topic authorization

Policy deve derivar o resource real e verificar:

```text
authenticated User
↓
resource
↓
context/Community
↓
active Membership / public policy / direct ownership
```

Nunca confiar em `community_id` arbitrário transmitido pelo client como evidência de autorização.

## N5.13.04.02 — Receive vs send

Para channels de domínio autoritativo:

```text
CLIENT SELECT/RECEIVE → allowed by scope
CLIENT INSERT/SEND    → denied by default
```

Server/database trusted path publica.

Client sending fica reservado a features explicitamente efêmeras, se vierem a existir.

## N5.13.04.03 — Revocation

Não assumir que remoção de Membership encerra instantaneamente todos os sockets já autorizados.

Portanto:

- payloads são minimizados;
- comandos reautorizam sempre;
- dados altamente sensíveis usam channels mais estreitos;
- client pode receber `access.revoked` para UX, mas isso não é security boundary;
- se houver requisito de revogação imediata de confidencialidade, precisamos de mecanismo/provider behavior específico testado.

## N10.13.04

- User removido da Community mantém WebSocket antigo por segundos/minutos: não consegue executar commands; novos snapshots protegidos por Query também negam.
- User tenta publicar `match.event_committed` manualmente: Realtime authorization bloqueia INSERT/send; mesmo se UI for adulterada, nenhum fato é criado.

# 7. N3.13.05 — Channel Boundaries

## N4.13.05.01 — Menor scope útil

Evitar um channel global:

```text
community:<id>:everything
```

para todos os casos.

Separar quando:

- audiência difere;
- sensibilidade difere;
- frequência difere;
- lifecycle difere.

## N5.13.05 — Exemplo

Uma Community pode ter:

```text
community:<id>
→ metadata/membership-safe invalidations

registration:<window_id>
→ capacity/status/revision

match:<match_id>
→ high-frequency Match events
```

Isso evita que todo membro da Community receba todo ponto de toda quadra aberta sem necessidade.

## N10.13.05

- Dois Matches simultâneos: subscriber de Match A não recebe eventos de B.
- Member que pode ver Community mas não Competition privada não entra no topic da Competition apenas por Membership genérica.

# 8. N3.13.06 — Realtime Envelope

## N4.13.06.01 — Envelope comum

Payload canônico candidato:

```text
RealtimeEnvelope
├── event_id
├── event_type
├── aggregate_type
├── aggregate_id
├── revision?        // revision-based aggregates
├── sequence?        // Match/event-log aggregates
├── schema_version
├── occurred_at
└── payload
```

`event_id` identifica a mensagem lógica para dedupe de UI/telemetry.

## N5.13.06 — Proibições

Envelope não deve carregar por padrão:

- access token;
- email;
- raw evaluation;
- entire DB row;
- entire Session aggregate;
- raw command payload;
- service-role metadata;
- secrets;
- desnecessário actor UUID em public/spectator payload.

## N5.13.06.02 — `occurred_at`

É informativo/observabilidade.

Não decide ordering quando existe revision/sequence.

```text
occurred_at
≠ conflict-resolution clock
```

# 9. N3.13.07 — Revision-based State

## N4.13.07.01 — Uso

Aggregates administrativos/relativamente baixa frequência usam revision monotônica.

Exemplos:

```text
RegistrationWindow.revision
Session revision where applicable
TeamSelection state revision
Competition projection/version
```

## N5.13.07 — Client rule

Dado local:

```text
revision = 12
```

Recebe:

```text
revision = 13
→ apply/refetch according to event contract
```

Recebe:

```text
revision = 15
→ GAP
→ authoritative refetch
```

Recebe:

```text
revision <= 12
→ duplicate/stale
→ ignore
```

## N5.13.07.02 — One revision / one state transition

Contexts devem evitar emitir uma sequência ambígua de vários envelopes com a mesma revision quando o client precisa inferir ordenação.

Quando um command altera vários aspectos do aggregate, preferir um envelope semântico de mudança com a nova revision ou um contract que trate a transação como unidade.

# 10. N3.13.08 — Sequence-based State

## N4.13.08.01 — Match

Match usa `MatchEvent.sequence` autoritativa.

```text
last_sequence = 50
recebe 51 → apply
recebe 52 sem 51 → gap
recebe 49 → stale/duplicate
```

## N5.13.08 — Sequence vem do servidor

Client sequence é precondition/base, não valor final autoritativo.

Offline outbox carrega base/ordering local, mas a reconciliação segue C2.07/C2.12.

## N5.13.08.02 — Projection checkpoint

Snapshot deve informar:

```text
MatchProjection.last_sequence
```

para que handshake/reconnect possa reconciliar.

# 11. N3.13.09 — Subscription + Snapshot Handshake

## N4.13.09.01 — Problema clássico

Errado:

```text
fetch snapshot
↓
subscribe
```

porque uma mudança pode ocorrer entre as duas ações e nunca ser vista.

## N5.13.09 — Protocolo

```text
1. authorize + subscribe
2. start buffering envelopes
3. fetch authoritative snapshot
4. read snapshot revision/last_sequence
5. discard buffered events <= snapshot checkpoint
6. apply contiguous events > checkpoint
7. if gap/incompatibility → refetch
8. enter LIVE state
```

## N5.13.09.02 — UI states

Candidato:

```text
CONNECTING
SYNCING_SNAPSHOT
LIVE
RECONNECTING
DEGRADED
```

Não confundir `SUBSCRIBED` do WebSocket com `data is current`.

## N10.13.09

- Commit acontece depois do subscribe mas antes do snapshot query: buffered event é reconciliado.
- Commit acontece antes do subscribe e snapshot já contém: event não é necessário.

# 12. N3.13.10 — Gap Detection

## N4.13.10.01 — Gaps são esperados

Realtime não recebe requisito de entrega exactly-once.

Mensagens podem:

- atrasar;
- duplicar;
- ser perdidas em reconnect;
- chegar após snapshot mais novo.

O protocolo deve sobreviver.

## N5.13.10 — Recovery

```text
GAP DETECTED
↓
mark local view potentially stale
↓
fetch authoritative snapshot / missing range
↓
reconcile checkpoint
↓
resume live
```

## N5.13.10.02 — No synthetic fill

Nunca inventar revision/event faltante para manter UI fluida.

---

# 13. N3.13.11 — Reconnect Reconciliation

## N4.13.11.01 — Regra

Todo reconnect relevante inclui refetch/reconciliation.

Não assumir:

```text
socket connected again
=
I received everything I missed
```

## N5.13.11 — Context-specific reconcile

- Registration → fetch RegistrationSnapshot.
- Team Selection → fetch TeamSelectionSnapshot.
- Match → fetch MatchProjection + checkpoint/events as needed.
- Competition → fetch current competition/standings projection.
- Notification Inbox → fetch messages newer than local cursor.

## N10.13.11

- App fica background por 20 minutos e socket é suspenso: resume refaz snapshot, não confia no último event local.

# 14. N3.13.12 — Registration Realtime

## N4.13.12.01 — Payload minimizado

Exemplo:

```text
registration.changed
├── window_id
├── revision
├── status
├── capacity
├── confirmed_count
└── waitlist_count
```

Não transmitir lista completa de participantes a cada Join/Leave.

## N5.13.12 — Dados personalizados

Estado do próprio usuário:

```text
CONFIRMED
WAITLISTED
position
```

pode vir do command response ou snapshot autorizado.

Promoção também pode gerar NotificationIntent individual.

## N5.13.12.02 — Privacy

Channel genérico da Registration não precisa divulgar:

- quem entrou;
- quem saiu;
- ordem completa da fila;
- emails;
- Player data desnecessária.

Se a UI Organizer exigir roster detalhado, usa Query autorizada/read model próprio.

## N10.13.12

- 100 joins simultâneos: spectators recebem revisions possivelmente condensadas/perdidas; qualquer gap leva a snapshot correto.
- Waitlisted não descobre identidade dos demais por payload de Realtime.

# 15. N3.13.13 — Team Selection Realtime

## N4.13.13.01 — CandidateSet

Eventos permitidos:

```text
team_selection.candidates_published
team_selection.voting_opened
team_selection.voting_closed
team_selection.finalized
team_selection.invalidated
```

## N5.13.13 — Ballot confidentiality

Não transmitir:

```text
user X voted candidate B
```

em channel compartilhado.

## N5.13.13.02 — AFTER_CLOSE

Se policy diz resultados `AFTER_CLOSE`, Realtime não transmite tally corrente durante OPEN.

Nem payload indireto deve permitir inferência fácil, por exemplo:

```text
candidate_A_votes = 4
```

## N5.13.13.03 — Own vote

Actor sabe que seu vote foi aceito pelo **command response**.

Não precisamos de broadcast grupal de cada ballot.

## N10.13.13

- DevTools conectado ao channel durante votação não revela tally protegido.
- CandidateSet invalidado por roster change gera event de invalidação; client refaz snapshot e não continua votando localmente.

# 16. N3.13.14 — Match Realtime

## N4.13.14.01 — High-frequency path

Match é o principal caso de delta semântico frequente.

Envelope candidato:

```text
match.event_committed
├── match_id
├── sequence
├── event_type
├── safe event payload
└── projection_delta / small projection summary if justified
```

## N5.13.14 — Actor vs spectator

Controller recebe command response autoritativo imediatamente.

Spectators recebem Broadcast e aplicam somente sequência contígua.

## N5.13.14.02 — Payload público

Se spectator público existir, DTO deve conter apenas dados apropriados:

```text
score
sets
team display
current state
event sports meaning
```

Não incluir automaticamente:

- `actor_user_id`;
- device ID;
- lease metadata;
- command ID;
- internal correction reason;
- private Player metadata.

## N5.13.14.03 — Projection refresh

Client pode manter MatchProjection local derivada dos deltas, mas:

```text
snapshot/replay authoritative checkpoint
wins on disagreement
```

## N5.13.14.04 — Fan-out

Não subscrever toda Community a todos os Matches ativos por default.

Clients entram somente nos Matches visíveis/abertos na UI, salvo use case comprovado.

## N10.13.14

- Spectator perde sequence 201 e recebe 202: detecta gap e refetch.
- Correction event não exige mutar evento antigo no client; novo event semântico atualiza/reconstrói projection.
- 10 courts simultâneas têm topics independentes.

# 17. N3.13.15 — Competition Realtime

## N4.13.15.01 — Baixa frequência

Competition não precisa transmitir cada detalhe como delta fino.

Preferir invalidation events:

```text
competition.updated
official_result.changed
fixture.updated
stage.updated
standings.updated / standings.invalidated
```

## N5.13.15 — Snapshot

Após evento relevante, telas podem refetch read model paginado/compacto.

Isso reduz complexidade de tentar reproduzir todo bracket/standings state machine no browser via deltas.

## N10.13.15

- OfficialResult corrigido enquanto client estava offline: reconnect snapshot mostra standings/bracket autoritativos, independente de eventos perdidos.

# 18. N3.13.16 — Notification Realtime

## N4.13.16.01 — Inbox é authority

Realtime para Notification apenas acelera uma Inbox persistente.

```text
NotificationIntent / Inbox row committed
↓
user:<uid>:notifications broadcast
↓
client fetches/appends authorized inbox state
```

## N5.13.16 — Payload

Pode ser somente:

```text
notification_id
revision/cursor hint
```

O conteúdo completo continua vindo da Query da Inbox quando apropriado.

## N10.13.16

- Broadcast de notification perdido: ao abrir Inbox, Query encontra mensagem normalmente.
- Push e Realtime caem: Inbox persistente continua correta.

# 19. N3.13.17 — Presence

## N4.13.17.01 — Definition

Realtime Presence é estado **efêmero** de conexão.

Possíveis usos futuros:

```text
who is viewing this Match
controller connection indicator
Organizer currently on operational screen
```

Não usar Presence para:

```text
registration
attendance history
who actually played
last seen audit
ownership
Match controller authority
```

## N5.13.17 — Approximate semantics

Presence é inerentemente transitória.

Viewer count pode ser aproximado; não é estatística financeira/auditável.

## N5.13.17.02 — Payload minimization

Presence state não precisa carregar profile completo.

Exemplo suficiente:

```text
connection_id/device ephemeral id
user display-safe identity if allowed
role_hint for UI only
joined_at
```

Nunca usar `role_hint` para authorization.

## N5.13.17.03 — Naming collision

O registro persistente atualmente denominado `CommunityPresence` deve ser renomeado ou claramente isolado, pois não é Realtime Presence.

## N10.13.17

- Socket morre sem leave limpo: eventual Presence cleanup não altera Match facts.
- User falsifica `role_hint=OWNER`: UI pode até exibir bug, mas nenhum command recebe privilege.

# 20. N3.13.18 — Client Publish Restrictions

## N4.13.18.01 — Baseline receive-only

Clients comuns recebem Broadcast de domínio, mas não publicam eventos autoritativos.

```text
Browser
cannot publish
match.event_committed
registration.changed
voting.finalized
official_result.changed
```

## N5.13.18 — Ephemeral exception

Client Broadcast só poderá ser introduzido para features explicitamente efêmeras, como futuramente:

```text
typing indicator
cursor
view focus
non-authoritative reaction
```

Mesmo assim:

- rate-limited;
- authorized by topic;
- payload validated/minimized;
- nunca modifica source facts.

## N10.13.18

- Attacker chama SDK Realtime diretamente e tenta broadcast autoritativo: policy deny.
- Attacker usa Presence para fingir controller: MatchControlLease continua server-side e command é negado.

# 21. N3.13.19 — Schema Versioning

## N4.13.19.01 — Envelope version

`schema_version` versiona o contrato do event, não a tabela.

Exemplo:

```text
match.event_committed
schema_version = 1
```

## N5.13.19 — Evolution

Preferir evolução aditiva:

```text
add optional field
```

em vez de alterar significado de campo existente.

Se semântica incompatível mudar:

```text
new schema_version
```

ou novo `event_type`.

## N5.13.19.02 — Old clients

Old client que recebe schema desconhecido:

```text
DO NOT GUESS
↓
refetch snapshot
```

Se não consegue entender snapshot/contract mínimo, pode exigir safe reload/update fora de workflow crítico.

## N5.13.19.03 — Match live compatibility

Deploy novo não pode quebrar Match LIVE de tab antiga.

Realtime contract precisa de compatibility window alinhada a N2.21/N2.22.

## N10.13.19

- Client v1 recebe event schema v2 desconhecido: faz refetch, não aplica campos parcialmente por adivinhação.

# 22. N3.13.20 — Realtime Observability

## N4.13.20.01 — Métricas

Medir por capability/context:

```text
active connections
channel joins / join failures
authorization failures
subscribe latency
reconnect rate
broadcast volume
message size
gap detections
snapshot resync count
schema incompatibility count
Match spectator fan-out
Presence size if enabled
```

## N5.13.20 — Domain-level indicators

Mais importante que “WebSocket uptime”:

```text
percentage of Match clients needing gap recovery
Registration revision gaps
median time commit → spectator-visible
reconnect convergence time
```

## N5.13.20.02 — No sensitive payload logging

Não logar raw Broadcast payload em produção por default.

Logs podem registrar:

```text
event_type
aggregate_type
aggregate_id or safe hashed/contextual identifier
revision/sequence
payload byte size
channel category
result/latency
```

sem ballots, evaluations ou private user fields.

# 23. Realtime Production Flow

## 23.1 Revision aggregate

```text
Client A
  │ Command
  ▼
Server/RPC
  │ transaction
  ├── mutate authoritative rows
  ├── revision 12 → 13
```

# 24. Delivery Semantics

Realtime does **not** promise domain exactly-once.

Client must tolerate:

```text
AT MOST perceived once through local dedupe
but transport may duplicate
transport may omit during disconnect
```

Durable semantics live elsewhere:

- Command receipt → command idempotency.
- MatchEvent → durable history.
- Registration rows/revision → capacity/FIFO.
- NotificationIntent → durable Inbox/delivery.

Realtime event is disposable after clients have converged.

# 25. Security Model

## 25.1 Trust boundaries

Untrusted:

```text
browser
channel name supplied by browser
Presence metadata
client Broadcast payload
device_id
Realtime event timing
```

Trusted only after server validation:

```text
auth principal
resource context
channel authorization decision
committed domain state
server/database-originated semantic event
```

## 25.2 BOLA protection

Topic IDs are not capabilities.

```text
knowing session_id
≠ subscribe permission
```

RLS/topic authorization resolves actual resource context.

## 25.3 Client publishing

For receive-only domain channels, configure Realtime Authorization so authenticated clients may receive allowed messages but not insert/send domain Broadcasts.

## 25.4 Sensitive contexts

Never broadcast individual:

```text
PlayerEvaluation
ballot
account-link security state
privacy request details
health data
raw audit trail
```

through broad Community channels.

# 26. Performance / Scalability

## 26.1 Active-screen subscription

Clients subscribe only to what is currently useful.

Avoid:

```text
login
→ subscribe to every Community
→ every Session
→ every Match
→ every Competition
```

## 26.2 Payload budget

Realtime event must be small enough that a spike of Match events does not become a full-row serialization problem.

No fixed byte target is invented here; N2.18 establishes measurable budgets.

## 26.3 Match fan-out

If spectator count grows materially:

- measure Broadcast fan-out and connection limits;
- public spectator channels may be isolated from internal channels;
- consider edge/cached snapshot mechanisms before changing domain authority;
- do not move score authority into Realtime nodes merely for scale.

## 26.4 Postgres Changes scalability

Raw Postgres Changes subscriptions are not the default because per-subscriber authorization/fan-out and coupling to WAL/schema become costly under scale.

Use provider benchmarks and production telemetry before exceptions.

# 27. Reliability / Degradation Matrix

| Failure | Domain writes | Realtime UX | Recovery |
|---|---:|---|---|
| Realtime service unavailable | continues if DB/API healthy | stale/slower | refetch/poll/reconnect |
| WebSocket disconnected one client | continues | that client stale | snapshot on reconnect |
| Broadcast event lost | committed state intact | potential gap | revision/sequence detects/refetch |
| Duplicate event | intact | potential duplicate UI | event/revision/sequence dedupe |
| Out-of-order delivery | intact | local delta cannot be trusted blindly | revision/sequence |
| Channel auth failure | writes may still be allowed by command capability | no live updates | query fallback / fix auth |
| DB unavailable | shared writes fail closed | realtime may show stale last state | normal DB recovery |
| Client background suspension | writes from others continue | missed messages | resume snapshot |

# 33. N10 — Adversarial / Acceptance Matrix

## RT-N10-001 — Lost event

Client at revision 20 receives 22. Must detect gap and fetch authoritative state.

## RT-N10-002 — Duplicate event

Same event delivered twice. UI/domain view changes once.

## RT-N10-003 — Old event

Snapshot revision 30 followed by delayed event 28. Event ignored.

## RT-N10-004 — Snapshot race

Change commits between subscribe and snapshot. Buffered/revision handshake preserves it.

## RT-N10-005 — Background tab

Browser suspends socket and resumes later. Snapshot reconciliation restores current state.

## RT-N10-006 — Realtime outage

`AwardPoint` command still works while Realtime provider is unavailable if DB/API are healthy.

## RT-N10-007 — Fake Match broadcast

Authenticated spectator tries to publish `match.event_committed`. Denied; no MatchEvent created.

## RT-N10-008 — Fake Registration broadcast

Attacker publishes `registration.changed capacity=999`. Clients cannot receive trusted domain event from untrusted sender under receive-only policy; authoritative query remains correct.

## RT-N10-009 — UUID enumeration

User guesses another Community Match UUID and tries channel join. Denied by resource context.

## RT-N10-010 — Revoked member

Member removed while old socket remains. Commands immediately denied; snapshot query denied; payload minimization limits exposure while provider revocation semantics catch up.

## RT-N10-011 — Vote privacy

Participant inspects all WebSocket frames during OPEN with AFTER_CLOSE policy. No ballot/tally leakage.

## RT-N10-012 — Waitlist privacy

Waitlisted participant sees counts/own status, not full queue identities through Broadcast.

## RT-N10-013 — Match gap

Spectator gets 101 then 103. Does not render 103 over missing 102; triggers resync.

## RT-N10-014 — Match correction

Correction is appended as new Match event. Realtime never mutates an already-consumed historical event silently.

## RT-N10-015 — Controller response

Controller's own AwardPoint is shown from authoritative command response even if its WebSocket is disconnected.

## RT-N10-016 — Two courts

Court A subscriber never receives Court B Match events.

## RT-N10-017 — Competition correction

Client misses OfficialResult correction event; reconnect snapshot still yields correct standings.

## RT-N10-018 — Inbox event lost

Notification Broadcast missed; Inbox Query still returns durable notification.

## RT-N10-019 — Presence spoof

Client publishes Presence metadata claiming Organizer/Owner. No capability changes.

## RT-N10-020 — Presence disconnect

Unclean disconnect leaves temporary stale Presence entry. No persisted attendance/history changes.

## RT-N10-021 — Public Match

Public spectator topic returns safe score DTO only, not internal control metadata.

## RT-N10-022 — Schema v2

Old client receives unknown event version. It refetches rather than guessing.

## RT-N10-023 — Old client during deploy

Live Match remains readable/controllable through compatibility window; deploy does not require immediate reload.

## RT-N10-024 — Raw Postgres schema change

DB column renamed. Semantic Broadcast contract remains stable.

## RT-N10-025 — Realtime authorization outage

Channel join fails but authorized Query/Command path remains usable where backend healthy; UI enters degraded live-update mode.

## RT-N10-026 — Socket connected, DB stale

Client has active socket but missed previous changes. Handshake snapshot prevents false `LIVE` state.

## RT-N10-027 — Large Community

User does not subscribe to every Match by joining Community dashboard; subscriptions are screen/context scoped.

## RT-N10-028 — Event burst

50 Match events arrive rapidly. Client processes sequence or coalesces rendering without changing event order.

## RT-N10-029 — Slow client

Slow spectator cannot exert backpressure that changes authoritative Match processing.

## RT-N10-030 — Reconnect storm

Many clients reconnect after outage. Snapshot/query endpoints and channel auth are observable/rate-aware; correctness does not depend on all events replaying from Realtime.

## RT-N10-031 — Notification payload PII

Realtime log/telemetry records event type and ID, not full notification content containing personal details.

## RT-N10-032 — Cross-account local state

Account B does not reuse account A's channel subscriptions/cached private snapshots after switch.

## RT-N10-033 — Auth refresh

Token refresh/channel reauth does not allow a stale Membership claim to authorize domain command; command always checks current DB state.

## RT-N10-034 — Client event replay

Attacker records a valid old Broadcast and replays locally. Revision/sequence marks it stale; server state unaffected.

## RT-N10-035 — Time skew

Client device clock is wrong. Ordering still follows revision/sequence, not `occurred_at` comparison.

## RT-N10-036 — Event ID collision

Server-generated event IDs are sufficiently unique; even if local dedupe cache resets, revision/sequence still prevents state corruption.

## RT-N10-037 — Registration close race

Join commits before/after close transaction according to DB serialization. Broadcast order does not decide result.

## RT-N10-038 — Voting close race

Vote/Close result is determined by server transaction; Realtime delivery order cannot reopen voting.

## RT-N10-039 — Takeover race

Match control epoch changes. Realtime informs UI quickly, but old controller commands are rejected by server even if takeover Broadcast is delayed.

## RT-N10-040 — Standings fan-out

OfficialResult triggers one semantic invalidation/update rather than sending full standings row sets to every client.

## RT-N10-041 — Public channel accidentally enabled

Security/CI configuration test detects domain topics becoming public without approved exception.

## RT-N10-042 — Client send permission regression

RLS test detects authenticated client can INSERT/send authoritative Broadcast events and fails release.

## RT-N10-043 — Sensitive evaluation

No generic Player/Community realtime event contains individual evaluation scores.

## RT-N10-044 — Ballot metadata

Even event size/type patterns should not intentionally reveal vote choice; no candidate-specific broadcast per ballot.

## RT-N10-045 — Cache invalidation duplicate

Ten `competition.updated` events can collapse into one refetch without semantic loss.

## RT-N10-046 — Realtime provider delayed

Broadcast arrives seconds after command. Revision makes it stale if a newer snapshot is already loaded.

## RT-N10-047 — Provider replacement

Switching away from Supabase Realtime does not alter domain tables/commands because clients depend on semantic event contracts + snapshots.

## RT-N10-048 — Database rollback

Transaction that rolls back must not result in a trusted Realtime event representing a commit that never happened.

## RT-N10-049 — Projection rebuild

Stats/standings projection rebuilt server-side. Realtime can signal invalidation, but clients ultimately trust new projection Query.

## RT-N10-050 — Global sync retirement

After target cutover, no Realtime handler invokes the legacy global `syncService` to merge entire domain payloads.

# 34. Decisions / Hypotheses / Open Questions

## DECIDED

- Realtime is transport, not source of truth.
- Broadcast is the default Supabase Realtime mechanism for domain updates.
- Private channels are default.
- Domain clients are receive-only by default.
- Commands always authorize server-side independently of channel access.
- Semantic event DTOs replace raw row-change contracts.
- Revision handles administrative aggregates; sequence handles Match.
- Subscribe/buffer before snapshot handshake.
- Gaps and reconnects cause authoritative reconciliation.
- Registration payloads are minimal and privacy-aware.
- Voting never broadcasts individual ballots; protected tally is not leaked.
- Match uses per-Match topics and contiguous sequence.
- Competition uses lower-frequency invalidation/update events.
- Notification Realtime accelerates persistent Inbox.
- Presence is ephemeral and never authority.
- Current persisted `CommunityPresence` must not be confused with Realtime Presence.
- Unknown event schema triggers safe refetch/incompatibility handling.

## STRONG HYPOTHESIS

- Supabase private Broadcast from database/server will be sufficient for V1/V2 without a separate realtime broker.
- Most Competition/Session changes should use invalidation + refetch rather than complex client delta replication.
- Match spectator events can include a small projection delta/summary in addition to the semantic event if measured UX needs justify it.

## OPEN

- Final topic naming grammar and authorization helper design.
- Whether production project should globally disable all public channels from first release or reserve an explicit public Match namespace.
- Exact policy for immediate confidentiality revocation on already-connected private channels.
- Whether public Match spectator surfaces are required in V1.
- Exact resync/poll fallback intervals during provider outage; must be performance-tested.
- Whether Match spectator scale will eventually require a dedicated distribution layer; decision is evidence-triggered.

# 37. Definition of Realtime Compliance

Uma implementação está alinhada a N2.13 quando:

1. commands permanecem corretos sem Realtime;
2. semantic Broadcasts são originados por trusted path;
3. domain channels são privados por default;
4. channel auth é testado contra BOLA;
5. clients não publicam fatos autoritativos;
6. event contracts são versionados e não expõem rows físicas;
7. revision/sequence detectam stale/gaps;
8. subscribe-buffer-snapshot handshake elimina a race inicial;
9. reconnect refaz estado autoritativo;
10. Registration não vaza queue identities;
11. Voting não vaza ballots/tally protegido;
12. Match usa sequence por Match, não timestamps;
13. Notification possui Inbox persistente independente;
14. Presence permanece efêmera/não autoritativa;
15. Realtime outage degrada UX, não correctness;
16. active subscriptions são scope/screen-aware;
17. observabilidade mede gaps/convergência/fan-out sem raw sensitive payload;
18. legacy global sync não é chamado para “resolver” eventos Realtime.
