## 0. Regra de leitura

Este documento define o **target canônico de persistência** do Volley.

A regra mais importante é:

```text
POSTGRES
=
AUTHORITATIVE RELATIONAL MODEL

POSTGRES
≠
SERIALIZED COPY OF TYPESCRIPT/REACT STATE
≠
CLOUD MIRROR OF LOCAL STORAGE
```

Toda tabela nova deve ser classificada em uma das quatro naturezas:

```text
SOURCE FACT
MUTABLE CURRENT STATE
IMMUTABLE SNAPSHOT
DERIVED PROJECTION
```

Se uma equipe não consegue responder a qual categoria uma tabela pertence, o modelo ainda não está pronto.

# 1. Current State — evidência do repositório

## 1.1 O schema operacional atual espelha o modelo local-first

A migration de sync operacional criou `sessions`, `teams`, `games`, `point_events`, reports, presence e WhatsApp drafts com um padrão recorrente:

```text
owner_id
community_id
local_id
sync_version
deleted_at
created_at
updated_at
```

Além disso, relações importantes aparecem serializadas em arrays ou JSONB:

```text
sessions.selected_player_ids text[]
sessions.team_ids text[]
sessions.config jsonb
teams.player_ids text[]
teams.strength_snapshot jsonb
games.point_ids text[]
games.metadata jsonb
point_events.score_before jsonb
point_events.score_after jsonb
community_presence.items jsonb
```

Esse modelo foi útil para sincronizar entidades locais, mas não é o target de um banco relacional autoritativo.

## 1.2 `local_id` virou requisito estrutural do sync

A migration posterior de conflito de upsert precisou transformar os índices `(owner_id, local_id)` em unique indexes não parciais para que `supabase-js` pudesse usá-los como `ON CONFLICT` target.

Isso mostra que:

```text
local_id
```

não é uma identidade de domínio; é uma adaptação imposta pelo protocolo local↔cloud atual.

No target, entidades offline-capable usam UUID final desde a criação, e `local_id/cloudId` deixam de existir como chaves canônicas.

## 1.3 `owner_id ON DELETE CASCADE` ameaça fatos compartilhados

`Session`, `Team`, `Game`, `PointEvent` e reports atuais usam:

```text
owner_id uuid not null references auth.users(id) on delete cascade
```

Esse padrão é incompatível com a separação:

```text
ACCOUNT DELETION
≠
SPORTS HISTORY DELETION
```

A remoção de uma conta não pode apagar partidas, pontos, resultados ou snapshots de terceiros.

## 1.4 Há boas direções já presentes

Algumas decisões atuais devem ser preservadas:

- UUID já é usado extensivamente como PK;
- `players.id` já é explicitamente identidade global canônica;
- há partial unique indexes em vários workflows;
- RLS é habilitado nas tabelas compartilhadas;
- `players.user_id` usa `ON DELETE SET NULL`, evitando apagar a identidade esportiva com a conta;
- há triggers/audit e functions server-side para operações sensíveis.

O target generaliza essas boas práticas e elimina inconsistências.

## 1.5 Avaliações ainda refletem o sync genérico

`player_evaluations` hoje possui:

```text
owner_id
player_id
attributes jsonb
profile jsonb
status jsonb
notes
local_id
sync_version
deleted_at
```

com unique `(owner_id, player_id)` e sem `community_id` explícito.

No target, PlayerEvaluation vira source fact contextual por Community/evaluator/revision; Skill Profiles são projections separados.

## 1.6 CommunityPlayer ainda contém state duplication

A migration de `community_players` adicionou simultaneamente:

```text
active boolean
status text
```

com trigger para manter os dois sincronizados, além de `role`, `sync_version` e `deleted_at`.

Isso ilustra uma regra importante do target:

> não manter duas representações mutáveis do mesmo estado quando uma pode ser derivada da outra.

# 2. N3.14.01 — PostgreSQL Authority Model

## N4.14.01.01 — Autoridade

Para estado compartilhado do Volley:

```text
Postgres committed state
=
authority
```

Browser state, IndexedDB cache, Realtime payload e projection local são representações subordinadas.

## N5.14.01 — Consequências

- mutations compartilhadas relevantes terminam em transaction server-side;
- browser não decide ownership, FIFO, winner oficial, sequence ou capability;
- Realtime apenas transporta informação commitada;
- cache pode estar stale sem alterar a verdade;
- Quick Session não publicada é exceção consciente: authority local até handoff explícito.

## N10.14.01

- Browser altera row local: DB compartilhado não muda sem command autorizado.
- Realtime perde mensagem: snapshot autoritativo recupera estado.
- IndexedDB corrompe cache remoto: refetch reconstrói.

# 3. N3.14.02 — Schema Strategy

## N4.14.02.01 — Estrutura inicial

O target não cria um schema PostgreSQL diferente para cada bounded context no V1.

Preferência:

```text
public
├── domain/source/current/snapshot tables exposed as needed through Data API/RLS
├── safe read views/functions as needed
└── explicitly controlled RPC entry points

app_private
├── command_receipts
├── domain_outbox
├── internal worker state
├── projection checkpoints
├── audit internals not intended for direct client read
├── repair/migration internals where appropriate
└── other server-only support tables/functions
```

## N5.14.02 — Por que não schema-per-context agora

Schema-per-context poderia melhorar namespacing, mas adiciona complexidade a:

- Supabase Data API exposure;
- grants/RLS;
- migrations;
- generated types;
- function search paths;
- cross-context FKs.

Bounded-context ownership será principalmente uma regra de arquitetura/aplicação, não uma multiplicação prematura de schemas PostgreSQL.

## N5.14.02.02 — `app_private`

Objetos internos não devem ficar expostos ao browser apenas porque pertencem ao mesmo projeto.

`app_private` funciona como boundary de infraestrutura interna.

---

# 4. N3.14.03 — Public vs Private Schemas

## N4.14.03.01 — `public`

Uma tabela em `public` não significa “dados públicos na internet”. Significa que pode estar no schema exposto e deve ter grants/RLS coerentes.

## N4.14.03.02 — `app_private`

Objetos server-only:

```text
command_receipts
domain_outbox
worker_leases
internal_rebuild_jobs
migration_anomalies
security/internal audit support
```

não devem possuir grants para browser autenticado.

## N5.14.03 — Funções

Functions `SECURITY DEFINER` server-sensitive devem:

- autenticar/autorizar explicitamente;
- usar `search_path=''` no target e nomes totalmente qualificados;
- possuir grants/revokes mínimos;
- evitar dynamic SQL quando desnecessário.

A configuração atual de `search_path=public` foi uma melhoria sobre funções mutáveis, mas o target de hardening fica mais restritivo.

# 5. N3.14.04 — Naming Conventions

## N4.14.04.01 — Tabelas

Preferência:

```text
snake_case plural
```

Exemplos:

```text
community_memberships
registration_windows
registration_entries
match_events
match_projections
competition_fixtures
```

## N4.14.04.02 — Colunas

- PK: `id`;
- FKs: `<entity>_id`;
- timestamps: `<verb>_at` ou `created_at/updated_at`;
- revisions: `revision`;
- ordered event sequence: `sequence_number` ou `sequence` consistentemente por contexto;
- versions semânticas: `schema_version`, `algorithm_version`, `calculation_version`.

## N5.14.04 — Não esconder semântica

Evitar:

```text
data
payload
metadata
status
```

sem contrato ou state machine claramente definida.

# 6. N3.14.05 — Primary Keys / UUID

## N4.14.05.01 — Regra

Entidades principais usam UUID final.

```text
id uuid primary key
```

## N5.14.05 — Offline-capable

Quick/Match local-capable geram UUID antes da nuvem.

Esse UUID continua sendo o mesmo depois da publicação.

## N5.14.05.02 — Sem `local_id/cloud_id`

No target:

```text
entity.id
=
identity everywhere
```

`legacy_local_id` pode existir temporariamente em import/provenance, nunca como segunda identidade operacional permanente.

# 7. N3.14.06 — Timestamps

## N4.14.06.01 — Tipo

Instantes usam:

```text
timestamptz
```

Datas civis puras podem usar `date` quando semanticamente correto.

## N5.14.06 — Server time

Ordering compartilhado não depende de relógio do browser.

`created_at`/`updated_at` são úteis para auditoria/UX, mas não substituem revision/sequence em concorrência.

## N5.14.06.02 — `updated_at`

Nunca usar:

```text
max(updated_at)
```

como mecanismo de merge de Match, Registration, Voting, governance ou OfficialResult.

# 8. N3.14.07 — Revisions / Sequences

## N4.14.07.01 — Revision

Aggregates administrativos/shared state podem possuir:

```text
revision bigint/int
```

incrementada por mutation autoritativa relevante.

Exemplos:

```text
RegistrationWindow.revision
RosterRevision sequence/version
CandidateSet source roster revision
```

## N4.14.07.02 — Sequence

Event streams ordenados como Match usam sequence por aggregate:

```text
unique(match_id, sequence)
```

## N5.14.07 — Não confundir

```text
revision
≠ sync_version
≠ updated_at
```

`sync_version` genérico desaparece. Revision existe porque o domínio daquele aggregate precisa detectar staleness/concurrency.

# 9. N3.14.08 — Source Facts

## N4.14.08.01 — Definição

Source Fact é dado autoritativo que registra algo ocorrido/decidido e do qual outras informações podem ser derivadas.

Exemplos:

```text
PlayerEvaluation revision
RegistrationEntry lifecycle fact/current record according to model
MatchEvent
MatchResult
OfficialCompetitionResult revision/current record + history
CompetitionPenalty
MatchParticipation
```

## N5.14.08 — Regra

Projection não substitui source fact.

Se:

```text
MatchProjection.score
```

divergir de replay de eventos efetivos:

```text
MatchEvents win
Projection rebuilds
```

---

# 10. N3.14.09 — Mutable State

## N4.14.09.01 — Definição

Mutable Current State representa o estado atual necessário para commands/queries e pode ser atualizado transactionalmente.

Exemplos:

```text
Community lifecycle
CommunityMembership current status/role
RegistrationWindow current state/revision
MatchControlLease
MatchProjection
NotificationIntent current delivery state
MediaAsset current processing state
```

## N5.14.09 — Mutável não significa histórico descartável

Mudanças relevantes podem gerar:

- audit;
- revision records;
- domain events;
- immutable history source.

Não precisamos event-sourcear tudo apenas porque queremos histórico.

---

# 11. N3.14.10 — Immutable Snapshots

## N4.14.10.01 — Definição

Snapshot congela inputs/representações necessários para explicar história futura.

Exemplos:

```text
SessionRulesSnapshot
RosterRevision + entries
PlayerBalanceSnapshot
TeamCandidateSet published candidates
Confirmed TeamDraw revision
MatchRoster
CompetitionRosterRevision
Notification rendered template snapshot
```

## N5.14.10 — Regras

- snapshot publicado/confirmado não é atualizado em place;
- mudança gera nova revisão/novo snapshot;
- snapshots guardam somente o necessário para finalidade histórica;
- snapshot não copia aggregate inteiro indiscriminadamente.

---

# 12. N3.14.11 — Projections

## N4.14.11.01 — Definição

Projection é materialização derivada e reconstruível.

Exemplos:

```text
MatchProjection
CommunityPlayerSkillProfile
GlobalPlayerSkillProfile
PlayerMatchStatContribution
CareerProjection
CompetitionStandingsProjection
```

## N5.14.11 — Contrato obrigatório

Toda projection deve documentar:

```text
source facts
source revision/sequence
calculation version
rebuild procedure
staleness rule
invariants
```

## N5.14.11.02 — Escrita

Browser não possui direct update em projection.

Mutation ocorre em source/current state; projection é atualizada pelo command transaction quando crítica ou worker quando eventual.

---

# 13. N3.14.12 — Audit / Outbox / Command Receipts

## N4.14.12.01 — Três conceitos distintos

```text
AUDIT
quem fez mudança administrativa/relevante

DOMAIN OUTBOX
fatos committed aguardando processamento assíncrono

COMMAND RECEIPT
resultado idempotente de command lógico
```

Não combinar tudo em uma tabela genérica de logs.

## N4.14.12.02 — `command_receipts`

Server-only, com retenção finita apropriada.

Campos conceituais:

```text
command_id
command_type
actor_user_id
resource_type/resource_id
result_code
result_payload_minimal
committed_at
expires_at?
```

## N4.14.12.03 — `domain_outbox`

Criada na mesma transaction que o fato que originou o efeito.

Consumer assume at-least-once e precisa ser idempotente.

## N4.14.12.04 — Audit

Audit semântico é preferível a dump completo indiscriminado de row quando o evento administrativo possui significado próprio.

# 14. N3.14.13 — Relational Modeling

## N4.14.13.01 — Regra

Relações de domínio são modeladas por FKs/join tables quando possuem identidade, cardinalidade, constraints ou queries relevantes.

Preferir:

```text
session_participants
roster_revision_entries
team_draw_assignments
match_roster_entries
competition_roster_entries
```

em vez de:

```text
player_ids[]
selected_player_ids[]
team_ids[]
point_ids[]
```

## N5.14.13 — Benefícios

- FK integrity;
- indexes reais;
- queries contextuais;
- RLS contextual;
- history/revision;
- constraints de uniqueness;
- sem remapeamento manual em arrays.

# 15. N3.14.14 — JSONB Policy

## N4.14.14.01 — JSONB é permitido quando semântica pede snapshot/payload flexível versionado

Bons candidatos:

```text
MatchEvent payload versioned
RulesSnapshot details
solver diagnostics
provider response summary
immutable rendered configuration snapshot
```

## N4.14.14.02 — JSONB não substitui relações centrais

Evitar JSONB para:

```text
membership list
roster
votes
match participation
standings source facts
player evaluations dimensions if queried/validated independently
```

## N5.14.14 — Contrato

Todo JSONB importante possui schema/runtime contract e, quando persistido historicamente, `schema_version` explícito quando necessário.

---

# 16. N3.14.15 — Array Policy

## N4.14.15.01 — Arrays não são proibidos

Podem ser adequados para valores atômicos bounded e sem identidade própria, por exemplo algumas tags/configurações pequenas.

## N4.14.15.02 — Array de foreign IDs exige forte justificativa

No target, arrays do tipo:

```text
selected_player_ids
team_ids
player_ids
point_ids
```

são considerados legado e substituídos por relações.

## N5.14.15 — Regra de review

Novo `uuid[]`/`text[]` que representa entities relacionadas deve responder por que uma join table não é melhor.

---

# 17. N3.14.16 — Foreign Keys

## N4.14.16.01 — FKs por padrão

Relações autoritativas persistentes usam FK sempre que possível.

Evitar IDs `text` sem FK para entidades internas, como ocorre atualmente em `games.team_a_id`, `point_events.game_id` etc.

## N5.14.16 — FK não substitui autorização

FK garante integridade referencial, não que recursos pertencem ao mesmo Community/contexto.

Commands precisam validar contexto; constraints adicionais podem reforçar onde modelável.

---

# 18. N3.14.17 — Delete Semantics

## N4.14.17.01 — Cada FK escolhe semântica explicitamente

Possibilidades:

```text
RESTRICT / NO ACTION
CASCADE
SET NULL
```

Nenhuma é default conceitual universal.

## N5.14.17 — Guidelines

### `CASCADE`

Adequado quando child não possui significado independente e o parent é realmente deletável.

Exemplo possível:

```text
temporary upload chunks → upload intent
```

### `SET NULL`

Adequado para actor/account reference histórica quando apagar a conta não deve apagar o fato.

### `RESTRICT`

Preferido quando remoção do parent destruiria história/consistência.

## N5.14.17.02 — Auth deletion

Shared sports facts não usam `auth.users ON DELETE CASCADE` como lifecycle.

---

# 19. N3.14.18 — Domain Lifecycle vs Soft Delete

## N4.14.18.01 — `deleted_at` não é lifecycle universal

O sync atual usa `deleted_at` como tombstone genérico.

No target, preferir estados semânticos:

```text
Community = ACTIVE / ARCHIVED
Membership = ACTIVE / LEFT / REMOVED / SUSPENDED
Session = DRAFT / SCHEDULED / IN_PROGRESS / COMPLETED / CANCELLED
VotingRound = OPEN / CLOSED / FINALIZED / INVALIDATED
Match = LIVE / FINISHED / ABANDONED / INVALIDATED
```

## N5.14.18 — Soft delete legítimo

Pode existir para recursos em que delete lógico é realmente a semântica de produto/retention.

Mas precisa ser decisão específica, não coluna copiada em toda tabela.

---

# 20. N3.14.19 — Constraints

## N4.14.19.01 — Banco protege invariantes estruturais

Use:

```text
NOT NULL
CHECK
UNIQUE
FK
EXCLUDE when justified
```

para regras que o banco consegue garantir localmente.

## N5.14.19 — Exemplos

```text
unique(match_id, sequence)
unique active membership per community/user
unique effective vote per round/user
unique current official result per fixture
positive registration capacity
revision >= 0
```

## N5.14.19.02 — Regra semântica complexa

“Community deve ter pelo menos um Owner” pode precisar de command transaction/lock além de index, porque ausência total não é facilmente garantida por simple unique constraint.

---

# 21. N3.14.20 — Partial Unique Indexes

## N4.14.20.01 — Uso recomendado

Partial unique indexes expressam uniqueness sobre estado atual/ativo.

Exemplos:

```text
one PENDING JoinRequest per community/user
one ACTIVE PlayerAccountLink per user
one ACTIVE PlayerAccountLink per player
one CURRENT OfficialResult per fixture
one effective vote per voting round/user
```

## N5.14.20 — Não usar por conveniência do sync

O legado `(owner_id, local_id)` foi criado para reconciliação cloud. Esse padrão desaparece com UUID final.

---

# 22. N3.14.21 — Index Strategy

## N4.14.21.01 — Índices derivam de access paths

Não “indexar tudo”.

Exemplos:

```text
registration_entries(window_id, status, queue_sequence)
match_events(match_id, sequence)
community_memberships(user_id, status)
community_players(community_id, player_id)
player_match_stats(player_id, match_id)
```

## N5.14.21 — Índices e RLS

Colunas usadas em RLS/EXISTS precisam de índices coerentes para evitar scans inesperados.

## N5.14.21.02 — JSONB indexes

GIN somente se query real justificar.

Não criar GIN automático em cada JSONB.

## N5.14.21.03 — Performance validation

Queries críticas possuem `EXPLAIN/EXPLAIN ANALYZE` em datasets de benchmark conforme N2.18/N2.20.

---

# 23. N3.14.22 — Transaction Boundaries

## N4.14.22.01 — Command crítico = transaction semântica

Exemplos:

### Leave Registration

```text
mark current entry withdrawn
promote next eligible
increment window revision
write command receipt
write outbox as needed
COMMIT
```

### AwardPoint

```text
validate lease/epoch/sequence
append MatchEvent
update critical MatchProjection
write command receipt
outbox/broadcast signal
COMMIT
```

### Transfer Ownership

```text
lock Community/memberships
validate current owner
assign new owner
remove old owner role appropriately
audit
receipt
COMMIT
```

## N5.14.22 — External provider calls

Push/email/storage provider network calls não ocorrem dentro da transaction do domínio.

Persistir intent/outbox primeiro.

---

# 24. N3.14.23 — Row Locks

## N4.14.23.01 — Lock hot root do aggregate

Exemplos:

```text
RegistrationWindow FOR UPDATE
MatchProjection / Match root FOR UPDATE
VotingRound FOR UPDATE on finalization
Community root/membership set on ownership transfer
Fixture/OfficialResult root on officialization
```

## N5.14.23 — Localized contention

Locks devem ser por aggregate, não globais.

100 RegistrationWindows independentes não competem pelo mesmo lock.

## N5.14.23.02 — Lock ordering

Commands que travam múltiplos recursos devem possuir ordem consistente para minimizar deadlocks.

---

# 25. N3.14.24 — Projection Rebuildability

## N4.14.24.01 — Rebuild é requisito, não promessa

Uma projection só pode ser chamada de rebuildable se existir:

```text
source facts preserved
rebuild algorithm/version
checkpoint/source version
integrity test
operational command/job
```

## N5.14.24 — Crítica vs eventual

### Projection crítica

`MatchProjection` participa da validação do próximo command; portanto atualiza na mesma transaction ou por mecanismo equivalente que preserve correctness.

### Projection eventual

Career/Stats/Global Skill Profile podem atualizar async quando o produto tolera staleness, desde que isso seja detectável e não utilizado silenciosamente como fresh.

---

# 26. N3.14.25 — Migration Strategy

## N4.14.25.01 — Source of truth do schema

```text
ordered versioned migrations in Git
```

O schema consolidado, se mantido, é artifact gerado/verificado, não segunda source manual.

## N4.14.25.02 — Padrão

```text
EXPAND
↓
DUAL COMPATIBILITY when required
↓
BACKFILL / MIGRATE
↓
SWITCH WRITES
↓
SWITCH READS
↓
VERIFY
↓
CONTRACT
```

## N5.14.25 — Backfills

Grandes backfills são:

- idempotentes;
- batchable;
- resumable;
- observáveis;
- semanticamente verificáveis.

Não apenas `row_count source == row_count target`.

## N5.14.25.02 — Legacy provenance

Dados importados ambíguos preservam provenance/anomaly; não se inventa semântica ausente.

---

# 27. N3.14.26 — Partitioning Triggers

## N4.14.26.01 — Não particionar prematuramente

`match_events` permanece tabela comum inicialmente.

Postgres com índices adequados deve ser benchmarkado antes de adicionar partitioning.

## N5.14.26 — Triggers de revisão

Considerar partitioning quando métricas mostrarem impacto material em:

```text
index size
vacuum/maintenance
query latency
backup/restore
retention operations
```

Possível estratégia futura:

```text
time-range partitioning
```

mas não decidida antecipadamente.

# 31. Delete Semantics Examples

## 31.1 Auth User → historical actor

Prefer:

```text
actor_user_id FK ON DELETE SET NULL
```

quando o fato precisa sobreviver à conta.

## 31.2 Community → historical Session

Community archive é preferido a hard-delete. Portanto, `ON DELETE CASCADE` não é lifecycle operacional normal.

## 31.3 Session → Match

Se Session realmente nunca é hard-deleted após possuir Match, FK pode ser RESTRICT e lifecycle semântico faz o trabalho.

## 31.4 Match → MatchEvent

MatchEvent é history source. Não deve desaparecer por deleção casual da Match. A própria Match deve usar lifecycle `INVALIDATED/CANCELLED` conforme semântica.

## 31.5 Projection → Source

Deleting/rebuilding projection nunca apaga source facts.

# 33. RLS/Data Boundary

N2.16 detalhará segurança, mas Data Architecture fixa:

- toda tabela exposta via Data API possui RLS apropriada;
- critical source tables podem permitir SELECT controlado mas negar direct INSERT/UPDATE/DELETE ao browser;
- projections são read-only para client;
- server-only tables ficam fora do schema/grants expostos;
- RLS nunca confia em `community_id` fornecido isoladamente sem resolver o resource real.

# 34. Data Integrity Checks

Além de constraints, teremos checks operacionais periódicos.

Exemplos:

```text
active Community with owner count != 1
MatchProjection.last_sequence != max(MatchEvent.sequence)

orphan Media attachment
```

Resultado esperado:

```text
0 violations
```

Checks não substituem constraints; capturam invariantes cross-row/cross-context difíceis de impor puramente no schema.

# 35. Repair Policy

Auto-repair somente para estado claramente derivado/técnico:

```text
rebuild projection
recreate cache
cleanup orphan upload
```

Não auto-reparar fatos ambíguos:

```text
two owners
conflicting Player merge
old/new Match history divergence
retroactive Competition conflict
```

Esses casos exigem review/repair command.

# 37. N10 — Adversarial / Acceptance Matrix

## DATA-N10-001 — Account deletion vs Match history

Delete User who created 100 Sessions. Sessions/Matches/Events remain according to retention policy; no `ON DELETE CASCADE` destroys shared sports facts.

## DATA-N10-002 — Local ID removal

Quick Session created offline uses UUID final. Publishing does not remap Session/Match/Event foreign keys.

## DATA-N10-003 — Duplicate Match sequence

Two transactions try to insert `(match_id=X, sequence=101)`. Constraint/locking ensures at most one succeeds.

## DATA-N10-004 — Registration over-capacity

100 concurrent joins into capacity 12 produce a state satisfying domain constraints; generic upsert cannot bypass capacity transaction.

## DATA-N10-005 — Two current OfficialResults

Concurrent officializations cannot leave two CURRENT OfficialResults for one Fixture.

## DATA-N10-006 — Projection rebuild

Delete MatchProjection in test environment, rebuild from MatchEvents, obtain same effective state.

## DATA-N10-007 — Projection stale

GlobalSkillProfile source revision lags Evaluation source. System can detect staleness without comparing timestamps.

## DATA-N10-008 — Array regression

New Session code cannot persist participant relation solely in `selected_player_ids[]` without architecture exception/ADR.

## DATA-N10-009 — JSONB misuse

Proposal to store all Competition entries inside `competition.config` JSONB is rejected; entries require relational model.

## DATA-N10-010 — Soft delete ambiguity

Legacy `deleted_at` cannot be blindly mapped to `CANCELLED`, `ARCHIVED` or `REMOVED` without context.

## DATA-N10-011 — User removal from Membership

Removing Membership does not cascade-delete Player, CommunityPlayer, MatchParticipation or evaluations historically justified.

## DATA-N10-012 — Player merge

Merge preserves historical references/provenance; source UUID is not recycled.

## DATA-N10-013 — Command timeout

DB commits command receipt and domain change; response is lost; retry same command_id returns prior result without duplicate facts.

## DATA-N10-014 — Outbox worker duplicate

Two workers receive same outbox item. Downstream idempotency prevents duplicate NotificationIntent/effect.

## DATA-N10-015 — Poison outbox

One permanently failing outbox item transitions to failed/dead-letter state and does not block unrelated items.

## DATA-N10-016 — Transaction failure after Leave

Artificial error after marking RegistrationEntry withdrawn but before promotion rolls back whole transaction.

## DATA-N10-017 — External Push outage

Push provider down does not extend/rollback JoinRegistration transaction.

## DATA-N10-018 — RLS scan

Critical contextual query uses indexed predicates; benchmark does not require scanning all Membership rows globally.

## DATA-N10-019 — FK type

Internal MatchEvent references Match by UUID FK, not free-form text.

## DATA-N10-020 — Current Player changed

Updating Player position/name does not mutate MatchRoster or PlayerBalanceSnapshot historical rows.

## DATA-N10-021 — Unknown statistics

SCORE_ONLY Match does not persist detailed stat zeros for metrics that were never captured.

## DATA-N10-022 — Community owner integrity

Integrity check detects any active Community with zero or multiple owners; zero is the expected metric.

## DATA-N10-023 — Restore

Restored backup passes FK/constraint/integrity suite and privacy deletion replay before serving traffic.

## DATA-N10-024 — Backfill interruption

Game→Match backfill stops at 40%, reruns, and produces exactly one imported target per legacy source.

## DATA-N10-025 — Ambiguous legacy evaluation

Evaluation without reliable Community is stored/imported as legacy-unscoped/anomaly, not assigned to first Community found.

## DATA-N10-026 — Duplicate current vote

Concurrent CastVote operations leave one effective vote per round/user according to policy.

## DATA-N10-027 — Snapshot mutation attempt

Published CandidateSet/ConfirmedTeamDraw cannot be updated in place by normal command; new revision required.

## DATA-N10-028 — Projection client update

Authenticated browser direct UPDATE against standings/skill/career projection is denied.

## DATA-N10-029 — Direct critical table insert

Browser cannot bypass AwardPoint/JoinRegistration by directly inserting MatchEvent/RegistrationEntry if target security model is active.

## DATA-N10-030 — `updated_at` tie

Two events share same timestamp; ordering remains deterministic from sequence/revision, not time.

## DATA-N10-031 — Clock skew

Client clock one hour ahead cannot jump Registration queue or Match sequence.

## DATA-N10-032 — Context mismatch

Payload references Session in Community A and Player/Registration resource in B; command rejects despite individually valid FKs.

## DATA-N10-033 — Orphan projection

Source deleted only through allowed lifecycle; projection references do not keep invalid domain row silently.

## DATA-N10-034 — Orphan media

Unattached MediaAsset is eventually GC-eligible, but deleting media cannot cascade-delete Player.

## DATA-N10-036 — Partitioning not needed

Large historical dataset still meets query/maintenance budgets; no partitioning introduced just because row count sounds large.

## DATA-N10-038 — Migration drift

Production schema change not represented by migration is detected before next release/contract step.

## DATA-N10-039 — Old browser tab

Schema expand remains compatible with old client until contract window ends; destructive removal is delayed.

## DATA-N10-040 — New browser with old schema

Deployment ordering prevents app requiring new table/function before migration is applied.

## DATA-N10-041 — Multiple evaluations

Raw evaluations are source rows/revisions; aggregate profile does not overwrite them.

## DATA-N10-042 — Overall formula change

Changing derived Overall formula does not alter stored TeamDraw balance input snapshots nor historical Match facts.

Deleting high-volume telemetry does not delete domain audit/source facts because they are separate stores/concepts.

## DATA-N10-050 — Source/projection mismatch

# 38. Decisions / Hypotheses / Open Questions

## DECIDED

- PostgreSQL is authoritative for shared committed state.
- Target data is explicitly classified into Source Fact / Mutable State / Immutable Snapshot / Derived Projection.
- UUID is canonical ID; `local_id/cloudId` leave the target.
- `sync_version` generic leaves the target.
- Relations use normalized FK/join tables instead of ID arrays by default.
- JSONB is for versioned payload/snapshot/flexible bounded structures, not core relationship modeling.
- Shared sports facts do not cascade-delete on account removal.
- Lifecycle is semantic; generic `deleted_at` is not universal.
- Critical commands use explicit transaction boundaries and aggregate-local locks.
- Outbox and command receipts live server-side and are distinct from audit.
- Projections are rebuildable only with explicit source/version/rebuild contracts.
- Versioned migrations in Git are the schema source of truth.
- Partitioning is deferred until measured need.

## STRONG HYPOTHESIS

- Initial schema split will be `public` + `app_private`, not schema-per-bounded-context.
- `app_private` will hold command receipts, outbox, worker/checkpoint/internal support.
- MatchEvent table remains unpartitioned for the initial product scale.
- Most historical source tables will prefer semantic invalidation/archive over hard delete.

## OPEN

- Exact retention window for command receipts/outbox/audit classes.
- Whether some internal operational tables should live in provider-specific schema instead of `app_private`.
- Exact partitioning strategy if/when MatchEvent triggers are reached.
- Whether specific immutable snapshot tables should share generic revision metadata helpers or stay context-specific.
- Whether certain read projections should be materialized views versus ordinary projection tables/jobs.

# 41. Definition of Data-Architecture Compliance

Uma implementação está alinhada a N2.14 quando:

1. shared state commitado possui Postgres como autoridade;
2. cada tabela está classificada por natureza de verdade;
3. UUID final elimina local/cloud identity remapping no target;
4. relações centrais são normalizadas e protegidas por FKs/constraints;
5. `sync_version`, `deleted_at` genérico e arrays de IDs não contaminam novos bounded contexts;
6. snapshots históricos são imutáveis/revisionados;
7. projections possuem source/version/rebuild explícitos e são read-only para client;
8. command receipts, outbox e audit são conceitos separados;
9. critical commands são transactions idempotentes com locks apropriados;
10. account deletion não destrói shared sports history por cascade;
11. indexes correspondem a queries/RLS reais;
12. migrations são versionadas, testadas e backfills são semanticamente verificáveis;
13. ambiguity de dados legados é registrada, não inventada;
14. partitioning permanece uma opção futura baseada em métricas, não uma complexidade inicial.
