## 0. Regra de leitura

A regra central deste capítulo é:

```text
APPLICATION API
=
SEMANTIC INTENT

NOT
GENERIC TABLE CRUD
```

A UI deve pedir:

```text
JoinRegistration
LeaveRegistration
TransferCommunityOwnership
GenerateTeamCandidates
ConfirmTeamDraw
AwardPoint
OfficializeCompetitionResult
```

não:

```text
updateRow
saveSession
patchCommunity
upsertGame
softDeleteEntity
```

O Application Layer coordena intenção, autorização, policies, ports e resposta ao usuário. Ele não transforma o frontend em administrador de tabelas PostgreSQL.

# 1. Current State — evidência do repositório

## 1.1 Existe uma camada Application reaproveitável

O repositório já possui `src/application` com:

- use cases;
- gateways;
- view models;
- auth/session helpers;
- `AppResult`;
- testes associados.

Exemplo positivo:

```text
ensureAccountReadyCommand
        ↓
AccountGateway.ensureReady()
```

O use case não chama Supabase diretamente.

Essa direção será preservada.

## 1.2 `AppResult` já separa famílias de erro

O código atual distingue:

```text
product
technical
validation
authorization
conflict
offline_unavailable
unexpected
```

Isso é uma boa fundação.

Problemas a corrigir:

- `required: owner | admin | master | programmer` ainda expressa autorização por labels/hierarchy, não capability contextual;
- `recoverable: boolean` é simples demais para representar `retry`, `refresh`, `reauth`, `reconcile`, `contact support` etc.;
- `unexpectedError()` cria `correlationId` no browser, que não garante correlação com server logs;
- ProductErrorCode é pequeno/global e tende a virar enum monolítica se todos os bounded contexts adicionarem erros ali.

## 1.3 Cloud services ainda expõem CRUD/table shape

`communityCloudService` atualmente:

```text
fetchAll()
upsert()
softDelete()
```

fazendo diretamente:

```text
supabase.from('communities').select('*')
.update(...)
.upsert(...)
```

Também mapeia:

```text
cloudId
local_id
syncStatus
deleted_at
```

e possui fallback de colisão de PK/reconciliação dentro do adapter.

Isso é coerente com a arquitetura local-first atual, mas não com o target server-authoritative por bounded context.

## 1.4 SQLSTATE aparece como contrato implícito

Use cases atuais podem mapear:

```text
23505 → username_unavailable
22023 → invalid_username
```

Isso é aceitável como detalhe transitório de adapter, mas SQLSTATE não deve se tornar o contrato público estável de produto.

## 1.5 Alguns RPCs atuais estão mais próximos do target

Fluxos como Player Link já usam RPCs semânticos para proposal/approval em vez de permitir alteração direta irrestrita do vínculo.

A direção correta é:

```text
semantic command
→ trusted transactional boundary
```

não necessariamente “toda operação deve virar Edge Function”.

# 2. N3.15.01 — Application Boundary

## N4.15.01.01 — Fluxo canônico

```text
UI / Presentation
      ↓
Application Use Case
      ↓
CommandPort / QueryPort
      ↓
Infrastructure Adapter
      ↓
RPC / SQL Read Model / Edge Function / Provider
```

## N5.15.01 — Responsabilidades da Application

Application coordena:

- intenção do usuário;
- input DTO;
- seleção do port apropriado;
- policy offline;
- mapping de resultado técnico para contrato de produto;
- eventual composição entre bounded contexts;
- observabilidade de request/use case;
- retorno de ViewModel/DTO apropriado.

Application não deve:

- implementar regras matemáticas profundas do domínio;
- escrever SQL;
- depender de React;
- depender diretamente de `@supabase/supabase-js`;
- usar row shape do banco como domínio.

## N6.15.01 — Boundary rule

```text
UI may import Application
Application may import Domain contracts
Infrastructure implements Application/Domain ports
Domain imports neither UI nor Infrastructure
```

# 3. N3.15.02 — Commands

## N4.15.02.01 — Definição

Command representa intenção que pode alterar estado autoritativo.

Exemplos:

```text
CreateCommunity
ApproveCommunityJoinRequest
TransferCommunityOwnership
OpenRegistration
JoinRegistration
FinalizeSessionRoster
ConfirmTeamDraw
AwardPoint
CorrectMatchEvent
OfficializeCompetitionResult
RequestAccountDeletion
```

## N5.15.02 — Command naming

Preferir:

```text
Verb + Domain Noun
```

Evitar:

```text
save()
update()
patch()
setData()
```

quando a ação possui semântica própria.

## N5.15.02.02 — Não equivalem a HTTP verbs

`JoinRegistration` pode internamente usar RPC/Postgres transaction, mas seu significado não é `POST /registration_entries`.

## N6.15.02 — Command result

Command crítico retorna estado autoritativo mínimo necessário:

```text
resource id
new revision / sequence
result status
relevant projection summary
```

Não retornar apenas:

```text
{ success: true }
```

quando o client precisa saber qual estado foi de fato comprometido.

# 4. N3.15.03 — Queries

## N4.15.03.01 — Definição

Query obtém read model sem alterar intenção de domínio.

Exemplos:

```text
GetCommunityDashboard
GetRegistrationSnapshot
GetTeamCandidateSet
GetMatchLiveSnapshot
GetCompetitionStandings
GetPlayerCareer
GetNotificationInbox
```

## N5.15.03 — Query não significa `select *`

Query contract deve representar o que a tela/caso de uso precisa, não expor tabelas indiscriminadamente.

## N6.15.03 — Direct SELECT

Direct Supabase SELECT + RLS pode continuar apropriado para read models simples quando:

- shape é deliberadamente público/privado;
- RLS é suficiente;
- não expõe schema interno desnecessário;
- runtime DTO validation existe quando risco justifica.

Não é obrigatório criar RPC para cada leitura trivial.

# 5. N3.15.04 — Command Contracts

## N4.15.04.01 — Envelope conceitual

```text
CommandRequest<T>
├── command_id
├── payload
└── concurrency fields when required
```

Actor não vem do payload.

Server resolve:

```text
auth.uid()
```

## N5.15.04 — Campos condicionais

Commands versionados/revisionados podem receber:

```text
expected_revision
expected_last_sequence
control_epoch
```

somente quando a semântica exige.

## N5.15.04.02 — Não incluir

Payload não aceita como autoridade:

```text
actor_user_id
actor_role
is_admin
owner_id escolhível
winner calculado pelo client
score oficial
```

## N6.15.04 — Exemplos

### JoinRegistration

```text
command_id
window_id
expected_revision?  // somente se policy exigir
```

Player/Member elegível é resolvido server-side a partir do actor/context.

### AwardPoint

```text
command_id
match_id
side/team intent
expected_last_sequence
control_epoch
optional capture metadata
```

Client não envia `score_after` autoritativo.

# 6. N3.15.05 — Query Contracts

## N4.15.05.01 — Read DTO explícito

Query response não é `DatabaseRow`.

Exemplo:

```text
RegistrationSnapshotDTO
├── window_id
├── status
├── capacity
├── confirmed_count
├── waitlist_count
├── my_status
├── my_waitlist_position?
└── revision
```

Não precisa expor toda `registration_entries` table.

## N5.15.05 — Public vs private shape

O mesmo aggregate pode ter diferentes DTOs:

```text
PublicMatchSnapshotDTO
CommunityMatchSnapshotDTO
ControllerMatchSnapshotDTO
```

conforme autorização/privacidade.

# 7. N3.15.06 — DTOs

## N4.15.06.01 — Separações obrigatórias

```text
Database Row
≠
Domain Model
≠
Command DTO
≠
Query DTO
≠
ViewModel
```

## N5.15.06 — Generated DB types

Types gerados do Supabase/Postgres são infraestrutura.

Podem ajudar adapters, mas não devem ser reexportados como contrato canônico da UI/domínio.

## N5.15.06.02 — Runtime validation

Dados vindos de:

- network;
- Realtime;
- legacy import;
- local persisted storage;
- external providers;

precisam de runtime validation proporcional ao risco.

TypeScript não valida JSON runtime.

# 8. N3.15.07 — Domain Models

Domain model mantém invariantes e semântica, sem conhecer transporte.

Exemplo:

```text
MatchRulesSnapshot
RegistrationWindow state machine
TeamFormation objective
CompetitionStage rules
```

Domain não precisa possuir um objeto gigante com todas as colunas da tabela.

---

# 9. N3.15.08 — Validation

## N4.15.08.01 — Três camadas

```text
CLIENT UX VALIDATION
→ feedback rápido

SERVER/DOMAIN VALIDATION
→ regra autoritativa

DATABASE CONSTRAINT
→ última barreira de integridade
```

## N5.15.08 — Client validation não é security

Ocultar botão ou validar Zod no browser não substitui validação/RLS/RPC server-side.

## N5.15.08.02 — Mass assignment

Command DTO usa allowlist estrita de fields.

Fields desconhecidos sensíveis devem ser rejeitados ou ignorados por contrato explícito; preferimos rejeição em commands críticos para revelar client incompatível/tentativa indevida.

---

# 10. N3.15.09 — Authentication

Authentication prova qual User está realizando a chamada.

Não prova que pode acessar o recurso.

Server deriva actor de token/session válida.

Não confiar em:

```text
payload.user_id
localStorage user
query parameter actor
```

---

# 11. N3.15.10 — Authorization

## N4.15.10.01 — Contextual

Autorização segue:

```text
Actor
↓
Resource real
↓
Context real (Community / Session / Match / Competition)
↓
Membership / Assignment / Capability
↓
Allow / Deny
```

Não:

```text
payload.community_id says A
→ check role in A
→ mutate resource actually from B
```

## N5.15.10 — BOLA protection

Sempre resolver target resource real antes de autorizar contexto.

---

# 12. N3.15.11 — Capabilities

## N4.15.11.01 — Não usar role hierarchy como API

O `AppResult` atual aceita requirements como `owner/admin/master/programmer`; o target usa capabilities semânticas.

Exemplos:

```text
community.members.manage
community.ownership.transfer
session.create
session.manage
match.control
player.evaluate
competition.result.officialize
```

## N5.15.11 — Organizer separation

```text
ADMIN
≠
ORGANIZER
```

Application nunca implementa:

```text
if role >= admin then allow match control
```

---

# 13. N3.15.12 — Transaction Boundaries

Command que possui invariantes multi-row deve executar em boundary transacional única no servidor.

Exemplos:

```text
LeaveRegistration + Promotion + Revision
AwardPoint + MatchEvent + Projection + Receipt
TransferOwnership + old/new Membership changes
FinalizeVoting + winner + TeamDraw
OfficializeResult + current-result uniqueness + outbox
```

UI nunca deve orquestrar essas etapas como várias mutations independentes.

---

# 14. N3.15.13 — Idempotency

## N4.15.13.01 — `command_id`

Toda mutation crítica/retryable recebe identidade lógica estável:

```text
command_id UUID
```

Retry do mesmo intento usa o **mesmo** `command_id`.

## N5.15.13 — Command Receipt

Servidor mantém receipt interno suficiente para retornar o mesmo resultado lógico sem repetir side effects.

Conceitualmente:

```text
app_private.command_receipts
├── command_id
├── actor_id
├── command_type
├── aggregate_id
├── result metadata
├── committed_at
└── retention metadata
```

## N5.15.13.02 — Domain uniqueness continua necessária

Dois double-clicks podem gerar command IDs diferentes.

Então idempotency receipt não substitui:

```text
unique active RegistrationEntry
one current OfficialResult
one active Owner
unique MatchEvent sequence
```

# 15. N3.15.14 — Optimistic Concurrency

## N4.15.14.01 — Revision-based

Usar revision/sequence semântica, não `updated_at`.

Exemplos:

```text
expected_revision
expected_last_sequence
```

## N5.15.14 — Conflict response

Stale client recebe código estável e recuperação apropriada:

```text
REGISTRATION_STALE
MATCH_SEQUENCE_STALE
TEAM_DRAW_STALE_ROSTER
VOTING_ALREADY_CLOSED
```

Não sobrescrever por LWW.

# 16. N3.15.15 — Error Contracts

## N4.15.15.01 — Objetivo

Erro deve comunicar:

```text
machine-readable code
human-safe message
category
retryability
recovery action
request/correlation reference when applicable
field/resource metadata only when safe
```

## N5.15.15 — Modelo conceitual

```text
AppError
├── code
├── category
├── message
├── retry_policy
├── recovery_action
├── request_id?
└── safe_details?
```

### Categories candidatas

```text
VALIDATION
AUTHENTICATION
AUTHORIZATION
DOMAIN_REJECTION
CONFLICT
OFFLINE_UNAVAILABLE
DEPENDENCY_UNAVAILABLE
TECHNICAL
UNEXPECTED
```

## N5.15.15.02 — Domain codes por contexto

Evitar um mega-enum global impossível de manter.

Exemplo namespaces/convenções:

```text
REGISTRATION_CLOSED
REGISTRATION_NOT_ELIGIBLE
MATCH_CONTROL_LOST
MATCH_SEQUENCE_STALE
COMPETITION_RESULT_CONFLICT
```

## N5.15.15.03 — SQLSTATE

SQLSTATE permanece detalhe interno de adapter/DB.

Pode ser traduzido para produto, mas frontend não deve depender diretamente de `23505`, `42501` etc.

# 17. N3.15.16 — Retries

## N4.15.16.01 — Retry policy por operação

### Reads

Podem ter bounded retry automático em falhas transitórias.

### Mutations

Somente retry automático quando idempotency está garantida e erro é compatível.

### Conflicts

Não retry cego.

Normalmente:

```text
refetch / reconcile / user action
```

## N5.15.16 — Backoff

Bounded exponential backoff + jitter para falhas transitórias apropriadas.

Não loops infinitos.

---

# 18. N3.15.17 — Unknown Outcomes

## N4.15.17.01 — Regra

```text
TIMEOUT
≠
COMMAND FAILED
```

Servidor pode ter commitado e resposta ter se perdido.

## N5.15.17 — Recuperação

Retry:

```text
same command_id
```

Server retorna receipt/result autoritativo.

Client não gera novo command ID até saber que se trata de nova intenção.

# 19. N3.15.18 — Read Models

## N4.15.18.01 — Objetivo

Read model otimiza leitura/privacidade sem tornar frontend dependente do write schema.

Exemplos:

```text
CommunityDashboardView
RegistrationSnapshotView
MatchLiveSnapshotView
PlayerCareerView
CompetitionStandingsView
```

## N5.15.18 — Projection vs view

Read model pode ser:

- SQL view segura;
- query sobre tabelas normalizadas;
- materialized/projection table rebuildable;
- RPC query;

conforme necessidade.

---

# 20. N3.15.19 — Pagination

## N4.15.19.01 — Default

Coleções potencialmente grandes usam paginação.

Preferir keyset/cursor quando crescimento/consistência justificarem.

Exemplos:

```text
notifications inbox
player search
match history
competition history
audit/support lists
```

## N5.15.19 — Offset

Offset pode ser suficiente para datasets pequenos/admin simples, mas não deve ser o default automático para feeds grandes.

---

# 21. N3.15.20 — Filtering

Filtros são allowlisted pelo Query Contract.

Não expor genericamente:

```text
column
operator
value
```

para o browser construir SQL arbitrário.

Filtros precisam de indexes/query plans coerentes com N2.18.

# 22. N3.15.21 — Public Views

Public DTO contém somente dados explicitamente classificados como públicos.

Exemplos futuros:

```text
PublicMatchScoreboard
PublicCompetitionBracket
```

Nunca reutilizar DTO interno e “esconder alguns campos no React”.

---

# 23. N3.15.22 — Private Views

Private/contextual read models aplicam:

- authentication;
- RLS/capability;
- minimal disclosure;
- separation de ballots/evaluations/security metadata.

O fato de um User ter acesso a Community não significa acesso a todos os dados privados de todos os contexts.

---

# 24. N3.15.23 — RPC

## N4.15.23.01 — Quando preferir Postgres RPC

RPC é especialmente apropriada para operações:

```text
DB-local
transactional
lock-sensitive
latency-sensitive
requiring atomic multi-row invariants
```

Exemplos:

```text
JoinRegistration
LeaveRegistration
TransferOwnership
AwardPoint
CloseVoting
OfficializeResult
```

## N5.15.23 — RPC não significa business logic inteira em PL/pgSQL

Regra:

```text
DB enforces transactional invariants
Domain/application owns reusable domain computation when appropriate
```

Por exemplo, Team Solver continua TypeScript/Worker; servidor revalida e publica resultado.

## N5.15.23.02 — SECURITY DEFINER

RPC privileged precisa:

- auth check explícito;
- capability/context validation;
- `search_path = ''` target;
- identifiers schema-qualified;
- grants mínimos;
- sem dynamic SQL desnecessário;
- testes BOLA/RLS.

---

# 25. N3.15.24 — Edge Functions

## N4.15.24.01 — Quando usar

Edge/server function é apropriada quando operação precisa de:

- secrets externos;
- HTTP/provider calls;
- processamento de media;
- integração externa;
- logic/process orchestration que não deve rodar no DB;
- server runtime TypeScript específico.

## N5.15.24 — Quando não usar

Não esconder toda SQL query atrás de Edge Function sem motivo.

Isso adicionaria:

```text
network hop
runtime surface
observability burden
cost
failure domain
```

sem necessariamente aumentar segurança.

---

# 26. N3.15.25 — External Integrations

Providers são adapters:

```text
PushProvider
EmailProvider
MediaStorage
FutureWhatsAppProvider
TelemetryExporter
```

Domain/Application não conhecem SDK específico do provider.

External delivery ocorre após domain commit, normalmente via Outbox/Jobs.

---

# 27. N3.15.26 — Background Jobs

Jobs processam trabalho assíncrono que não precisa bloquear command response:

```text
notification delivery
media processing
eventual statistics rebuild
orphan cleanup
reminders
large backfills
```

Não usar background job para operação que precisa decidir imediatamente:

```text
JoinRegistration capacity
AwardPoint sequence
TransferOwnership
```

---

# 28. N3.15.27 — Outbox Integration

## N4.15.27.01 — Mesma transaction

Command crítico pode gravar:

```text
domain state
+
domain_outbox
```

na mesma transaction.

Após commit, worker/publicador processa side effects.

## N5.15.27 — At-least-once

Consumers devem tolerar duplicidade.

Não prometer distributed exactly-once.

---

# 29. N3.15.28 — Contract Versioning

## N4.15.28.01 — Regra

Preferir evolução aditiva.

Breaking contract exige:

```text
compatibility strategy
version marker/new endpoint when needed
migration window
telemetry of old usage
contract removal gate
```

## N5.15.28 — Persisted schemas

MatchEvents/Outbox/Realtime payloads persistidos ou consumidos por versões diferentes exigem `schema_version` quando semântica muda.

Nem todo DTO interno precisa de `V1` no nome.

---

# 30. N3.15.29 — Compatibility

Old browser tabs/client versions são parte da arquitetura.

Durante Expand/Migrate/Contract:

```text
new server understands compatible old client
new client understands expanded server
```

até telemetry provar que contrato legado pode ser removido.

Client incompatível recebe erro explícito seguro, não corrupção silenciosa.

# 31. N3.15.30 — Rate Limiting

## N4.15.30.01 — Operações candidatas

```text
player/community discovery
join requests
account link proposals
media upload intents
votes
match takeover
public match reads
authentication-sensitive endpoints
```

## N5.15.30 — Rate limit não substitui autorização

Ele mitiga abuso/custo, mas target resource continua sendo autorizado normalmente.

## N5.15.30.02 — Dimensions

Dependendo do endpoint:

```text
user
IP
resource
Community
provider quota
```

sem criar cardinalidade/PII indevida na observabilidade.

# 32. N3.15.31 — Observability

Todo command crítico deve permitir correlacionar:

```text
command_type
command_id
request_id
actor_id/internal subject
resource/context ids
result code
latency
retry/attempt
revision/sequence when relevant
```

Logs não carregam payload sensível completo.

## N5.15.31 — `request_id ≠ command_id`

```text
command_id
= identidade lógica da mutation

request_id
= tentativa HTTP/RPC concreta
```

Um command pode possuir vários request IDs por retry.

`correlationId` criado apenas no browser não substitui request ID emitido/propagado pelo server.

---

# 33. N3.15.32 — Security

## N4.15.32.01 — Browser é não confiável

Nunca confiar em:

```text
role
actor id
score
winner
overall
community context supplied without resolving resource
provider URL
raw DTO extra fields
```

## N5.15.32 — RLS + Commands

RLS permanece defense-in-depth.

Para critical writes:

- direct table insert/update/delete pelo browser deve ser negado quando command RPC controla invariantes;
- projection tables são read-only para client;
- server command revalida auth/capability.

# 35. N3.15.34 — Migration

## N4.15.34.01 — Strangler por vertical slice

Não converter todos os cloud services ao mesmo tempo.

Sequência:

```text
1. Introduce semantic Application port
2. Implement new command/query adapter
3. Route one bounded-context operation
4. Observe/test
5. Remove corresponding generic CRUD path
6. Continue operation by operation
```

## N5.15.34 — Registration como reference slice

Registration é candidato ideal para provar:

```text
UI
↓
Application
↓
semantic CommandPort
↓
RPC transaction
↓
AppResult
↓
Realtime secondary notification
```

## N5.15.34.02 — Generic cloud services shrink monotonically

Novos contexts não entram em:

```text
fetchAll/upsert/softDelete generic sync
```

Legacy services perdem responsabilidades até serem removidos.

# 37. Command Response Pattern

Exemplo conceitual:

```text
JoinRegistrationResponse
├── command_id
├── entry_id
├── status: CONFIRMED | WAITLISTED
├── waitlist_position?
├── window_revision
└── snapshot_summary
```

`WAITLISTED` é sucesso de negócio, não exception.

Outro:

```text
AwardPointResponse
```

# 39. RPC vs Edge Decision Matrix

| Necessidade | RPC Postgres | Edge/Server Function |
|---|---:|---:|
| row locks / atomic multi-row | preferido | somente se chama RPC internamente |
| capacity/FIFO | preferido | não necessário |
| Match sequence | preferido | não necessário para core commit |
| external provider secret | não | preferido |
| media processing | não | preferido |
| solver pesado | não no DB | TS worker/server depending flow |
| simple secure read | SELECT/View/RPC | geralmente não |
| webhook receiver | não | preferido |

# 41. N10 — Adversarial / Acceptance Matrix

## API-N10-001 — Role injection

Client sends:

```text
{ role: "OWNER", isAdmin: true }
```

inside unrelated command. Server ignores/rejects unauthorized fields; privilege does not change.

## API-N10-002 — Actor spoofing

User A sends `actor_user_id = B`. Server acts as A from auth context.

## API-N10-003 — BOLA context spoof

User authorized in Community A sends resource from B plus `community_id=A`. Server resolves resource B and denies.

## API-N10-004 — Join response loss

Join commits, response disappears, same `command_id` retried. One entry exists and same logical outcome returns.

## API-N10-005 — Different command IDs double click

Two Join attempts with different IDs still cannot create two active entries because domain unique constraint protects.

## API-N10-006 — AwardPoint duplicate

Same command ID sent concurrently: one event logical, one receipt result.

## API-N10-007 — AwardPoint different IDs same expected sequence

Exactly one transaction advances sequence; other returns stale conflict.

## API-N10-008 — updated_at misuse

Client with newer wall-clock timestamp cannot overwrite authoritative Match/Registration state.

## API-N10-009 — SQLSTATE leakage

DB returns `23505`; Application exposes stable product code, not asks UI to parse SQLSTATE/message.

## API-N10-010 — Waitlist normal outcome

Capacity full → `WAITLISTED` success response, not technical exception.

## API-N10-011 — Permission denied retry

Authorization denial does not enter exponential automatic retry loop.

## API-N10-012 — Dependency timeout read

Safe Query retries bounded with jitter and returns dependency/unavailable contract if exhausted.

## API-N10-013 — Mutation timeout unknown

Mutation timeout does not create fresh command ID automatically.

## API-N10-014 — Client-calculated score

Payload includes `score_after=99`. Server ignores/rejects it; score derives from Match rules/events.

## API-N10-015 — Client-calculated winner

Officialize payload cannot force arbitrary winner inconsistent with authorized result flow.

## API-N10-016 — Mass assignment status

Client includes `status=FINISHED` in generic DTO. No generic patch endpoint allows lifecycle bypass.

## API-N10-017 — Direct projection write

Authenticated client attempts UPDATE standings/career/profile projection. DB denies.

## API-N10-018 — Direct Registration insert

Authenticated client attempts INSERT directly into `registration_entries`; critical write grants/policies deny if command RPC is required.

## API-N10-019 — Public DTO privacy

Public Match query does not contain actor/device/control metadata.

## API-N10-020 — Vote DTO privacy

Voting OPEN query under AFTER_CLOSE does not expose ballots/tally.

## API-N10-021 — Unknown response field

Older client tolerates additive safe field according to runtime schema compatibility policy.

## API-N10-022 — Removed required field

Breaking server response does not silently produce `undefined`; contract validation fails safely and triggers compatibility handling.

## API-N10-023 — Old client mutation

Client too old for critical contract receives explicit unsupported-client/domain error rather than malformed write.

## API-N10-024 — Filter injection

Client cannot send arbitrary SQL operator/column through generic filter endpoint.

## API-N10-025 — Pagination race

Keyset-paginated history remains stable enough under inserts and does not rely on offset for hot feed correctness where policy requires cursor.

## API-N10-026 — Request ID correlation

Two retries share one command ID but have distinct request IDs visible in telemetry.

## API-N10-027 — Browser-generated correlation

Random browser UUID alone is never treated as proof that server logged the same request.

## API-N10-028 — Edge provider failure

Push provider unavailable after Registration commit: domain command remains success; outbox retries provider work.

## API-N10-029 — Edge function extra hop

DB-local transaction does not require unnecessary Edge wrapper when RPC provides secure atomic behavior.

## API-N10-030 — Worker duplicate

Outbox worker executes same item twice; downstream idempotency prevents duplicate NotificationIntent/effect.

## API-N10-031 — Poison job

Permanent provider payload error becomes failed/dead-lettered without blocking unrelated jobs.

## API-N10-032 — Rate limit bypass by resource

User rotates resource IDs to exceed expensive endpoint; rate policy can include actor/IP dimensions as appropriate.

## API-N10-033 — Rate limit is not auth

User under limit but unauthorized still denied.

## API-N10-034 — AAL2

Sensitive command requires step-up; Application returns explicit recovery action rather than role label confusion.

## API-N10-035 — Admin not Organizer

Admin invokes `AwardPoint` without match control capability/assignment. Denied.

## API-N10-036 — Organizer not Admin

Organizer invokes `TransferCommunityOwnership`. Denied.

## API-N10-037 — Transaction partial failure

Artificial error between LeaveRegistration withdrawal and promotion causes full rollback.

## API-N10-038 — Outbox transaction failure

Domain transaction fails: no orphan domain outbox item representing event that never committed.

## API-N10-039 — Outbox processor failure

Domain commits + outbox commits; worker down does not lose source fact.

## API-N10-040 — Runtime DTO tampering

Realtime/network payload with invalid enum/schema version is rejected/resynced rather than trusted because TypeScript compiled.

## API-N10-041 — Legacy cloud upsert

Aggregate already cut over to new command path cannot still be mutated through generic legacy upsert.

## API-N10-042 — Generic soft delete

Legacy `softDelete()` cannot bypass semantic Archive/Leave/Cancel lifecycle for cutover aggregates.

## API-N10-043 — Command returns stale local state

UI uses authoritative command response rather than assuming optimistic local object is final.

## API-N10-044 — Realtime missing

Command success remains correct even if client receives no Broadcast; subsequent Query recovers state.

## API-N10-045 — Client offline generic queue

JoinRegistration offline is not stored in generic outbox as accepted domain fact.

## API-N10-046 — Match offline special path

Approved Match outbox includes expected sequence/control epoch; generic remote command queue is not used.

## API-N10-047 — SECURITY DEFINER search path

Static/integration test rejects privileged RPC with unsafe mutable search path.

## API-N10-048 — Service role browser leak

No client command adapter requires service-role key.

## API-N10-049 — N+1 read model

Dashboard Query contract is implemented as deliberate aggregate/read model rather than UI issuing one query per participant.

## API-N10-050 — Contract retirement

Legacy endpoint has nonzero telemetry usage: removal/contract gate remains blocked.

# 42. Decisions / Hypotheses / Open Questions

## DECIDED

- Application API represents semantic intent, not generic CRUD.
- UI → Application → Port → Infrastructure is the target boundary.
- DTO, Domain Model, DB Row and ViewModel remain distinct.
- Actor identity is server-derived.
- Authorization is capability/context based.
- Critical commands use idempotency through `command_id`.
- `command_id ≠ request_id`.
- Optimistic concurrency uses revision/sequence, not `updated_at`.
- Command success means authoritative transaction committed.
- SQLSTATE is implementation detail, not public contract.
- RPC is preferred for DB-local transactional/lock-sensitive operations.
- Edge Functions are used for external secrets/providers/processes, not as universal SQL proxy.
- Background jobs do not decide synchronous capacity/order invariants.
- Outbox carries post-commit side effects.
- Public/internal read DTOs are separate.
- New target modules do not enter generic sync/cloud upsert architecture.

## STRONG HYPOTHESIS

- Stable error codes will use bounded-context prefixes/conventions rather than one giant TypeScript enum.
- `command_receipts` will live in `app_private` with finite retention.
- Keyset pagination becomes default for large user-facing feeds.
- Runtime schemas will be centralized per contract boundary rather than manually checked field-by-field.

## OPEN

- Exact runtime validation library/convention after migration.
- Exact retention of command receipts per command class.
- Which simple reads remain direct PostgREST SELECT versus Query RPC/view.
- Exact external rate-limit provider/implementation if database-level mechanisms are insufficient.
- Whether future public API requires explicit API version namespace beyond internal compatibility strategy.

# 45. Definition of API/Application Compliance

Uma implementação está alinhada a N2.15 quando:

1. critical mutations são Commands semânticos;
2. UI não administra tabelas diretamente;
3. Application não depende de Supabase implementation details;
4. actor é server-derived;
5. resource/context são resolvidos antes de authorization;
6. capabilities substituem hierarchy implícita;
7. critical commands são idempotentes por `command_id`;
8. retries preservam command identity;
9. revision/sequence governam conflicts;
10. error contract possui código estável e recovery semantics;
11. query DTOs são purpose-specific;
12. public/private shapes são separados;
13. RPC/Edge são escolhidos conforme transaction/provider needs;
14. external side effects ficam pós-commit/outbox;
15. generic cloud services diminuem durante Strangler em vez de receber features novas;
16. integration tests provam RLS/RPC/transactions em banco real.
