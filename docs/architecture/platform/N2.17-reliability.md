## 0. Regra de leitura

A regra central é:

```text
AVAILABILITY
≠
DURABILITY
≠
CORRECTNESS
```

Um sistema pode estar:

```text
online e errado
```

ou:

```text
temporariamente indisponível e correto
```

Para estado compartilhado crítico, o Volley prefere:

```text
CORRECTNESS
>
UNRESTRICTED AVAILABILITY
```

quando aceitar uma escrita durante degradação puder criar uma verdade impossível de reconciliar com segurança.

Exemplos:

```text
Registration sem autoridade server
→ não aceita Join offline

Voting sem autoridade server
→ não aceita CastVote offline

Community ownership sem autoridade server
→ não altera offline

Match com protocolo explícito de lease/epoch/sequence
→ pode aceitar comandos offline somente dentro da policy condicionada
```

Reliability não será obtida com um único mecanismo universal de retry/sync. Cada bounded context define o que pode ser reconstruído, repetido, conciliado ou bloqueado.

# 1. Current State — evidência do repositório

## 1.1 Já existe classificação de retry

`src/logic/syncBackoff.ts` diferencia falhas de rede de erros estruturais e não tenta automaticamente `validation`, `authorization` ou `conflict`.

O backoff atual usa uma sequência crescente de intervalos e classifica erros desconhecidos como `technical`, evitando assumir que todo erro é offline/transiente.

A intenção é correta e será preservada, mas o target aplica retry por **Command/Job**, não por payload global de sync.

## 1.2 Já existe ledger persistente de falhas

`src/logic/syncIssueLedger.ts` mantém um ledger local com:

```text
operation
context
message
status
count
first_seen
last_seen
kind
next_attempt_at
```

Isso já cria boa observabilidade/recovery UX no cliente.

No target:

- o conceito é preservado para operações locais e recovery UX;
- falhas server-side críticas também possuem observabilidade central;
- o ledger local não é autoridade sobre sucesso/commit server-side;
- o ledger global de sync desaparece junto com o sync universal.

## 1.3 Recovery de Match legado usa conflito de versões

`sessionConflictResolution.ts` permite marcar conflitos e escolher:

```text
KEEP MINE
KEEP THEIRS
```

preservando eventos locais com tombstones quando necessário.

Isso foi útil para o modelo atual, mas não é o protocolo canônico para Match V2.

Target:

```text
control_epoch
+
MatchEvent.sequence
+
command_id
+
expected_last_sequence
+
reconciliation
```

Nenhuma versão completa de placar vence por timestamp ou escolha genérica.

## 1.4 Sync atual possui reentrancy/retry/recovery locais

`useCloudSync` já contém:

- inflight guard;
- TTL de proteção após crash/remount;
- partial failure reporting;
- reconnect-triggered retry;
- cache-owner isolation;
- conflict detection.

Essas intenções são úteis, mas hoje estão acopladas a um sync de dataset heterogêneo. C2.12 e este capítulo substituem isso por reliability específica por operação.

# 2. N3.17.01 — Reliability Model

## N4.17.01 — Três propriedades independentes

### Correctness

O estado respeita invariantes e história autoritativa.

### Durability

Um fato confirmado não desaparece após crash/falha/restart dentro das garantias definidas.

### Availability

A operação pode ser executada ou lida quando solicitada.

Não trocar uma propriedade pela outra sem decisão explícita.

## N5.17.01 — Success contract

Para Commands server-authoritative:

```text
SUCCESS
=
authoritative transaction committed
```

Não significa:

```text
request sent
UI updated optimistically
Realtime received
worker scheduled
provider accepted
```

# 3. N3.17.02 — Criticality Classes

Todo dado/processo é classificado.

## C0 — Irreplaceable Source Facts

Exemplos:

```text
MatchEvent committed
OfficialCompetitionResult revision
PlayerEvaluation revision
Registration authoritative transition where historical audit is required
ownership transfer audit
privacy/security incident record
```

Perda é corrupção de negócio/história.

## C1 — Immutable Authoritative Snapshots

Exemplos:

```text
RosterRevision
MatchRoster
RulesSnapshot
PlayerBalanceSnapshot
TeamDraw confirmed
CompetitionRosterRevision
```

Podem ser derivados de fatos em alguns casos, mas normalmente são preservados como evidência da decisão histórica.

## C2 — Derived Projections

Exemplos:

```text
MatchProjection
StandingsProjection
CommunitySkillProfile
GlobalSkillProfile
Career totals
Notification Inbox read-model counters
```

Devem ser rebuildable ou possuir recovery documentado.

## C3 — Ephemeral / Cache

Exemplos:

```text
Realtime Presence
browser cache
computed UI filters
transient loading state
```

Perda é aceitável.

## N5.17.02 — Local irreplaceable exception

Quick Session ainda não publicada e Match offline outbox são localmente irreplaceable enquanto não reconhecidos pelo servidor.

Não podem ser tratados como C3 só porque estão em IndexedDB.

# 5. N3.17.04 — Durability

## N4.17.04 — Commit before acknowledgement

Server-authoritative facts são reconhecidos somente após commit.

## N4.17.04.02 — Local offline durability

Para Quick e Match offline:

```text
persist to IndexedDB transaction
↓
commit local transaction
↓
then acknowledge in UI as durable-local
```

Se persistência falha, a UI não deve fingir que o fato está seguro.

## N5.17.04 — Durable does not mean cloud-confirmed

UI pode distinguir:

```text
LOCAL_DURABLE
SERVER_CONFIRMED
RECONCILIATION_REQUIRED
```

# 6. N3.17.05 — Availability

Availability é definida por capability, não pelo app inteiro.

Exemplo de degradação:

| Dependency | Capability impact |
|---|---|
| Realtime down | writes/reads via HTTP continuam; atualização automática degrada |
| Notification provider down | domain commands continuam; delivery atrasa |
| Storage down | media upload indisponível; Registration/Match continuam |
| Postgres down | shared authoritative writes bloqueados |
| Network down | Quick continua; eligible Match controller pode continuar condicionado; Registration/Voting bloqueiam |

# 7. N3.17.06 — Correctness

Correctness inclui:

```text
invariants
transaction boundaries
authorization
ordering
idempotency
revision/sequence checks
immutable-history preservation
projection/source consistency
```

Para shared critical state, aceitar uma escrita que não pode ser validada é pior que retornar temporariamente indisponível.

# 8. N3.17.07 — RPO

Não inventar RPO numérico sem requisito operacional.

A arquitetura define classes:

```text
C0/C1
→ target conceptual RPO tende a zero após acknowledged commit

C2
→ pode perder projection se rebuildable e source facts preservados

C3
→ perda aceitável

local Quick/Match unacknowledged
→ depende da durabilidade IndexedDB/device; precisa UX de backup/recovery conforme maturidade
```

RPO formal e valores numéricos ficam `OPEN` até existir requisito de negócio/infra e evidência de backup capability.

# 9. N3.17.08 — RTO

Não inventar RTO global.

RTO precisa ser definido por capability/criticality:

```text
shared registration write
live match recovery
competition official result
media processing
notification delivery
analytics/projections
```

`OPEN`: valores numéricos de RTO após ambiente de produção e objetivos de negócio.

# 11. N3.17.10 — Atomicity

Operações críticas têm transação única para tudo que precisa ser indivisível.

## Registration

```text
withdraw
+ promote next eligible
+ revision++
+ command_receipt
+ domain_outbox
= one transaction
```

## Match

```text
validate lease/epoch/sequence
+ append MatchEvent
+ update MatchProjection
+ command_receipt
+ domain_outbox marker
= one transaction
```

## Voting

```text
close
+ freeze eligibility/result input
+ tally/finalize where command semantics require
+ revision
+ receipt/outbox
= transactional boundary defined by command
```

## Competition

```text
official result revision
+ invalidate/recompute dependency state markers
+ audit/outbox
= atomic authoritative transition
```

External network calls never participate in the DB transaction.

# 12. N3.17.11 — Idempotency

Critical mutation commands accept `command_id`.

Canonical behavior:

```text
same actor/context + same command_id
→ same logical effect
→ return prior authoritative result or compatible receipt
```

Idempotency does not replace domain uniqueness.

Two separate double-clicks with different IDs still cannot create impossible duplicate membership/vote/registration due to constraints/invariants.

# 13. N3.17.12 — Retry

Retry classes:

## Safe automatic retry

```text
idempotent GET/query
idempotent command with known retryable transport failure
worker item with idempotent handler
provider delivery attempt according to provider policy
```

## Retry only after refetch/revalidation

```text
optimistic concurrency conflict
stale revision
Match stale sequence
expired lease
```

## No automatic retry

```text
validation error
authorization denial
business rejection
hard constraint violation
manual reconciliation required
```

# 14. N3.17.13 — Backoff

Baseline:

```text
bounded exponential backoff
+
jitter
+
retry class awareness
+
max age / operational visibility
```

O backoff atual do sync serve como referência de intenção, mas o target não reutiliza necessariamente seus intervalos.

Evitar thundering herd após recuperação de Postgres/provider.

# 15. N3.17.14 — Unknown Outcome

Caso crítico:

```text
client sends Command C
server commits C
network drops before response
```

O client não pode concluir automaticamente:

```text
FAILED
```

Estado é:

```text
UNKNOWN_OUTCOME
```

Recovery:

```text
retry SAME command_id
or
query command receipt/state
```

Nunca gerar novo `command_id` só porque a resposta não chegou.

---

# 16. N3.17.15 — Deduplication

Dedup ocorre em camadas:

```text
command receipt
DB unique/partial unique constraints
event sequence uniqueness
provider idempotency key where supported
worker job semantic key where needed
```

Não prometer “exactly once delivery”.

Target realista:

```text
at-least-once processing
+
idempotent effects
```

---

# 17. N3.17.16 — Reconciliation

Reconciliation é explícita quando duas cadeias de fatos não podem ser automaticamente mescladas.

Especialmente Match:

```text
local outbox epoch=7
server epoch=8
→ RECONCILIATION_REQUIRED
```

Não usar:

```text
latest updated_at wins
keep complete local state
keep complete cloud state
```

como protocolo canônico.

Reconciliation gera resultado auditável e nunca apaga silenciosamente fatos necessários para investigação.

# 18. N3.17.17 — Outbox Reliability

`domain_outbox` pertence à mesma transaction do fato que originou o efeito externo.

Estado conceitual:

```text
PENDING
CLAIMED
DELIVERED
FAILED_RETRYABLE
FAILED_TERMINAL
```

Requisitos:

- lease/claim expirável;
- processamento idempotente;
- retry/backoff;
- age observável;
- nenhuma dependência externa bloqueia domain commit;
- cleanup/retention depois de terminal/delivered conforme policy.

---

# 19. N3.17.18 — Worker Reliability

Workers processam pelo menos uma vez.

Handler deve tolerar:

```text
duplicate invocation
crash after external side effect
crash before marking success
lease expiry
concurrent workers
provider timeout
```

Um worker não pode depender de memória do processo para saber se algo foi processado.

---

# 20. N3.17.19 — Poison Messages

Item é `poison` quando falha repetidamente por causa não transitória ou payload/invariant incompatível.

Policy:

```text
retry bounded by class
↓
quarantine / terminal state
↓
operator visibility
↓
manual/replay action after correction
```

Um poison item não bloqueia a fila inteira.

---

# 21. N3.17.20 — Dead Letter Handling

Não introduzir broker/DLQ externo por padrão.

Baseline pode ser uma tabela/estado interno de itens terminalmente falhos com:

```text
item_id
type
source_reference
failure_class
attempt_count
first_failure_at
last_failure_at
last_error_summary
payload_version
operator_status
```

Sem copiar secrets/PII desnecessária para o dead-letter payload.

# 22. N3.17.21 — Projection Recovery

Toda projection importante documenta:

```text
source facts
source revision/sequence
calculation version
rebuild procedure
integrity comparison
cutover strategy
```

Pattern:

```text
build shadow projection
↓
validate against invariants/sample/all data as appropriate
↓
atomically switch/read version
```

Não destruir projection atual antes de provar que a nova rebuild está consistente.

# 23. N3.17.22 — Match Recovery

Match é o fluxo mais crítico de continuidade operacional.

## Server-connected crash

Controller reabre:

```text
fetch Match snapshot/projection
fetch current lease/epoch
fetch last_sequence
re-subscribe realtime
continue if authorized
```

## Offline crash

IndexedDB deve preservar:

```text
Match identity
lease/epoch evidence
last server checkpoint
ordered pending commands
local projected state
```

Após restart, não auto-replay antes de revalidar epoch/sequence.

## Projection corruption

```text
replay effective MatchEvents
→ rebuild MatchProjection
→ compare expected checksum/state
```

## Takeover divergence

Epoch mismatch → reconciliation, never auto-merge.

---

# 24. N3.17.23 — Registration Recovery

Registration source truth é o estado transacional server-side.

Recovery cases:

```text
lost realtime
→ refetch snapshot/revision

response lost after Join
→ retry same command_id / query state

worker notification failed after promotion
→ registration remains correct; notification retries separately

projection/count inconsistency
→ recompute counts from authoritative active entries under repair procedure
```

Nunca reconstruir FIFO por `created_at`/`updated_at` se a sequence autoritativa existe.

---

# 25. N3.17.24 — Voting Recovery

Source truth:

```text
VotingRound
eligible voter freeze/policy
Vote current facts/revisions
CandidateSet
```

Recovery:

- duplicate CastVote → idempotent/unique effective vote;
- lost close/finalize response → same command ID;
- stale CandidateSet/roster → invalidate round, never silently rebind ballots;
- projection/result cache rebuild from votes under visibility/privacy policy.

Ballot privacy survives diagnostic/recovery paths.

---

# 26. N3.17.25 — Competition Recovery

Official result history is append/revision-oriented.

Recovery principles:

```text
technical MatchResult
≠ OfficialCompetitionResult
```

If standings/bracket projection corrupts:

```text
OfficialResults + Penalties + Ruleset
→ rebuild
```

Retroactive correction performs dependency impact analysis.

No automatic rewriting of downstream already-executed matches.

---

# 27. N3.17.26 — Media Recovery

Pipeline resilience:

```text
incoming uploaded
↓
processing job may retry
↓
SANITIZED READY only after successful processing
↓
attachment switch only after new asset ready
```

Failures do not replace the current good asset.

Orphan sweeper is idempotent and grace-period based.

Missing Storage object referenced by DB is integrity failure, not silently treated as normal deletion.

---

# 28. N3.17.27 — Notification Recovery

Domain truth commits before delivery.

Recovery:

```text
outbox retry
intent idempotency
provider attempt history
scheduled reminder revalidation
```

Provider timeout can be unknown outcome; use provider idempotency/status lookup where supported before blind duplicate send.

Notification failure never rolls back Registration/Match/Competition state.

---

# 29. N3.17.28 — Realtime Recovery

Realtime can be lost, duplicated or reordered.

Recovery is always:

```text
snapshot + revision/sequence
```

not replay of assumed complete Realtime history.

Gap/reconnect:

```text
detect
→ authoritative refetch
→ continue
```

Realtime outage is a latency degradation, not a correctness incident by itself.

---

# 30. N3.17.29 — Local Data Recovery

IndexedDB data classes:

```text
RECREATABLE CACHE
LOCAL DRAFT
LOCAL IRREPLACEABLE QUICK
LOCAL IRREPLACEABLE MATCH OUTBOX
```

Recovery/migration policy differs by class.

Do not respond to IndexedDB migration error with unconditional DB deletion.

Account switching preserves sealed local critical items under original owner scope.

Future recovery/export tooling for irreplaceable local data is desirable before broad offline production use.

# 32. N3.17.31 — Graceful Degradation

Examples:

```text
Realtime down
→ polling/refetch on focus/manual refresh; commands still work

Notification provider down
→ Inbox/domain truth works; external delivery delayed

Media processor down
→ current avatar remains; new upload pending

Stats projection lagging
→ show stale/provisional marker; Match facts remain correct

Team solver worker fails
→ retry local computation/fallback deterministic implementation if available; never use overall as fallback

Network down
→ Quick works; shared admin operations blocked; approved Match offline protocol may work
```

Never degrade by weakening authorization or invariants.

# 33. N3.17.32 — Backup

# 34. N3.17.33 — Restore

Restore drill checks:


Restore into isolated environment first where feasible.

# 36. N3.17.35 — Data Integrity Verification

Scheduled/on-demand integrity checks include examples:

## Community

- exactly one active owner under target invariant;
- no invalid responsibility/capability assignments.

## Registration

- confirmed count ≤ capacity unless explicitly grandfathered migration state;
- active FIFO sequence unique;
- no Player simultaneously confirmed and waitlisted in same window.

## Team Formation

- confirmed draw references exact roster revision;
- hard constraints satisfied;
- balance snapshots contain no optimizer dependence on Overall.

## Match

- sequence contiguous/effective per model;
- replay(events) == MatchProjection;
- Result agrees with finished projection/rules;
- no current commands from stale control epoch accepted.

## Competition

- official result revision graph valid;
- standings rebuild equals stored projection;
- downstream fixture slots resolve to valid official sources.

## Stats

- contribution source sequence/version consistent;
- aggregate totals equal contribution rollup.

## Media

- READY object exists;
- attachment references valid READY asset.

Automatic repair is allowed only when derivation is deterministic and source facts are intact. Otherwise open incident/manual repair.

# 37. N3.17.36 — Deployment Safety

Preferred pattern:

```text
EXPAND
→ deploy compatible application
→ migrate/backfill
→ verify
→ switch traffic/reads/writes
→ CONTRACT later
```

Rules:

- migrations forward-compatible where practical;
- no dropping columns still required by current clients;
- no rewriting active Match cohorts mid-game;
- canary/staged rollout when exposure justifies;
- feature flags for risky capability transitions;
- rollback application does not assume irreversible schema rollback exists.

Database rollback is often roll-forward repair, not `DOWN migration` magic.

# 41. N3.17.40 — Migration

Reliability migration follows the same strangler principle.

## Phase R0 — Inventory current failure/retry paths

Map:

```text
sync retries
local ledgers
session conflict handling
cloud service retries
provider calls
background-like operations
local persistence
```

## Phase R1 — Command idempotency foundation

Introduce:

```text
command_id
command_receipts
stable error/recovery contracts
unknown outcome handling
```

for critical shared commands.

## Phase R2 — Transactional outbox

Move external/async side effects behind `domain_outbox` for new contexts.

## Phase R3 — Context-specific recovery

Registration/Voting/Match/Competition/Media/Notifications adopt their canonical recovery protocols.

## Phase R4 — Projection rebuild tooling

Add rebuild/integrity procedures before declaring projections rebuildable in production.

## Phase R5 — Local durability migration

Quick/Match critical local state moves from generic localStorage state toward structured IndexedDB transactions per C2.12.

## Phase R6 — Retire global sync conflict model

Remove generic `keep mine/keep theirs`, generic sync retry and generic tombstone reconciliation once no authoritative context depends on them.

## Phase R7 — Operational maturity

Backup verification, restore drills, runbooks, dependency dashboards and failure tests become release/ops practice according to deployment maturity.

# 42. Reliability decision matrix

| Context / operation | When dependency unavailable | Retry | Recovery authority |
|---|---|---|---|
| Community governance write | fail closed | same id only if unknown/transient | server state |
| Registration Join/Leave | fail closed offline | same command ID | RegistrationWindow revision |
| Voting CastVote | fail closed offline | same command ID | VotingRound revision |
| Team solver local compute | can continue locally | local recompute | immutable balance snapshots |
| Confirm TeamDraw | fail closed if server unavailable | same command ID | roster/draw revision |
| Match connected command | fail/conditional transition | same command ID | Match sequence + epoch |
| Match approved offline | durable local outbox | ordered replay only after validation | server sequence + epoch + reconciliation |
| Quick Session pre-publish | continue local | local persistence retry | device-local authority |
| Quick publish | unknown state can freeze handoff | same command ID | server receipt/state |
| Competition officialization | fail closed | same command ID | official-result revision |
| Stats projection | may lag | worker retry/rebuild | match/official source facts |
| Media processing | pending | worker retry | sanitized asset state |
| Notification delivery | domain unaffected | provider-aware retry | NotificationIntent/Attempt |
| Realtime | degrade | reconnect | authoritative snapshot |

# 43. Explicit anti-patterns

Do not introduce:

```text
retry everything forever
catch error and mark success
updated_at-based conflict resolution for critical state
global distributed lock
exactly-once delivery claims
provider call inside core DB transaction
delete/recreate projection without validated replacement
delete IndexedDB automatically on migration failure
restore backup directly into production without integrity/privacy checks
silent automatic repair of ambiguous source facts
```

```text
REL-INV-005  Optimistic UI never defines durability.
REL-INV-006  C0 source facts are not silently reconstructable from projections.

REL-INV-008  C3 cache loss must not destroy authoritative facts.
REL-INV-009  Local unpublished Quick facts are treated as locally irreplaceable.
REL-INV-010  Pending offline Match commands are treated as locally irreplaceable until acknowledged/discarded explicitly.
REL-INV-011  Critical local offline actions are acknowledged only after durable local commit.
REL-INV-012  Unknown outcome is distinct from confirmed failure.
REL-INV-013  Unknown mutation outcome retries with the same command_id.
REL-INV-014  Critical mutation commands are idempotent by command_id.
REL-INV-015  Idempotency does not replace domain uniqueness constraints.
REL-INV-016  Validation errors are not automatically retried.
REL-INV-017  Authorization denials are not automatically retried.
REL-INV-018  Business conflicts require refetch/reconciliation according to context, not blind retry.
REL-INV-019  Automatic retry uses bounded backoff and jitter appropriate to failure class.
REL-INV-020  Retry storms after dependency recovery are mitigated.
REL-INV-021  External provider calls never participate in core authoritative DB transactions.
REL-INV-022  Domain outbox records are committed atomically with the originating domain transition.
REL-INV-023  Worker processing is assumed at-least-once.
REL-INV-024  Worker effects are idempotent or deduplicated.
REL-INV-025  Worker crash after effect but before ack cannot create unbounded duplicate domain effects.
REL-INV-026  Poison work does not block unrelated work indefinitely.
REL-INV-027  Terminal worker failures remain visible for operator action.
REL-INV-028  Match event ordering is resolved by authoritative sequence, never updated_at.
REL-INV-029  Match takeover invalidates stale control epochs.
REL-INV-030  Epoch divergence requires reconciliation, never generic keep-mine/keep-theirs merge.
REL-INV-031  Registration FIFO recovery uses authoritative queue sequence, never timestamps.
REL-INV-032  Registration promotion notification failure cannot roll back promotion.
REL-INV-033  Voting stale CandidateSet invalidates/requires policy action; ballots are not silently rebound.
REL-INV-034  Competition standings are rebuildable from official results, penalties and ruleset inputs.
REL-INV-035  Retroactive competition correction does not silently rewrite already-executed downstream matches.
REL-INV-036  Media replacement occurs only after the new asset is READY.
REL-INV-037  Media processing failure preserves the previously valid attachment.
REL-INV-038  Notification provider failure never rolls back the originating domain fact.
REL-INV-039  Realtime outage may delay convergence but cannot corrupt authoritative state.
REL-INV-040  Realtime recovery uses authoritative snapshot plus revision/sequence.
REL-INV-041  IndexedDB migration failure never automatically deletes irreplaceable local data.
REL-INV-042  Pending local commands never replay under a different authenticated user.
REL-INV-043  Dependency degradation does not weaken authorization or invariants.
REL-INV-044  Backup existence is not considered proven recovery until restore is tested.
REL-INV-045  Restore procedures include privacy deletion/anonymization replay where required.
REL-INV-046  Restore cannot blindly resend stale outbox/provider side effects.
REL-INV-047  Integrity checks distinguish deterministic projection repair from ambiguous source-fact repair.
REL-INV-048  Automatic repair is allowed only where source truth and repair algorithm are unambiguous.
REL-INV-049  Deployments use expand/verify/contract rather than destructive synchronized cutovers where feasible.
REL-INV-050  Active Match cohorts are not migrated destructively mid-execution.
REL-INV-051  Runbooks define safe and unsafe recovery actions for critical failure modes.

REL-INV-054  RPO/RTO numerical claims require explicit business requirements and tested infrastructure evidence.
```

# 45. N10 — Failure / Recovery Acceptance Matrix

## N10.17.01 — Command outcome

1. Server commits JoinRegistration then response drops → retry same command ID returns the committed logical outcome, no duplicate queue entry.
2. Server rejects JoinRegistration validation → client does not retry forever.
3. Authorization denied → reconnect does not automatically retry the forbidden command.
4. Client times out before knowing whether AwardPoint committed → state shown as unknown/pending until same-ID recovery.
5. Double-click generates two different command IDs → DB/domain invariants still prevent impossible duplicate effective membership/vote/registration.

## N10.17.02 — Atomicity

6. LeaveRegistration crashes after withdrawal logic but before promotion commit → transaction rolls back both.
7. Promotion succeeds but notification provider is down → promoted state remains correct and delivery retries separately.
8. AwardPoint event insert fails after projection computation but before commit → neither event nor projection commits.
9. OfficializeCompetitionResult fails mid-transition → no half-officialized result/standings state.

## N10.17.03 — Retry/backoff

10. 1,000 clients reconnect together → jitter prevents synchronized hot-loop retries.
11. Provider returns 429 → worker respects retry policy rather than tight loop.
12. Provider returns permanent 4xx invalid recipient → terminal/quarantine rather than infinite retry.
13. DB returns retryable deadlock → bounded transaction retry with same semantic command.
14. Stale expected revision → refetch/retry policy, not blind backoff loop.

## N10.17.04 — Worker/outbox

15. Worker claims outbox item then crashes before delivery → lease expires; another worker may process.
16. Worker calls provider successfully then crashes before local ack → retry uses provider/idempotency semantics to avoid uncontrolled duplicate.
17. One poison item repeatedly fails → unrelated notifications/media jobs continue.
18. Two workers claim concurrently → lease/claim prevents simultaneous ownership or handlers remain idempotent.
19. Outbox grows for hours → alert/metric exposes age and backlog.

## N10.17.05 — Match

20. Controller browser crashes online → restart fetches projection/lease/sequence and resumes correctly if authorized.
21. Browser crashes offline after three locally durable commands → commands survive restart.
22. IndexedDB write fails while offline Match → UI fails closed instead of showing an unpersisted point as safe.
23. Another controller takes over while first is offline → old epoch replay blocked.
24. Local epoch differs on reconnect → reconciliation required.
25. Realtime skipped sequence 102 and delivers 103 → spectator/controller detects gap and refetches.
26. MatchProjection row corrupted in test → replay MatchEvents reconstructs expected projection.
27. Duplicate AwardPoint command replay → one effective event only.
28. Client clock is wrong by one hour → Match ordering unaffected.

## N10.17.06 — Registration/Voting

29. Two users compete for final slot → serialized transaction yields one confirmed and one waitlisted.
30. Registration realtime unavailable → subsequent authoritative snapshot is correct.
31. FIFO projection/cache deleted → queue reconstructed from authoritative sequence/state, not updated_at.
32. CastVote response lost → same-ID retry does not create duplicate effective ballot.
33. CandidateSet becomes stale after roster change → round cannot finalize against old set silently.

## N10.17.07 — Competition/Stats

34. StandingsProjection deleted → rebuild from OfficialResults/Penalties/Ruleset equals previous valid state.
35. Upstream result corrected after downstream match started → manual impact review, no silent participant rewrite.
36. Stats worker runs twice → same PlayerMatchStatContribution not double-counted.
37. Career aggregate is stale → freshness visible/rebuildable; Match facts remain untouched.
38. Calculation version changes → rebuild can distinguish old/new projection semantics.

## N10.17.08 — Media/Notifications

39. Media processor crashes halfway → asset never becomes READY prematurely.
40. New avatar processing fails → old avatar remains attached.
41. Storage object disappears unexpectedly for READY asset → integrity alarm, not silent normal state.
42. Push provider offline → NotificationIntent/Inbox remains available.
43. Scheduled reminder retries after Session cancelled → revalidation suppresses stale delivery.
44. Provider timeout with unknown send state → provider-aware reconciliation/idempotency before duplicate send where supported.

## N10.17.09 — Realtime/dependencies

45. Realtime is fully down for 30 minutes → HTTP commands/read refetch remain correct where backend reachable.
46. Storage outage → Registration and Match remain operational.
47. Auth outage → no fallback that trusts local role metadata.
48. Postgres outage → shared critical writes fail closed; Quick remains local.
49. Team worker crashes → local computation can retry/fallback without using Overall.

## N10.17.10 — Local data

50. IndexedDB migration throws → application does not erase unpublished Quick automatically.
51. User A logs out with pending Match outbox → items sealed to A.
52. User B logs in → A's commands never replay with B's token.
53. Cache is corrupt but no irreplaceable local data → recreate cache safely.
54. Device storage quota nearly full → preflight/monitoring or write failure is surfaced before claiming durable success.

## N10.17.11 — Backup/restore

55. Backup file exists but restore fails schema compatibility → recovery considered failed until repaired/tested.
56. Restored database contains previously deleted personal data → deletion replay removes/anonymizes before normal service.
57. Restore resurrects old pending outbox rows → runbook prevents accidental mass resend.
58. Restore lacks some media objects → integrity report identifies broken references.
59. Projection rows missing after restore → rebuild from source facts.
60. Command receipts older than configured retention missing → no false claim that unlimited historic idempotency remains available.

## N10.17.12 — Deployment

61. New schema deployed while old frontend remains open → expand compatibility preserves old reads/writes until cutover policy.
62. Migration attempts destructive change on active Match → deployment guard/cohort policy blocks it.
63. New projection version fails validation → old projection remains serving.
64. Application rollback happens after additive migration → older app still compatible or rollout halted by compatibility gate.

## N10.17.13 — Integrity/operations

65. Integrity check finds MatchProjection != replay → deterministic rebuild possible; incident logged.
66. Integrity check finds two effective Community owners → no blind auto-delete; governance repair workflow/manual incident.
67. Runbook operator retries a terminal validation failure → tooling makes unsafe action evident/prevented where possible.
68. Logs are inspected during incident → no auth tokens/provider secrets.
69. Dashboard shows low HTTP error rate but oldest outbox age is hours → reliability incident still visible.
70. Chaos test drops response after commit → command remains exactly one logical effect through same-ID recovery.

# 48. Exit criteria — C2.17

C2.17 is complete when architecture can answer all of the following without relying on generic sync semantics:

- what is correctness vs durability vs availability;
- which data is C0/C1/C2/C3;
- what constitutes command success;
- what happens after timeout with unknown commit state;
- how idempotency and deduplication differ;
- which failures retry automatically;
- how outbox/workers survive duplication/crashes;
- how poison work is isolated;
- how every major projection is recovered;
- how Match recovers online/offline/takeover divergence;
- how Registration preserves FIFO during recovery;
- how Voting protects stale candidates/ballots;
- how Competition handles projection rebuild and retroactive corrections;
- how Media/Notification failures avoid corrupting domain state;
- how Realtime recovers from loss/gaps;
- how irreplaceable IndexedDB data is protected;
- how dependencies degrade independently;
- how backup/restore/DR are validated;
- how privacy deletion survives restore;
- how integrity is verified and repairs classified;
- how deployments avoid destructive synchronized cutovers;
- what runbooks/observability/failure tests are required;
- which numeric reliability targets remain OPEN pending evidence.
