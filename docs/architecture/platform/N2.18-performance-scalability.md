## 0. Regra de leitura

Este documento define o **target canônico de Performance / Scalability** do Volley.

A regra central é:

```text
OPERATIONAL WORK
MUST BE BOUNDED BY THE CURRENT OPERATIONAL CONTEXT

NOT
BY TOTAL HISTORICAL SYSTEM SIZE
```

Exemplos:

```text
abrir uma Session atual
≠ baixar todas as Sessions históricas

marcar um ponto
≠ recalcular todo o Career

entrar numa Registration
≠ carregar a fila inteira no client para decidir vaga

assistir um Match
≠ assinar todos os Matches da Community

calcular standings
≠ reler toda a aplicação no browser
```

Performance também não será confundida com arquitetura prematuramente distribuída.

```text
MEASURE
→ IDENTIFY BOTTLENECK
→ FIX QUERY / INDEX / BOUNDARY / ALGORITHM
→ RE-MEASURE
→ SCALE COMPONENT ONLY WHEN EVIDENCE REQUIRES
```

Não partimos automaticamente para:

```text
microservices
Redis
Kafka
read replicas
partitioning
server-side solver farm
CDN para tudo
```

sem gatilho mensurável.

A segunda regra é:

```text
PERFORMANCE OPTIMIZATION
MUST NOT BREAK
CORRECTNESS / SECURITY / PRIVACY / AUDITABILITY
```

Portanto não são otimizações aceitáveis:

- retirar o lock da Registration para ganhar throughput e perder FIFO;
- confiar em role do JWT desatualizada para evitar query de autorização crítica;
- pular RLS em endpoints públicos por conveniência;
- remover `control_epoch`/sequence do Match para reduzir payload;
- publicar ballots privados em Realtime para evitar uma query;
- usar `overall` no balancer porque é computacionalmente mais barato;
- manter URLs públicas de media crua para evitar autorização;
- converter projection em única cópia da verdade para poupar storage.

# 1. Current State — evidência do repositório

## 1.1 O modelo atual ainda favorece carregamento/sync de coleções amplas

O legado local-first armazena em `localStorage` coleções completas para:

```text
players
sessions
teams
games
points
reports
communities
presence
championships
...
```

`saveToStorage()` serializa o valor inteiro com `JSON.stringify` e grava via API síncrona de `localStorage`.

Isso é funcional para o volume atual, mas possui duas propriedades ruins para escala:

1. custo de serialização cresce com a coleção completa;
2. a operação bloqueia a main thread.

N2.12 já substitui esse modelo por IndexedDB estruturado para dados locais relevantes.

## 1.2 Cloud services ainda contêm queries amplas

Há adapters que executam padrões como:

```text
supabase.from('communities').select('*')
```

seguido de mapeamento do conjunto inteiro para objetos de domínio/local sync.

Esse padrão não será a API alvo para listas potencialmente crescentes.

Target:

```text
query use case
→ columns explícitas
→ scope explícito
→ page/cursor explícito
→ DTO explícito
```

## 1.3 O schema atual possui índices úteis, mas nasceu orientado ao sync

A migration operacional já cria índices em eixos como:

```text
community_id
session_id
updated_at
deleted_at
(owner_id, local_id)
```

Isso é positivo como experiência prática com indexação, mas parte relevante dos índices suporta o modelo legado de:

```text
local_id + sync_version + deleted_at + broad reconciliation
```

O target troca “índice para sync genérico” por **índice derivado de query shape autoritativa**.

## 1.4 Statistics atual faz scans client-side de coleções históricas

`calculatePlayerStats()` recebe:

```text
allGames
allPoints
allTeams
allSessions
```

E filtra essas coleções para descobrir:

- Sessions finalizadas;
- Games registrados;
- Teams do Player;
- Points relevantes;
- wins/losses;
- fundamentos/erros/assistências.

A função é adequada como implementação local inicial, mas o custo cresce com o histórico carregado. Repeti-la para múltiplos Players pode multiplicar o custo.

N2.09 já muda a unidade para `PlayerMatchStatContribution` e projections server-side/rebuildable.

## 1.5 O Team Balancer já possui Worker, mas possui custo algorítmico relevante

Pontos positivos atuais:

- existe `balancer.worker.ts`;
- cálculo pesado pode sair da main thread;
- existem perfis de velocidade;
- número de iterations é bounded;
- múltiplas seeds produzem portfolio;
- runtime/iterations já aparecem no resultado.

Entretanto o perfil `advanced` atualmente pode chegar a:

```text
maxIterations = clamp(players * 4000, 20_000, 120_000)
numSeeds = 10
```

O annealing reavalia a solução repetidamente, incluindo métricas por Team, constraints, role coverage e partnership pairs.

Além disso, o core atual possui um limite temporal por run. N2.06 já define que o **resultado canônico target não depende de wall-clock**, porque o mesmo input precisa ser reproduzível por version/seed/iteration budget.

O Worker protege responsividade, mas:

```text
WEB WORKER
≠
FREE CPU
≠
FREE MEMORY
```

## 1.6 O payload do Worker atual carrega `Player[]`

O worker recebe os Players e config, então a structured clone boundary pode copiar muito mais campos do que o solver realmente precisa.

O target usa:

```text
PlayerBalanceSnapshot[]
```

compacto e congelado.

## 1.7 Router atual usa imports estáticos das famílias de rotas

`AppRouter.tsx` importa diretamente módulos de:

- auth;
- campeonato;
- global routes;
- Community;
- Session.

Isso não prova que o bundle atual é inadequado, mas significa que **route-level lazy loading não está explicitamente desenhado** na boundary do router.

O projeto também usa bibliotecas potencialmente pesadas, como charting/calendar/image tooling, então bundle composition precisa ser medida em vez de assumida.

## 1.8 Não existe evidência suficiente para justificar arquitetura distribuída pesada

O repositório não apresenta evidência de:

- DB saturado;
- filas com backlog grande;
- milhões de MatchEvents;
- fan-out público massivo;
- solver inviável em target devices;
- necessidade de read replica;
- necessidade de table partitioning.

Portanto essas soluções continuam condicionadas a triggers observáveis.

# 2. Performance model

## N3.18.01 — Performance Model

Performance será avaliada por fluxo de produto, não por benchmark isolado de função.

Cada fluxo relevante deve identificar:

```text
user action
→ client work
→ network calls
→ DB work
→ locks
→ async work
→ Realtime fan-out
→ rendering
```

Dimensões principais:

```text
latency
throughput
concurrency
CPU
memory
I/O
network bytes
database rows touched
lock time
queue lag
fan-out
cost
```

### N4.18.01 — No “fast” without semantics

Uma operação não é considerada saudável apenas porque responde rápido.

Exemplo:

```text
JoinRegistration em 20 ms
mas permite confirmed > capacity
```

é falha, não performance.

A medida válida combina:

```text
latency + correctness + error rate + saturation
```

# 4. Performance budgets

## N3.18.03 — Performance Budgets

Existem dois tipos de budget.

### Structural budgets — canônicos agora

Estes não precisam de benchmark para existir:

```text
list query → bounded page
active workflow → no full-history scan
Match command → aggregate-local transaction
Registration command → one window lock, bounded candidate lookup
Realtime → resource-scoped subscription
solver → bounded iterations/seeds/input
worker → bounded batch
media → bounded dimensions/bytes
cache → bounded retention
projection rebuild → bounded batch/checkpoint
```

### Quantitative budgets — `OPEN` até medição

Precisam ser medidos em target environments/devices:

```text
p50/p95/p99 command latency
p95 read latency
max acceptable Registration lock wait
Match command throughput
Realtime end-to-end propagation
max route chunk
max initial JS
max balancer runtime by roster class
max balancer memory by roster class
projection lag
worker queue age
IndexedDB operation latency
```

Não inventaremos números apenas para preencher uma tabela.

### N4.18.03 — Budget ownership

Cada budget tem:

```text
metric
scope
measurement point
target device/environment
owner
alert threshold
review cadence
```

N2.19 consolida a instrumentação/alerting.

# 5. Latency

## N3.18.04 — Latency

Classificamos operações por expectativa de UX.

### Interactive command

Exemplos:

```text
JoinRegistration
LeaveRegistration
CastVote
AwardPoint
PauseMatch
```

O usuário espera confirmação autoritativa imediata.

O path deve evitar trabalho downstream não essencial.

```text
transaction COMMIT
→ authoritative response
→ external effects after commit
```

### Interactive read

Exemplos:

```text
Session detail
Registration snapshot
Match snapshot
Community overview
```

Usar read model/columns/page adequados.

### Local compute

```text
Team Balancer
```

Pode levar mais que uma command comum, mas precisa:

- não bloquear UI;
- fornecer progress quando útil;
- ter budget bounded;
- poder ser cancelado;
- ser reproduzível no target canônico.

### Async work

```text
notifications
stats projection
media processing
standings rebuild
```

Não bloqueia command original quando não for necessário para correctness.

# 6. Throughput

## N3.18.05 — Throughput

Throughput é medido por **hot path**, não apenas requests/second globais.

Exemplos separados:

```text
Registration joins/s in one window
AwardPoint commands/s across Matches
AwardPoint commands/s in one Match
Realtime deliveries/s in one popular Match
projection jobs/s
media jobs/s
```

Um banco pode suportar alto throughput global e ainda sofrer em um único hot row de Registration.

# 7. Concurrency

## N3.18.06 — Concurrency

Performance concurrency nunca remove serialization necessária.

### Registration

FIFO/capacity exige serialização no `RegistrationWindow` hot root.

### Match

Sequence exige serialização por Match, mas Matches diferentes são independentes.

```text
Match A lock
≠ Match B lock
```

### Voting

Close/finalize serializa o VotingRound relevante, não a Competition inteira.

### Competition

Officialization/fixture dependency locks permanecem no menor root correto.

### N4.18.06 — Lock scope rule

```text
lock the smallest aggregate root that protects the invariant
```

Evitar:

```text
Community-wide lock
application-wide mutex
global advisory lock
```

sem necessidade comprovada.

# 8. Database queries

## N3.18.07 — Database Queries

Toda query importante deve possuir query shape explícita:

```text
scope predicate
filter predicates
sort order
page limit
selected columns
expected cardinality
required indexes
```

### Proibido como default em lists

```text
SELECT *
sem LIMIT
```

### Appropriate direct reads

Queries pequenas e bem scopeadas podem continuar via PostgREST/Supabase client + RLS.

Não é necessário criar RPC para toda leitura apenas por performance.

### Aggregate reads

Quando a tela exige múltiplas relações e o client faria várias round trips/N+1:

```text
read model view/query RPC
```

pode ser preferível.

# 9. Index strategy

## N3.18.08 — Index Strategy

Índice nasce de query/invariant, não de hábito.

Cada índice deve responder:

```text
which query/invariant needs it?
which predicates/order?
what write cost does it add?
is another index redundant?
```

### Canonical examples

Registration:

```text
(window_id, queue_sequence)
WHERE status = 'WAITLISTED'
```

para localizar o primeiro reserva de forma bounded.

Match:

```text
UNIQUE(match_id, sequence)
```

além da integridade, oferece leitura ordered do log.

Membership:

```text
UNIQUE(community_id, user_id)
```

mais lookup por `user_id` quando necessário.

Notification Inbox:

```text
(user_id, created_at DESC, id DESC)
```

para keyset pagination.

Outbox:

```text
(status, next_attempt_at, id)
```

conforme claim strategy.

### N4.18.08 — Index budget

Mais índices não é sempre melhor.

Custos:

- insert/update overhead;
- disk;
- vacuum;
- cache pressure;
- migration time.

Revisar índices não usados/redundantes com evidência do ambiente.

# 11. RLS performance

## N3.18.10 — RLS Performance

RLS é requisito de segurança e não será removido como primeira otimização.

Performance de RLS exige:

- colunas usadas nas policies indexadas quando aplicável;
- helpers pequenos;
- evitar subqueries redundantes por row quando uma query/boundary melhor resolve;
- medir plano real com RLS ativo;
- manter `auth.uid()`/contexto server-side;
- não mover autorização dinâmica crítica para metadata user-editable.

### N4.18.10 — Capability resolution

Se capability resolution se provar hot:

1. otimizar query e índices;
2. reduzir chamadas repetidas dentro da transaction;
3. considerar helper/read structure seguro;
4. somente depois considerar cache específico com invalidation correta.

Não sacrificar revogação/segurança por micro-otimização.

# 13. Pagination

## N3.18.12 — Pagination

Qualquer coleção potencialmente crescente possui paginação desde a API, não apenas na UI.

Preferência:

```text
keyset/cursor
```

para histórico/inbox/audit/event browsing.

Exemplo:

```text
ORDER BY created_at DESC, id DESC
WHERE (created_at, id) < (:cursor_created_at, :cursor_id)
LIMIT :page_size
```

### Offset

Offset continua aceitável para listas pequenas/fixas onde simplicidade é melhor.

Não usar offset profundo em histórico grande como default.

# 14. N+1 prevention

## N3.18.13 — N+1 Prevention

A UI não deve fazer:

```text
1 query Sessions
+ 1 query organizer por Session
+ 1 query roster count por Session
+ 1 query registration por Session
...
```

quando a tela precisa do conjunto agregado.

Alternativas:

- join/read model;
- batched lookup;
- projection;
- explicit include query.

### N4.18.13 — No mega-query reflex

Evitar o extremo oposto:

```text
one gigantic join returning cartesian duplication
```

Read model deve ser desenhado para o shape da tela.

# 15. Payload size

## N3.18.14 — Payload Size

Payload minimization é requisito de performance e privacy.

### Commands

Enviar somente intenção.

```text
AwardPoint
→ match_id + command metadata + side/player/event detail allowed
```

não:

```text
entire Match object + entire Session + all players
```

### Queries

DTOs não retornam columns que a view não usa.

### Realtime

Envelopes semanticamente mínimos.

### Solver

Worker recebe `PlayerBalanceSnapshot[]`, não `Player[]` completo.

# 16. Caching

## N3.18.15 — Caching

Caching só é correto quando classificado.

### Client remote cache

```text
recreateable
fresh/stale metadata
scope by account/resource
```

### Static asset cache

Service Worker/CDN/browser para shell/assets versionados.

### Server/query cache

Somente se houver bottleneck medido e invalidation definida.

### Proibido

```text
cache undefined
```

Toda cache precisa declarar:

```text
key
scope
TTL/invalidation
source of truth
privacy class
staleness behavior
```

### N4.18.15 — No Redis by reflex

Postgres + browser cache + projections devem ser explorados antes de introduzir Redis operacional.

Redis entra apenas com hot read/cache/rate-limit/ephemeral coordination requirement comprovado e ADR próprio.

# 17. Projections

## N3.18.16 — Projections

Projections evitam recomputar histórico em read path.

Regras:

```text
bounded incremental update
or
bounded checkpointed rebuild
```

Evitar:

```text
on every profile view
→ scan every MatchEvent ever
```

### Projection lag

Projection async possui lag observável.

A UI deve saber quando:

```text
projection_version < source_version
```

se isso for material ao fluxo.

### Critical projection

`MatchProjection` permanece síncrona na mesma transaction do MatchEvent porque score atual é parte crítica do comando.

# 18. Registration contention

## N3.18.17 — Registration Contention

Registration possui um hotspot legítimo: todos os Joins de uma mesma lista precisam respeitar capacidade/FIFO.

Target:

```text
lock RegistrationWindow
→ small eligibility read
→ insert/update one entry
→ maybe promote one/few eligible waitlisted
→ revision++
→ COMMIT
```

### Keep transaction short

Não fazer dentro do lock:

- push notification;
- email;
- rendering de template;
- analytics externo;
- standings/stat recalculation;
- long network call.

### Waitlist lookup

Primeiro candidato deve ser index-assisted, não scan/sort completo da tabela.

### Capacity increase

Se abrir muitas vagas, promoção pode processar os primeiros candidatos elegíveis em um loop bounded pela quantidade de vagas abertas.

### N4.18.17 — Scaling trigger

Se uma única window mostrar lock waits incompatíveis com budget mesmo com query/index/transaction mínimos:

- medir burst shape;
- avaliar admission queue/serialized server worker específico;
- preservar FIFO authoritative sequence.

Não shardear uma única fila de forma que destrua sua ordem sem redefinir o produto.

# 19. Match throughput

## N3.18.18 — Match Throughput

Match tem serialização natural por Match, não global.

```text
Match A seq=101
Match B seq=87
```

podem commit em paralelo.

`AwardPoint` deve tocar um conjunto pequeno e previsível:

```text
Match / Projection root
lease/control fields
append MatchEvent
update MatchProjection
command receipt
outbox/broadcast marker
```

### N4.18.18 — No history scan on point

AwardPoint nunca recalcula:

- Session inteira;
- Career;
- Competition standings completos;
- reports longos.

Esses são downstream.

# 20. Match Event growth

## N3.18.19 — Match Event Growth

`MatchEvent` é append-heavy e tende a ser uma das maiores tabelas ao longo do tempo.

Baseline:

- UUID/id apropriado;
- `UNIQUE(match_id, sequence)`;
- queries sempre scopeadas por Match/sequence/range;
- projection atual evita ler log inteiro para cada spectator;
- estatísticas usam contributions/projections;
- retention segue requirements de histórico, não performance arbitrária.

### N4.18.19 — Partitioning trigger

Conforme N2.14, **sem partitioning V1**.

Reavaliar quando métricas mostrarem problemas como:

- índice grande comprometendo cache;
- vacuum/autovacuum relevante;
- maintenance/backup/restore degradado;
- scans de períodos difíceis mesmo com índices;
- migration/index operation impraticável no monólito da tabela.

Partitioning é resposta a evidência operacional, não ritual de escala.

# 21. Realtime fan-out

## N3.18.20 — Realtime Fan-out

Fan-out cresce aproximadamente com:

```text
messages generated × active subscribers
```

Portanto o design reduz ambos.

### Resource scopes

```text
match:<matchId>
registration:<windowId>
voting:<roundId>
user:<userId>:notifications
```

Evitar um único channel de Community recebendo tudo.

### Payload

Eventos pequenos e sem DB row completa.

### Match spectators

High-frequency Match usa event + projection protocol; public spectator DTO separado se necessário.

### Active screen subscription

Client assina o que está usando e desassina ao sair.

### N4.18.20 — Scale trigger

Monitorar:

- concurrent subscribers;
- msgs/s;
- egress bytes;
- disconnect/reconnect rate;
- delivery latency;
- popular-match fan-out concentration.

Somente se isso virar bottleneck considerar arquitetura adicional de fan-out/streaming.

# 22. Team Balancer CPU

## N3.18.21 — Team Balancer CPU

O balancer target preserva algoritmo multidimensional, mas torna custo explícito.

### Current cost sources

- múltiplas seeds;
- muitas iterations;
- cloning de Team arrays;
- recalculating metrics por candidate;
- constraint checks;
- composition checks;
- partnership pair cost;
- candidate portfolio comparison.

### Target principles

1. fixed iteration budget por algorithm version/config;
2. Worker obrigatório para compute relevante no browser;
3. cancellation support;
4. progress bounded;
5. feasibility precheck antes do annealing;
6. compact snapshots;
7. benchmark por roster size/device class;
8. incremental scoring somente se mantém determinismo/correção;
9. no `overall` shortcut.

### N4.18.21 — Canonical determinism

Wall-clock não decide resultado canônico.

```text
same canonical input
+ algorithm version
+ policy version
+ seed
+ iteration budget
=
same solution
```

Performance tuning muda algorithm/version/policy de modo explícito.

### N5.18.21 — Device vs server

Baseline continua client Worker porque:

- reduz custo server;
- funciona Quick offline;
- roster é relativamente pequeno;
- compute é puro.

Migrar solver para server only se benchmarks em devices-alvo mostrarem UX inviável ou se requisitos de trust/compute mudarem.

Mesmo nesse caso, Quick offline precisa de estratégia local compatível.

# 23. Team Balancer Memory

## N3.18.22 — Team Balancer Memory

Target worker payload:

```text
PlayerBalanceSnapshot[]
TeamFormationConfig
constraints
seed/version metadata
```

Não enviar full Player/Community/Session models.

### Candidate representation

Durante search, usar representação compacta suficiente para IDs/assignments/métricas.

Evitar manter deep copies de objetos grandes por iteration.

### Portfolio

Persistir somente candidates finais necessários, não todas as soluções intermediárias.

### N4.18.22 — Structured clone

Structured clone de payloads grandes também consome CPU/memory.

# 31. Scaling Triggers

## N3.18.30 — Scaling Triggers

Tecnologia adicional só entra após trigger mensurável.

## N4.18.30 — Database trigger examples

Considerar read replica/cache especializado quando houver combinação de:

- read load claramente dominante;
- queries/indexes/read models já otimizados;
- primary CPU/I/O/saturation comprovados;
- freshness model compatível.

Considerar partitioning quando os sinais de N3.18.19 aparecerem.

Considerar maior compute tier quando:

- working set/cache/CPU realmente exceder tier atual;
- query tuning não resolver.

## N4.18.30 — Queue trigger

Introduzir queue/broker externo além de Postgres outbox se houver:

- throughput/backlog incompatível;
- fan-out/job routing complexo;
- retention/replay requirements que Postgres outbox não atende economicamente;
- operational evidence.

## N4.18.30 — Solver trigger

Migrar/expandir compute server-side se:

- runtime target device exceder UX budget;
- memory crashar devices relevantes;
- roster size crescer além do envelope local;
- necessidade de central compute superar benefício offline/cost.

## N4.18.30 — Realtime trigger

Arquitetura adicional de streaming/fan-out somente com spectator volume/egress/latency medidos.

## N4.18.30 — Search trigger

Adicionar search engine dedicado somente se Postgres indexes/full-text/trigram não atenderem discoverability/query requirements medidos.

# 34. Migration Performance

## N3.18.33 — Migration Performance

Migração arquitetural não pode criar indisponibilidade desnecessária.

# 39. N10 — Performance / Scalability Acceptance Matrix

## N10.18.01 — Growing lists

1. Community reaches thousands of historical Sessions; agenda loads only requested period/page.
2. User has years of Notifications; Inbox first page does not download entire history.
3. Audit table grows; admin audit query uses cursor/range and does not deep-offset by default.
4. Competition list grows; opening one Competition does not load all Competition history.

## N10.18.02 — Database query shape

5. A developer adds `select('*')` to a growing historical list → review/test flags contract regression.
6. Query needs only five columns but row contains large JSONB → read DTO avoids transferring JSONB.
7. Query plan switches to unexpected Seq Scan after cardinality growth → performance investigation identifies/indexes/query fix before cache technology.
8. Planner estimate differs heavily from actual rows → statistics/query design reviewed.

## N10.18.03 — Indexes

9. New partial waitlist index makes promotion lookup bounded while write overhead remains acceptable.
10. Two indexes become redundant after migration → usage review allows safe retirement.
11. Index creation on hot large table would block writes → deployment procedure schedules safe mechanism rather than blind migration.
12. Index helps query but causes excessive write amplification → query/read model alternatives evaluated.

## N10.18.04 — RLS

13. Community list query is slow with RLS → optimize supporting membership indexes/helper plan; do not disable RLS.
14. Cached stale role could speed command but member was revoked → current DB authorization wins.
15. BOLA test remains denied under load; no performance bypass path exists.
16. RLS helper is called repeatedly per row and dominates query → query/read model boundary redesigned safely.

## N10.18.05 — Registration hotspot

17. 100 users Join the final single slot concurrently → one CONFIRMED, remaining eligible users WAITLISTED FIFO.
18. Registration latency rises due to notification provider → provider removed from transaction/outbox used.
19. Capacity increases by 20 → only needed first eligible reserves are processed in order.
20. Two independent Registration windows receive bursts simultaneously → no global lock serializes them.
21. Waitlist contains many withdrawn/ineligible old rows → index/query finds next eligible candidates without full client scan.
22. Lock wait exceeds budget → transaction/query/index measured before changing FIFO semantics.

## N10.18.06 — Match throughput

23. 50 independent Matches receive point commands → per-Match sequence remains correct without global Match lock.
24. Same Match gets two simultaneous commands for expected sequence 20 → one wins sequence 21; other gets stale conflict/refetch semantics.
25. Career projection worker is slow → AwardPoint latency remains unaffected after commit.
26. Realtime provider is slow/down → authoritative AwardPoint response remains bounded by DB transaction, not fan-out delivery.
27. Match has 500 events → current score fetch uses MatchProjection, not replay of 500 events on every screen load.
28. Event history drill-down requests old events → sequence pagination/range query used.

## N10.18.07 — Realtime fan-out

29. One Match gets 10x normal spectators → other Match channels remain isolated.
30. User leaves Match page → subscription is removed; no continued event stream.
31. Reconnect storm occurs after network recovery → snapshot/reconciliation prevents client from requesting full history repeatedly.
32. Payload accidentally includes full Player objects per point → payload budget/contract test rejects regression.
33. Public spectator mode grows → public DTO contains scoreboard data only, not actor/device/internal metadata.

## N10.18.08 — Balancer CPU

34. 12-player roster on normal device → Worker keeps UI responsive while solver executes.
35. Larger roster increases runtime → iterations remain bounded according to explicit policy/version.
36. Same input/seed/version on faster and slower devices → canonical candidate remains identical because wall-clock is not stopping criterion.
37. Feasibility precheck detects impossible hard constraints → expensive annealing is not started pointlessly.
38. Solver profiling identifies repeated full metric recomputation → incremental scorer optimization may be introduced only with equivalence/property tests.
39. Product asks to replace attributes with overall for speed → rejected by BAL/PERF invariants.

## N10.18.09 — Balancer memory

40. Worker payload currently includes large Player profiles → migration uses compact PlayerBalanceSnapshot.
41. Candidate search generates thousands of intermediates → only current/best/necessary portfolio structures retained.
42. Three final options are returned → raw intermediate search graph is not persisted.
43. Structured clone dominates runtime only at unusually large rosters → binary/transfer optimization considered after measurement, not before.

## N10.18.10 — Statistics

44. Player has five years of matches → Career summary does not ship all PointEvents to browser.
45. One old Match is corrected → affected PlayerMatchStatContribution/aggregates recompute without global full-history client scan.
46. Community leaderboard opens → metric-specific projection/page query used.
47. Detailed Match stats requested → only that Match contribution/events loaded.

## N10.18.11 — Competition

48. League contains many rounds → current Stage/round view loads scoped fixtures.
49. Upstream playoff result changes before downstream starts → only affected dependency subgraph recalculates.
50. Standings screen refreshes repeatedly → reads projection instead of recomputing every result client-side.
51. Historical competitions grow → opening current competition cost remains bounded by current competition.

## N10.18.12 — Media

52. Community list shows 100 avatars → thumbnail variants used, not original master images.
53. User uploads huge-dimension compressed image → pixel limits reject before unbounded processing memory.
54. Same avatar viewed repeatedly → immutable key enables browser/CDN caching.
55. Avatar replaced → new object key avoids invalidation race on old cached bytes.

## N10.18.13 — Frontend rendering

56. Point is awarded → unrelated Community management/chart views do not rerender unnecessarily.
57. Long participant list reaches a measured rendering bottleneck → pagination/virtualization introduced at list boundary.
58. Developer memoizes every component without evidence → rejected as complexity without measured gain.
59. Chart library is only needed on performance route → route chunk can defer it from initial load.

## N10.18.14 — Bundle/loading

60. Cold load on constrained mobile is slow → bundle analyzer identifies actual heavy modules before dependency removal.
61. Competition/Admin routes are rarely used → lazy route chunks reduce initial work.
62. Code splitting creates dozens of tiny sequential chunks → chunk strategy consolidated based on waterfall measurement.
63. Fonts/assets dominate initial transfer → asset strategy optimized independently of domain code.

## N10.18.15 — IndexedDB

64. One offline point is added → one bounded local transaction, not JSON.stringify of every Point ever.
65. Cache has years of stale remote snapshots → pruning removes recreateable data without touching irreplaceable Quick/Match data.
66. IndexedDB migration has 100k local cache records → migration batches/checkpoints instead of one giant transaction when needed.
67. Quota approaches limit → recreateable cache is first cleanup candidate; irreplaceable local facts protected.

## N10.18.16 — Workers/backpressure

68. Notification provider is unavailable for one hour → retries back off; worker concurrency does not create a storm.
69. One poison notification repeatedly fails → quarantined without blocking unrelated intents.
70. Stats rebuild queue grows → processing lag visible; commands remain available.
71. Large rebuild restarts after deploy → resumes from checkpoint rather than zero.

## N10.18.17 — Scaling decisions

72. DB CPU rises → team inspects top queries/plans before adding cache/read replica.
73. Realtime egress dominates cost → subscription scope/payload/fan-out examined before platform rewrite.
74. MatchEvents become operationally huge → partitioning evaluated against measured vacuum/index/restore pain.
75. Solver becomes slow only on low-end devices → adjust algorithm/version/budget or compute placement with benchmarks, not guesswork.
76. Search becomes a product feature with fuzzy/global scale → benchmark Postgres search before dedicated engine.
77. Postgres outbox backlog becomes structurally too large → broker decision gets its own ADR/evidence.

## N10.18.18 — Cost efficiency

78. Feature doubles DB reads per active Session without UX change → read amplification regression detected.
79. New index improves rare query but significantly increases hot Match writes → trade-off documented/measured.
80. Realtime sends redundant full snapshots every point → egress cost exposes protocol regression.
81. Media variant policy creates many never-used sizes → variant set simplified based on usage.

## N10.18.19 — Load testing correctness

82. Registration benchmark is fast but produces capacity violation → test fails regardless of latency.
83. Match benchmark is fast but sequence gap appears → test fails.
84. Worker benchmark has throughput but duplicates Notification delivery → idempotency assertion fails.
85. Realtime fan-out benchmark drops events → clients still reconcile by snapshot/sequence; correctness test verifies final convergence.

## N10.18.20 — Migration performance

86. Backfill of normalized roster tables is large → runs in restartable batches.
87. Dual-write period increases command latency → measured and kept temporary with cutover criteria.
88. New index migration on large table exceeds safe lock budget → rollout procedure changes before production.
89. Active Match exists during Match V2 rollout → stays on old execution cohort until finish.
90. Contract phase wants to drop legacy column still read by old client version → compatibility telemetry blocks premature drop.

# 42. Scaling decision ladder

Usar esta ordem por default:

```text
1. remove unnecessary work
2. bound data set
3. fix query shape
4. add/fix index
5. move aggregation to read model/projection
6. reduce payload/round trips
7. batch safely
8. tune algorithm/data structure
9. add cache with explicit invalidation
10. scale single component vertically
11. add specialized infrastructure only with measured trigger
```

Pular diretamente ao passo 11 cria operational complexity sem garantir que o problema real foi resolvido.

# 46. Final canonical statement

The target architecture should make the common operation look like:

```text
SMALL SCOPE
+ SMALL AUTHORITATIVE TRANSACTION/QUERY
+ APPROPRIATE INDEX
+ BOUNDED RESPONSE
+ OPTIONAL ASYNC DOWNSTREAM WORK
+ RESOURCE-SCOPED REALTIME
```

not:

```text
DOWNLOAD EVERYTHING
→ FILTER EVERYTHING
→ RECOMPUTE EVERYTHING
→ SYNC EVERYTHING
```

Scalability is therefore primarily achieved by **correct boundaries and bounded work**. Specialized infrastructure is introduced only when measured growth proves those boundaries are no longer enough.
