## 0. Regra de leitura

A separação mais importante deste capítulo é:

```text
DOMAIN HISTORY
≠
AUDIT
≠
TELEMETRY
≠
APPLICATION LOGS
```

Cada um responde a uma pergunta diferente.

```text
Domain History
→ o que aconteceu no domínio e precisa continuar verdadeiro?

Audit
→ quem executou uma ação sensível, em qual contexto e com qual resultado?

Telemetry
→ o sistema está saudável, rápido, correto e recuperável?

Application Logs
→ quais fatos técnicos ajudam a explicar uma execução específica?
```

Observability não será source of truth de nenhuma regra esportiva.

Se os logs sumirem:

```text
MatchResult continua verdadeiro
Registration FIFO continua verdadeiro
OfficialCompetitionResult continua verdadeiro
PlayerEvaluation continua verdadeiro
```

A segunda regra é:

```text
OBSERVABILITY
=
ABILITY TO EXPLAIN SYSTEM BEHAVIOR
FROM EXTERNAL OUTPUTS AND INTERNAL SIGNALS
```

não:

```text
console.log everywhere
```

A terceira regra é:

```text
MORE TELEMETRY
≠
BETTER TELEMETRY
```

High-cardinality labels, payload dumps, PII excessiva e logs duplicados aumentam custo e risco sem necessariamente melhorar diagnóstico.

# 1. Current State — evidência do repositório

## 1.1 `AppResult` já possui um conceito local de correlação

O `UnexpectedAppError` atual inclui:

```text
correlationId
```

mas `unexpectedError()` gera `crypto.randomUUID()` no browser.

Isso é útil como referência de UI, mas não garante que o mesmo identificador exista em RPC, banco, outbox ou worker.

### Target

Preservar a ideia de uma referência apresentada ao usuário, porém ligá-la a um `request_id`/trace server-side real quando houver chamada remota.

---

## 1.2 Existe um ledger local de falhas de sync

`syncIssueLedger` já registra:

```text
operation
context
message
status
count
firstSeenAt
lastSeenAt
nextAttemptAt
kind
```

Isso demonstra uma intenção correta de:

- agrupar falhas repetidas;
- distinguir open/resolved;
- tornar retry diagnosticável;
- manter informação após reload.

### Limitação

O mecanismo:

- é local;
- pertence ao sync genérico legado;
- não correlaciona client e server;
- não mede Command/Query/DB/worker separadamente;
- não substitui métricas agregadas nem tracing.

### Target

A ideia de `operational diagnostics` será preservada em N3.19.31, mas o sync ledger desaparece com a aposentadoria do sync genérico.

---

## 1.3 O balancer já produz sinais úteis

O balanceador atual já conhece:

```text
seed
iterations
runtimeMillis
objective score
progress
```

Isso é uma boa base de observability do algoritmo.

Porém:

```text
runtime measurement
≠
canonical termination rule
```

O target do N2.06 exige determinismo pelo iteration budget/version/seed; runtime serve como métrica, não como autoridade de resultado.

---

## 1.4 Logs locais ainda são ad hoc

O código atual usa `console.error`/`console.warn` em vários boundaries locais e storage/recovery paths.

Isso é aceitável durante desenvolvimento, mas não forma um contrato operacional consistente de produção.

---

## 1.5 Não criar um observability stack distribuído antes da necessidade

O target deste capítulo define contratos e sinais.

Ele não obriga imediatamente:

```text
OpenTelemetry Collector
Prometheus
Grafana
Datadog
Sentry
Honeycomb
ELK
```

A infraestrutura concreta pode começar simples e evoluir.

O importante é que instrumentation e naming não dependam semanticamente de um vendor.

# 2. N3.19.01 — Observability Model

## N4.19.01 — Signal model

O Volley terá quatro famílias operacionais de sinais:

```text
LOGS
METRICS
TRACES / execution correlation
OPERATIONAL DIAGNOSTICS
```

E uma família deliberadamente separada:

```text
AUDIT RECORDS
```

## N4.19.01.01 — Questions first

Antes de adicionar um sinal, declarar qual pergunta operacional ele responde.

Exemplo:

```text
metric: registration_command_duration
question:
"JoinRegistration está ficando lento sob burst?"
```

Não criar métricas sem consumidor/hipótese.

## N5.19.01 — Bounded-context ownership

Platform define envelope, naming, retention e plumbing.

Cada bounded context define:

- sucessos importantes;
- falhas importantes;
- invariants operacionais;
- latências relevantes;
- saturation/backlog;
- recovery signals.

# 3. N3.19.02 — Structured Logging

## N4.19.02 — Canonical log envelope

Um log server-side estruturado deve poder conter, quando aplicável:

```text
timestamp
level
event_name
service/component
environment
release_id
request_id
trace_id nullable
span_id nullable
command_id nullable
job_id nullable
actor_ref_hashed_or_internal nullable
resource_type nullable
resource_id nullable
community_id nullable
session_id nullable
match_id nullable
operation
outcome
error_code nullable
duration_ms nullable
retry_count nullable
```

Não é obrigatório preencher todos os campos em toda linha.

## N4.19.02.01 — Event names, not prose parsing

Preferir:

```text
event_name = "match.award_point.rejected"
error_code = "MATCH_SEQUENCE_STALE"
```

em vez de depender de parsing de:

```text
"deu erro ao marcar ponto porque a sequência mudou"
```

## N4.19.02.02 — No raw payload logging by default

Não registrar automaticamente:

- request body completo;
- JWT;
- cookies;
- email;
- password;
- MFA code;
- media bytes;
- Player evaluations completas;
- ballot individual;
- notification body com PII;
- provider credentials.


## N5.19.03 — Bounded dimensions

# 5. N3.19.04 — Distributed Tracing

## N4.19.04 — Trace purpose

Tracing serve para decompor uma execução causal:

```text
browser action
  ↓
HTTP/RPC
  ↓
application command
  ↓
DB transaction
  ↓
outbox write
  ↓
worker
  ↓
provider
```

## N4.19.04.01 — Incremental adoption

Não é necessário instrumentar cada função TypeScript.

Prioridade:

1. remote command/query boundaries;
2. DB/RPC latency;
3. workers/outbox;
4. external providers;
5. selected frontend transactions.

## N5.19.04 — Vendor neutrality

Quando tracing distribuído for ativado, preferir propagação compatível com padrões amplamente suportados e não acoplar domínio a SDK de vendor.

# 6. N3.19.05 — Correlation

## N4.19.05 — Identifier taxonomy

```text
request_id
→ uma tentativa de transporte/request

command_id
→ uma intenção lógica idempotente

trace_id
→ uma cadeia causal observada

job_id
→ uma execução lógica de background

event_id
→ identidade de evento de domínio/realtime onde existir

release_id
→ versão implantada
```

Nunca fundir esses conceitos num único UUID.

## N4.19.05.01 — Unknown outcome

Exemplo:

```text
command_id = C1
request_id = R1 → timeout
request_id = R2 → receipt found / success
```

Os dois requests permanecem correlacionáveis ao mesmo command.

## N5.19.05 — User-facing support reference

Quando uma falha inesperada precisar de referência para suporte, mostrar identificador seguro e correlacionável, preferencialmente `request_id`/support reference server-issued.

Não mostrar stack trace ou identificadores sensíveis.

## N4.19.06 — Every critical command

```text

```

## N4.19.06.01 — Semantic rejection is not infrastructure failure

Exemplo:

```text

```

é rejection de negócio, não HTTP/database outage.

## N5.19.06 — Command receipt linkage

Quando houver `command_receipt`, permitir diagnosticar:

- first processing;
- duplicate retry;
- final outcome;
- response reconstruction.

Sem armazenar payload desnecessário em telemetry.

# 21. N3.19.20 — Audit vs Telemetry

## N4.19.20 — Canonical distinction

### Audit

Características:

- semântico;
- durable conforme policy;
- focado em ação relevante;
- actor/context/outcome;
- acesso restrito;
- não sampled quando exigido.

### Telemetry

Características:

- operacional;
- agregável;
- pode ser sampled;
- retenção menor;
- otimizada para diagnóstico/alerta.

## N4.19.20.01 — Never reconstruct domain history from telemetry

Não depender de logs para reconstruir MatchEvents, votos, evaluations ou official results.

## N5.19.20 — Audit does not mean row dump

Audit deve registrar ação semântica, não necessariamente `old_row JSONB + new_row JSONB` de toda tabela.

Sampling de telemetry não pode apagar audit obrigatório.

## N5.19.22 — Adaptive future

Adaptive sampling é evolução possível, não requisito V1.

# 26. N3.19.25 — Severity

## N4.19.25 — Operational severity model

Working model:

```text
SEV-1
critical integrity/security or broad unavailability

SEV-2
major degraded core capability / significant user impact

SEV-3
localized degradation / workaround exists

SEV-4
non-urgent defect/diagnostic anomaly
```

Valores exatos de response target ficam fora deste capítulo até operação real.

## N4.19.25.01 — Severity by impact, not stack trace

Uma exception ruidosa de analytics pode ser SEV-4.

Uma silenciosa corrupção de Match sequence pode ser SEV-1/2 conforme alcance.

# 28. N3.19.27 — SLO

## N4.19.27 — No invented targets

SLO quantitativo exige:

- baseline;
- product criticality;
- dependency limits;
- operational capacity;
- agreed response model.

Até então registrar:

```text
OPEN: exact SLO target
```

## N5.19.27 — Context-specific

Não criar um único SLO “Volley uptime”.

JoinRegistration, spectator Realtime e email delivery possuem criticidades distintas.

# 29. N3.19.28 — Error Budgets

## N4.19.28 — Purpose

Quando SLOs existirem:

```text
error budget
→ operational decision signal
```

Pode orientar:

- reduzir rollout velocity;
- priorizar reliability work;
- bloquear expansão arriscada;
- investigar provider/dependency.

## N4.19.28.01 — Not a correctness license

Error budget nunca autoriza:

```text
perder MatchEvent
violar FIFO
vazar dados
```

Correctness/security invariants não viram “permitidos até X%”.

# 30. N3.19.29 — Frontend Errors

## N4.19.29 — Categories

## N4.19.29.01 — Error boundary

## N4.19.29.02 — Browser context

Contexto útil, minimizado:


# 43. Decisions / Hypotheses / Open

## DECIDED

- `Domain History ≠ Audit ≠ Telemetry ≠ Application Logs`.
- `request_id ≠ command_id ≠ trace_id ≠ job_id`.
- Metric labels precisam de cardinalidade bounded.
- IDs de User/Player/Community/Session/Match não são labels normais de métricas.
- Structured logs não recebem raw payloads por padrão.
- Secrets/tokens/MFA nunca são logados.
- Critical command outcome distingue domain rejection, authorization rejection e technical failure.
- Realtime gap/recovery, Match reconciliation e Registration contention são sinais de primeira classe.
- Balancer runtime não influencia resultado canônico.
- Worker/outbox backlog age/depth é observável.
- Audit obrigatório não sofre sampling de telemetry.
- SLOs quantitativos não serão inventados antes de baseline/requisito.
- Telemetry exporter failure normalmente não pode derrubar domain command.
- Release correlation é obrigatória para telemetry central relevante.

## HYPOTHESES

- Um stack vendor-neutral/OpenTelemetry-compatible provavelmente reduzirá lock-in quando tracing distribuído se tornar necessário.
- Para o estágio inicial, logs estruturados + métricas essenciais + provider/platform observability podem ser suficientes antes de um collector dedicado.
- Error tracking frontend especializado pode justificar-se quando uso externo/produção crescer.

## OPEN

- Vendor/stack final de logs/metrics/traces/error tracking.
- Sampling rates.
- Retention windows por sinal.
- Numeric SLO targets.
- Alert thresholds/burn-rate windows.
- Whether browser tracing is enabled globally or only selected flows.
- Exact support diagnostic export format.
- Exact Platform Admin access model for observability backend.
