## 0. Regra de leitura

A regra central é:

```text
CRITICAL INVARIANT
REQUIRES
EXECUTABLE EVIDENCE
```

Não basta que a arquitetura diga:

```text
confirmed <= capacity
```

se nenhuma suíte consegue provocar duas inscrições concorrentes na última vaga e provar que o banco mantém a regra.

Da mesma forma:

```text
coverage = 90%
```

não prova:

```text
FIFO correto
BOLA bloqueado
MatchEvent não duplicado
projection rebuildable
overall fora do solver
restore realmente funciona
```

Portanto:

```text
QUALITY
≠ TEST COUNT
≠ LINE COVERAGE
≠ E2E COUNT
```

O modelo é:

```text
PREVENT
├── types
├── schemas
├── constraints
└── static analysis

PROVE
├── domain/property tests
├── integration tests
├── concurrency tests
├── security tests
└── end-to-end tests

OBSERVE
├── production telemetry
└── integrity checks

RECOVER
├── failure injection
├── rebuild tests
└── restore drills
```

Outra regra:

```text
TEST AT THE LOWEST LAYER
THAT CAN PROVE THE INVARIANT
```

mas:

```text
DO NOT MOCK AWAY
THE LAYER THAT OWNS THE INVARIANT
```

Exemplo:

- `RegistrationWindow` arithmetic pode ter unit tests;
- a race da última vaga precisa de PostgreSQL real/compatível e transações concorrentes;
- RLS precisa de identidades/RLS reais;
- a experiência “Organizer inicia Match” precisa de E2E fino sobre contratos já testados abaixo.

# 1. Current State — evidência do repositório

## 1.1 Portfólio atual já possui múltiplas camadas

`package.json` possui scripts separados para:

```text
typecheck
ESLint
format check
node:test
Vitest
Playwright
build
```

Isso é uma base saudável: não há necessidade de substituir toda a stack de testes apenas para alcançar o target.

## 1.2 CI atual não executa E2E

O workflow `.github/workflows/ci.yml` executa:

```text
npm ci
npm run typecheck
npm run lint:eslint
npm run format:check
npm test
npm run build
```

Enquanto `npm test` é:

```text
npm run test:unit && npm run test:ui
```

`npm run test:e2e` é um script separado e não faz parte do gate atual.

Isso não significa que todo E2E deva obrigatoriamente rodar em toda PR; significa que a política precisa ser deliberada e não acidental.

## 1.3 Playwright já produz bons artefatos de falha

`playwright.config.ts` usa Chromium, execução serial (`workers: 1`), retries em CI, `trace: on-first-retry` e screenshot em falha.

Preservar:

- artefatos diagnósticos;
- `forbidOnly` em CI;
- browser automation real.

Evoluir:

- distinguir retry diagnóstico de tolerância a flakiness;
- definir quais journeys são release gates;
- adicionar matriz de browser somente quando produto/evidência justificar.

## 1.4 Balancer já tem testes de propriedades importantes

`src/logic/balancing.test.ts` já prova exemplos como:

- todos os Players aparecem exatamente uma vez;
- tamanhos diferem no máximo em 1 em cenários atuais;
- locked assignment é respeitado;
- fundamentos alteram a solução;
- composição/roles possuem comportamento testado.

Isso deve ser preservado e elevado de exemplos específicos para propriedades do solver target.

## 1.5 O solver atual ainda possui wall-clock no critério de parada

O balancer atual combina:

```text
maxIterations
Date.now() - startTime < 45000
maxNoImprovement
```

No target do N2.06, o resultado canônico deve depender de input/version/seed/budget determinístico e não de velocidade da máquina. Testing precisa impedir regressão nessa regra.

## 1.6 Não foi identificado harness PostgreSQL/Supabase de teste versionado

O diretório `supabase/` contém atualmente `migrations/`.

Não foi identificado ali um harness versionado para executar automaticamente:

- migrations do zero;
- RLS;
- RPCs;
- locks;
- concorrência real;
- rollback transacional;
- backfills.

Essa lacuna é P0 para os novos bounded contexts compartilhados.

## 1.7 Fixtures atuais refletem o modelo legado

A suíte possui fixtures reutilizáveis, o que é positivo, mas os builders/fixtures precisarão acompanhar o target:

```text
SessionParticipant
RosterRevision
RegistrationWindow
MatchEvent
MatchProjection
OfficialCompetitionResult
PlayerEvaluation revision
MediaAsset
```

em vez de cristalizar arrays e entidades legadas como único formato de teste.

# 2. N3.20.01 — Quality Model

## N4.20.01 — Quality como evidência

A pergunta não é:

> “Tem teste?”

A pergunta é:

> “Qual risco/invariante este teste prova, em qual boundary, e que falha ele detectaria?”

Cada requisito crítico deve mapear para pelo menos uma forma de evidência executável.

## N5.20.01 — Risk tiers

### Q0 — Integridade crítica

Exemplos:

- Match facts;
- Registration FIFO/capacity;
- ownership;
- votes finais;
- OfficialCompetitionResult;
- avaliações/source facts;
- privacy/security isolation.

Exigem múltiplas camadas quando apropriado: DB constraint + integration + adversarial/concurrency.

### Q1 — Authoritative workflow

Exemplos:

- Session lifecycle;
- TeamDraw confirmation;
- notification intent;
- media attachment.

### Q2 — Derived/read behavior

Exemplos:

- standings projection;
- statistics projection;
- dashboards;
- read models.

### Q3 — Presentation

Exemplos:

- labels;
- visual arrangement;
- hints;
- non-critical formatting.

A profundidade e frequência de testes seguem risco, não quantidade uniforme.

# 3. N3.20.02 — Test Portfolio

## N4.20.02 — Pirâmide adaptada ao domínio

```text
STATIC / TYPES / SCHEMAS
        ↓
UNIT + DOMAIN + PROPERTY
        ↓
APPLICATION + CONTRACT
        ↓
DB / RLS / RPC / CONCURRENCY
        ↓
UI COMPONENT
        ↓
THIN CRITICAL E2E
        ↓
LOAD / FAILURE / RESTORE
```

Não adotamos “E2E para tudo”.

E2E é caro, mais lento e menos preciso para localizar falha.

Também não adotamos “unit test para tudo”: mocks não provam RLS, lock, transaction ou browser behavior.

## N5.20.02 — Ownership

Cada bounded context é responsável por seus invariantes; Quality Engineering fornece harnesses, padrões, gates e ferramentas transversais.

# 4. N3.20.03 — Static Analysis

Baseline:

```text
TypeScript strictness appropriate to repository
ESLint
format verification
build/type generation checks
migration/schema lint where available
forbidden dependency checks where useful
```

Target adicional:

- DTO/runtime schema drift detection;
- generated DB type drift check, se generated types forem adotados;
- imports arquiteturalmente proibidos quando boundaries estiverem estabilizadas;
- secret scanning e dependency/security checks conforme N2.16/N2.21.

Static analysis não substitui runtime validation de payload externo.

# 5. N3.20.04 — Unit Tests

Unit tests são adequados para funções pequenas e determinísticas:

- lifecycle predicates;
- state transitions puras;
- score/set rule calculations;
- tie-break calculation;
- stat definition functions;
- template rendering;
- policy selection;
- serialization/version transforms.

Evitar unit tests que mockam cinco layers apenas para verificar que um método chamou outro.

# 6. N3.20.05 — Domain Tests

Domain tests trabalham linguagem de negócio e invariantes.

Exemplos:

```text
Session cannot finish with active Match
Waitlisted is not SessionParticipant
Match cannot start without READY blockers resolved
WO creates no PointEvents
Overall change cannot alter balancing
Organizer alone cannot transfer Community ownership
```

Builders devem expressar estados semanticamente:

```text
aRegistrationWindow().open().capacity(12)
aMatch().live().epoch(4).lastSequence(17)
aCommunity().withOwner(userA)
```

# 7. N3.20.06 — Property-Based Tests

Property-based testing é obrigatório para invariantes com grande espaço combinatório.

Framework exato: `OPEN`; `fast-check` é candidato natural em TypeScript, mas não é congelado neste C2.

## N4.20.06 — Candidate properties

### Registration

```text
confirmed_count <= capacity
active Player appears at most once per window
queue sequence is monotonic
promotion chooses first eligible waiter
```

### Team Formation

```text
union(all teams) == roster
intersection(team_i, team_j) == empty
hard constraints always hold for confirmed candidate
same canonical input + seed + versions == same result
```

### Match

```text
replay(effective MatchEvents) == MatchProjection
sequence is contiguous
one command_id cannot create two effective events
```

### Statistics

```text
aggregate(parts) == aggregate(whole)
when definitions/eligibility are equal
```

### Rating

```text
repeating same evaluator revision does not increase weight
one Community with many evaluators does not gain multiple global-community votes
missing != zero
```

# 8. N3.20.07 — Determinism Tests

Determinism precisa ser explicitamente provado onde é requisito.

## N4.20.07 — Balancer

```text
canonical PlayerBalanceSnapshot[]
+ roster_revision
+ config
+ algorithm_version
+ objective_policy_version
+ seed
+ iteration_budget
=
identical canonical candidate fingerprint
```

Testar:

- mesma execução repetida;
- Worker vs execução direta;
- diferente velocidade de CPU não muda resultado;
- alteração apenas em telemetry/runtime não muda resultado;
- mudança de version/seed pode legitimamente mudar resultado.

Wall-clock pode cancelar UX não-canônica, mas não deve determinar o TeamDraw canônico publicado.

## N4.20.07 — Standings / projections

Mesmos official facts + ruleset version devem reconstruir a mesma projection.

# 9. N3.20.08 — Application Tests

Use cases são testados contra ports/fakes controlados para provar orchestration:

```text
UI-independent input
→ Use Case
→ capability/port calls
→ AppResult/domain response
```

Testar especialmente:

- recovery actions;
- mapping de domínio para AppResult;
- command_id propagation;
- unknown outcome behavior;
- offline policy routing.

Mocks não devem substituir testes de DB quando a regra vive no DB.

# 10. N3.20.09 — Contract Tests

Contratos versionados precisam de testes para:

- Command request DTO;
- Query response DTO;
- stable product error code;
- Realtime envelope;
- provider adapter boundary;
- event payload schema/version;
- public vs private DTO.

## N4.20.09 — Compatibility

Para mudanças aditivas:

- client antigo ignora campo novo;
- server novo aceita contrato antigo dentro da janela suportada;
- breaking change exige version/expand-contract deliberado.

Golden fixtures podem ser usados quando o contrato serializado for a coisa testada, evitando snapshots gigantes de UI.

---

# 11. N3.20.10 — Database Integration

Testes de banco devem rodar contra PostgreSQL/Supabase local/isolado suficientemente fiel.

Devem aplicar migrations **desde zero**.

Baseline a provar:

```text
schema builds from migrations
constraints exist
FK semantics work
RLS behaves by actor
RPCs execute transactionally
indexes/queries required are present
```

Framework/orchestration exato (`Supabase CLI`, containers ou equivalente) é `OPEN`, mas mock in-memory não é substituto para esses testes.

---

# 12. N3.20.11 — Constraint Tests

DB constraints são executáveis e precisam de negative tests.

Exemplos:

- no duplicate active RegistrationEntry;
- one effective evaluation key according to revision policy;
- unique Match sequence per Match;
- valid lifecycle enum/state;
- one active Community owner constraint where representável;
- FK delete behavior;
- snapshot references cannot point to nonexistent source where required.

Todo constraint introduzido para integridade crítica ganha pelo menos um teste que tenta violá-lo.

---

# 13. N3.20.12 — RLS Tests

RLS é testada por identidade real simulada no ambiente de integração.

Matriz mínima:

```text
anonymous
member same Community
member other Community
Organizer assigned/unassigned
Admin
Owner
MatchController
CompetitionAdministrator
Platform internal role when applicable
```

Para cada tabela/view protegida:

- allowed SELECT;
- denied SELECT;
- denied generic INSERT/UPDATE/DELETE quando command-only;
- cross-context access.

Happy path sem negative path é insuficiente.

---

# 14. N3.20.13 — RPC Tests

Cada RPC crítica deve provar:

- unauthenticated denied;
- foreign resource denied;
- actor derived server-side;
- protected payload fields cannot mass-assign authority;
- expected revision/sequence enforced;
- idempotency behavior;
- all-or-nothing transaction;
- stable domain errors at adapter boundary.

`SECURITY DEFINER` tests ainda verificam grants e hardening esperado (`search_path=''`, objetos qualificados no target).

---

# 15. N3.20.14 — Authorization Matrix

A matriz canônica de capabilities vira suite table-driven.

Exemplos obrigatórios:

| Actor | Action | Expected |
|---|---|---|
| Community Owner | transfer ownership | allow + step-up if policy |
| Community Admin only | evaluate Player | deny unless Organizer/evaluation capability |
| Organizer assigned | manage own Session | allow |
| Organizer unassigned | mutate another Organizer Session | deny unless override capability |
| Organizer | approve Community membership | deny |
| MatchController with current lease | AwardPoint | allow |
| old MatchController | AwardPoint after takeover | deny |
| Session Organizer | officialize Competition | deny without Competition capability |

A matriz é executada no application layer e, para critical paths, no DB/RPC layer.

# 16. N3.20.15 — BOLA / IDOR Tests

BOLA tests alteram deliberadamente IDs mantendo um JWT válido.

Padrão:

```text
Actor belongs to Community A
owns/knows resource A
also knows UUID of resource B
payload substitutes resource_id B
→ DENY
```

Cobrir:

- Community;
- Session;
- Registration;
- Player contextual evaluation;
- TeamCandidateSet/Vote;
- Match;
- Competition;
- Media;
- Notification/read DTO where applicable.

Também testar payload com `community_id=A` e resource real pertencendo a B; autorização resolve contexto do resource, não o valor enviado.

# 17. N3.20.16 — Concurrency Tests

Concorrência crítica usa transações realmente concorrentes.

Cenários mínimos:

1. dois JoinRegistration disputam a última vaga;
2. Join vs Leave/promotion;
3. Join vs CloseRegistration;
4. Capacity change vs Join;
5. dois ownership transfers;
6. owner Leave vs ownership transfer;
7. dois AwardPoint com mesmo expected sequence;
8. AwardPoint vs Match takeover;
9. two ConfirmTeamDraw attempts;
10. CastVote vs CloseVoting;
11. two FinalizeTeamVote attempts;
12. two OfficializeResult attempts.

Assertions precisam provar **resultado final e ausência de efeito parcial**, não apenas que uma request retornou erro.

---

# 18. N3.20.17 — Idempotency Tests

Para todo Command marcado idempotente:

```text
same command_id
N retries
→ one logical effect
```

Cobrir o caso de maior risco:

```text
COMMIT succeeds
response is lost
retry same command_id
→ original authoritative response/effect recovered
```

Também provar:

```text
different command_id
same semantic duplicate input
```

é protegido por invariantes/uniqueness quando o domínio proíbe duplicação.

Command receipt não substitui constraint de domínio.

---

# 19. N3.20.18 — Transaction Failure Tests

Failure points deliberados entre substeps.

Exemplo `LeaveRegistration`:

```text
withdraw entry
[FAIL HERE]
promote waiter
revision++
```

Após rollback:

```text
entry unchanged
promotion absent
revision unchanged
outbox absent
```

Outros:

- AwardPoint before event insert;
- after event insert but before projection update;
- ownership transfer halfway;
- OfficializeResult before standings invalidation/outbox;
- media pointer switch before READY validation.

---

# 20. N3.20.19 — Realtime Tests

Realtime é testado como transporte tolerante a perda.

Cenários:

- duplicate event;
- out-of-order;
- missing revision/sequence;
- initial subscribe/fetch race;
- reconnect;
- browser suspend/resume;
- unauthorized channel;
- removed member with existing socket;
- client tries authoritative publish;
- schema version unsupported.

Principal assertion:

```text
lost Realtime message
→ authoritative refetch converges
```

Não testamos “Realtime nunca perde mensagem” porque o protocolo não depende disso.

# 21. N3.20.20 — Offline Tests

Offline test matrix é por operation class.

### ONLINE_AUTHORITATIVE

Registration, Voting, governance:

```text
offline mutation
→ explicit unavailable result
→ no fake local authoritative success
→ no generic outbox replay later
```

### OFFLINE_OWNED

- create/configure/balance/play offline;
- reload/crash recovery;
- publish handoff;
- unknown publish outcome;
- server-owned state cannot revert to local authority after connectivity loss.

### CONDITIONALLY_OFFLINE_COMMAND

Match:

- current epoch only;
- ordered durable outbox;
- reconnect/reconcile;
- takeover divergence.

# 23. N3.20.22 — Match Reconciliation

Canonical scenarios:

```text
same epoch + contiguous sequence
→ replay possible

old epoch after takeover
→ RECONCILIATION_REQUIRED / reject auto-apply

sequence base diverged
→ no LWW
```

Test cases include:

- controller A offline, B takeover, A returns;
- duplicate local command;
- missing local outbox item;
- response-lost command;
- correction/revert after reconnect;
- two devices same user;
- lease expires while offline.

No test may resolve the authoritative result using `updated_at`.

# 24. N3.20.23 — Team Balancer Tests

This context receives one of the deepest suites because solver bugs may look plausible to users.

## N4.20.23 — Non-negotiable overall test

At least three independent guards:

1. target solver input type contains no `overall` optimization field;
2. change only derived/display overall while attributes/constraints stay identical → identical candidate fingerprints;
3. objective diagnostics used for ranking contain only permitted attributes/constraints.

`overall weight = 0` is not enough as the architecture guard.

## N4.20.23 — Hard constraints

Property tests prove every published/confirmable candidate satisfies all true hard constraints.

A penalty that can still be violated is not accepted as proof of a hard constraint.

## N4.20.23 — Portfolio

Test:

- deterministic seeds;
- diversity threshold;
- no duplicate candidate fingerprint;
- candidate ranking from canonical objective;
- stale roster rejection;
- manual adjustment creates revision;
- Worker/direct solver parity.

## N4.20.23 — Performance

Benchmarks measure CPU/memory/iterations separately from correctness tests.

Performance variability must never alter deterministic canonical output.

# 25. N3.20.24 — Ratings Tests

The hierarchy must be directly tested:

```text
Organizer evaluations
→ CommunitySkillProfile
→ GlobalSkillProfile
```

Mandatory scenarios:

- two evaluators same Community are consolidated before global;
- ten evaluators in one Community do not give that Community ten times global weight;
- evaluator revision replaces effective contribution rather than accumulating duplicates;
- extreme evaluator does not dominate under chosen robust policy;
- missing dimension is not zero;
- confidence is separate from score;
- formula/version change marks projection rebuild/stale correctly;
- historical TeamDraw snapshot remains unchanged after profile changes;
- overall formula changes do not alter balancer result.

Exact aggregation algorithm tests are version-specific once ADR is finalized.

# 26. N3.20.25 — Competition Tests

Cover:

- Round contains 0..N Fixtures;
- Fixture may have 0..N Match executions;
- technical MatchResult does not auto-become official;
- WO creates administrative result and zero fake PointEvents;
- deterministic standings/tie-breaks;
- penalties affect projection according to versioned rules;
- bracket slot dependencies resolve only from official sources;
- BYE without fake Match;
- retroactive correction before downstream execution recalculates safely;
- retroactive correction after downstream start requires impact/manual workflow;
- concurrent officialization is safe.

---

# 27. N3.20.26 — Statistics Tests

Facts and projections are tested separately.

Mandatory:

- `MatchParticipation` determines participation, not current Team membership;
- invalidated Match excluded according to eligibility policy;
- one Match contributes once;
- correction recomputes bounded contribution;
- rebuild from source facts equals projection;
- `0` differs from `UNKNOWN` when capture coverage is incomplete;
- SCORE_ONLY does not fabricate detailed zero stats;
- provisional Quick overlay is superseded, not double-counted, after publication;
- evaluation/overall changes do not change factual stats.

# 28. N3.20.27 — Media Tests

# 29. N3.20.28 — Notification Tests

Prove separation:

```text
domain commit
≠ delivery success
```

Scenarios:

- provider down after domain commit;
- worker duplicate;
- timeout after provider accepted request;
- reminder source state became stale;
- recipient lost eligibility;
- preference changed before scheduled delivery;
- Inbox persists while Push fails;
- template version/render snapshot remains historical;
- poison recipient/job does not block queue;
- provider credentials/errors not leaked in user-facing payload/log.

# 30. N3.20.29 — UI Component Tests

Use React Testing Library/Vitest for deterministic UI state and interaction.

Prefer testing semantics:

```text
button accessible name
loading/error/success state
keyboard interaction
recovery action
```

Avoid brittle assertions on implementation classes/DOM nesting when behavior is the contract.

Backend-independent component tests should not require a live Supabase instance.

# 31. N3.20.30 — Accessibility Tests

Accessibility quality combines:

```text
automated checks
+ semantic component tests
+ keyboard journeys
+ targeted manual review
```

Automation alone cannot prove accessibility.

Critical journeys to cover include:

- authentication/MFA;
- Quick Session;
- Registration;
- Team candidate selection/voting;
- Match controller;
- Community administration.

Exact automation library (for example axe integration) remains `OPEN`.

# 32. N3.20.31 — E2E Tests

E2E remains thin and risk-based.

Recommended canonical journeys:

1. anonymous/local Quick Session from setup to recap;
2. account sign-in/account gates;
3. Community membership/admin boundary;
4. Registration join/waitlist/leave visible outcome;
5. Team Formation candidate selection/voting happy path;
6. Organizer prepares Session and starts Match;
7. MatchController scores/pauses/finishes;
8. spectator/reconnect snapshot convergence;
9. Competition result officialization/standings read;
10. recovery path after representative failure.

Business invariants remain primarily proved below E2E.

## N4.20.31 — Connected vs deterministic E2E

Separate suites:

```text
browser/product E2E with deterministic local/test backend

connected integration smoke against external/dev services
```

A backend outage should not silently convert mandatory security coverage into `skip`.

---

# 33. N3.20.32 — Migration Tests

Every migration slice tests:

```text
old schema/data
→ apply expand
→ backfill
→ compatibility window
→ switch
→ verify
→ contract
```

Test production-like edge records, not only pristine fixtures.

Examples:

- legacy `local_id/cloudId` collisions;
- deleted_at ambiguities;
- arrays with missing references;
- Session active at migration boundary;
- Auth user deleted while Player/history remains;
- legacy avatar URL;
- duplicate legacy Community membership/evaluation edge cases.

Active execution cohorts must not be migrated mid-Match when migration plan prohibits it.

---

# 34. N3.20.33 — Backfill Tests

Every substantial backfill needs:

- idempotency;
- resumability/checkpoint behavior where required;
- bounded batching;
- verification query;
- anomaly capture;
- retry after partial infrastructure failure;
- no duplicate source contribution.

Row count equality is not enough.

Verify semantic invariants.

# 36. N3.20.35 — Load Tests

Load tests model contention shapes, not vanity concurrency.

Priority workloads:

```text
Registration opens → burst of Joins
multiple live Matches → AwardPoint + spectators
Competition event → standings reads
```

Measure:

- latency percentiles;
- error/rejection taxonomy;
- lock wait;
- DB connections;
- CPU/memory;
- queue age;
- Realtime gaps/reconnect;
- correctness after load.

A load test that is fast but violates FIFO fails.

Tool (`k6`, Artillery or equivalent) remains `OPEN`.

# 43. N3.20.42 — Flaky Test Policy

Retry is diagnostic, not acceptance of randomness.

Policy:

```text
flaky detected
→ record owner + evidence
→ classify root cause
→ fix or time-bounded quarantine
→ track age
```

Forbidden steady state:

```text
retry=5
→ eventually green
→ ignore
```

For concurrency/timing tests, prefer deterministic barriers/hooks over arbitrary `sleep()`.

Quarantined Q0/Q1 security/correctness tests cannot permit release without explicit risk decision.
