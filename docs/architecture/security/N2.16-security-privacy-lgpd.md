## 0. Regra de leitura

Este documento define o **target canônico de Security / Privacy / LGPD** do Volley.

A primeira regra é:

```text
AUTHENTICATED
≠
AUTHORIZED
```

A segunda é:

```text
KNOWING A UUID
≠
HAVING ACCESS TO THE RESOURCE
```

A terceira é:

```text
BROWSER
PAYLOAD
URL PARAMETER
LOCAL STORAGE / INDEXEDDB
DEVICE CLOCK
REALTIME MESSAGE
FILE MIME / EXTENSION
CLIENT ROLE LABEL
=
UNTRUSTED INPUT
```

A defesa esperada é em camadas:

```text
Application authorization
        +
RLS / query isolation
        +
semantic RPC validation
        +
DB constraints / locks
        +
audit / observability
```

Nenhuma camada individual é tratada como suficiente para operações críticas.

Este documento também diferencia:

```text
SECURITY REQUIREMENT
≠
LEGAL BASIS DECISION
```

Arquitetura define mecanismos para inventário, minimização, retenção, transparência, direitos e incident response. A base legal concreta de cada atividade de tratamento precisa ser registrada no inventário de tratamento e validada pelo responsável jurídico/privacy; não será inventada por conveniência técnica.

# 1. Current State — evidência do repositório

## 1.1 Já existe uso significativo de RLS e RPCs privilegiadas

As migrations atuais habilitam RLS em múltiplas tabelas e possuem helpers/RPCs `SECURITY DEFINER` para membership, Player linking, avatar approval e outras operações sensíveis.

Existe uma migration de hardening que:

- fixa `search_path = public` em funções;
- revoga `EXECUTE` de `public` e `anon` em helpers privilegiados.

Isso demonstra intenção correta de reduzir superfície de ataque.

Porém, o target endurece a regra para novas/migradas funções privilegiadas:

```text
SECURITY DEFINER
SET search_path = ''
+
fully qualified object names
+
minimal EXECUTE grants
```

A documentação atual do Supabase recomenda exatamente esse padrão para funções `SECURITY DEFINER`.

## 1.2 O schema operacional ainda concede escrita de tabela de forma ampla

A migration operacional concede `select, insert, update, delete` a `authenticated` em várias tabelas e depende de RLS para filtrar as operações.

RLS continuará defesa importante, mas bounded contexts críticos migram para:

```text
reads permitidos por DTO/query
+
semantic command RPC for critical writes
```

O browser não precisa manter capacidade genérica de administrar rows de Registration, Match, Voting, ownership ou OfficialResults.

## 1.3 Há FKs perigosas entre conta e história esportiva

O modelo legado possui entidades compartilhadas/históricas com `owner_id REFERENCES auth.users ON DELETE CASCADE`.

Isso viola o target:

```text
DELETE AUTH ACCOUNT
≠
DELETE SPORTS HISTORY
```

A remoção da conta deve desacoplar identidade autenticável de fatos esportivos que precisam sobreviver conforme lifecycle/retention.

## 1.4 MFA/AAL2 já possui base real no frontend

O client atual já implementa:

- leitura de authenticator assurance level;
- enrollment TOTP;
- challenge/verify;
- sign-out de outras sessões.

Portanto step-up authentication será evolução da infraestrutura existente, não reimplementação do zero.

## 1.5 User metadata existe no onboarding

O signup atual envia `name`, `username` e `claim_code` em metadata de Auth.

Essa informação pode apoiar onboarding, mas:

```text
raw_user_meta_data
MUST NOT authorize capabilities
```

Capacidades dinâmicas de Community/Session/Competition são resolvidas a partir de estado autoritativo do banco.

## 1.6 Avatar atual já reconhece que RLS não é column-level security

A migration atual de avatar adicionou trigger que impede mutation direta de `avatar_url` fora do fluxo de aprovação, justamente porque uma policy de UPDATE de row não protege automaticamente uma coluna específica.

Essa é uma boa lição arquitetural:

```text
ROW ACCESS
≠
PERMISSION TO MUTATE EVERY FIELD IN THAT ROW
```

Mas o fluxo legado ainda usa bucket público e URL como identidade; isso é substituído pelo modelo `MediaAsset` de N2.11.

# 2. N3.16.01 — Security Governance

## N4.16.01 — Security ownership

Security é transversal, mas cada bounded context continua responsável por seus próprios invariantes.

```text
Security owner
├── standards / threat model
├── cross-context controls
├── security gates
└── incident process

Context owner
├── resource authorization
├── data minimization
├── abuse cases
└── N10 tests
```

## N5.16.01 — Change rule

Mudança que altera qualquer um destes itens exige security review explícito:

- boundary de autorização;
- exposição pública;
- `SECURITY DEFINER`;
- service role;
- novos dados pessoais/sensíveis;
- novo provider/subprocessor;
- novo upload format;
- nova capability administrativa;
- auth/session behavior;
- cross-community read/write;
- destructive lifecycle.

# 3. N3.16.02 — Threat Model

## N4.16.02 — Threat actors

Considerar pelo menos:

```text
anonymous attacker
authenticated malicious member
malicious Organizer
compromised legitimate account
stale/offline old controller
malicious/curious internal operator
XSS executing in authenticated browser
leaked token
leaked service-role credential
malicious file uploader
bot / abuse actor
misconfigured provider
```

## N4.16.02.02 — Trust boundaries

```text
Browser
  ↕
Supabase Auth
  ↕
Data API / RPC / RLS
  ↕
Postgres

Browser ↔ Realtime
Browser ↔ Storage upload boundary
Server/worker ↔ external providers
IndexedDB ↔ authenticated account scope
```

## N5.16.02 — Highest-priority abuse class

Para o modelo multi-Community, a maior classe recorrente de risco é BOLA/IDOR:

```text
valid authenticated user
+
UUID of resource from Community B
+
request made while member of Community A
```

O sistema precisa rejeitar por contexto real do resource.

# 4. N3.16.03 — Data Classification

## N4.16.03 — Candidate classes

```text
PUBLIC
INTERNAL
PERSONAL
SENSITIVE / HIGH-RISK PERSONAL
SECURITY SECRET
```

Exemplos candidatos:

| Data | Class | Notes |
|---|---|---|
| public competition score | PUBLIC when policy allows | public DTO only |
| Community membership | PERSONAL | social/organizational relation |
| email/account identifiers | PERSONAL | minimize exposure |
| Player sports profile | PERSONAL | global Player does not imply public directory |
| subjective evaluation | PERSONAL / potentially high impact | restricted contextual access |
| injury/health information | SENSITIVE | if collected, health data needs stronger controls |
| avatar/photo | PERSONAL | not automatically biometric-sensitive unless processed for biometric identification |
| auth tokens/TOTP secrets | SECURITY SECRET | never application logs |
| service-role secret | SECURITY SECRET | server-only |
| precise EXIF/GPS | PERSONAL / potentially high risk | stripped from final media |

## N5.16.03 — Data classification is operational

Classification determines:

- read audience;
- log policy;
- retention;
- export/deletion behavior;
- incident severity;
- encryption/access expectations;
- whether public delivery is allowed.

# 5. N3.16.04 — Authentication

## N4.16.04 — Identity source

Supabase Auth remains authentication authority in V1.

Application actor is derived from verified auth context:

```text
actor_user_id = auth.uid()
```

Never from request payload.

## N5.16.04 — User metadata

`raw_user_meta_data` may be used for non-authoritative onboarding hints only.

Do not put authoritative:

```text
community_role
organizer=true
platform_admin=true
competition_admin=true
```

there.

Dynamic capabilities are DB-authoritative.

# 6. N3.16.05 — Session Security

## N4.16.05 — Session lifecycle

Security-sensitive account events must support:

- sign out current session;
- sign out other sessions where appropriate;
- password reset;
- MFA enrollment/recovery;
- auth state refresh.

## N5.16.05 — Stale JWT principle

JWT claims may remain stale until refresh.

Therefore fast-changing membership/capability revocation must not depend exclusively on embedded dynamic team/community lists in JWT.

Critical Commands resolve current DB state.

# 7. N3.16.06 — MFA / Step-up

## N4.16.06 — AAL

Supabase Auth exposes:

```text
aal1
=
conventional authentication

aal2
=
additional verified factor
```

The frontend already supports TOTP flow.

## N4.16.06.02 — Step-up candidates

Require or strongly target AAL2 for high-impact commands such as:

```text
TransferCommunityOwnership
Delete/AnonymizeAccount irreversible confirmation
MergePlayers
Approve high-risk PlayerAccountLink conflict
change platform/internal administration privileges
security-sensitive account operations
```

Other commands may remain AAL1 based on risk.

## N5.16.06 — Server enforcement

UI prompting for MFA is UX only.

High-risk endpoint must enforce required AAL server-side/RLS/RPC.

# 8. N3.16.07 — Authorization

## N4.16.07 — Resource-first authorization

Canonical resolution:

```text
JWT → User
  ↓
requested resource
  ↓
actual resource context
  ↓
active Membership / Assignment / Lease
  ↓
Capability
  ↓
allow / deny
```

Never:

```text
payload.community_id says A
but resource belongs to B
→ authorize against A
```

# 10. N3.16.09 — Community Isolation

## N4.16.09 — Context isolation

Every Community-scoped resource either:

- stores `community_id` directly; or
- has an unambiguous FK path to its Community.

Authorization follows that path.

## N5.16.09 — No user-supplied scope substitution

If `session_id` resolves to Community B, passing `community_id=A` cannot broaden access.

---

# 11. N3.16.10 — RLS

## N4.16.10 — Defense in depth

Every table exposed through Data API containing protected data must have intentional RLS/grants.

## N5.16.10 — Separate operation policies

Prefer explicit policies for:

```text
SELECT
INSERT
UPDATE
DELETE
```

Avoid broad `FOR ALL` where it obscures semantics.

## N5.16.10.02 — RLS performance

Index policy filter/join columns and measure query plans.

Security policy that times out under real scale is operational risk.

## N5.16.10.03 — Views

Exposed views must not accidentally bypass underlying RLS. Use security-invoker behavior or keep privileged/internal views unexposed as appropriate.

---

# 12. N3.16.11 — RPC Security

## N4.16.11 — Semantic RPCs

Critical mutations occur through semantic endpoints that:

1. derive actor from auth;
2. resolve actual resource;
3. check capability;
4. validate expected revision/sequence/epoch;
5. lock required aggregate;
6. mutate atomically;
7. write command receipt/audit/outbox as required.

## N5.16.11 — No actor/role payload

Reject API designs containing authoritative fields such as:

```text
actor_user_id
is_admin
role
owner_id of caller
```

supplied by the browser.

---

# 13. N3.16.12 — SECURITY DEFINER

## N4.16.12 — Privileged endpoint model

Treat each `SECURITY DEFINER` function as a privileged API surface.

Required target baseline:

```text
SECURITY DEFINER
SET search_path = ''
fully qualified table/function references
explicit auth check
explicit resource authorization
minimal EXECUTE grants
no dynamic SQL unless strictly necessary and safely bound
```

## N5.16.12 — Migration from current state

Current functions commonly use:

```text
set search_path = public
```

Target migration hardens them to empty search path + qualified names where supported/relevant.

## N5.16.12.02 — Exposed schema

Prefer privileged helpers in unexposed/private schema when they do not need direct Data API invocation.

Publicly callable RPCs expose only the minimal deliberate command surface.

# 14. N3.16.13 — Service Roles

## N4.16.13 — Server-only

Service-role credentials:

```text
NEVER browser
NEVER VITE_ env
NEVER localStorage
NEVER source control
```

Use only trusted server/worker environments with narrow operational purpose.

## N5.16.13 — Bypass warning

Because service-role access can bypass RLS, application authorization must not assume RLS protects code executing under service role.

# 15. N3.16.14 — IDOR / BOLA

## N4.16.14 — Canonical test pattern

For every resource endpoint, include tests:

```text
User A / Community A / Resource A → allowed as expected
User A / Community A / Resource B from Community B → denied
User B with different responsibility in same Community → capability-dependent
revoked user → denied
```

## N5.16.14 — UUID is not a secret

Do not rely on UUID unguessability as authorization.

# 16. N3.16.15 — Mass Assignment

## N4.16.15 — Allowlisted DTO

Commands accept explicit fields.

Never pass an arbitrary object directly to `.update()`/`.upsert()` for sensitive entities.

Protected fields include examples:

```text
community_id
owner/user actor IDs
role/capability
status controlled by lifecycle
revision
sequence
control_epoch
officialized_by
created_at
```

# 17. N3.16.16 — Realtime Security

## N4.16.16 — Private by default

Protected channels are private and authorization reflects actual resource access.

## N5.16.16 — Receive-only authority

Ordinary clients cannot publish authoritative events such as:

```text
match.event_committed
registration.changed
voting.finalized
official_result.changed
```

## N5.16.16.02 — Revocation window

Channel authorization/cache is not the only security boundary.

After membership revocation:

- commands reauthorize current state immediately;
- future authoritative queries deny;
- realtime payloads are minimized to reduce leakage during any socket revocation window.

# 18. N3.16.17 — Storage Security

## N4.16.17 — Trust zones

Storage distinguishes:

```text
private incoming
private sanitized master
public approved variant
```

Browser cannot write arbitrary final public object paths.

## N5.16.17 — Object path is not authorization

Knowing a Storage path/asset UUID does not grant attachment/read rights for private media.

# 19. N3.16.18 — Media Security

N2.11 remains authoritative.

Security summary:

- server-side actual decode/format validation;
- byte/dimension/pixel budgets;
- EXIF/GPS stripping;
- raster allowlist V1;
- SVG rejected V1;
- raw incoming private;
- moderation does not bypass technical processing;
- signed URL is delivery artifact, not identity.

# 20. N3.16.19 — Browser Security

## N4.16.19 — Browser is hostile-capable

Assume any authenticated user can:

- modify JS state;
- call Supabase REST/RPC manually;
- forge request payloads;
- replay requests;
- inspect IDs;
- alter local storage;
- intercept own network traffic.

Client-side permissions only improve UX.

---

# 21. N3.16.20 — XSS

## N4.16.20 — Primary SPA concern

XSS can act with the user's authenticated browser context and read accessible local state.

Controls include:

- React escaping/default safe rendering;
- no unsanitized `dangerouslySetInnerHTML` for user content;
- strict handling of rich text/URLs if introduced;
- CSP/security headers;
- dependency hygiene;
- avoid putting secrets in DOM/local storage unnecessarily;
- output encoding appropriate to context.

## N10.16.20

Stored Community description containing script-like payload renders as inert text, not executable HTML.

---

# 22. N3.16.21 — CSRF

## N4.16.21 — Token transport-aware

Current browser API architecture primarily uses bearer JWT via Supabase client rather than ambient app cookies.

If future server routes introduce cookie-based authenticated mutations, CSRF controls become mandatory for those routes:

- SameSite policy;
- origin checks;
- anti-CSRF tokens where appropriate.

Do not claim “SPA has no CSRF” globally; evaluate per credential transport.

## N4.16.22 — Baseline

- vulnerability scanning in CI;

- secret scanning;
- no production credentials in test fixtures;

# 24. N3.16.23 — Local Data / IndexedDB

## N4.16.23 — Account isolation

Local structured data is scoped by account/device authority as defined in N2.12.

On account switch:

```text
stop replay
seal pending account-owned outbox
clear in-memory state
open next account scope
```

## N5.16.23 — Local confidentiality limitation

IndexedDB is not a trusted secret vault against XSS or a compromised browser profile.

Minimize cached personal data and do not store server secrets/TOTP secrets there.

# 26. N3.16.25 — Abuse / Rate Limiting

## N4.16.25 — Sensitive operations

Rate limit/abuse protect at least:

- sign-in/signup/password recovery;
- username/player discovery enumeration;
- join/request flows;
- PlayerAccountLink proposals;
- media upload intents/processing;
- vote submission abuse;
- notification-triggering actions;

## N5.16.25 — Rate limit is not authorization

A request below quota can still be unauthorized and must fail authorization independently.

# 27. N3.16.26 — Audit

## N4.16.26 — Semantic audit

Audit security-relevant actions by semantic command, not only generic row dumps.

Examples:

```text

ChangeGovernanceRole
AssignSessionOrganizer
TakeOverMatchControl
CorrectFinishedMatch
MergePlayers
```

## N5.16.26 — Minimize audit PII

# 28. N3.16.27 — Privacy by Design

## N4.16.27 — Default questions

Before adding a field/feature:

1. Why is this data needed?
2. Is it necessary for the purpose?
3. Who needs to see it?
4. Does it need to be retained?
5. Can it be derived instead?
6. Does it need to be public?
7. Does offline cache need it?
8. How is it exported/corrected/deleted?
9. What incident impact does it create?

## N5.16.27 — Global Player is not public directory

Global identity means canonical identity across Communities, not automatic public discoverability of every profile field.

# 33. N3.16.32 — Retention

## N4.16.32 — Retention matrix

No universal `keep forever` and no universal `delete on account deletion`.

Each category has a retention rule and deletion/anonymization behavior.

Examples requiring explicit policy:

```text
Auth/profile data
Player identity
Membership history
Match facts
Competition official results
Evaluations/revisions
Media raw/sanitized
Notification delivery attempts
Audit logs
Command receipts
Security incident records
Backups
```

## N5.16.32 — Raw media

Raw uploads receive short bounded retention per N2.11; sanitized/attached media follow attachment/privacy lifecycle.

# 34. N3.16.33 — Deletion / Anonymization

## N4.16.33 — Account deletion split

```text
Delete User Account
        ↓
remove authentication capability
remove/transform account-specific personal data as applicable
unlink PlayerAccountLink
        ↓
DO NOT CASCADE sports history
```

Historical Session/Match/Competition facts remain according to lawful retention/product integrity policy, with minimization/anonymization where appropriate.

## N5.16.33 — Backups

Deletion workflow must account for backups:

- production data removed/anonymized according to request/policy;
- restored old backup must not permanently resurrect deleted personal data;
- maintain deletion/tombstone replay mechanism or equivalent restoration procedure.

# 36. N3.16.35 — Vendors / Subprocessors

## N4.16.35 — Vendor register

For every provider processing personal data record:

- categories;
- access level;
- region;

- subprocessors where relevant;
- incident contact/terms;

# 37. N3.16.36 — Security Incidents

## N4.16.36 — Incident lifecycle

```text
DETECT
→ TRIAGE
→ CONTAIN
→ INVESTIGATE
→ ASSESS DATA/RISK
→ NOTIFY if required
→ ERADICATE/RECOVER
→ POSTMORTEM
```

## N5.16.36 — Personal-data incident register

Maintain a structured record containing necessary incident facts, risk assessment, affected categories/subjects, mitigations and communication decision.

For incidents subject to the current ANPD security-incident regulation, the controller needs a process capable of meeting the regulatory communication deadline and record-retention requirements.

## N5.16.36.02 — No delayed architecture decision

Do not wait for a breach to decide:

- who assesses relevance/risk;
- who contacts providers;
- who can revoke credentials;
- how affected users are identified;
- how notification data is exported;
- where incident records are stored.

---

# 38. N3.16.37 — Backup Security

## N4.16.37 — Confidentiality and access

Backups contain the same or greater sensitivity as production.

Required principles:

- provider encryption capabilities understood;
- access restricted;
- restore access audited;
- backup copies not exposed to normal frontend paths;
- retention documented;
- restore drills include privacy/deletion replay.

# 39. N3.16.38 — Internal Administration

## N4.16.38 — Platform Admin separate

Internal/platform administration is not a Community role.

```text
PlatformAdmin
≠ Community OWNER
≠ Community ADMIN
≠ Organizer
```

## N5.16.38 — Least privilege

Internal tooling uses purpose-specific privileges, strong authentication/step-up and audit.

No invisible “master=true in browser metadata” authorization.

## N5.16.38.02 — Support access

# 42. N3.16.41 — Security Migration

## N4.16.41 — Security strangler

Security migration proceeds by risk, not merely domain order.

### P0 — before expanding shared authoritative features

1. remove dangerous auth-account cascades from sports history;
2. harden `SECURITY DEFINER` functions and grants;
3. enforce semantic critical write paths instead of generic row mutation;
4. implement/verify capability split and BOLA tests;
5. ensure service-role/provider secrets never ship to browser;
6. isolate local data by account;
7. adopt private incoming Media pipeline before broad media expansion;
8. establish dependency/secret scanning and incident credential-rotation procedure.

### P1 — before broad production scale

1. enforce AAL2 for selected high-impact actions;
2. processing/vendor/retention inventory;
3. data-subject request/export/deletion workflows;
4. privacy-aware audit/observability;
5. incident response runbook + contact/assessment process;
6. backup restore + deletion replay test;
7. explicit Realtime/Storage authorization tests;
8. abuse/rate-limit policies on public/sensitive paths.

### P2 — maturity

1. automated policy drift/integrity checks;
2. periodic access reviews;
3. formal threat-model refresh cadence;
4. additional security monitoring/alert tuning;
5. external security testing as exposure/scale justifies;
6. vendor/subprocessor periodic review.

# 47. N10 — Adversarial / Security Acceptance Matrix

## N10.16.01 — Authentication / authorization

1. Unauthenticated caller guesses Session UUID → denied.
2. Authenticated Member A guesses Session UUID in Community B → denied.
3. Admin without Organizer responsibility tries `player.evaluate` → denied unless explicitly granted.
4. Organizer tries TransferOwnership → denied.
5. MatchController tries Community media update → denied.
6. Competition admin tries global PlayerAccountLink mutation without link authority → denied.

## N10.16.02 — Resource-scope manipulation

7. Payload says `community_id=A` while `session_id` belongs to B → authorization uses B and rejects.
8. Payload changes `owner_id` to caller → ignored/rejected.
9. User submits arbitrary `officialized_by` → ignored; server derives actor.
10. User changes lifecycle status directly via generic update → impossible on protected command path.

## N10.16.03 — RLS / RPC

11. Direct REST UPDATE attempts to bypass semantic Registration command → denied/no grant/policy.
12. Direct INSERT MatchEvent without AwardPoint RPC → denied.
13. SECURITY DEFINER called anonymously → no EXECUTE/explicit auth denial.
14. SECURITY DEFINER receives foreign resource UUID → context authorization denies.
15. Attacker creates object/name intended to hijack unqualified search path → target qualified function unaffected.

## N10.16.04 — MFA / session

16. AAL1 user attempts ownership transfer requiring AAL2 → step-up required.
17. UI is modified to hide MFA prompt and calls RPC directly → server still rejects.
18. Stale JWT still contains old app claim → current DB membership denial wins for critical command.
19. Password reset/sign-out does not transfer pending local outbox to another account.

## N10.16.05 — User metadata

20. User changes own `raw_user_meta_data.organizer=true` → gains no capability.
21. User modifies onboarding `claim_code` metadata after signup → authorization unaffected.

## N10.16.06 — Realtime

22. Client publishes fake `registration.changed` → cannot create authoritative event.
23. Client publishes fake Match score broadcast → spectator state refetch/protocol ignores non-authoritative source.
24. User removed from Community keeps socket briefly → command access immediately denied; minimized payload limits leakage.
25. User subscribes to another Community private channel → authorization denies.

## N10.16.07 — Storage / Media

26. User guesses private incoming path → cannot read.
27. Browser writes directly to public final bucket/path → denied.
28. `.png` containing SVG/script → server processing rejects.
29. image contains GPS EXIF → final sanitized asset omits it.
30. Community Admin attempts global Player avatar action without required media authority → denied.

## N10.16.08 — XSS / browser

31. Community description contains `<script>` → renders inert.
32. User-controlled URL uses dangerous scheme → validation prevents executable link behavior.
33. XSS steals local cache opportunity → minimized cached data limits blast radius; no service secret present.
34. DevTools changes local role label → server authorization unchanged.

## N10.16.09 — Local data

35. User A logs out with pending Match commands → sealed to A.
36. User B logs in → A commands never replay under B token.
37. Anonymous Quick exists then login → not silently claimed without explicit import policy.
38. localStorage edited to mark resource `synced`/`admin` → no server authority change.

## N10.16.10 — Secrets

39. Build output inspected → no service-role/provider secret.
40. `.env.example` contains placeholders only.
41. Secret accidentally committed → CI secret scan fails and rotation procedure triggers.
42. Logs from provider failure → API secret/redacted auth token absent.

## N10.16.11 — Abuse

43. Bot enumerates usernames → bounded responses/rate limits and minimal lookup DTO.
44. Bot creates media upload intents → rate-limit/quota stops unbounded processing.
45. Vote endpoint spammed → authorization/idempotency/rate controls preserve one effective vote.
46. Repeated password recovery → auth-provider/captcha/rate protections apply.

## N10.16.12 — Privacy rights

47. User requests export → receives own personal data, not another Community member's private evaluation notes.
48. User requests correction → mutable profile data corrected without rewriting immutable Match facts incorrectly.
49. User deletes account → auth access removed; required Match history survives without auth cascade.
50. Deleted account had linked Player → link removed/anonymized according to policy; Player/MatchParticipation remains.
51. Consent withdrawn for a consent-based optional communication → future such processing stops without deleting unrelated official results.

## N10.16.13 — Backup / deletion

52. Privacy deletion completed, then old backup restored in disaster drill → deletion replay/repair re-applies removal/anonymization.
53. Backup operator tries ordinary frontend URL → backup not exposed.
54. Restore access is auditable and limited.

## N10.16.14 — Incident

55. Leak of authentication data detected → incident triage classifies affected categories and risk.
56. Provider supplies incomplete facts → preliminary assessment/communication workflow can continue and complement later where allowed.
57. Incident judged below notification threshold → reason for non-notification is recorded.
58. Incident requires notification → affected subjects can be identified without reconstructing from ad-hoc logs.
59. Credential compromise → service/provider secrets can be rotated without redeploying secret to browser.

## N10.16.15 — Internal administration

60. Platform operator accesses support/admin function → strong auth, explicit capability and audit.
61. Platform operator is not implicitly Community owner.
62. Internal admin cannot silently become MatchController without domain command/assignment.

## N10.16.16 — Supply chain

63. Dependency with high-risk vulnerability enters lockfile → CI/review detects according to policy.
64. Compromised package attempts to read runtime browser env → only publishable values are present.
65. New GitHub Action requests broad secret access → review blocks unless explicitly justified.

# 48. ADR anchors for C3 canonicalization

## ADR-0247 — Browser and payload are untrusted

Server/database revalidate all authoritative decisions.

## ADR-0248 — Authentication and authorization remain separate

JWT identity is only the beginning of access resolution.

## ADR-0249 — Authorization is resource-context + capability based

No global role hierarchy authorizes unrelated contexts.

## ADR-0250 — Community governance and Organizer responsibility remain separate

Admin does not automatically evaluate/control Sessions; Organizer does not automatically govern Community.

## ADR-0251 — RLS is mandatory defense in depth for exposed protected data

Application authorization does not replace RLS.

## ADR-0252 — Critical mutations use semantic server-side commands

Generic browser table writes are retired for critical aggregates.

## ADR-0253 — SECURITY DEFINER uses empty search path + qualified names in target

Privileged functions are treated as security endpoints.

## ADR-0254 — Service role is server-only and never bundled

Any browser exposure is a security incident requiring rotation.

## ADR-0255 — raw_user_meta_data never carries authoritative permissions

Mutable user metadata is not authorization state.

## ADR-0256 — MFA/AAL2 is step-up for selected high-impact operations

Enforcement occurs server-side.

## ADR-0257 — BOLA/IDOR tests are mandatory per resource type

UUIDs are identifiers, not secrets.

## ADR-0258 — Mass assignment is prohibited

Command DTOs explicitly allowlist mutable fields.

## ADR-0259 — Protected Realtime is private, minimized and receive-only for authoritative events

Realtime never becomes an authorization bypass.

## ADR-0260 — Storage/media use trust zones

Raw uploads remain private until server-controlled processing.

## ADR-0261 — XSS is primary authenticated-browser threat

Client data/secrets are minimized accordingly.

## ADR-0262 — Local data is account-scoped and not a secret vault

Logout/account switch seals pending ownership correctly.

## ADR-0263 — Security secrets are classified and rotatable

`VITE_*` is always public by assumption.

## ADR-0264 — Security audit is semantic and privacy-minimized

Do not use full row/payload dumps as default audit model.

## ADR-0265 — Privacy processing inventory is required

Purpose/legal basis/retention/vendor/transfer are explicit metadata of the privacy program.

## ADR-0266 — Consent is modeled only where consent is the actual legal basis

No blanket consent flag for the entire platform.

## ADR-0267 — Account deletion is separate from sports-history deletion

Historical facts survive subject to retention/anonymization rules.

## ADR-0268 — Retention is category-specific

No universal hard delete or infinite retention.

## ADR-0269 — International transfers and subprocessors are inventoried

Mechanism is recorded per provider/processing activity.

## ADR-0270 — Incident response is predesigned and records personal-data incidents

Regulatory communication/retention obligations are operational requirements.

## ADR-0271 — Platform administration is separate from Community roles

Internal privilege requires separate strong controls and audit.

## ADR-0272 — Security migration uses P0/P1/P2 risk gates

Security debt is not deferred solely because the domain migration is incomplete.
